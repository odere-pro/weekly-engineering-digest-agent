              <section class="relative w-full">
                <p class="text-body-large text-text-primary mb-10">
                  Most developer tools start the same way. You need to do a thing repeatedly, so you
                  write a script. The script grows flags. The flags grow subcommands. Before you
                  know it, you&#39;ve got a CLI.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  We had this exact experience when building an internal platform tool to help our
                  solutions team ship faster. It scaffolds projects, spins up dev environments,
                  generates configs, and deploys to staging.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  As our CLI grew in scope, so did the number of our internal users. But then,
                  something interesting happened: suddenly, we were no longer building just for
                  human developers, but for coding agents too.
                </p>
                <section class="mb-10">
                  <div class="iframe-wrapper relative w-full">

                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  What Good DX Looks Like
                </h2>
                <p class="text-body-large text-text-primary mb-10">
                  Before we talk about agents, let&#39;s talk about what makes a CLI actually
                  pleasant for human developers.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  Spaces is opinionated about the boring stuff. It picks sane directory structures
                  so you don&#39;t have to. It generates the config files you&#39;d otherwise copy
                  from the last project. It wires services together so your API and your frontend
                  can talk on day one, not after an hour of YAML editing or “vibing”.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  Here&#39;s what a typical session looks like:
                </p>
                <div class="expressive-code mb-10">
                  <link rel="stylesheet" href="/_astro/ec.srnkc.css" />
                  <figure class="frame">
                    <figcaption class="header"></figcaption>

                <p class="text-body-large text-text-primary mb-10">
                  Three commands. You go from nothing to a running multi-service project with hot
                  reload, a database, and generated Dockerfiles. That&#39;s the bar.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  The commands that matter tend to fall into three buckets:
                </p>
                <ul class="mb-10 pl-5 flex flex-col gap-2 list-disc">
                  <li>
                    <p class="text-body-large text-current">
                      <strong>Scaffolding</strong> -- These create structure, ask questions, show

                    </p>

                      before acting
                    </p>

                </ul>
                <p class="text-body-large text-text-primary mb-10">
                  This is all table stakes. But then our second user showed up and we discovered we
                  needed something a little different, and a lot more interesting.
                </p>
                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  The Second User: The Agent
                </h2>
                <p class="text-body-large text-text-primary mb-10">
                  We built a TUI module picker for
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >init</code
                  >. Fancy changes, commands, it looked super.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  Then an agent tried to use it.
                </p>
                <section class="mb-10">
                  <div class="iframe-wrapper relative w-full">
                    <iframe
                      class="iframe-aspect-free"
                      title="demo"
                      src="https://spaces-blogs-staging-mistral-01d83c8e.koyeb.app/interface-gap"
                      width="720"

                <p class="text-body-large text-text-primary mb-10">
                  The agent saw raw ANSI escape codes.
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >\\\\x1b[36m?\\\\x1b[0m Select components</code
                  >. It couldn&#39;t send arrow keys or toggle selections. It was locked out of the
                  command entirely.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  The fix seems obvious in retrospect: add a
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >--components</code
                  >
                  flag. But the real insight was bigger than one flag.
                </p>
                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  Every prompt is a flag in disguise
                </h2>
                <p class="text-body-large text-text-primary mb-10">
                  Every time your CLI asks an interactive question, there&#39;s an implicit
                  contract: &quot;I need this piece of information to proceed.&quot; To fulfill that
                  contract, you can use an interactive prompt. Or you can use a flag or config file.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  The trick is to think about the <em>information</em> first and the
                  <em>input method</em> second.
                </p>

                <p class="text-body-large text-text-primary mb-10">
                  Three input paths, one execution path. The business logic doesn&#39;t know how the
                  inputs arrived. This means you test it once, not three times.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  The
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >-y</code
                  >
                  flag deserves special attention. It&#39;s not just &quot;skip confirmations.&quot;
                  It&#39;s a contract that says:
                  <em
                    >I&#39;m providing everything you need programmatically, don&#39;t block on
                    stdin.</em
                  >
                  When you run with
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >-y</code
                  >, every prompt resolves to either a flag value or a smart default. If it
                  can&#39;t, it fails loudly instead of hanging.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  <strong>Example in practice: the interactive elements in this post.</strong>
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  The elements were built in a fresh repository. An agent was retroactively asked to
                  wire the project into [spaces cli] for deployment. It started by running
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >--help</code
                  >
                  across the relevant commands to understand the interface. From that, it figured
                  out which configuration files were needed, generated a
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >config.yaml</code
                  >, and connected the Dockerfile and registry settings - no hand-holding required.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  In the same pass, it set up the GitHub Actions CI pipeline. From a single prompt
                  to a live deployment took under 10 minutes (a cycle time we&#39;re actively
                  working to bring down). After that, the repository was fully configured and the
                  embeds were
                  <a
                    href="https://spaces-blogs-staging-mistral-01d83c8e.koyeb.app/"
                    class="underline font-semibold"
                    >deployed</a
                  >
                  with <a href="https://www.koyeb.com/" class="underline font-semibold">Koyeb </a>—
                  as a Space, scaffolded and deployed through Spaces itself. Yes, the interactive
                  demos embedded in this blog post about Spaces are running as a Space.
                  <em>Spaception</em>.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  Because every interactive input had a flag equivalent, the agent could operate
                  autonomously end-to-end.
                </p>
                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  Structured Data as Interface
                </h2>
                <p class="text-body-large text-text-primary mb-10">
                  The CLI our team was building helped our applied AI engineers ship apps. But not
                  every app looks the same. Some need a backend and a vector database. Others just
                  need a relational database, a frontend, and some APIs. A few are worker-only
                  services with no UI at all.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  We were not about to hardcode the module types. So we built a plugin system where
                  each component is a plugin that declares its own properties:
                </p>

                      >
                        <div></div>
                      </button>
                    </div>
                  </figure>
                </div>
                <p class="text-body-large text-text-primary mb-10">
                  Plugins are introspectable. You can list them, serialize them, diff them. A human
                  browses a TUI picker. An agent queries the registry and gets JSON back. Same data,
                  different rendering.
                </p>
                <section class="mb-10">
                  <div class="iframe-wrapper relative w-full">
                    <iframe
                      class="iframe-aspect-free"
                      style="--mobile-height: 850px"
                      title="demo"
                      src="https://spaces-blogs-staging-mistral-01d83c8e.koyeb.app/plugin-registry"
                      width="720"
                      height="600"
                    ></iframe>
                  </div>
                </section>
                <p class="text-body-large text-text-primary mb-10">
                  This accidentally solved a problem we didn&#39;t know we had. Before, adding a new
                  module type meant updating the picker, the Dockerfile generator, the env file
                  writer, and the compose template. Now it means writing one plugin class. The
                  registry is the single source of truth and everything reads from it.
                </p>
                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  Teaching Agents About Your Project
                </h2>
                <blockquote class="w-full relative flex flex-col lg:flex-row gap-0 mb-10">
                  <span class="before:content-[''] absolute h-full w-0.75 bg-text-primary"></span>
                  <div class="relative ml-8">
                    <blockquote class="text-h4 font-mistral text-current">
                      <p class="text-body-large text-text-primary mb-10">
                        There&#39;s an old saying that content is king. With agents, context is.
                      </p>
                    </blockquote>
                  </div>
                </blockquote>
                <p class="text-body-large text-text-primary mb-10">
                  The most impactful thing we did for agent usability was generating two files on
                  every
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >init</code
                  >:
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >context.json</code
                  >
                  -- a structured snapshot of the project: what modules exist, ports they use,
                  commands to run, env vars they need.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >AGENTS.md</code
                  >
                  -- a set of rules written for LLMs and more imperative than your regular one. Not
                  &quot;this project uses PostgreSQL&quot; but &quot;run
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >mycli dev --migrate</code
                  >
                  before testing database changes.&quot;
                </p>
                <section class="mb-10">
                  <div class="iframe-wrapper relative w-full">
                    <iframe
                      class="iframe-aspect-free"
                      style="--mobile-height: 1150px"
                      title="demo"
                      src="https://spaces-blogs-staging-mistral-01d83c8e.koyeb.app/agent-context"
                      width="720"
                      height="550"
                    ></iframe>
                  </div>
                </section>
                <p class="text-body-large text-text-primary mb-10">
                  An agent that reads these files before acting makes dramatically fewer mistakes.
                  Basically, it won’t guess at port numbers, run the wrong test command, try to
                  install dependencies that are already managed by the toolchain.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  The context file also acts as a cache-buster for stale agent assumptions. When you
                  add a module or change a deploy target, the context file updates automatically on
                  the next
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >dev</code
                  >
                  or
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >init</code
                  >. The agent reads fresh state every time.
                </p>
                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  Implicit State is the Enemy
                </h2>
                <p class="text-body-large text-text-primary mb-10">
                  The subtlest problem we hit was implicit state. Our
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >add</code
                  >
                  command read
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >config.yaml</code
                  >
                  from the current working directory. A human
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >cd</code
                  >s to the right folder without thinking. An agent running commands from a
                  workspace root has no idea it needs to be in a subdirectory.
                </p>
                <p class="text-body-large text-text-primary mb-10">The fix:</p>
                <div class="expressive-code mb-10">
                  <figure class="frame">
                    <figcaption class="header"></figcaption>
                    <pre
                      data-language="python"
                    ><code><div class="ec-line"><div class="code"><span style="--0:#646568;--0fs:italic"># Before: CWD dependency</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383A42">config = load_config(Path.cwd() / </span><span style="--0:#387138">"config.yaml"</span><span style="--0:#383A42">)</span></div></div><div class="ec-line"><div class="code">
</div></div><div class="ec-line"><div class="code"><span style="--0:#646568;--0fs:italic"># After: explicit with fallback</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383A42">config = load_config(</span></div></div><div class="ec-line"><div class="code"><span class="indent"><span style="--0:#383A42">    </span></span><span style="--0:#383A42">path </span><span style="--0:#A626A4">or</span><span style="--0:#383A42"> find_config_in_parents(Path.cwd())</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383A42">)</span></div></div></code></pre>
                    <div class="copy">
                      <div aria-live="polite"></div>
                      <button
                        title="Copy to clipboard"
                        data-copied="Copied!"
                        data-code="# Before: CWD dependencyconfig = load_config(Path.cwd() / &#x22;config.yaml&#x22;)# After: explicit with fallbackconfig = load_config(    path or find_config_in_parents(Path.cwd()))"
                      >
                        <div></div>
                      </button>
                    </div>
                  </figure>
                </div>
                <p class="text-body-large text-text-primary mb-10">
                  Every hidden assumption -- CWD, environment variables, dotfiles in
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >$HOME</code
                  >
                  -- is a place where an agent will trip. Explicit parameters with sensible
                  fallbacks solve it for agents and make scripting easier for humans too.
                </p>
                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  The Checklist
                </h2>
                <p class="text-body-large text-text-primary mb-10">
                  Looking back, the changes were small individually. Just a set of principles
                  applied consistently:
                </p>
                <ul class="mb-10 pl-5 flex flex-col gap-2 list-disc">
                  <li>
                    <p class="text-body-large text-current">
                      Every interactive input has a flag equivalent
                    </p>
                  </li>
                  <li>
                    <p class="text-body-large text-current">
                      Every flag has a smart default for headless mode
                    </p>
                  </li>
                  <li>
                    <p class="text-body-large text-current">
                      State is explicit. CWD, env vars, and config paths are inputs, not assumptions
                    </p>
                  </li>
                  <li>
                    <p class="text-body-large text-current">
                      Plugins are data models, not just code. Introspectable by default
                    </p>
                  </li>
                  <li>
                    <p class="text-body-large text-current">
                      Context files give agents (and CI, and scripts) a structured description of
                      the project
                    </p>
                  </li>
                </ul>
                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  Building a Better Tool for Everyone
                </h2>
                <p class="text-body-large text-text-primary mb-10">
                  The funny part is that none of this made the CLI worse for humans. The TUI picker
                  still works and looks fancy, progress spinners still spin, confirmation dialogs
                  still confirm. We just added a second door.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  And that second door turned out to be the more important one. Not because agents
                  matter more than humans, but because the constraints they impose are the same
                  constraints that make a CLI composable, scriptable, and testable. Designing for
                  agents forced us to build a better tool for everyone.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  If you&#39;re building developer tools right now, you don&#39;t need a separate
                  agent API. You need to look at every
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >input()</code
                  >
                  call, every CWD assumption, every pretty-printed-only output, and ask: what if the
                  user on the other end is a process, not a person?
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  The answer to that question will improve your tool either way.
                </p>
