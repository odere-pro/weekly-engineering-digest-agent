              <section class="relative w-full">
                <p class="text-body-large text-text-primary mb-10">
                  In most large Rails monoliths, organizations prioritize writing new features over
                  writing tests for them. Over time, more and more code goes untested, forcing teams
                  to spend more time debugging painful bugs.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  We built an autonomous agent that closes that gap. It reads Rails source files,
                  generates or improves RSpec tests, validates them against style rules and coverage
                  targets, and runs inside a CI/CD pipeline with no human intervention. To operate
                  on codebases at this scale, it runs in parallel: multiple instances working on
                  different files simultaneously.
                </p>
                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  RSpec through an agent&#39;s eyes
                </h2>
                <p class="text-body-large text-text-primary mb-10">
                  Ruby is dynamically typed: there is no compilation step, so errors surface at
                  runtime. For our agent, this means the only way to verify test syntax is to
                  execute it.
                  <a href="https://rspec.info/" class="underline font-semibold"
                    ><strong>RSpec</strong></a
                  >, the standard Rails testing framework, makes tests expressive and readable, but
                  its domain-specific language is easy to get wrong.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  When the agent reads a Ruby on Rails codebase, it reads five main file types
                  (models, serializers, controllers, mailers, helpers), each structured differently
                  (therefore tested in different ways). The agent needs distinct instructions for
                  each type.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  One benefit: the mapping from source file to spec file is nearly 1:1. The general
                  convention is:
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  <figure class="mb-10">
                    <img

                  There are a few exceptions to that rule however, like that
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >app/controllers/</code
                  >
                  are sometimes mapped to
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >spec/requests/</code
                  >, or that sometimes a single source file can have multiple spec files, in which
                  case the convention is:
                </p>

                  <figure class="mb-10">
                    <img

                </p>
                <p class="text-body-large text-text-primary mb-10">
                  This straightforward mapping makes it easy to locate the tests for any given file,
                  or to identify files that lack tests entirely.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  Where it gets harder for our agent is that to avoid duplicating code, RSpec relies
                  heavily on shared context: factories, fixtures, database schemas...
                </p>
                <ul class="mb-10 pl-5 flex flex-col gap-2 list-disc">
                  <li>
                    <p class="text-body-large text-current">
                      <strong>Factories:</strong> Reusable templates for creating test objects with
                      predefined attributes, making it easy to generate consistent test data.
                    </p>
                  </li>
                  <li>
                    <p class="text-body-large text-current">
                      <strong>Fixtures:</strong> Static data files that preload test database
                      records, providing a fixed baseline for tests.
                    </p>
                  </li>
                </ul>
                <p class="text-body-large text-text-primary mb-10">
                  If a factory file doesn’t exist, the agent creates it; if it does, the agent
                  reuses it. Because factories are shared across many tests (unlike spec files),
                  careless changes can easily break tests elsewhere, so updates to these files must
                  be made with caution.
                </p>
                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  Building the agent with Vibe
                </h2>
                <p class="text-body-large text-text-primary mb-10">
                  We built the agent on top of
                  <a href="https://mistral.ai/products/vibe" class="underline font-semibold"
                    ><strong>Vibe</strong></a
                  >, Mistral&#39;s open-source coding assistant. The default system prompt was
                  sufficient for this project, so we focused on three levers: repository-level
                  context, specialized skills, and custom tools.
                </p>
                <h3 class="text-h4 font-mistral text-current mb-5 not-first:mt-12">
                  Context engineering
                </h3>
                <p class="text-body-large text-text-primary mb-10">
                  Context engineering was central to our approach. Vibe supports a repository-level
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >AGENTS.md</code
                  >
                  file: when running on a repository with this file at its root, its contents are
                  automatically appended to the system prompt.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  The
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >AGENTS.md</code
                  >
                  we used provided basic details about the target repositories, but mostly, it
                  provided the agent with a <strong>step-by-step execution plan:</strong>
                </p>
                <div class="expressive-code mb-10">
                  <link rel="stylesheet" href="/_astro/ec.srnkc.css" />

                <p class="text-body-large text-text-primary mb-10">
                  Each step included details about what to do and what the success criteria are. We
                  also included some best practices of RSpec on areas where we felt it was important
                  to orient the agent. Example:
                </p>
                <div class="expressive-code mb-10">
                  <figure class="frame">
                    <figcaption class="header"></figcaption>

                      >
                        <div></div>
                      </button>
                    </div>
                  </figure>
                </div>
                <p class="text-body-large text-text-primary mb-10">
                  We found the agent would sometimes skip methods or leave edge cases untested: it
                  would generate a spec that <em>looked</em> complete but quietly ignored a few
                  public methods from the source file. To counter this, the
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >AGENTS.md</code
                  >
                  ends with a forced self-review: the agent must re-read the source file and
                  explicitly ask itself &quot;Did I test every public method? Count them.&quot;
                  before finishing. If anything is missing, it goes back.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  With this generic
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >AGENTS.md</code
                  >
                  file forcing the agent to follow strict planning, our quality score went from
                  <strong>0.68 to 0.74</strong>, all from a single markdown file with
                  framework-level instructions.
                </p>
                <h3 class="text-h4 font-mistral text-current mb-5 not-first:mt-12">
                  Using SKILLS files:
                </h3>
                <p class="text-body-large text-text-primary mb-10">
                  Recall step 4 of our
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >AGENTS.md</code
                  >:
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >4. Choose and read exactly one skill based on the source file location</code
                  >
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  A single generic skill would produce mediocre results: the instructions precise
                  enough for testing a model file are the wrong instructions for a controller file.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  What worked was creating a separate skills file for each category, plus one for
                  plain Ruby files.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  Here is an example of a basic skills file for testing controllers:
                </p>
                <div class="expressive-code mb-10">
                  <figure class="frame">
                    <figcaption class="header"></figcaption>
                    <pre
                      data-language="text"
                    ><code><div class="ec-line"><div class="code"><span style="--0:#383a42">---</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">name: "Generate Request Spec"</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">description: "Generate RSpec request tests for a Rails controller. </div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">- `spec/requests//_spec.rb` — drop `_controller` from the filename</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">- `spec/factories/.rb` — create or update if needed</span></div></div><div class="ec-line"><div class="code">

                <h3 class="text-h4 font-mistral text-current mb-5 not-first:mt-12">
                  Adding custom tools
                </h3>
                <p class="text-body-large text-text-primary mb-10">
                  Vibe has built-in tools for reading and writing files, running bash commands, and
                  editing code. But it also supports custom tools &amp; MCPs to expand its action
                  space. For this project, custom tools were key.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  After some experimentation, we went for:
                </p>
                <ul class="mb-10 pl-5 flex flex-col gap-2 list-disc">
                  <li>
                    <p class="text-body-large text-current">
                      A
                      <a href="https://rubocop.org/" class="underline font-semibold">RuboCop</a>
                      linting tool that runs the
                      <code
                        class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                        >rubocop</code
                      >
                      command to detect style violations, so that the agent goes back to the code
                      and fixes them.
                    </p>
                  </li>
                  <li>
                    <p class="text-body-large text-current">
                      A
                      <a
                        href="https://github.com/simplecov-ruby/simplecov"
                        class="underline font-semibold"

                      >
                      tool integrated with RSpec that checks both code coverage and test
                      correctness. Placing this as the final step was key: it guarantees every test
                      the agent writes actually runs.

                  </li>

                  The SimpleCov tool follows the same pattern but does more: it runs the spec file
                  with RSpec, collects pass/fail results for each test, and reports the coverage
                  percentage of the source file. The agent gets back which tests failed (with error
                  messages), and which lines of the source file were never exercised. This gives it
                  enough to self-correct when needed.
                </p>

                  When we first wired this tool in, only around a third of generated tests passed on
                  first execution. The agent self-corrected all failures within a few iterations.
                  Without this step, some of those tests would not have ran.

                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  Measuring test quality
                </h2>
                <p class="text-body-large text-text-primary mb-10">
                  A good unit test follows the
                  <a
                    href="https://semaphore.io/blog/aaa-pattern-test-automation"
                    class="underline font-semibold"
                    ><strong>Arrange-Act-Assert</strong></a
                  >
                  pattern: set up state, execute one behavior, verify the outcome. It should use
                  precise assertions, cover both happy and error paths, and produce failures that
                  clearly identify what broke.
                </p>

                <h3 class="text-h4 font-mistral text-current mb-5 not-first:mt-12">
                  Tool-based metrics
                </h3>
                <p class="text-body-large text-text-primary mb-10">
                  Existing Ruby on Rails tools allow us to get several metrics easily:
                </p>
                <ul class="mb-10 pl-5 flex flex-col gap-2 list-disc">
                  <li>
                    <p class="text-body-large text-current">
                      <strong>RSpec:</strong> the most popular testing framework for Ruby.
                      Expressive syntax for writing readable, well-structured tests.
                    </p>
                  </li>
                  <li>
                    <p class="text-body-large text-current">
                      <strong>RuboCop:</strong> a static Ruby code analyzer and formatter, helping
                      enforce style guidelines and keeping code consistent
                    </p>
                  </li>
                  <li>
                    <p class="text-body-large text-current">
                      <strong>SimpleCov:</strong> a code coverage tool for Ruby, measuring how much
                      code is executed by the test suite.
                    </p>
                  </li>
                </ul>
                <p class="text-body-large text-text-primary mb-10">
                  From these tools, we can extract several useful quantitative metrics: the
                  proportion of tests that pass, the number of RuboCop violations per file, the
                  proportion of code covered by the unit test suite, and the speed of execution.
                  These metrics provide a solid baseline for measuring the overall performance of a
                  test suite.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  But these numbers alone cannot determine whether a test file is actually good. How
                  should we compare two files that both have zero RuboCop violations, 100% coverage,
                  and all tests passing? The quantitative metrics may look identical, yet
                  qualitative differences in test quality can still exist.
                </p>
                <h3 class="text-h4 font-mistral text-current mb-5 not-first:mt-12">
                  LLM-as-a-judge
                </h3>
                <p class="text-body-large text-text-primary mb-10">
                  The idea behind LLM-as-a-judge is to ask an LLM: “Are all error conditions
                  tested?” or “Is this a good test?” and get back a score from 0 to 1 based on clear
                  criteria.
                </p>
                <p class="text-body-large text-text-primary mb-10">Example prompt:</p>
                <div class="expressive-code mb-10">
                  <figure class="frame">
                    <figcaption class="header"></figcaption>
                    <pre
                      data-language="text"
                    ><code><div class="ec-line"><div class="code"><span style="--0:#383a42">## Good Tests</span></div></div><div class="ec-line"><div class="code">
</div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">Precise values: `eq(100)`, not `be_present` or `be_a(Float)`.</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">State changes: `change { User.count }.by(1)`.</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">Error paths: `raise_error(ArgumentError, "message")`.</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">Boundary cases: Test exact values at thresholds (e.g., `page(0)`).</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">Public interface: No `.send(:private_method)`.</span></div></div><div class="ec-line"><div class="code">
</div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">## Bad Tests</span></div></div><div class="ec-line"><div class="code">
</div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">Vague assertions: `be_truthy`, `be_an(Array)`.</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">"Doesn't crash" tests: `not_to raise_error`.</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">Testing private methods.</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">Over-mocking (tests mocks, not behavior).</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">No assertions on return values.</span></div></div><div class="ec-line"><div class="code">
</div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">## Scoring Rules</span></div></div><div class="ec-line"><div class="code">
</div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">- 1.0: Precise assertions on return values/state + all key paths covered (happy, error, boundaries).</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">- 0.8: Precise assertions on all tested paths, but 1-2 edge cases missing entirely.</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">- 0.6: All key paths covered, but 1-2 tests use vague assertions (e.g., `be_truthy` instead of `eq(expected)`) or minor over-mocking.</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">- 0.4: Some tests have precise assertions; others are vague, over-mocked, or skip return value checks.</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">- 0.2: Most tests lack meaningful assertions: vague matchers, stubbed-out logic, no verification of actual output.</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">- 0.0: Tests are structurally broken: testing private methods, no real assertions, or verifying mocks instead of behavior.</span></div></div></code></pre>
                    <div class="copy">
                      <div aria-live="polite"></div>
                      <button title="Copy to clipboard" data-copied="Copied!" data-code="">
                        <div></div>
                      </button>
                    </div>
                  </figure>
                </div>
                <p class="text-body-large text-text-primary mb-10">
                  The &quot;Scoring Rules&quot; section here is especially important as it enforces
                  the score to be more consistent across runs. Without it, the agent would lack
                  clear definition of how strict or how lax the scoring is.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  Such a score is less authoritative than a tool&#39;s output or a thorough
                  developer review. But it is a good indication of how well the current version of
                  our agent is doing, especially when run at scale across every file in a
                  repository.
                </p>
                <h4 class="text-h5 font-mistral text-current mb-5">
                  Limitations of LLM-as-a-judge evaluation:
                </h4>
                <p class="text-body-large text-text-primary mb-10">
                  Anything that can be put into text can be scored with LLM-as-a-judge, which makes
                  it versatile. But the score output is not deterministic. Even with
                  <em>temperature=0</em>, there will be variance due to the order of kernel
                  operations. In practice the outputs for the same evaluation are always close, but
                  this lack of determinism can be an issue for some use cases.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  For our use case, since we score not a single test but usually tens to hundreds at
                  a time, this was an acceptable limitation. The aggregated score stayed consistent.
                </p>
                <h3 class="text-h4 font-mistral text-current mb-5 not-first:mt-12">
                  The missing parenthesis problem
                </h3>
                <p class="text-body-large text-text-primary mb-10">
                  There was another core problem with LLM-as-a-judge: a test can be of great quality
                  but not run, or have the logic behind it be wrong altogether.
                </p>
                <p class="text-body-large text-text-primary mb-10">Example:</p>
                <div class="expressive-code mb-10">
                  <figure class="frame">
                    <figcaption class="header"></figcaption>
                    <pre
                      data-language="text"
                    ><code><div class="ec-line"><div class="code"><span style="--0:#383a42">RSpec.describe User, "#full_name" do</span></div></div><div class="ec-line"><div class="code"><span class="indent"><span style="--0:#383a42">  </span></span><span style="--0:#383a42">it "combines first and last name with a space" do</span></div></div><div class="ec-line"><div class="code"><span class="indent"><span style="--0:#383a42">    </span></span><span style="--0:#383a42">user = User.new(first_name: "Ada", last_name: "Lovelace"</span></div></div><div class="ec-line"><div class="code">
</div></div><div class="ec-line"><div class="code"><span class="indent"><span style="--0:#383a42">    </span></span><span style="--0:#383a42">expect(user.full_name).to eq("Ada Lovelace")</span></div></div><div class="ec-line"><div class="code"><span class="indent"><span style="--0:#383a42">  </span></span><span style="--0:#383a42">end</span></div></div><div class="ec-line"><div class="code"><span style="--0:#383a42">end</span></div></div></code></pre>
                    <div class="copy">
                      <div aria-live="polite"></div>
                      <button
                        title="Copy to clipboard"
                        data-copied="Copied!"
                        data-code="RSpec.describe User, &#x22;#full_name&#x22; do  it &#x22;combines first and last name with a space&#x22; do    user = User.new(first_name: &#x22;Ada&#x22;, last_name: &#x22;Lovelace&#x22;    expect(user.full_name).to eq(&#x22;Ada Lovelace&#x22;)  endend"
                      >
                        <div></div>

                  </figure>
                </div>
                <p class="text-body-large text-text-primary mb-10">
                  This test looks great. It tests one behavior, has a clear description that reads
                  as documentation, follows
                  <a
                    href="https://semaphore.io/blog/aaa-pattern-test-automation"
                    class="underline font-semibold"
                    ><strong>Arrange-Act-Assert</strong></a
                  >:, and would fail with a useful message if broken.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  We ran this test through multiple models using the scoring prompt defined earlier.
                  The average score given was 0.75. A developer taking a quick look would likely
                  agree.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  But this test has one core flaw: <strong>it will not run.</strong> All because of
                  a missing closing parenthesis
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >)</code
                  >
                  on the
                  <code
                    class="bg-surface-brand-secondary border border-border-primary rounded-sm px-2 py-px text-text-brand-8 dark:text-text-brand-7 text-base"
                    >User.new()</code
                  >. This is a critical flaw that makes this test definitely not suitable.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  This example is easy to mitigate. But there are a lot other possibilities that can
                  lead to syntax error:
                </p>
                <ul class="mb-10 pl-5 flex flex-col gap-2 list-disc">
                  <li>
                    <p class="text-body-large text-current">
                      <strong>Versioning errors:</strong> Using methods or syntax from an
                      incompatible Ruby or Rails version
                    </p>
                  </li>
                  <li>
                    <p class="text-body-large text-current">
                      <strong>Non-existent methods:</strong> some methods might have been removed,
                      renamed, or never existed.
                    </p>
                  </li>
                  <li>
                    <p class="text-body-large text-current">
                      <strong>Factory/fixture errors:</strong> Referencing missing factories,
                      incorrect attributes, or missing associations
                    </p>
                  </li>
                  <li>
                    <p class="text-body-large text-current">
                      <strong>Missing dependencies:</strong> Using gems or modules not included in
                      the test environment
                    </p>
                  </li>
                </ul>
                <h2
                  class="text-h3 font-mistral text-current mb-5 pb-5 border-b border-border-primary not-first:mt-16"
                >
                  The experiment
                </h2>
                <p class="text-body-large text-text-primary mb-10">
                  We ran an experiment to check the agent could hold up against a real codebase. The
                  target repository contained 275 source files. Half of them already had test
                  coverage. The other half had none.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  We pointed the agent at every file, whether it already had tests or not. For
                  uncovered files, it generated specs from scratch successfully. For files that
                  already had tests, it rewrote and improved them.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  We scored every spec file before and after with LLM-as-a-judge. The aggregate
                  score for tested files went from 0.49 to 0.74, and coverage reached 100%.
                  There&#39;s still room for improvement, but the results validated the approach.
                </p>

                <h3 class="text-h4 font-mistral text-current mb-5 not-first:mt-12">Does it run?</h3>
                <p class="text-body-large text-text-primary mb-10">
                  Bundling SimpleCov with RSpec execution as the final step, forcing the agent to
                  run every test it wrote, was the single most impactful decision. Only a third of
                  tests passed on first execution. The agent self-corrected all failures within a
                  few iterations.
                </p>
                <p class="text-body-large text-text-primary mb-10">
                  Without this step, LLM-as-a-judge would have rated these non-running tests as high
                  quality: the missing parenthesis problem at scale.
