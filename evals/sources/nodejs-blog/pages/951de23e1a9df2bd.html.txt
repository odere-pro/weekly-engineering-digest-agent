            <h1>Evolving the Node.js Release Schedule</h1>
            <section>

            <div class="index-module__pL4wLa__root index-module__pL4wLa__announcements">
              <div class="index-module__pL4wLa__container" aria-hidden="true">
                Evolving the Node.js Release Schedule
              </div>
            </div>
            <p>
              Starting with 27.x, Node.js will move from two major releases per year to one. This
              post explains what&#x27;s changing, why, and what it means for users. For the full
              discussion and background, see
              <a href="https://github.com/nodejs/Release/issues/1113">nodejs/Release#1113</a>.
            </p>
            <p>
              <strong>TL;DR:</strong> If you already only upgrade to LTS versions, little changes
              beyond version numbering. LTS support windows remain similar, and now every release
              becomes LTS.
            </p>
            <p>
              <strong>Library authors:</strong> Please integrate Alpha releases to your CI as early
              as possible; if you only test on LTS releases, you will not be able to report bugs
              before they affect your users.
            </p>
            <h2 id="why-this-change"><a href="#why-this-change">Why This Change</a></h2>
            <p>
              The current release schedule is 10 years old. It was created during the io.js merger
              to balance the needs of a growing ecosystem. As one contributor put it at the time, it
              was &quot;an educated guess of what enterprises would need.&quot;
            </p>
            <p>We now have a decade of data showing how people actually use Node.js:</p>
            <ul>
              <li>
                Odd-numbered releases see minimal adoption. Most users wait for Long-Term Support.
              </li>
              <li>The odd/even distinction confuses newcomers.</li>
              <li>
                Many organizations skip odd releases entirely, upgrading only to LTS versions.
              </li>
            </ul>
            <p>
              We also recognize that enterprises need predictability. The new schedule is designed
              to be well-defined, so teams can plan upgrades and allocate resources accordingly.
            </p>
            <h3 id="volunteer-sustainability">
              <a href="#volunteer-sustainability">Volunteer Sustainability</a>
            </h3>
            <p>
              Node.js is maintained primarily by volunteers. While some contributors receive
              sponsorship, most of the work (reviewing Pull Requests, handling security issues,
              cutting releases, backporting fixes) is done by people in their spare time.
            </p>
            <p>
              Managing security releases across four or five active release lines has become
              difficult to sustain. Each additional line increases backporting complexity. By
              reducing the number of concurrent release lines, we can focus on better supporting the
              releases people actually use.
            </p>
            <h2 id="whats-changing"><a href="#whats-changing">What&#x27;s Changing</a></h2>
            <p>As of October 2026:</p>
            <ul>
              <li>
                <strong>One major release per year</strong> (April), with LTS promotion in October.
              </li>
              <li>
                <strong>Every release becomes LTS</strong>. No more odd/even distinction - Node.js
                27 will become LTS.
              </li>
              <li>
                <strong>Alpha channel for early testing</strong> with semver-major changes allowed.
              </li>
              <li>
                <strong>Alpha versioning</strong> follows semver prerelease format (e.g.,
                <code>27.0.0-alpha.1</code>).
              </li>
              <li>
                <strong
                  >Version numbers align with the calendar year of their initial Current
                  release</strong
                >: 27.0.0 in 2027, 28.0.0 in 2028.
              </li>
              <li><strong>Reduced Releasers&#x27; burden</strong>.</li>
            </ul>
            <h3 id="new-schedule"><a href="#new-schedule">New Schedule</a></h3>
            <table>
              <thead>
                <tr>
                  <th>Phase</th>
                  <th>Duration</th>
                  <th>Description</th>
                </tr>
              </thead>
              <tbody>
                <tr>
                  <td data-label="Phase">Alpha</td>
                  <td data-label="Duration">6 months</td>
                  <td data-label="Description">Oct to Mar. Early testing, semver-major allowed</td>
                </tr>
                <tr>
                  <td data-label="Phase">Current</td>
                  <td data-label="Duration">6 months</td>
                  <td data-label="Description">Apr to Oct. Stabilization</td>
                </tr>
                <tr>
                  <td data-label="Phase">LTS</td>
                  <td data-label="Duration">30 months</td>
                  <td data-label="Description">Long-term support with security fixes</td>
                </tr>
                <tr>
                  <td data-label="Phase">EOL</td>
                  <td data-label="Duration">Infinity</td>
                  <td data-label="Description">The project no longer provides any support</td>
                </tr>
              </tbody>
            </table>
            <p>
              Total support: 36 months from first Current release to
              <a href="https://nodejs.org/en/about/eol">End of Life (EOL)</a>.
            </p>
            <h3 id="about-the-alpha-channel">
              <a href="#about-the-alpha-channel">About the Alpha Channel</a>
            </h3>
            <p>
              The Alpha channel fills the early-testing role that odd-numbered releases once served,
              but with a key difference: semver-major changes are allowed during Alpha. Alpha
              releases are signed, tagged, and tested through
              <a href="https://github.com/nodejs/citgm">CITGM</a>. CITGM (Canary in the Goldmine) is
              a tool we maintain that runs the test suite of major open-source packages on the
              upcoming version of Node.js, which can let us detect ecosystem breakage and notify the
              package authors ahead of the release.
            </p>
            <p>
              This is different from
              <a href="https://nodejs.org/download/nightly/">Nightly builds</a>, which remain
              available as automated untested builds from <code>main</code> – Alpha releases may not
              contain all changes from <code>main</code>, a change may not be included in an Alpha
              release if:
            </p>
            <ul>
              <li>
                during Pull Request review, reviewers add a label requesting the change not to be
                backported (e.g. if an API is getting runtime deprecated in an Alpha release, the
                change actually removing that API should not land until the next release line).
              </li>
              <li>
                during the Alpha release preparation, the releaser ultimately decides which commits
                actually make the release (e.g. if a dependency update contains a major bug).
              </li>
            </ul>
            <p>
              <strong>Who it&#x27;s for:</strong> Library authors and CI pipelines testing
              compatibility with upcoming breaking changes. Not intended for production use.
            </p>
            <p><strong>What to expect:</strong></p>
            <ul>
              <li>Releases are signed and tagged (unlike nightly).</li>
              <li>API may change between releases.</li>
              <li>
                The release cadence is flexible; the Release Team will determine the timing and
                frequency of Alpha releases based on the volume of changes and project needs.
              </li>
            </ul>
            <p>
              <strong>Why:</strong> Provides early feedback on breaking changes with quality gates
              that Nightly builds lack. Also allows landing V8 updates earlier in the cycle.
            </p>
            <p>
              The rules for shipping semver-major commits in Alpha versions will be defined by the
              Release Team and documented in the
              <a href="https://github.com/nodejs/Release">Release repository</a>.
            </p>
            <h2 id="whats-not-changing">
              <a href="#whats-not-changing">What&#x27;s NOT Changing</a>
            </h2>
            <ul>
              <li><strong>Long-Term Support duration</strong> remains similar (30 months).</li>
              <li>
                <strong>Migration windows preserved</strong>. Overlap between LTS versions remains.
              </li>
              <li>
                <strong>Quality standards unchanged</strong>. Same testing, same CITGM, same
                security process.
              </li>
              <li><strong>Predictable schedule</strong>. April releases, October LTS promotion.</li>
              <li>
                <strong>V8 adoption cycle</strong>. Node.js latest releases will still include a
                version of V8 that&#x27;s at most about 6 months old.
              </li>
            </ul>
