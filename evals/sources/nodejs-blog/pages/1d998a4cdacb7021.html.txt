            <h1>
              Developing a minimally HashDoS resistant, yet quickly reversible integer hash for V8
            </h1>
            <section>
              <div class="index-module__mLkwoq__avatarGroup index-module__mLkwoq__medium">
                <span
                  class="index-module__j-1Igq__avatar index-module__j-1Igq__medium cursor-pointer"
                  data-state="closed"
                  ><a
                    href="https://github.com/joyeecheung"
                    target="_blank"
                    class="index-module__j-1Igq__wrapper"
                    ><span class="index-module__j-1Igq__item index-module__j-1Igq__medium"
                      >JC</span
                    ></a
                  ></span
                >
              </div>
              <p>Joyee Cheung</p>
            </section>
            <div class="index-module__pL4wLa__root index-module__pL4wLa__vulnerability">
              <div class="index-module__pL4wLa__container" aria-hidden="true">
                Developing a minimally HashDoS resistant, yet quickly reversible integer hash for V8
              </div>
            </div>
            <p>
              What happens when a hashing scheme needs to be both HashDoS resistant and quickly
              reversible? That&#x27;s the puzzle we tried to solve for addressing
              <a href="https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2026-21717"
                >CVE-2026-21717</a
              >
              in the
              <a href="/en/blog/vulnerability/march-2026-security-releases"
                >March 2026 Node.js security release</a
              >. This led to the development of an integer hash that we believe is unpredictable
              enough to prevent a blind attacker from reliably triggering severe performance
              degradation in our threat model. At the same time, it is also a
              <a href="https://en.wikipedia.org/wiki/Permutation">permutation</a> that can be
              efficiently inverted to recover the original integer value by the runtime holding the
              secret random keys, which is important for maintaining V8&#x27;s performance
              optimizations.
            </p>
            <p>
              In this post, we will go into the details of this vulnerability, explain why and how
              the design tried to meet the two seemingly contradictory requirements, and sample the
              statistical analysis we performed to evaluate the quality of the hash. Along the way,
              we will also discuss some specifics of how V8 stores and uses string hashes internally
              that lead to these constraints, the implementation techniques, and the performance
              analysis.
            </p>
            <h2 id="what-is-hashdos-and-why-does-it-matter-for-nodejs">
              <a href="#what-is-hashdos-and-why-does-it-matter-for-nodejs"
                >What is HashDoS and why does it matter for Node.js?</a
              >
            </h2>
            <p>
              <a href="https://en.wikipedia.org/wiki/Hash_table">Hash tables</a> are one of the most
              important data structures in software, and Node.js/V8 are no exceptions. With hash
              tables, there comes the problem of
              <a href="https://en.wikipedia.org/wiki/Hash_collision">collisions</a> - while hash
              tables are designed to have O(1) average time complexity for, e.g., single lookup and
              insertion, when there are so many keys whose hashed values can be mapped to the same
              slot that the table has to walk through many locations to insert a new key, it&#x27;s
              theoretically possible to degrade to O(n<sup>2</sup>) in total for inserting
              <em>n</em> keys.
            </p>
            <p>
              In many applications, the worst-case performance of hash tables is usually just a
              theoretical concern and maybe an occasional nuisance, but for servers that need to
              process untrusted input, this can be an attack vector. If an attacker manages to find
              a path that allows them to cause a large number of collisions in the server&#x27;s
              internal hash table with a small number of inputs, they can effectively
              &quot;freeze&quot; the thread without much effort. And, with enough threads frozen,
              they could render the service unavailable for a sustained period of time. This is
              commonly called a
              <a href="https://en.wikipedia.org/wiki/Collision_attack#Hash_flooding"
                >hash flooding or Hash-DoS (Denial of Service) attack</a
              >.
            </p>
            <p>
              HashDoS vulnerabilities can show up in a wide range of platforms. In the case of V8,
              when it&#x27;s used in a browser, DoS issues are
              <a
                href="https://chromium.googlesource.com/chromium/src/+/a2be834619701017dfcb830cc5b0b6522f4d52cf/docs/security/faq.md#Are-denial-of-service-issues-considered-security-bugs"
                >not considered vulnerabilities</a
              >
              because they typically only affect the tab that processes the malicious input, and
              users can simply close the tab. But when it&#x27;s used in event-loop-based
              server-side runtimes, a single malicious request that manages to block the entire
              event loop for a sustained period of time has a much bigger impact. As one of the most
              widely deployed server-side runtimes, Node.js draws extensive scrutiny from security
              researchers, which helps us find and address weak spots like these.
            </p>
            <p>
              Unlike other DoS attack vectors that can be more easily mitigated by userland
              restrictions, HashDoS vulnerabilities are particularly tricky because they lurk inside
              widely used internal data structures and well-defined operations trusted by
              developers. For V8 embedders, this means fixes for HashDoS vulnerabilities usually
              fall on the runtime maintainers, and they are a critical part of maintaining the
              security and reliability of the ecosystem.
            </p>
            <h2 id="mitigating-hashdos-with-seeded-hashes">
              <a href="#mitigating-hashdos-with-seeded-hashes"
                >Mitigating HashDoS with seeded hashes</a
              >
            </h2>
            <p>
              The core of HashDoS vulnerabilities lies in deterministic hash functions - if the
              attacker can predict the hash values of their inputs, they can craft inputs that
              reliably trigger worst-case performance in the target server. The standard mitigation
              is to
              <a
                href="https://www.usenix.org/legacy/events/sec03/tech/full_papers/crosby/crosby.pdf"
                >mix a seed value into the computation of the hash, and make sure that the seed is
                randomly generated at program initialization</a
              >. This way, even if the attacker knows the hash function, they can&#x27;t predict the
              hash values without knowing the seed that changes whenever the server restarts, and
              therefore can&#x27;t craft inputs that will reliably collide.
            </p>
            <p>
              In Node.js/V8, HashDoS vulnerabilities tend to center around misconfigurations that
              lead to unseeded hashes or hashes seeded by a constant value. For an early history of
              HashDoS vulnerabilities in Node.js/V8 and their mitigations, check out this
              <a href="https://v8.dev/blog/hash-flooding">V8 blog post</a>. A more recent example is
              <a href="https://nodejs.org/en/blog/vulnerability/july-2025-security-releases"
                >CVE-2025-27209</a
              >, reported by Mate Marjanović and addressed in Node.js&#x27;s July 2025 security
              release: during V8&#x27;s switch to
              <a href="https://github.com/Nicoshev/rapidhash">rapidhash</a>, a configuration gap
              left the constants used by rapidhash hard-coded in V8 without seeding. To mitigate
              this, Node.js temporarily reverted back to a seeded hash in its copy of V8. Later, Gus
              Caplan from Deno
              <a href="https://chromium-review.googlesource.com/c/v8/v8/+/6733490"
                >ported rapidhash&#x27;s secret generation code to V8 and wired it up to seed the
                constants used by rapidhash at runtime</a
              >, which became the eventual mitigation that shipped in newer versions of Node.js. The
              generation of rapidhash secrets turned out to be important to our later design for the
              seeded integer hash, which we will discuss below.
            </p>
            <p>
              Until recently, most HashDoS discoveries in V8 had centered on hashing of regular
              strings, since they are more commonly found in paths exposed to server handlers. It
              wasn&#x27;t until the recent HackerOne report by Mate Marjanović that our attention
              was drawn to an elephant in the room: array index strings (those that look like
              non-negative integers and fit within 24 bits) in V8 used a different deterministic
              hash that can be trivially predicted.
            </p>
            <h2 id="what-string-hashes-look-like-in-v8">
              <a href="#what-string-hashes-look-like-in-v8">What string hashes look like in V8</a>
            </h2>
            <p>
              To understand the vulnerability, let&#x27;s look at how V8 stores string hashes
              internally.
            </p>
            <p>
              Every
              <a
                href="https://chromium.googlesource.com/v8/v8/+/1361b2a49d020a718dc5495713eae0fa67d697b9/src/objects/name.h#83"
                ><code>v8::internal::Name</code></a
              >
              object (the superclass of
              <a
                href="https://chromium.googlesource.com/v8/v8/+/64b77c7889ed7149dd4c124ea0163091d026d2f3/src/objects/string.h#119"
                ><code>v8::internal::String</code></a
              >
              in V8) carries a 32-bit
              <a
                href="https://chromium.googlesource.com/v8/v8/+/1361b2a49d020a718dc5495713eae0fa67d697b9/src/objects/name.tq#7"
                ><code>raw_hash_field</code></a
              >. The composition of this field varies depending on the type of string. The bottom 2
              bits (<a
                href="https://chromium.googlesource.com/v8/v8/+/1361b2a49d020a718dc5495713eae0fa67d697b9/src/objects/name.h#172"
                ><code>HashFieldTypeBits</code></a
              >) determine the interpretation, and two of the most common types are:
            </p>
            <ul>
              <li>
                Regular strings (type
                <a
                  href="https://chromium.googlesource.com/v8/v8/+/1361b2a49d020a718dc5495713eae0fa67d697b9/src/objects/name.h#166"
                  ><code>kHash = 0b10</code></a
                >): bits 2-31 store a 30-bit hash value computed by rapidhash, seeded with randomly
                generated secrets. This is considered to be
                <a
                  href="https://github.com/hoxxep/rapidhash?tab=readme-ov-file#minimal-dos-resistance"
                  >&quot;minimally HashDoS resistant&quot;</a
                >, which we will discuss later.
              </li>
              <li>
                Array index strings (type
                <a
                  href="https://chromium.googlesource.com/v8/v8/+/1361b2a49d020a718dc5495713eae0fa67d697b9/src/objects/name.h#167"
                  ><code>kIntegerIndex = 0b00</code></a
                >): these are decimal-integer-looking strings whose numeric value fits in 24 bits.
                bits 2-25 (24 bits) hold the numeric value of the integer (<a
                  href="https://chromium.googlesource.com/v8/v8/+/1361b2a49d020a718dc5495713eae0fa67d697b9/src/objects/name.h#214"
                  ><code>ArrayIndexValueBits</code></a
                >), and bits 26-31 (6 bits) hold the string length (<a
                  href="https://chromium.googlesource.com/v8/v8/+/1361b2a49d020a718dc5495713eae0fa67d697b9/src/objects/name.h#227"
                  ><code>ArrayIndexLengthBits</code></a
                >).
              </li>
            </ul>

              The layout of the hash fields looks like this (the least significant bits are on the
              right):

            </div>
            <p>
              As you can see, the hash for array index strings is fully deterministic and
              there&#x27;s no seeding involved. An attacker can easily predict their hash values,
              and with a bit of effort, craft colliding inputs.
            </p>
            <h3 id="exploiting-the-deterministic-hash-for-array-index-strings">
              <a href="#exploiting-the-deterministic-hash-for-array-index-strings"
                >Exploiting the deterministic hash for array index strings</a
              >
            </h3>
            <p>
              One of the most commonly used hash tables in V8 is the
              <a
                href="https://chromium.googlesource.com/v8/v8/+/6ded7b3c4d79fc170b8e104dc0efc33cc4f67021/src/objects/string-table.h#51"
                >string table</a
              >, which is used for
              <a href="https://en.wikipedia.org/wiki/String_interning">string internalization</a> -
              deduplicating and caching strings in a global table for time and memory efficiency.
              The string table uses
              <a href="https://en.wikipedia.org/wiki/Open_addressing">open addressing</a> with
              <a href="https://en.wikipedia.org/wiki/Quadratic_probing">quadratic probing</a> to
              deal with collisions. The
              <a
                href="https://chromium.googlesource.com/v8/v8/+/de546675cd3b496a44138edccb06ed5289b9c60f/src/objects/off-heap-hash-table-inl.h#160"
                >probing sequence</a
              >
              is:
            </p>

              initial capacity <code>32768</code> for example:

            <h2 id="hashdos-resistant-vs-efficiently-reversible">
              <a href="#hashdos-resistant-vs-efficiently-reversible"
                >HashDoS resistant vs. efficiently reversible</a
              >
            </h2>
            <p>
              As mentioned above, the standard mitigation for HashDoS is to seed the hash function,
              so we need to look for a more robust, seeded hashing scheme for array index strings.
            </p>
            <p>
              When we talk about hashes for security purposes, we often naturally think of
              <a href="https://en.wikipedia.org/wiki/Cryptographic_hash_function"
                >cryptographic hashes</a
              >
              - which are, by design, irreversible. And here we have a dilemma: V8&#x27;s array
              index hash is not just a hash - it&#x27;s a reversible encoding. This enables an
              important optimization that happens everywhere in V8: for example, in many fast paths
              that involve string-to-integer conversion, like
              <code>parseInt(&quot;42&quot;)</code> or <code>obj[&quot;42&quot;] = 1</code>, instead
              of trying to parse the number from the string (whose content is not necessarily in CPU
              cache), V8 simply reads the <code>raw_hash_field</code> of the string and extracts the
              numeric value directly from the hash field. V8 also takes advantage of this encoding
              in e.g., string equality checks, where it would just compare two integer strings by
              their hashes. By nature, an irreversible cryptographic hash would break these
              optimizations and could lead to significant performance regressions in many hot paths.
            </p>
            <p>
              So it looks like we are in a bind: do we have to either live with this vulnerability
              because of the reversibility requirement, or accept the performance regression?
            </p>
            <h3 id="finding-a-middle-ground-minimal-hashdos-resistance">
              <a href="#finding-a-middle-ground-minimal-hashdos-resistance"
                >Finding a middle ground: minimal HashDoS resistance</a
              >
            </h3>
            <p>
              Now is the time to take a step back and think about what exactly makes a hash
              resistant to HashDoS attacks. It turned out that those who looked into rapidhash
              wondered the same and proposed the idea of
              <a
                href="https://github.com/hoxxep/rapidhash?tab=readme-ov-file#minimal-dos-resistance"
                >&quot;minimal HashDoS resistance&quot;</a
              >, with constraints that apply to our case:
            </p>
            <ol>
              <li>
                The attacker cannot observe the hash output: The hash values are internal to V8 and
                not exposed directly to JavaScript or network responses. The attacker has to work
                blind.
              </li>
              <li>
                <a href="https://github.com/nodejs/node/blob/main/SECURITY.md"
                  >Node.js trusts the code it is asked to run and the infrastructure that runs it</a
                >. The attacker should be sending untrusted input from a remote machine, and network
                jitter, garbage collection latency, server load etc. typically render the cost of
                exploiting timing side channels prohibitive.
              </li>
            </ol>
            <p>
              In the specific context of Node.js/V8 servers, there are also a few other important
              factors in play:
            </p>
            <ol>
              <li>
                The attacker needs to work with a noisy table with application-specific entries out
                of their control. It is shared by both array-index strings and regular strings
                hashed by rapidhash, and the capacity growth can also be affected by pre-existing
                entries, making it harder for the attacker to predict the exact probe chain
                consistently.
              </li>
              <li>
                Standard operational practices in production servers typically enforce payload size
                limits and rate limits. Without them, the server can already be exposed to simpler
                resource exhaustion attacks. These bound how many collisions an attacker can inject
                per request and how often they can retry. Other common practices like load balancing
                can further complicate the attacker&#x27;s ability to accumulate collisions on the
                same server.
              </li>
              <li>
                Hash table entries held weakly are subject to V8&#x27;s garbage collection. For
                example, between requests, internalized strings that become unreachable are cleaned,
                which helps prevent collisions from accumulating across requests and limit what an
                attacker can achieve in each payload. If the server allows an attacker to keep
                unlimited entries alive across GC cycles, no hash is strong enough to fix the
                off-table memory growth and it&#x27;s that unbounded retention path that needs to be
                fixed.
              </li>
            </ol>
            <p>
              These contributed to the evaluation of high attack complexity in
              <a href="https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2026-21717"
                >CVE-2026-21717</a
              >
              since the extreme amplification cannot be consistently reproduced against all Node.js
              servers, e.g., an Express server with its default
              <a href="https://expressjs.com/en/resources/middleware/body-parser.html"
                >100 KB body limit</a
              >.
            </p>
            <p>
              That said, for servers with fewer guardrails or simpler states, a fully deterministic
              hash still makes the attack feasible. So while we don&#x27;t need the hash to be
              cryptographically secure (or due to the reversibility requirement it just can&#x27;t
              be), we still need to find an efficiently invertible, randomly keyed permutation with
              good diffusion on the 24-bit space, in order to bring the unpredictability of array
              index string hashes up to a level similar to randomly keyed rapidhash&#x27;s
              unpredictability for regular strings.
            </p>

            <p>
              The first naive idea that came to mind was the classic
              <a href="https://en.wikipedia.org/wiki/Linear_congruential_generator"
                >linear congruential generator</a
              >
              (LCG) construction, but applied individually on the input instead of on a sequence.
              This is bijective when <code>secrets[0]</code> is odd, and can be quickly inverted
              (just subtract and multiply by the
              <a href="https://en.wikipedia.org/wiki/Modular_multiplicative_inverse"
                >modular inverse</a
              >). Unfortunately, this construction preserves linear relationships, and the low bits
              of the output depend only on the low bits of the input. As mentioned before, in many
              hash tables only the lower bits matter in probing, so an attacker can still generate
              collisions by picking values that are congruent modulo a guessed capacity.
            </p>

            <p>
              Another suggestion that came up during the development to minimize the overhead was to
              XOR the value with the randomly generated seed. This is also bijective and the
              inversion is extremely fast (just XOR the secret again), but each bit of the output
              depends on exactly one bit of the input. An attacker can still construct collisions
              just by choosing values that agree in the low bits.
            </p>
            <p>
              These were clearly not good enough. We needed something with genuine bit diffusion,
              where changing a single input bit would affect many output bits in an unpredictable
              way for the attacker.
            </p>
            <h3 id="the-xorshift-multiply-mixers">
              <a href="#the-xorshift-multiply-mixers">The xorshift-multiply mixers</a>
            </h3>

              <a href="https://github.com/skeeto/hash-prospector">hash-prospector</a> project, which

              reversible operations, then evaluates and ranks them. This project
              <a href="https://nullprogram.com/blog/2018/07/31/">showed</a> that many of the
              best-performing functions came from the same family of constructions that use
              alternating rounds of two operations:

            <p>
              This family of xorshift-multiply constructions is used in many pseudorandom number
              generators/mixers like Java&#x27;s
              <a href="https://doi.org/10.1145/2660193.2660195">SplittableRandom</a> and
              <a
                href="https://github.com/aappleby/smhasher/blob/92cf370/src/MurmurHash3.cpp#L68-L77"
                >MurmurHash3&#x27;s finalizer</a
              >. A great explanation of this construction can be found in
              <a
                href="https://www.pcg-random.org/posts/developing-a-seed_seq-alternative.html#multiplyxorshift"
                >this article</a
              >
              (and
              <a
                href="https://ticki.github.io/blog/designing-a-good-non-cryptographic-hash-function/"
                >this</a
              >): multiplication propagates information upward through its carry chain, while
              XOR-shift propagates information downward by folding high bits into low positions. By
              <a href="https://doi.org/10.5555/112331.112375"
                >mixing operations from different algebraic groups</a
              >, this construction helps break the patterns each one preserves.
            </p>

            <h3 id="multiplier-generation">
              <a href="#multiplier-generation">Multiplier generation</a>
            </h3>
            <p>
              Now that we had found a(nother) plausible structure to mix the bits, the next step was
              to find a way to generate good multipliers. The multipliers need to be 24-bit since
              the permutation needs to operate on the 24-bit modular arithmetic space, and they also
              need to be chosen well - if the multiplier is 1, for example, it won&#x27;t mix the
              bits at all. On the other hand, since they need to be generated at startup, we need to
              minimize the cost of finding good multipliers.
            </p>
            <p>
              We turned to the existing rapidhash secrets that V8 already generates at startup,
              which appeared to be a decent fit for our needs. While there is a width mismatch
              (rapidhash secrets are 64-bit), the secrets still retain some
              <a
                href="https://chromium.googlesource.com/v8/v8/+/0a8b1cdcc8b243c62cf045fa8beb50600e11758a/third_party/rapidhash-v8/secret.h#50"
                >desirable properties</a
              >
              after truncation. For example, each byte in the secrets must have exactly 4 bits set,
              and the generation ensures the secrets are odd, which is needed for the permutation to
              work. So we ended up just taking the lowest 24 bits of each rapidhash secret to derive
              the multipliers:

            <h2 id="statistical-evaluation">
              <a href="#statistical-evaluation">Statistical evaluation</a>
            </h2>
            <p>
              With the construction taking shape, we&#x27;d like to see some empirical evidence
              about how well it diffuses the bits. While our threat model primarily relies on the
              secrecy of the multipliers and the invisibility of hash output, good diffusion is
              needed for that secrecy to reach every output bit. One common way to quantify
              diffusion for a hash function is to check its
              <a href="https://en.wikipedia.org/wiki/Avalanche_effect">avalanche effect</a>, which
              measures how a small change in the input affects the output bits. For example, if for
              each input <em>x</em> and each input bit position <em>j</em>, we compute the hash of
              both <em>x</em> and <em>x</em> with bit <em>j</em> flipped, then count how often each
              output bit <em>k</em> changed, the ideal hash function should have each output bit
              flipped 50% of the time for each input bit flip, known as the
              <a href="https://en.wikipedia.org/wiki/Avalanche_effect#Strict_avalanche_criterion"
                >strict avalanche criterion (SAC)</a
              >. We adapted the code in
              <a href="https://github.com/skeeto/hash-prospector/tree/master">hash-prospector</a> to
              evaluate the bias (root-mean-square relative deviation) from the SAC for our 24-bit
              input space (scaled by 1000 for readability):
            </p>
            <math display="block"
              ><mtable columnalign="left"

            <h3 id="limitations"><a href="#limitations">Limitations</a></h3>
            <p>
              The SAC is a necessary but insufficient condition for a good hash function. Since this
              hashing scheme was developed to address a specific vulnerability, not to be a
              general-purpose PRNG or a non-cryptographic hash, we only measured bias from SAC as an
              empirical smoke test to guide the development, which happened in a limited timeframe.
              We have been
              <a href="https://github.com/joyeecheung/rapid-xorshift-multiply/"
                >exploring other evaluations</a
              >, but to keep this post focused we won&#x27;t go into them here. To avoid falling
              into the trap of identifying weaknesses in a
              <a href="https://en.wikipedia.org/wiki/Spherical_cow">spherical cow</a>, it&#x27;s
              important to keep in mind that structural weaknesses that cannot be exploited by a
              blind attacker to cause worst-case performance would only be informative rather than
              actionable in our threat model. The defense lies not only in the hash construction
              itself, but also in the lack of visibility of the randomly generated multipliers and
              the hash output.
            </p>
            <h2 id="implementation"><a href="#implementation">Implementation</a></h2>
            <p>
              With a security release deadline to meet, we iterated on the hash design and V8
              implementation in parallel, using the statistical analysis above to guide our choices
              while finding ways to reduce the impact on performance and code complexity.
            </p>
            <h3 id="improving-the-access-to-hash-secrets">
              <a href="#improving-the-access-to-hash-secrets"
                >Improving the access to hash secrets</a
              >
            </h3>
            <p>
              Since our design will require even more frequent access to the hash secrets in hot
              paths, we need to ensure the access to them is efficient. In V8, the hash seed and the

                >a <code>ByteArray</code> in the read-only roots</a
              >, which in the default configuration of Node.js, are shared across isolates and
              initialized during process startup. The layout of the <code>ByteArray</code> was as
              follows:

              The roots tend to be hot and in cache, so reading the secrets from the roots directly
              should be efficient. However, like most heap objects in V8, the
              <code>ByteArray</code> was previously allocated with the default 4-byte alignment. To
              deal with the potential misalignment when reading 8-byte secrets, the
              <a
                href="https://chromium.googlesource.com/v8/v8/+/aac14dd95e5be0d487eba6bcdaf9cef4f8bd806c/src/numbers/hash-seed.h#22"
                ><code>HashSeed</code></a
              >
              struct that was used to map them for access in C++ was passed around by value, with
              each part <code>memcpy</code>-ed from the <code>ByteArray</code>, or copied from
              another <code>HashSeed</code> that&#x27;s not necessarily in cache. To reduce the
              overhead, we
              <a href="https://chromium-review.googlesource.com/c/v8/v8/+/7609720/"
                >updated the <code>ByteArray</code> to be allocated with 8-byte alignment, and
                changed the <code>HashSeed</code> to only hold a pointer to the beginning of the
                <code>ByteArray</code> in the read-only roots</a
              >. Accesses to individual parts of the structure were then just direct loads from a
              pointer that points to the roots without copying, and in code they are just simple
              field accesses from a <code>HashSeed</code> struct reinterpreted over the
              <code>ByteArray</code>.

              This was later extended to include <code>m3</code> and <code>m3_inv</code> for the

            </p>
            <h3 id="applying-the-new-hashing-scheme-across-v8">
              <a href="#applying-the-new-hashing-scheme-across-v8"
                >Applying the new hashing scheme across V8</a
              >
            </h3>
            <p>
              To implement the new seeded hashing scheme, we consolidated all the code paths that
              treated the value bits as the original numeric value to go through a few helpers and
              <a href="https://chromium-review.googlesource.com/c/v8/v8/+/7564330"
                >enforce seeding when it&#x27;s enabled</a
              >:
            </p>
            <ol>
              <li>
                In runtime C++, e.g., slow paths for JS operations that involve conversions between
                strings and integers, numeric string parsing, equality checks in internal tables:
                when the code needs to encode or decode an array index hash, it will first load the
                <code>HashSeed</code> from the read-only roots of either the current
                <a href="https://dbezhetskov.dev/multi-sandboxes/">isolate group</a> or the shared
                <a
                  href="https://chromium.googlesource.com/v8/v8/+/4d1e2794e00a1071e774361994ac5ac4b6d3f147/src/heap/read-only-heap.h#36"
                  >read-only heap</a
                >, then call the new
                <a
                  href="https://chromium.googlesource.com/v8/v8/+/aac14dd95e5be0d487eba6bcdaf9cef4f8bd806c/src/strings/string-hasher.h#49"
                  >encoding</a
                >
                and
                <a
                  href="https://chromium.googlesource.com/v8/v8/+/aac14dd95e5be0d487eba6bcdaf9cef4f8bd806c/src/strings/string-hasher.h#64"
                  >decoding</a
                >
                helpers we added that perform the xorshift-multiply-based
                <a
                  href="https://chromium.googlesource.com/v8/v8/+/aac14dd95e5be0d487eba6bcdaf9cef4f8bd806c/src/strings/string-hasher.h#101"
                  >seeding</a
                >
                and
                <a
                  href="https://chromium.googlesource.com/v8/v8/+/aac14dd95e5be0d487eba6bcdaf9cef4f8bd806c/src/strings/string-hasher.h#104"
                  >unseeding</a
                >.
              </li>
              <li>
                In JIT-compiled code, e.g., fast paths for JS operations that involve conversions
                between strings and integers like <code>parseInt</code>: the secrets need to be
                loaded from the roots of the current isolate. We added
                <a href="https://v8.dev/docs/torque">Torque</a> macros to facilitate generating code
                that
                <a
                  href="https://chromium.googlesource.com/v8/v8/+/1361b2a49d020a718dc5495713eae0fa67d697b9/src/objects/name.tq#115"
                  >encodes</a
                >
                and
                <a
                  href="https://chromium.googlesource.com/v8/v8/+/1361b2a49d020a718dc5495713eae0fa67d697b9/src/objects/name.tq#126"
                  >decodes</a
                >
                array index hashes, while code generation for
                <a
                  href="https://chromium.googlesource.com/v8/v8/+/aac14dd95e5be0d487eba6bcdaf9cef4f8bd806c/src/codegen/code-stub-assembler.cc#2708"
                  >seeding</a
                >/<a
                  href="https://chromium.googlesource.com/v8/v8/+/aac14dd95e5be0d487eba6bcdaf9cef4f8bd806c/src/codegen/code-stub-assembler.cc#2737"
                  >unseeding</a
                >
                algorithms was implemented in the
                <a href="https://v8.dev/blog/csa"><code>CodeStubAssembler</code></a> instead since
                the necessary operations were not yet well supported in Torque.
              </li>
            </ol>
            <p>
              After the changes, the layout of the <code>raw_hash_field</code> for array index
              strings looks like this:

            <h2 id="performance-evaluation">
              <a href="#performance-evaluation">Performance evaluation</a>
            </h2>
            <p>
              At first glance, adding 3 rounds of xorshift-multiply to every array index
              string&#x27;s decoding might seem like a lot. The encoding direction has less impact
              since it only runs once during string construction, and would be dwarfed by the cost
              of the initial string-to-integer conversion. But what about decoding, which is where
              the optimization that requires reversibility lies?
            </p>
            <h3 id="decoding-cost-showdown">
              <a href="#decoding-cost-showdown">Decoding cost showdown</a>
            </h3>
            <ol>
              <li>
                Without seeding: recovering the integer from <code>raw_hash_field</code> is
                essentially <code>(raw_hash_field &gt;&gt; 2) &amp; 0xFFFFFF</code>, which is just
                one shift and one mask.
              </li>
              <li>
                With seeding: on top of 1, this adds 4 xors, 4 shifts, 3 multiplies, 3 masks, and 3
                loads of precomputed modular inverses from read-only roots that are likely in cache.
              </li>
              <li>
                Re-parsing the string: if we used an irreversible hash and had to recover the
                integer by parsing the string content, the CPU would need to read the string&#x27;s
                content (a potential cache miss), then loop over each character doing
                <code>result = result * 10 + (c - &#x27;0&#x27;)</code>.
              </li>
            </ol>
            <p>
              Compared to unseeded decoding, the seeded decoding incurs a few more ALU instructions.
              But these are still a lot cheaper than any memory access that could happen around
              them, and can be offset by the improvements in hash diffusion - the previous scheme
              produced consecutive hashes for consecutive integers, which can already lead to
              <a href="https://v8.dev/blog/speeding-up-v8-heap-snapshots"
                >worst-case performance issues in real-world workloads</a
              >. As for reparsing, at length 5 the ALU costs alone would add up to be comparable to
              the seeded decoding, and when the string content is not in cache, the memory access
              cost would dominate.
            </p>
            <h3 id="benchmark-results"><a href="#benchmark-results">Benchmark results</a></h3>
            <p>
              To quantify the performance impact of the changes, we ran four JavaScript benchmark
              suites - Octane, SunSpider, Kraken, JetStream 3 - with and without
              <code>v8_enable_seeded_array_index_hash</code> on an x64 Linux server. The performance
              impact
              <a href="https://github.com/joyeecheung/rapid-xorshift-multiply/blob/main/data"
                >appeared neutral and within noise</a
              >, which was adequate since our goal was to fix the vulnerability without causing a
              significant performance regression.

            <h2 id="deployment"><a href="#deployment">Deployment</a></h2>
            <p>
              The new seeded hashing scheme for array index strings has been merged into V8, gated
              by
              <a
                href="https://chromium.googlesource.com/v8/v8/+/d3f0ec122bd234aa82347cc0e838c8fae8cd6565/BUILD.gn#510"
                ><code>v8_enable_seeded_array_index_hash = true</code></a
              >, and it needs to be used together with
              <a
                href="https://chromium.googlesource.com/v8/v8/+/d3f0ec122bd234aa82347cc0e838c8fae8cd6565/BUILD.gn#507"
                ><code>v8_use_default_hasher_secret = false</code></a
              >
              for HashDoS resistance. For Chrome, where DoS attacks are not applicable, this will be
              disabled. In Node.js, this is enabled and shipped to v25, v24, v22, and v20 in the
              <a href="/en/blog/vulnerability/march-2026-security-releases"
                >March 2026 security release</a
              >.
            </p>
            <p>
              We have also notified other V8 embedders (Deno and Cloudflare workers) about the
              vulnerability and the fix during the development and the rollout.
            </p>
