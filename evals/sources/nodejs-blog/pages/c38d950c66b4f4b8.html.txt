            <div class="index-module__pL4wLa__root index-module__pL4wLa__announcements">
              <div class="index-module__pL4wLa__container" aria-hidden="true">
                Trip report: Node.js collaboration summit (2026 London)
              </div>
            </div>
            <p>
              This April, the first
              <a href="https://nodejs.org/en/about/get-involved/collab-summit"
                >Node.js Collaboration Summit</a
              >
              of 2026 was hosted by
              <a href="https://www.bloomberg.com/company/values/tech-at-bloomberg/">Bloomberg</a> in
              London. In this edition, we welcomed over 40 in-person participants, and around a
              dozen more joined remotely.
            </p>
            <p>
              The recording of the summit is available in
              <a href="https://www.youtube.com/playlist?list=PLfMzBWSH11xZhA93H_9ulECtLVWtSm6zy"
                >this playlist</a
              >. Here is a recap of what happened at the summit.
            </p>
            <h3 id="next-10"><a href="#next-10">Next 10</a></h3>
            <p>
              In this session,
              <a href="https://github.com/JakobJingleheimer">Jacob Smith</a> reviewed results from
              the Collaborator Health survey and compared health numbers between 2025 and 2026, as
              well as some key highlights from the 2025 user survey (including new areas, which have
              generally different usage); he and
              <a href="https://github.com/marco-ippolito">Marco Ippolito</a> led an on-site review
              of the questions that would be asked in the
              <a href="https://github.com/nodejs/next-10/issues/369">Next-10 survey for 2026</a>,
              including suggestions to existing questions, questions and options to add or remove,
              and recent AI discussions.
            </p>
            <h3 id="new-release-schedule">
              <a href="#new-release-schedule">New Release Schedule</a>
            </h3>
            <p>
              Rafael Gonzaga walked the audience through the new release schedule that will go into
              effect starting with Node.js v27. TL;DR, starting with Node.js v27, the Node.js
              version numbers align with the calendar year of their initial Current release!
            </p>
            <p>
              This is a reflection of the current Node.js volunteer-based maintenance and an effort
              to keep the Node.js project sustainable in the long run. When it comes to security
              vulnerabilities, managing security releases across four or five active release lines
              has become difficult to sustain in the current Node.js voluntary work model. By
              reducing the number of concurrent release lines, the project can focus on better
              supporting the releases people actually use.
            </p>
            <p>
              Read more about the new release schedule in
              <a
                href="https://nodejs.org/en/blog/announcements/evolving-the-nodejs-release-schedule"
                >this blog post</a
              >.
            </p>
            <h3 id="new-streams-api"><a href="#new-streams-api">New Streams API</a></h3>
            <p>
              <a href="https://github.com/jasnell">James Snell</a> presented a new, more unified
              Streams API for the Web and Node.js. Historically, Node.js has relied on the highly
              optimized <code>node:stream</code>. In recent years, Node.js has also implemented
              WHATWG Web Streams to ensure cross-platform compatibility with browsers, Deno, Bun,
              and edge environments (like Cloudflare Workers). However, managing two different
              stream ecosystems has created friction for developers.
            </p>
            <p>
              The Web Streams API has significant promise and allocation overhead. It was designed
              primarily for browsers, and when applied to high-throughput backend environments, the
              architectural cost becomes obvious.
            </p>
            <p>
              The proposed New Streams API takes advantage of modern JavaScript Async Iteration,
              treats streams natively as async iterables, leaning heavily into
              <code>async/await</code> and <code>for await...of</code> loops, which is how modern
              developers naturally write code. Handling a filled data buffer has historically been a
              confusing black box. The new API also proposes forcing developers to explicitly choose
              a backpressure strategy when a buffer is full.
            </p>
            <p>
              The new
              <a href="https://nodejs.org/docs/latest-v25.x/api/stream_iter.html"
                ><code>stream/iter</code></a
              >
              API has landed in Node.js core and shipped in v25.9.0 as an experimental feature. At
              the summit, we collected feedback on the design, compatibility with existing stream
              APIs, performance implications, additional use cases, whether the new proposal can
              help address some common issues in the existing APIs, and discussed whether the new
              Streams API can be implemented on the Web.
            </p>
            <h3 id="nodejs-collaboratorship">
              <a href="#nodejs-collaboratorship">Node.js Collaboratorship</a>
            </h3>
            <p>
              <a href="https://github.com/JakobJingleheimer">Jacob Smith</a> led the session on
              exploring ways to lower the barrier to entry for developers who want to contribute to
              the Node.js core, ensuring the project remains accessible to new talent.
            </p>
            <p>
              Triaging issues and reviewing pull requests takes a massive amount of maintainer
              bandwidth. At the session, we discussed ideas to enforce code ownership to encourage
              collaborators to take over more review work. Since in the Node.js voluntary work
              model, this can come with difficulties, we also brainstormed ideas about decoupling
              collaboratorship from the commit bits and extending reviewership to working group/team
              members, in order to encourage non-collaborators to review and build trust. We&#x27;ll
              continue the discussions on GitHub.
            </p>
            <h3 id="opentelemetry"><a href="#opentelemetry">OpenTelemetry</a></h3>
            <p>
              <a href="https://github.com/legendecas">Chengzhong Wu</a> presented the CNCF
              OpenTelemetry project. The session was prompted by a pull request from
              <a href="https://github.com/bengl">Bryan English</a> to add Node.js built-in
              OpenTelemetry support. OpenTelemetry is one of the most active projects in the Cloud
              Native Computing Foundation, right after Kubernetes. OpenTelemetry has emerged as the
              de-facto standard in the world of observability with three pillars: traces, metrics,
              and logs. The project defines a vendor-neutral API for instrumentation and an SDK with
              a data processing pipeline. Apart from the OpenTelemetry API and SDK, there are also
              efforts to define Semantic Conventions (SemConv) and the native data format
              OpenTelemetry Protocol (OTLP) for sending telemetry data to backends. OpenTelemetry is
              an open governance project and consists of contributors from both vendors and users.
            </p>
            <h3 id="observability-infrastructure">
              <a href="#observability-infrastructure">Observability Infrastructure</a>
            </h3>
            <p>
              <a href="https://github.com/Qard">Stephen Belanger</a> shared thoughts and work on
              improving Node.js observability infrastructure. The presentation covered
              <code>using</code> syntax support for <code>AsyncLocalStorage</code> and a new
              <code>diagnostic_channel</code> API <code>BoundedChannel</code>. Furthermore, Stephen
              presented ideas about new Node.js built-in modules for metrics and traces
              respectively, and the potential to add built-in support for the OpenTelemetry OTLP
              data protocol, improving OpenTelemetry serialization performance.
            </p>
            <h3 id="nodejs-use-of-ai-contributions">
              <a href="#nodejs-use-of-ai-contributions">Node.js use of AI contributions</a>
            </h3>
            <p>
              A few weeks before the summit, a large pull request implementing VFS in Node.js with
              the assistance of an AI coding agent led to debates over the use of AI in Node.js
              core. In this session,
              <a href="https://github.com/JakobJingleheimer">Jacob Smith</a> walked the audience
              through the background of this controversy, the legal opinion from the OpenJS
              foundation, and the current status of the use of AI in other OSS projects.
            </p>
            <p>
              We then started listing pros &amp; cons, concerns and thoughts about the use of AI in
              Node.js core using a retrospective board. There were a lot of diverse opinions about
              this topic. At the session, we discussed the challenges from reviewer bandwidth
              exacerbated by the use of AI, the ethical concerns about AI, whether a ban is feasible
              or desirable, whether a disclosure on the use of AI may help or draw further legal and
              ethical concerns, how AI may help maintenance and lower barrier of entry, and ideas on
              reducing the amount of noise caused by the use of AI.
            </p>
            <p>
              We also brainstormed how to adapt open-source governance for the modern era.
              Strategies discussed include enforcing a process that requires lightweight design
              documents, RFCs, explicit maintainer buy-in before a large PR, and pledge from the
              human contributor submitting the code who should take full responsibility for its
              quality, security, and integration. We&#x27;ll continue the discussions and iteration
              of the policy documents on GitHub.
            </p>
            <h3 id="userland-migrations"><a href="#userland-migrations">Userland migrations</a></h3>
            <p>
              <a href="https://github.com/JakobJingleheimer">Jacob Smith</a> and
              <a href="https://github.com/brunocroh">Bruno Rodrigues</a> presented increased usage
              of userland migrations. Migrations for Node.js 22.x to 24.x deprecations are almost
              complete. For Node.js 25.9.0, a codemod was published along side the deprecation
              introduced.
            </p>
            <h3 id="stabilization-of-module-customization-hooks-and-vmmodules">
              <a href="#stabilization-of-module-customization-hooks-and-vmmodules"
                >Stabilization of module customization hooks and vm.Modules</a
              >
            </h3>
            <p>
              <a href="https://github.com/joyeecheung">Joyee Cheung</a> facilitated a session to
              discuss the
              <a href="https://github.com/openjs-foundation/summit/issues/482"
                >stabilization of module loader hooks and the vm Module API</a
              >.
            </p>
            <p>
              As <code>module.register()</code> is set to be
              <a href="https://github.com/nodejs/node/pull/62395"
                >doc-deprecated for 25 and below</a
              >
              and
              <a href="https://github.com/nodejs/node/pull/62401"
                >runtime-deprecated for 26 and above</a
              >
              due to
              <a
                href="https://nodejs.org/docs/latest-v25.x/api/module.html#caveats-of-asynchronous-customization-hooks"
                >maintenance issues</a
              >, we are looking into helping the ecosystem migrate to the
              <code>module.registerHooks()</code> API. Ideas include providing a
              <a href="https://github.com/joyeecheung/module-register-ponyfill"
                >userland ponyfill</a
              >
              that re-implements most of the <code>module.register()</code> functionality using
              <code>module.registerHooks()</code>, and having some
              <a href="https://github.com/nodejs/userland-migrations">userland-migration</a>
              automation tools to help facilitate migration.
            </p>
            <p>
              Joyee also presented
              <a href="https://github.com/nodejs/node/issues/62720"
                >a new design for the vm Module APIs</a
              >
              that have been experimental for 9 years in order to address known issues and finally
              bring it to stabilization. We collected feedback on how to integrate it with
              WebAssembly modules to ensure it&#x27;s future-proof with ongoing ESM integration
              proposals in standardization bodies. We&#x27;ll continue iterating on the design in
              the GitHub issue.
            </p>
            <h3 id="libuv-v2"><a href="#libuv-v2">Libuv v2</a></h3>
            <p>
              <a href="https://github.com/santigimeno">Santiago Gimeno</a> shared that after more
              than a decade on version 1, there is a renewed push to launch libuv
              <a href="https://github.com/libuv/libuv/issues/4622">v2</a>, which introduces
              necessary breaking changes to clean up the codebase, remove legacy APIs, and improve
              cross-platform consistency—capabilities already being leveraged by
              <a href="https://julialang.org/">Julia</a>.
            </p>
            <p>
              As migrating to libuv v2 can break the ABI, we discussed ideas on how to mitigate it,
              for example by leveraging <a href="https://nodejs.org/api/n-api.html">Node-API</a>,
              and the nuances in this approach e.g.
              <a href="https://nodejs.org/api/n-api.html#napi-get-uv-event-loop"
                ><code>napi_get_uv_event_loop</code></a
              >
              can still be impacted by libuv ABI changes, though its use is limited and its ABI
              stability is warned in the documentation. We also discussed getting help to maintain
              v1 with security patches for a limited timespan, how to bring back
              <code>io_uring</code>, and which Node.js can start to ship libuv v2 (a very tentative
              timeline could be in 27).
            </p>
            <h3 id="nodejs-virtual-file-system">
              <a href="#nodejs-virtual-file-system">Node.js Virtual File System</a>
            </h3>
            <p>
              <a href="https://github.com/mcollina">Matteo Collina</a> presented the proposal for a
              Node.js built-in Virtual File System. By taking concepts previously explored in
              userland libraries (like <code>@platformatic/vfs</code>) and standardizing them into a
              core <code>node:vfs</code> module, Node.js can intercept standard filesystem calls and
              route them through a virtualized, memory-based layer. Developers can define specific
              data sources in memory (providers) and &quot;mount&quot; them so the runtime treats
              them exactly like local directories. The proposal also provides the ability to layer
              virtual filesystems on top of one another, or place a virtual layer directly over the
              physical disk to safely mock or override files.
            </p>
            <p>
              In this session, Matteo walked the audience through the motivation of this feature:
              making file system virtualization easier for single-executable applications and
              testing, and replaces existing brittle practices that achieve this through user-land
              monkey-patching. Following a brief overview of the implementation architecture and the
              design choices, we collected more feedback on the PR, including stack trace
              visibility, observability, security, worker thread propagation, the ability to toggle
              it in specific paths, and support in native code. We&#x27;ll continue iterating on
              this PR in GitHub.
            </p>
            <h3 id="nodejs-security---state-of-the-ecosystem--whats-next">
              <a href="#nodejs-security---state-of-the-ecosystem--whats-next"
                >Node.js Security - State of the Ecosystem &amp; What&#x27;s Next</a
              >
            </h3>
            <p>
              <a href="https://github.com/RafaelGSS">Rafael Gonzaga</a> shared that the security
              team has recently advanced the ecosystem through a refined threat model, improved
              permission models, and enhanced release automation, and the new VEX (Vulnerability
              Exploitability eXchange) files that the security team is working on to reduce false
              positives for security scanners.
            </p>
            <p>
              These efforts are currently being overshadowed by a massive influx of AI-generated
              vulnerability reports. This industry-wide surge, driven largely by users seeking CVE
              attribution and financial bounties, has severely strained maintainer capacity with
              high-noise, duplicative submissions that often lack reproduction steps or misclassify
              standard bugs as severe security threats. Despite attempted mitigations like pausing
              bug bounties, raising HackerOne signal requirements, and clarifying guidelines, the
              overwhelming volume has significantly driven up resolution times. To combat this
              bottleneck, the team is exploring strategies such as securing early access for
              proactive testing, attempting to alter reporting agent behaviors, and adopting a
              public security flow to bypass embargoes and speed up CI testing.
            </p>
            <p>
              In the session we revisited a thought-provoking proposal of making the security triage
              and bugfix process completely public to prevent a false sense of security in the age
              of AI, and to get rid of the CI embargo that has made testing inefficient. We
              discussed a few middle ground solutions, including keeping extending the visibility to
              more members in the organization, handling vulnerabilities of different severity with
              different visibility settings, and creating better documentations to drive AI agents
              away from generating false positive reports.
            </p>
