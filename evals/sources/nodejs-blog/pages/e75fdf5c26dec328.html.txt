            <h2 id="tldr"><a href="#tldr">TL;DR</a></h2>
            <p>
              Node.js/V8 makes a best-effort attempt to recover from stack space exhaustion with a
              catchable error, which frameworks have come to rely on for service availability. An
              edge case that reproduces only when <code>async_hooks</code> are enabled breaks this
              recovery path: when recursion in user code exhausts stack space, Node.js exits
              immediately with exit code 7 instead of throwing a recoverable error. This can be
              reproduced in countless applications because:
            </p>
            <ul>
              <li><strong>React Server Components</strong> use <code>AsyncLocalStorage</code></li>
              <li>
                <strong>Next.js</strong> uses <code>AsyncLocalStorage</code> for request context
                tracking
              </li>
              <li>
                <strong>Other frameworks</strong> may also use <code>AsyncLocalStorage</code> for
                request context tracking
              </li>
              <li>
                <strong>Most APM tools</strong> (Datadog, New Relic, Dynatrace, Elastic APM,
                OpenTelemetry) use <code>AsyncLocalStorage</code> or
                <code>async_hooks.createHook</code> to trace requests
              </li>
            </ul>
            <p>
              The weakness ultimately lies in the ecosystem&#x27;s reliance on an unspecified
              behavior in the language - recovery from stack space exhaustion - for service
              availability (<a href="https://cwe.mitre.org/data/definitions/758.html">CWE-758</a>).
              Given the widespread use of <code>async_hooks</code> by popular frameworks and APM
              tools, the aforementioned edge case can expose this weakness more frequently and can
              present a Denial‑of‑Service vector for many applications. Node.js shipped a mitigation
              in the January 2026 security release to make this unspecified behavior more
              consistent, reducing the chance of reproduction. However, the weakness remains in the
              ecosystem until applications and frameworks move away from relying on unspecified
              behavior for availability.
            </p>
            <p>
              <strong>For users of these frameworks/tools and server hosting providers</strong>:
              Update as soon as possible.
            </p>
            <p>
              <strong>For libraries and frameworks</strong>: apply more robust defenses against
              stack space exhaustion to ensure service availability (e.g., limit recursion depth or
              avoid recursion if the depth can be controlled by an attacker). A recoverable
              <code>RangeError: Maximum call stack size exceeded</code> is only an unspecified
              behavior maintained with best-effort, and cannot be depended on for security
              guarantees.
            </p>
            <h2 id="the-reproduction"><a href="#the-reproduction">The Reproduction</a></h2>
            <p>
              When a stack overflow occurs in user code while <code>async_hooks</code> is enabled,
              Node.js <strong>immediately exits with code <code>7</code></strong> instead of
              allowing <code>try-catch</code> blocks to catch the error. This is a special condition
              in Node.js that skips the
              <code>process.on(&#x27;uncaughtException&#x27;)</code> handlers, making the exception
              uncatchable.
            </p>

            <h2 id="why-the-use-of-apm-tools-makes-it-easier-to-reproduce">
              <a href="#why-the-use-of-apm-tools-makes-it-easier-to-reproduce"
                >Why the Use of APM Tools Makes It Easier to Reproduce</a
              >
            </h2>
            <p>
              Application Performance Monitoring (APM) tools are essential infrastructure for
              production applications. They track request latency, identify bottlenecks, trace
              errors to their source, and alert teams when something goes wrong. Companies use APM
              tools like Datadog, New Relic, Dynatrace, Elastic APM, and OpenTelemetry to maintain
              visibility into their distributed systems.
            </p>
            <p>
              To provide this functionality, APM tools need to follow a request as it flows through
              your application, even across async boundaries. When an HTTP request comes in, is
              processed by middleware, queries a database, calls an external API, and finally
              returns a response, the APM needs to correlate all of these operations into a single
              trace. This requires async context tracking.
            </p>
            <p>
              Most modern APM tools use <code>AsyncLocalStorage</code> (which is built on
              <code>async_hooks</code> in versions of Node.js before Node 24) to propagate trace
              context across async operations. The moment you
              <code>require(&#x27;dd-trace&#x27;)</code>,
              <code>require(&#x27;newrelic&#x27;)</code>, or initialize OpenTelemetry, your
              application has <code>async_hooks</code> enabled.
            </p>
            <p>
              The irony is notable: the tools you install to monitor and debug crashes can make a
              category of crashes behave differently. This is not the fault of the APM tools; they
              are using Node.js APIs exactly as intended.
            </p>
            <h2 id="why-this-is-only-a-mitigation-and-the-vulnerability-lies-elsewhere">
              <a href="#why-this-is-only-a-mitigation-and-the-vulnerability-lies-elsewhere"
                >Why This Is Only a Mitigation, and The Vulnerability Lies Elsewhere</a
              >
            </h2>
            <p>
              While this issue has significant practical impact, we want to be clear about why
              Node.js is treating this fix as a mere mitigation of security vulnerability risks at
              large:
            </p>
            <h3 id="stack-space-exhaustion-behavior-is-not-specified">
              <a href="#stack-space-exhaustion-behavior-is-not-specified"
                >Stack Space Exhaustion Behavior Is Not Specified</a
              >
            </h3>
            <p>
              The &quot;Maximum call stack size exceeded&quot; error is not part of the ECMAScript
              specification.
              <a href="https://tc39.es/ecma262/#execution-context-stack"
                >The specification does not impose any limit and assumes infinite stack space</a
              >. Imposing a limit and throwing a recoverable error are only behaviors that
              JavaScript engines implement with best-effort. Applications and frameworks are already
              at risk when they build a security model on top of these unspecified behaviors that
              are not guaranteed to reproduce consistently, see:
            </p>
            <ul>
              <li>
                <a href="https://cwe.mitre.org/data/definitions/758.html"
                  >CWE-758: Reliance on Undefined, Unspecified, or Implementation-Defined
                  Behavior</a
                >
              </li>
              <li>
                <a href="https://cwe.mitre.org/data/definitions/674.html"
                  >CWE-674: Uncontrolled Recursion</a
                >
              </li>
            </ul>
            <p>
              It&#x27;s worth noting that even when ECMAScript specifies that
              <a href="https://tc39.es/ecma262/#sec-tail-position-calls">proper tail calls</a>
              <a
                href="https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model#tail_calls"
                >should reuse stack frames</a
              >, this is not implemented by most JavaScript engines today, including V8. And in the
              few JavaScript engines that do implement it, proper tail calls (as used in
              <a href="#the-reproduction">the reproduction above</a>) can block an application with
              infinite recursion instead of hitting the stack size limit at some point and stopping
              with an error, which is another Denial-of-Service vector. This reinforces that stack
              overflow behavior cannot be relied upon for defending against Denial-of-Service
              attacks.
            </p>
            <h3 id="this-behavior-is-not-part-of-the-security-guarantees-of-v8">
              <a href="#this-behavior-is-not-part-of-the-security-guarantees-of-v8"
                >This Behavior Is Not Part of The Security Guarantees of V8</a
              >
            </h3>
            <p>
              In Node.js, the stack space usage from JavaScript function calls is primarily
              implemented by V8. JavaScript engines developed for browsers have a different security
              model, and they do not triage crashes like this as security vulnerabilities. This
              means similar behavior inconsistencies reported in the upstream (like
              <a href="https://issues.chromium.org/issues/432385241">this</a>) are not guaranteed to
              go through vulnerability disclosure procedures, making any security classification by
              Node.js alone ineffective.
            </p>
            <h3 id="uncaughtexception-limitations">
              <a href="#uncaughtexception-limitations">uncaughtException Limitations</a>
            </h3>
            <p>
              The <code>uncaughtException</code> handler is not designed to recover the process
              after it fires. The Node.js documentation explicitly warns against this pattern.
              Specifically, the documentation states that
              <a
                href="https://nodejs.org/api/process.html#warning-using-uncaughtexception-correctly"
                >&quot;Exceptions thrown from within the event handler will not be caught. Instead,
                the process will exit with a non-zero exit code, and the stack trace will be
                printed. This is to avoid infinite recursion.&quot;</a
              >
            </p>
            <p>
              Trying to invoke the handler after the call stack size is exceeded would itself throw.
              The fact that it works without promise hooks is largely coincidental rather than
              guaranteed behavior.
            </p>
            <h3 id="why-we-put-it-in-a-security-release">
              <a href="#why-we-put-it-in-a-security-release">Why We Put It In a Security Release</a>
            </h3>
            <p>
              Although it is a patch for an unspecified behavior, we chose to include it in the
              security release because of its widespread impact on the ecosystem. The prevalence of
              <code>async_hooks</code> usage by React Server Components, Next.js, and APM tools
              makes it a practical Denial-of-Service vector for many applications. Making the
              unspecified behavior more consistent in Node.js improves developer experience and
              makes error handling more predictable.
            </p>
            <p>
              However, it&#x27;s important to note that we were fortunate to be able to fix this
              particular case. There&#x27;s no guarantee that similar edge cases involving stack
              overflow and <code>async_hooks</code> can always be addressed.
              <strong
                >For mission-critical paths that must defend against infinite recursion or stack
                overflow from recursion whose depth can be controlled by an attacker, always
                sanitize the input or impose a limit on the depth of recursion by other
                means</strong
              >.
            </p>
            <p>
              It&#x27;s worth noting that large array allocations can suffer from similar issues,
              like the recent
              <a href="https://github.com/ljharb/qs"><code>qs</code></a> vulnerability
              <a href="https://github.com/ljharb/qs/security/advisories/GHSA-6rw7-vpxm-498p"
                >CVE-2025-15284</a
              >
              showed. It&#x27;s paramount that developers validate and constrain resource usage that
              could be controlled by an attacker. The runtime cannot always recover reliably from
              resource exhaustion after-the-fact.
            </p>

              <code>kFatal</code> means: &quot;If any error occurs here, it&#x27;s unrecoverable.
              Exit immediately.&quot;
            </p>
            <p>
              This behavior is documented and intentional. From the
              <a href="https://nodejs.org/api/async_hooks.html#error-handling"
                >async_hooks documentation</a
              >:
            </p>
            <blockquote class="index-module__x_agTG__wrapper">
              <p>
                If any <code>AsyncHook</code> callbacks throw, the application will print the stack
                trace and exit. The exit path does follow that of an uncaught exception, but all
                <code>&#x27;uncaughtException&#x27;</code> listeners are removed, thus forcing the
                process to exit.
              </p>
              <p>
                The reason for this error handling behavior is that these callbacks are running at
                potentially volatile points in an object&#x27;s lifetime, for example during class
                construction and destruction. Because of this, it is deemed necessary to bring down
                the process quickly in order to prevent an unintentional abort in the future.
              </p>
            </blockquote>
            <p>
              This design makes sense: if your APM tool&#x27;s <code>init</code> callback throws an
              error, the application is in an undefined state. The hook might have partially
              executed, resources might be leaked, and continuing could cause data corruption.
              Better to crash fast and loud.
            </p>
            <p>
              <strong>But stack overflow is different.</strong> The error doesn&#x27;t originate in
              the hook. Instead, it originates in user code. The stack just happens to overflow
              while the hook is on the call stack. The hook itself is fine; there&#x27;s no
              corrupted state to worry about.
            </p>
            <h3 id="the-bug-explained"><a href="#the-bug-explained">The Bug Explained</a></h3>
            <p>To understand the bug, we need to understand how promise hooks work.</p>
            <p>
              When you enable <code>async_hooks</code> with an <code>init</code> callback, Node.js
              registers a <strong>promise hook</strong> with V8. This hook is invoked by V8 itself
              every time a Promise is created, not by Node.js JavaScript code. The critical detail
              is that V8 calls this hook <strong>synchronously</strong> during the Promise
              constructor, before <code>new Promise()</code> returns to your code.
            </p>
            <p>The call sequence looks like this:</p>

            <p>
              Each recursive call adds frames for both the user code AND the async_hooks machinery.
              When the stack finally overflows, the currently executing code is the async_hooks
              callback, so the <code>TryCatchScope::kFatal</code> catches it.
            </p>
            <p>The complete sequence when stack overflow occurs:</p>
            <ol>
              <li>User code calls <code>new Promise()</code> recursively</li>
              <li>Each <code>new Promise()</code> synchronously triggers V8&#x27;s promise hook</li>
              <li>
                V8 calls into Node.js&#x27;s <code>promiseInitHook()</code>, then
                <code>emitInitNative()</code>
              </li>
              <li>The stack fills up with interleaved user code and hook frames</li>
              <li>
                Stack overflow throws a <code>RangeError</code> while inside the hook callback
              </li>
              <li><code>TryCatchScope::kFatal</code> catches the error</li>
              <li>
                <code>TryCatchScope::~TryCatchScope()</code> calls
                <code>env_-&gt;Exit(ExitCode::kExceptionInFatalExceptionHandler)</code>
              </li>
              <li>Node.js exits with code 7</li>
            </ol>
            <p>
              The error originated in <strong>user code</strong> (the recursive pattern), but
              because it manifests while the hook callback is the active frame, it&#x27;s treated as
              a fatal hook error.
            </p>

            <h2 id="a-brief-history-from-async_hooks-to-asynccontextframe">
              <a href="#a-brief-history-from-async_hooks-to-asynccontextframe"
                >A Brief History: From async_hooks to AsyncContextFrame</a
              >
            </h2>
            <p>
              Understanding this bug requires knowing how Node.js evolved its async context
              tracking.
            </p>
            <h3 id="the-async_hooks-era"><a href="#the-async_hooks-era">The async_hooks Era</a></h3>
            <p>
              <a href="https://nodejs.org/api/async_hooks.html"><code>async_hooks</code></a> was
              introduced in
              <a href="https://nodejs.org/en/blog/release/v8.0.0">Node.js 8 (2017)</a> as a
              low-level API to track asynchronous resources. It provides callbacks
              (<code>init</code>, <code>before</code>, <code>after</code>, <code>destroy</code>)
              that fire at key points in an async resource&#x27;s lifecycle. APM tools immediately
              adopted it to trace requests across async boundaries.
            </p>
            <p>
              However, <code>async_hooks</code> has significant performance overhead. Every Promise
              creation, every timer, and every I/O operation triggers these callbacks. This cost is
              unavoidable when the hooks are enabled.
            </p>
            <h3 id="asynclocalstorage"><a href="#asynclocalstorage">AsyncLocalStorage</a></h3>
            <p>
              <a href="https://nodejs.org/en/blog/release/v12.17.0">Node.js 12.17.0 (2020)</a>
              introduced
              <a href="https://nodejs.org/api/async_context.html#class-asynclocalstorage"
                ><code>AsyncLocalStorage</code></a
              >, a higher-level API built on top of <code>async_hooks</code>. It provides a cleaner
              interface for the most common use case: storing context that flows through async
              operations (like request IDs, user sessions, or tracing spans).
            </p>
            <p>
              React Server Components and Next.js adopted <code>AsyncLocalStorage</code> for request
              context tracking, unknowingly inheriting all of <code>async_hooks</code> behaviors,
              including this bug.
            </p>
            <h3 id="the-asynccontextframe-revolution-nodejs-24">
              <a href="#the-asynccontextframe-revolution-nodejs-24"
                >The AsyncContextFrame Revolution (Node.js 24+)</a
              >
            </h3>
            <p>
              In <a href="https://nodejs.org/en/blog/release/v24.0.0">Node.js 24</a>,
              <code>AsyncLocalStorage</code> was reimplemented using a new V8 feature called
              <a href="https://github.com/tc39/proposal-async-context"
                ><code>AsyncContextFrame</code></a
              >. This approach integrates context tracking directly into V8&#x27;s Promise
              implementation, eliminating the need for JavaScript callbacks on every async
              operation.
            </p>
            <p>
              The result is dramatically better performance. Importantly for this bug,
              <code>AsyncLocalStorage</code> no longer uses
              <code>async_hooks.createHook()</code> internally. This is why React and Next.js are
              not affected by this bug on Node.js 24+.
            </p>
            <p>
              Note: <code>AsyncLocalStorage</code> is still exported from the
              <code>async_hooks</code> module for backwards compatibility, even though it no longer
              uses the <code>async_hooks</code> machinery internally on Node.js 24+. It&#x27;s also
              available from <code>node:async_hooks</code> and the newer
              <code>node:async_context</code> module.
            </p>
            <p>
              For more details on this evolution and its performance implications, see
              <a href="https://blog.platformatic.dev/the-hidden-cost-of-context"
                >The Hidden Cost of Context</a
              >.
            </p>

            </p>
            <p>
              **APM tools that use only <code>AsyncLocalStorage</code> are not affected on Node.js
              24+. APM tools that directly use <code>async_hooks.createHook()</code> are still
              affected on all versions.
            </p>
            <h2 id="mitigation"><a href="#mitigation">Mitigation</a></h2>
            <p>
              <strong>Recommended</strong>: Upgrade to the patched versions released on January
              13th, 2026.
            </p>
            <p>
              If you cannot upgrade immediately, consider altering your application to avoid deep
              recursion, particularly when allocating promises within recursive functions.
            </p>
            <h2 id="timeline"><a href="#timeline">Timeline</a></h2>
            <ul>
              <li>

              </li>

            <h2 id="conclusion"><a href="#conclusion">Conclusion</a></h2>
            <p>
              This bug highlights how deeply <code>async_hooks</code> has become embedded in the
              Node.js ecosystem. What started as a low-level debugging API is now a critical
              dependency for React Server Components, Next.js, every major APM tool, and any code
              using <code>AsyncLocalStorage</code>.
            </p>
            <p>
              The fix improves the consistency of stack size limit errors caused by deep recursions.
              While we were able to address this particular case, developers should be aware that
              stack overflow behavior is not specified by ECMAScript and should not be relied upon
              for service availability. If the depth of recursion can be controlled by an attacker,
              always sanitize the input or impose a limit by other means to restrict the depth,
              instead of counting on the JS runtime to impose a limit or recover from it with a
              catchable error.
            </p>
            <p>
              <strong
                >Users running React RSC, Next.js, or any other framework using
                <code>AsyncLocalStorage</code>, as well as any APM tool in production, should
                upgrade to the patched versions released on January 13th, 2026.</strong
              >
            </p>
