<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]-->After building your Reachy Mini, you'll install the <a href="https://github.com/pollen-robotics/reachy_mini_conversation_app" rel="nofollow">conversation app</a> and start talking to it. Until now, you had to send your audio to a server. But not anymore. Today we'll walk you through running the whole stack locally.</p>
<p>This stack is powered by <a href="https://github.com/huggingface/speech-to-speech" rel="nofollow"><code>speech-to-speech</code></a>, our cascaded VAD → STT → LLM → TTS pipeline that exposes a Realtime API-compatible <code>/v1/realtime</code> WebSocket. Once you launch the backend, point the robot at it from the UI.</p>
<p>Cascades are the most flexible option in the open-source landscape today, and with the right pieces they're also the fastest. We'll recommend the components we like best, but the whole point of a cascade is that you can swap them. New models drop every week.</p>
<blockquote>
<p><strong>TL;DR</strong></p>
<ul>
<li>Deploy a local speech backend for your Reachy Mini.</li>
<li>We use our <code>speech-to-speech</code> library, a cascade approach.</li>
<li>Recommended: <strong>llama.cpp</strong> with <strong>Gemma 4</strong>, <strong>Silero VAD</strong>, <strong>Parakeet-TDT 0.6B v3 STT</strong>, <strong>Qwen3-TTS</strong>.</li>
</ul>
</blockquote>

<h3 class="relative group flex items-baseline">
	<a id="locally-serving-the-llm" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#locally-serving-the-llm" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Locally serving the LLM
	</span>
</h3>
<p>To serve the LLM, we'll use Hugging Face's <code>llama.cpp</code>. If you need to install it, the simplest way is <code>brew install llama.cpp</code> or <code>winget install llama.cpp</code>, for more help, <a href="https://github.com/ggml-org/llama.cpp/blob/master/docs/install.md" rel="nofollow">check the docs</a>.
First, we'll run:</p>
<pre><code class="language-bash">llama-server -hf ggml-org/gemma-4-E4B-it-GGUF -np 2 -c 65536 -fa on --swa-full
</code></pre>
<p>And done! The first time it will download the model, subsequent launches are fast.</p>
<details>
<summary>What do those flags do?</summary>

<ul>
<li><code>-hf ggml-org/gemma-4-E4B-it-GGUF</code> — pulls the model straight from the Hub. First run downloads it, subsequent runs use the cache.</li>
<li><code>-np 2</code> — two parallel slots. Lets the server handle a second request (e.g. a quick interruption) without blocking on the first.</li>
<li><code>-c 65536</code> — 64k context window, shared across slots. Plenty of headroom for long conversations.</li>
<li><code>-fa on</code> — flash attention. Faster and lower memory, basically free on modern hardware.</li>
<li><code>--swa-full</code> — keeps the full sliding-window attention cache instead of recomputing it. Trades a bit of RAM for noticeably faster prompt processing on Gemma.</li>
</ul>
</details>

<h3 class="relative group flex items-baseline">
	<a id="setting-up-speech-to-speech" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#setting-up-speech-to-speech" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Setting up speech-to-speech
	</span>
</h3>
<p>We'll begin by simply installing the library</p>
<pre><code class="language-bash">uv pip install speech-to-speech
</code></pre>
<p>Then, while we are serving the LLM in another terminal, we can simply run:</p>
<pre><code class="language-bash">speech-to-speech --responses_api_base_url <span class="hljs-string">"http://127.0.0.1:8080"</span> --responses_api_api_key <span class="hljs-string">""</span> --mode <span class="hljs-built_in">local</span>
</code></pre>
<p>And you can start talking to the model through your terminal! The first time it will need to download Parakeet-TDT 0.6B v3 and Qwen3TTS, but subsequent launches are fast.</p>
<p>Here's a video showing the local conversation mode: </p>
<video controls="" width="100%">
  <source src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/local_reachy_mini_conversation/s2s-llamacpp.mp4" type="video/mp4">
</video>

<p>Now, after you've tried it in <code>--mode local</code>, you can run again the command without that option to serve speech-to-speech to the robot.</p>
<h3 class="relative group flex items-baseline">
	<a id="connecting-reachy-mini-to-speech-to-speech" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#connecting-reachy-mini-to-speech-to-speech" rel="nofollow">

	<span>
		Connecting Reachy Mini to speech-to-speech
	</span>
</h3>
<p>Once you have llama.cpp and speech-to-speech running, you can start the robot with the desktop app and launch the conversation app. In the UI from the conversation app, you need to choose the local mode by clicking on "edit connection" in the HF backend. Here's a video showing how to do it:</p>
<video controls="" width="100%">
  <source src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/local_reachy_mini_conversation/setting_up_conv_app.mp4" type="video/mp4">
</video>


<p>And you're done. You can start talking to your robot. Every stage of the pipeline is a trade-off: there are faster TTS models with lower quality, slower STT models with higher quality. We optimized for multilingual, you might want to optimize for a single language. The rest of the blog covers how to customize.</p>

<h3 class="relative group flex items-baseline">
	<a id="why-run-your-own-speech-to-speech-server" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#why-run-your-own-speech-to-speech-server" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Why run your own Speech-to-Speech server?
	</span>
</h3>
<p>Hosted realtime backends are convenient, but running your own engine unlocks three things:</p>
<ul>
<li><strong>Privacy.</strong> Audio never leaves your network, the entire pipeline runs on hardware you control.</li>
<li><strong>No API costs.</strong> No per-minute or per-token fees.</li>
<li><strong>Full control over the pipeline.</strong> Swap any piece: VAD, STT, LLM, TTS. Whenever something better lands on the Hub 🤗.</li>
</ul>
<p>The <code>speech-to-speech</code> repo gives you all of that in a single CLI. It boots a WebSocket server at <code>/v1/realtime</code> that speaks the same protocol Reachy Mini already knows how to talk to.</p>
<h3 class="relative group flex items-baseline">
	<a id="our-opinionated-defaults-vad-stt-tts" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#our-opinionated-defaults-vad-stt-tts" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Our opinionated defaults: VAD, STT, TTS
	</span>
</h3>
<p>A cascaded voice pipeline has four stages: VAD, STT, LLM, and TTS. For three of them, we pick solid defaults so you can focus on the LLM:</p>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th>Stage</th>
<th>Choice</th>
<th>Why</th>
</tr>

		</thead><tbody><tr>
<td>VAD</td>
<td><strong>Silero VAD v5</strong></td>
<td>Tiny, accurate, runs on CPU. The de-facto default in the open-source voice-agent world.</td>
</tr>
<tr>
<td>STT</td>
<td><strong>Parakeet-TDT 0.6B v3</strong></td>
<td>Streaming-friendly, very fast, great quality on English.</td>
</tr>
<tr>
<td>TTS</td>
<td><strong>Qwen3-TTS</strong></td>
<td>Expressive, low-latency, multilingual, supports custom voices.</td>
</tr>
</tbody>
	</table>
</div>
<p>We are opinionated about these choices, feel free to swap them out for your own if you have a preference.</p>
<h3 class="relative group flex items-baseline">
	<a id="choosing-your-llm" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#choosing-your-llm" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Choosing your LLM
	</span>
</h3>
<p>The LLM is the layer with the most impact on latency and overall performance of the system. We support two options: <strong>run a model locally</strong> (llama.cpp, MLX, Transformers, vLLM), or <strong>use a server with a Responses API</strong> (OpenAI, Gemini, HF Inference Endpoints, llama.cpp, vLLM, etc).</p>
<h4 class="relative group flex items-baseline">
	<a id="the-responses-api-decouple-the-brain-from-the-voice-loop" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-responses-api-decouple-the-brain-from-the-voice-loop" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The Responses API: decouple the brain from the voice loop
	</span>
</h4>
<p>The main bottleneck in the system is LLM inference latency. To address that, we support external inference engines exposed through the Responses API protocol.</p>
<p>The <code>speech-to-speech</code> engine therefore supports a second mode where the LLM lives in a separate process as long as it speaks the Responses API protocol. You launch your model server in one terminal, you launch the voice loop in another terminal, and the two talk over HTTP.</p>
<h5 class="relative group flex items-baseline">
	<a id="option-1-llamacpp-in-one-terminal-speech-to-speech-in-the-other" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#option-1-llamacpp-in-one-terminal-speech-to-speech-in-the-other" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Option 1: llama.cpp in one terminal, speech-to-speech in the other
	</span>
</h5>
<p><strong>Terminal 1: llama.cpp server:</strong></p>
<pre><code class="language-bash">llama-server -hf ggml-org/gemma-4-E4B-it-GGUF -np 2 -c 65536 -fa on --swa-full
</code></pre>
<p><strong>Terminal 2: speech-to-speech client:</strong></p>
<pre><code class="language-bash">speech-to-speech \
  --mode realtime \
  --stt parakeet-tdt \
  --tts qwen3 \
  --llm_backend responses-api \
  --model_name <span class="hljs-string">"ggml-org/gemma-4-E4B-it-GGUF"</span> \
  --responses_api_base_url <span class="hljs-string">"http://127.0.0.1:8080/v1"</span>
</code></pre>
<h5 class="relative group flex items-baseline">
	<a id="option-2-vllm-in-one-terminal-speech-to-speech-in-the-other" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#option-2-vllm-in-one-terminal-speech-to-speech-in-the-other" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Option 2: vLLM in one terminal, speech-to-speech in the other
	</span>
</h5>
<blockquote>
<p><strong>Requires vLLM ≥ 0.21.0.</strong> Full support for the Responses API protocol, including tool-call streaming used by the speech-to-speech backend, landed in vLLM 0.21.0. Older versions will boot but trip up as soon as the assistant tries to call a tool.</p>
</blockquote>
<p>When serving a model through vLLM for this pipeline, three flags are effectively required:</p>
<ul>
<li><code>--enable-auto-tool-choice</code></li>
<li><code>--tool-call-parser &lt;tool_parser_name&gt;</code> — picks the per-family parser that turns the model's raw output into structured tool calls (e.g. <code>qwen3_coder</code> for Qwen3 instruct models, <code>llama3_json</code> for Llama 3, <code>hermes</code> for Hermes-style models, ...).</li>
<li><code>--default-chat-template-kwargs '{"enable_thinking":false}'</code> : disables the <code>&lt;think&gt;</code> reasoning channel for models that support it. For harder agentic tasks you can flip this to <code>true</code> and let the model reason, but for a natural-feeling conversation we strongly recommend keeping it off: every thinking token is latency the user hears as silence before the robot starts speaking.</li>
</ul>
<p><strong>Terminal 1: vLLM inference server (<code>Qwen/Qwen3-4B-Instruct-2507</code>):</strong></p>
<pre><code class="language-bash">vllm serve Qwen/Qwen3-4B-Instruct-2507 \
  --port 8000 \
  --host 127.0.0.1 \
  --max-model-len 32768 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder \
  --default-chat-template-kwargs <span class="hljs-string">'{"enable_thinking":false}'</span> \
  --speculative-config <span class="hljs-string">'{"method":"qwen3_next_mtp","num_speculative_tokens":1}'</span>
</code></pre>
<blockquote>
<p>The <code>--speculative-config</code> line enables Multi-Token Prediction (MTP). It is <strong>optional</strong>, but it has a great impact on end-to-end latency. Leave it on whenever the model supports it.</p>
</blockquote>
<p><strong>Terminal 2: speech-to-speech client:</strong></p>
<pre><code class="language-bash">speech-to-speech \
  --mode realtime \
  --stt parakeet-tdt \
  --tts qwen3 \
  --llm_backend responses-api \
  --model_name <span class="hljs-string">"Qwen/Qwen3-4B-Instruct-2507"</span> \
  --responses_api_base_url <span class="hljs-string">"http://127.0.0.1:8000/v1"</span>
</code></pre>
<h5 class="relative group flex items-baseline">
	<a id="option-3-hugging-face-inference-endpoints" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#option-3-hugging-face-inference-endpoints" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Option 3: Hugging Face Inference Endpoints
	</span>
</h5>
<p>Same protocol, but the model runs on a managed GPU on Hugging Face. Deploy any chat model as an Inference Endpoint, then point the voice loop at the endpoint URL:</p>
<pre><code class="language-bash">speech-to-speech \
  --mode realtime \
  --stt parakeet-tdt \
  --tts qwen3 \
  --llm_backend responses-api \
  --model_name <span class="hljs-string">"Qwen/Qwen3-4B-Instruct-2507"</span> \
  --responses_api_base_url <span class="hljs-string">"https://&lt;your-endpoint&gt;.endpoints.huggingface.cloud/v1"</span> \
  --responses_api_api_key <span class="hljs-string">"<span class="hljs-variable">$HF_TOKEN</span>"</span>
</code></pre>
<h5 class="relative group flex items-baseline">
	<a id="option-4-hugging-face-inference-providers" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#option-4-hugging-face-inference-providers" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Option 4: Hugging Face Inference Providers
	</span>
</h5>
<p>If you don't want to manage your own endpoint, use an <a href="https://huggingface.co/docs/inference-providers">Inference Provider</a>. Hugging Face routes your request to a third-party backend (e.g. Together, Fireworks, Replicate) with a single URL:</p>
<pre><code class="language-bash">speech-to-speech \
  --mode realtime \
  --stt parakeet-tdt \
  --tts qwen3 \
  --llm_backend responses-api \
  --model_name <span class="hljs-string">"Qwen/Qwen3.6-35B-A3B:deepinfra"</span> \
  --responses_api_base_url <span class="hljs-string">"https://router.huggingface.co/v1"</span> \
  --responses_api_api_key <span class="hljs-string">"<span class="hljs-variable">$HF_TOKEN</span>"</span>
</code></pre>
<h5 class="relative group flex items-baseline">
	<a id="option-5-openai-or-any-openai-compatible-provider" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#option-5-openai-or-any-openai-compatible-provider" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Option 5: OpenAI (or any OpenAI-compatible provider)
	</span>
</h5>
<p>When you want to test against a frontier model with zero infra, point the same flag at OpenAI:</p>
<pre><code class="language-bash">speech-to-speech \
  --mode realtime \
  --stt parakeet-tdt \
  --tts qwen3 \
  --llm_backend responses-api \
  --model_name <span class="hljs-string">"gpt-5.4"</span> \
  --responses_api_api_key <span class="hljs-string">"<span class="hljs-variable">$OPENAI_API_KEY</span>"</span>
</code></pre>
<p>The <code>--responses_api_*</code> flags work the same for any provider that implements the protocol (OpenRouter, Together, Fireworks, …). Swap the base URL and the API key, keep the rest of the pipeline identical.</p>
<hr>
<h4 class="relative group flex items-baseline">
	<a id="running-the-llm-in-process" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#running-the-llm-in-process" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Running the LLM in-process
	</span>
</h4>
<h5 class="relative group flex items-baseline">
	<a id="option-1-local-llm-on-mlx-apple-silicon" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#option-1-local-llm-on-mlx-apple-silicon" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Option 1: Local LLM on MLX (Apple Silicon)
	</span>
</h5>
<p>If you are on a Mac, MLX is the lowest-friction way to run a real model with sane latency. We recommend <strong>Qwen3-4B-Instruct-2507</strong>, which is small enough to feel instant on M-series chips and capable enough to hold a conversation.</p>
<pre><code class="language-bash">speech-to-speech \
  --llm_backend mlx-lm \
  --model_name <span class="hljs-string">"mlx-community/Qwen3-4B-Instruct-2507-bf16"</span>
</code></pre>
<p>The server listens on <code>ws://127.0.0.1:8765/v1/realtime</code> by default. Leave it running, connect the conversation app to the local backend, and you are talking to your robot.</p>
<h5 class="relative group flex items-baseline">
	<a id="option-2-local-llm-on-transformers-cuda--cpu--mps" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#option-2-local-llm-on-transformers-cuda--cpu--mps" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Option 2: Local LLM on Transformers (CUDA / CPU / MPS)
	</span>
</h5>
<p>Same idea, but using vanilla <code>transformers</code>. Use this if you are on a CUDA box, on Linux, or if you want to swap models freely without re-converting weights for MLX.</p>
<pre><code class="language-bash">speech-to-speech \
  --llm_backend transformers \
  --model_name <span class="hljs-string">"Qwen/Qwen3-4B-Instruct-2507"</span>
</code></pre>
<blockquote>
<p><strong>Tip.</strong> <code>Qwen3-4B-Instruct-2507</code> is another good option for LLM because it gives a good speed/quality balance on a single consumer GPU. You can point <code>--model_name</code> at any HF model the backend supports — for example a larger Gemma, Qwen, or a Mistral.</p>
</blockquote>
<h3 class="relative group flex items-baseline">
	<a id="running-the-engine-on-your-laptop-the-app-on-the-robot" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#running-the-engine-on-your-laptop-the-app-on-the-robot" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Running the engine on your laptop, the app on the robot
	</span>
</h3>
<p>If you are running the voice engine on your laptop and the conversation app on a Reachy Mini Wireless, the only thing that changes is the URL. Make sure the engine binds to a LAN address (not just <code>127.0.0.1</code>) and use the laptop's IP from the robot when you select the IP in the UI.</p>
<p>If you don't know your IP, here's how to find it:</p>
<details>
<summary>macOS</summary>

<pre><code class="language-bash">ipconfig getifaddr en0    <span class="hljs-comment"># wifi</span>
ipconfig getifaddr en1    <span class="hljs-comment"># ethernet (sometimes en0, varies)</span>
</code></pre>
</details>

<details>
<summary>Linux</summary>

<pre><code class="language-bash">hostname -I
</code></pre>
</details>

<details>
<summary>Windows</summary>

<pre><code class="language-powershell">ipconfig
</code></pre>
<p>Look for "IPv4 Address" under your active adapter.</p>
</details>

<p>You want the <code>192.168.x.x</code> or <code>10.x.x.x</code> one. If you see <code>169.254.x.x</code>, you're not actually on the network.</p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="wrap-up" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#wrap-up" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Wrap up
	</span>
</h2>
<p>You now have a fully local voice loop:</p>
<ul>
<li>A robot listening with <strong>Silero</strong>,</li>
<li>transcribing with <strong>Parakeet-TDT 0.6B v3</strong>,</li>
<li>thinking with whichever LLM you picked, whether that's local MLX, local Transformers, a vLLM or llama.cpp server next door, or a hosted Responses API endpoint,</li>
<li>and answering with <strong>Qwen3-TTS</strong>.</li>
</ul>
<p>Star <a href="https://github.com/huggingface/speech-to-speech" rel="nofollow"><code>huggingface/speech-to-speech</code></a> and <a href="https://github.com/pollen-robotics/reachy_mini_conversation_app" rel="nofollow"><code>pollen-robotics/reachy_mini_conversation_app</code></a>, and come tell us in the discussions which open-source cascade you ended up running on your robot.</p>
