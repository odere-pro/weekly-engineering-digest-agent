<p><strong>Authors:</strong> Granite Team, IBM</p>
<hr>
<p><strong>TL;DR:</strong> Granite 4.2 is our first family of dense, decoder-only reasoning LLMs, released in three sizes: <strong>3B, 8B, and 30B</strong>. These  models are post-trained from <a href="https://huggingface.co/collections/ibm-granite/granite-41-language-models">Granite-4.1</a> base models. <a href="https://huggingface.co/collections/ibm-granite/granite-41-language-models">Granite-4.1</a> base models were pre-trained from scratch on roughly 15T tokens with a five-phase strategy that extends the context window to 512K tokens, supervised fine-tuned on chain-of-thought, reasoning, and agentic-trajectory data, then post-trained with a <strong>multi-stage reinforcement learning pipeline</strong>. That pipeline includes agentic RL, where the 8B and 30B models learn to act with tools inside real sandboxed environments. Every model has a <strong>thinking / non-thinking</strong> switch, a <strong>low-effort</strong> thinking mode that spends a short reasoning budget on easy questions, and native tool calling. All Granite 4.2 models are released under the Apache 2.0 license.</p>

	<span>
		Overview
	</span>
</h2>
<p>Granite 4.2 is the reasoning-focused release of the Granite language-model family. Earlier Granite releases were strong instruction-following assistants; Granite 4.2 adds explicit reasoning. Every model can produce a chain of thought before its answer and can run in <strong>thinking</strong> or <strong>non-thinking</strong> mode depending on how much deliberation a task needs. A <strong>low-effort</strong> mode falls between the two, spending a short reasoning budget on easy questions.</p>
<p>The three sizes (<strong>3B, 8B, and 30B</strong>) share the same architectural design and follow the same training pipeline (base model, SFT, then multi-stage RL), each at its own scale. All three are strong reasoners and instruction followers. The clearest capability split shows up in post-training. The <strong>8B and 30B</strong> models additionally go through an <strong>agentic RL</strong> block that teaches them to operate as agents: calling tools, editing and running code, driving a terminal, and searching the web inside real environments. Every model supports native tool calling. Served through an OpenAI-compatible endpoint (for example, with vLLM), it emits tool calls in the OpenAI function-calling format and plugs into agentic harnesses without extra glue. Granite 4.2 is also supported in SGLang, see the <a href="https://docs.sglang.io/cookbook/autoregressive/IBM/Granite-4.2" rel="nofollow">SGLang cookbook</a> for a ready-to-serve recipe.</p>


<p>The rest of this post walks through the build: architecture, pre-training, supervised fine-tuning, the multi-stage RL pipeline, and results.</p>

<h2 class="relative group flex items-baseline">

<h2 class="relative group flex items-baseline">
	<a id="pre-training" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#pre-training" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Pre-Training
	</span>
</h2>
<p>Granite 4.2 models are post-trained from <a href="https://huggingface.co/collections/ibm-granite/granite-41-language-models">Granite-4.1</a> base models. <a href="https://huggingface.co/collections/ibm-granite/granite-41-language-models">Granite-4.1</a> base models were trained from scratch on approximately <strong>15 trillion tokens</strong> using a five-phase training strategy. Phases 1–2 focus on foundational pre-training, phases 3–4 perform mid-training with progressively higher-quality data annealing, and phase 5 introduces long-context training, extending the context window to <strong>512K tokens</strong>. Each phase uses a distinct data mixture and learning-rate schedule, gradually shifting from broad web-scale data toward more curated, high-quality sources.</p>
<p>The pre-training recipe closely follows the previous generation; for a detailed treatment of the data blend, phase schedule, and long-context extension, see the <a href="https://huggingface.co/blog/ibm-granite/granite-4-1">Granite 4.1 blog</a>.</p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="sft-data-preparation--quality-control" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#sft-data-preparation--quality-control" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		SFT: Data Preparation &amp; Quality Control
	</span>
</h2>
<p>Supervised fine-tuning (SFT) turns the base model into a reliable instruction-following, reasoning, and tool-using assistant. The SFT data mixture combines agentic (31.6%) and non-agentic (68.4%) data, totaling approximately 7.2 million samples, or roughly 100B tokens, of which about 65B are trainable.</p>
<p>The <strong>agentic corpus</strong> covers a broad range of domains, including software engineering (SWE, 69%), tool calling (12.1%), terminal use (8.0%), math (3.5%), search (0.8%), and action (0.2%). These samples and trajectories are generated using a diverse set of agent scaffolds and harnesses, including OpenHands, OpenCode, Terminus-2, SWE-agent, OpenResearcher, MiniSWE, OpenSeeker, EnvScaler, Gemini CLI, Hermes, Codex, and Goose. The agentic data combines samples from both open-source datasets and our own synthetically generated RL environments, spanning a variety of agent–harness combinations.</p>
<p>The <strong>non-agentic corpus</strong> consists of several major categories: instruction following (18.8%), coding (18.8%), math (14.6%), multilingual (7.0%), science (5.4%), reasoning (3.0%), and safety (0.8%).</p>
<h3 class="relative group flex items-baseline">
	<a id="data-quality-control" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#data-quality-control" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Data Quality Control
	</span>
</h3>
<p>We apply multiple stages of quality control before a sample enters the final SFT mixture. First, data from different sources is normalized and reformatted into a consistent OpenAI Chat format, making the conversation structure and tool interactions uniform across datasets and scaffolds.</p>
<p>We then use GPT-OSS-120B and Gemma 4 as LLM-based judges to assess sample quality. Low-scoring samples are removed, as are samples containing hallucinated or fabricated information, invalid tool interactions, or tool calls to functions that are not defined in the corresponding tool list. Several targeted, dataset-specific heuristic rules are also applied where appropriate to further improve quality and remove known sources of noise.</p>
<p>Finally, we perform both local and global deduplication. Deduplication is based on SHA-256 hashes computed over the combination of the <code>tools</code> and <code>messages</code> fields, removing duplicate samples both within individual data sources and across the overall SFT mixture.</p>
<h3 class="relative group flex items-baseline">
	<a id="sft-training-details" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#sft-training-details" rel="nofollow">

<h3 class="relative group flex items-baseline">
	<a id="phase-2-sft-for-the-30b-model" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#phase-2-sft-for-the-30b-model" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Phase 2 SFT for the 30B Model
	</span>
</h3>
<p>For the 30B model, we additionally perform a second phase of SFT focused specifically on agentic coding. In this phase, agentic, SWE, and coding data are upsampled to increase their effective contribution to the training distribution, while approximately 16% of the mixture is retained as replay data from the original SFT corpus.</p>
<p>The 30B model is then fine-tuned for roughly one additional epoch at a lower learning rate of 3.0e-6. This targeted second phase increases the model's exposure to agentic coding trajectories without discarding the capabilities acquired during the initial SFT phase.</p>

<h2 class="relative group flex items-baseline">
	<a id="reinforcement-learning-a-multi-stage-multi-environment-pipeline" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#reinforcement-learning-a-multi-stage-multi-environment-pipeline" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Reinforcement Learning: A Multi-Stage, Multi-Environment Pipeline
	</span>
</h2>
<p>After SFT, we apply a <strong>multi-stage, multi-environment reinforcement learning pipeline</strong>. Rather than a single RL pass, we run a <em>chain</em> of focused stages spanning many environments: math, code, science, instruction following, tool use, and structured output, then software engineering, terminal use, and web search. Each stage is an independent RL run that targets one capability and warm-starts from the previous stage's checkpoint.</p>

<p><a href="https://cdn-uploads.huggingface.co/production/uploads/65cc2c288ebd392213e58899/TuxEn5hma0bQf3-z_Ab6c.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/65cc2c288ebd392213e58899/TuxEn5hma0bQf3-z_Ab6c.png" alt="Granite 4.2 staged RL curriculum"></a></p>
<p><em>Figure 1. The staged RL curriculum. Foundational RL (verifiable rewards + skill boosters) runs for all sizes; the agentic RL block (SWE → Terminal → Search) runs for 8B and 30B only. Every model finishes with RLHF. Each stage is a separate GRPO run that warm-starts from the previous checkpoint.</em></p>
<h3 class="relative group flex items-baseline">
	<a id="training-methodology" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#training-methodology" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Training Methodology
	</span>
</h3>
<p>Every stage trains with <strong>asynchronous GRPO</strong> (<a href="https://arxiv.org/abs/2402.03300" rel="nofollow">Group Relative Policy Optimization</a>), so the generator and trainer halves of the loop never block on each other. A pool of generation workers keeps sampling responses and dropping the finished trajectories into a shared buffer; once the buffer holds a full step's worth, the trainer pulls that batch, takes an optimizer step, and streams the updated parameters back to the generator workers without pausing them. A refresh can land partway through a rollout, leaving a single trajectory stitched together from two adjacent policy versions. We allow this instead of paying to prevent it: the workers reuse their existing KV cache rather than rebuilding it after each refresh, and the one guardrail is a limit that keeps them from drifting more than a single update behind the trainer, which bounds how off-policy any sample can get. Whatever mismatch survives that limit is handled in the objective by <em>truncated importance sampling</em>, which clamps the train-versus-generation log-probability ratio to a fixed ceiling so a handful of stale tokens cannot dominate an update.</p>
<p>Advantages are group-relative with a <strong>leave-one-out baseline</strong>: each response is judged against the mean reward of the <em>other</em> samples drawn for the same prompt, which removes the need for a separate value network. To make this concrete, take <strong>RLVR</strong>, the first and longest-running stage: each step pairs <strong>256 prompts</strong> with <strong>16 sampled responses apiece</strong> for a <strong>4,096</strong>-example batch, which the trainer consumes in a single optimizer step before the next rollout begins. Later stages keep this machinery unchanged and adjust only the per-stage shape, shown next.</p>

<h3 class="relative group flex items-baseline">
	<a id="the-staged-curriculum" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-staged-curriculum" rel="nofollow">
		<span class="header-link"> </span>

	<span>
		The Staged Curriculum
	</span>
</h3>
<p>Each stage is a separate RL run with a single objective and its own reward signal. When it finishes, its policy is exported to Hugging Face format and becomes the base model for the next stage, so the pipeline is a sequence of warm-starts:</p>
<pre><code>SFT ─▶ RLVR ─▶ Skill boosters ─▶ SWE agent ─▶ Terminal ─▶ Search ─▶ RLHF
      └──────── foundational RL ────────┘   └──────── agentic RL (8B / 30B) ────────┘
</code></pre>
<p>The <strong>8B and 30B</strong> models follow the full ladder. The <strong>3B</strong> model takes a shortened path: foundational RL and alignment, without the agentic block.</p>
<h3 class="relative group flex items-baseline">
	<a id="reward-signals" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#reward-signals" rel="nofollow">

	</span>

<p>Verifiable rewards are objective and hard to game, so the pipeline front-loads them. Judge- and preference-based rewards handle open-ended qualities that no checker can express. Agentic-outcome rewards are the sparsest: often a single bit at the end of a long tool-use trajectory.</p>
<h3 class="relative group flex items-baseline">
	<a id="foundational-rl-build-the-skills" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#foundational-rl-build-the-skills" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Foundational RL: Build the Skills
	</span>
</h3>
<h4 class="relative group flex items-baseline">
	<a id="rlvr-verifiable-reward-rl" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#rlvr-verifiable-reward-rl" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		RLVR: verifiable-reward RL
	</span>
</h4>
<p>RLVR is the foundational stage and the broadest data mix in the pipeline: a single blended dataset spanning many verifiable domains.</p>
<ul>
<li><strong>Math:</strong> chain-of-thought with boxed-answer checking, plus formal proving in <strong>Lean</strong></li>
<li><strong>Competitive coding:</strong> solutions checked against hidden tests in a sandbox</li>
<li><strong>STEM / graduate-level science MCQA</strong> and general knowledge</li>
<li><strong>Instruction following:</strong> structured-output and inverse-instruction tasks</li>
<li><strong>Tool / function calling:</strong> single-step tool use</li>
<li><strong>Reasoning puzzles</strong> and <strong>abstention</strong> (knowing when to refuse)</li>
</ul>
<p>Each task type carries its own verifier, so the reward is grounded per example. RLVR runs for <strong>two rounds on 3B and 8B, and three on 30B</strong>. Each round is a fresh warm-started run on a re-weighted mix of public and internally curated RL data.</p>
<h4 class="relative group flex items-baseline">
	<a id="skill-boosters-targeted-lifts" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#skill-boosters-targeted-lifts" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Skill boosters: targeted lifts
	</span>
</h4>
<p>After RLVR, a few short <strong>booster</strong> stages sharpen specific capabilities that benefit from concentrated training focusing on the following domains:</p>
<ul>
<li><strong>Instruction following (IF):</strong> multi-turn chat, inverse-IFEval, structured outputs</li>
<li><strong>Code:</strong> competitive coding only</li>
</ul>
<p>Boosters are small, focused runs. A light KL penalty keeps the model close to its current behavior while nudging one skill. </p>


<h3 class="relative group flex items-baseline">
	<a id="agentic-rl-learning-to-act-8b--30b" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#agentic-rl-learning-to-act-8b--30b" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Agentic RL: Learning to Act (8B / 30B)
	</span>
</h3>
<p>In the agentic stages the model learns to <strong>act</strong>: call tools, observe results, and iterate inside a real environment, rewarded on whether the task was actually solved. These stages share the same shape: multi-turn tool use, real (not simulated) environments, sparse outcome rewards, and GRPO, warm-started from the coding-boosted checkpoint. They run in order: <strong>SWE → Terminal → Search</strong>.</p>

<p><a href="https://cdn-uploads.huggingface.co/production/uploads/65cc2c288ebd392213e58899/FxSMYasHnR4vpv263_DAL.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/65cc2c288ebd392213e58899/FxSMYasHnR4vpv263_DAL.png" alt="Agentic RL environments"></a></p>
<p><em>Figure 2. The three agentic-RL environments. Each pairs a real harness with a real environment and a sparse, outcome-based reward. The 3B model runs none of these.</em></p>
<ul>
<li><strong>SWE agent (software engineering).</strong> Each task is a real repository in its own sandbox. Driven by the <a href="https://github.com/All-Hands-AI/OpenHands" rel="nofollow">OpenHands</a> harness, the model reads code, edits files, and runs the test suite over many internal turns. The reward is verifiable: do the hidden tests pass? Tasks are drawn from open-source SWE datasets, each instance backed by a per-repo container image.</li>
<li><strong>Terminal agent (terminal / OS operation).</strong> Multi-step tasks in a live shell, run through the Harbor / <a href="https://www.harborframework.com/docs/agents/terminus-2" rel="nofollow">Terminus-2</a> agent harness. The model plans a sequence of commands, observes their output, and recovers from errors. Reward is assigned when the task completed successfully. This is the one stage that drives its multi-turn agent loop at the GRPO level, with rollouts spanning up to 64 environment turns.</li>
<li><strong>Search agent (deep research).</strong> The model answers hard, multi-hop questions using live web-search tool calls inside a browsing agent loop: gather evidence across hops, reason over it, and produce an answer. Because correctness here is open-ended, the reward is an LLM judge on the final answer.</li>
</ul>
<h3 class="relative group flex items-baseline">
	<a id="alignment-rlhf" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#alignment-rlhf" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Alignment: RLHF
	</span>
</h3>
<p>The final stage of every model is <strong>RLHF for human preference and safety.</strong> It optimizes against a generative reward model (GenRM) for preference, plus a safety reward covering jailbreak resistance and appropriate refusals. This stage uses the highest KL penalty in the pipeline, aligning tone and safety without eroding the capabilities the earlier stages built. In addition to human preference and safety alignment, this stage also applies a reasoning-length penalty to discourage overly verbose reasoning behavior acquired during earlier stages.</p>
<h3 class="relative group flex items-baseline">

<h2 class="relative group flex items-baseline">
	<a id="agentic-ai-infrastructure-for-scalable-rl" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#agentic-ai-infrastructure-for-scalable-rl" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Agentic AI Infrastructure for Scalable RL
	</span>
</h2>
<p>Reinforcement learning at this scale needs infrastructure that can drive a training loop and a fleet of live environments at the same time. This matters most in the agentic stages, where every training example is a multi-turn rollout that edits code, runs commands, or browses the web. Granite 4.2's RL runs on two open components: <strong><a href="https://github.com/NVIDIA-NeMo/RL" rel="nofollow">NeMo-RL</a></strong> on the training side and <strong><a href="https://github.com/NVIDIA-NeMo/gym" rel="nofollow">NeMo-Gym</a></strong> on the rollout side.</p>

<p><a href="https://cdn-uploads.huggingface.co/production/uploads/65cc2c288ebd392213e58899/ceRxgjK0m0kVHp1iJ7P34.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/65cc2c288ebd392213e58899/ceRxgjK0m0kVHp1iJ7P34.png" alt="NeMo-RL + NeMo-Gym system architecture"></a></p>
<p><em>Figure 3. The RL system. NeMo-RL drives the GRPO loop (Megatron-Core training backend, vLLM generation, and Megatron-Bridge for HF⇄Megatron weight conversion). NeMo-Gym orchestrates rollouts and hosts the tools, sandboxes, and reward/verifier calls as pluggable <strong>Resources</strong>.</em></p>
<p>The division of labor:</p>
<ul>
<li><strong>NeMo-RL (training side).</strong> <a href="https://github.com/NVIDIA/Megatron-LM" rel="nofollow">Megatron-Core</a> is the training backend; <a href="https://github.com/vllm-project/vllm" rel="nofollow">vLLM</a> generates rollouts; <strong>Megatron-Bridge</strong> converts weights between Megatron and Hugging Face formats, so each stage can export a clean HF checkpoint for the next one.</li>
<li><strong>NeMo-Gym (rollout side).</strong> It exposes each environment as a set of <strong>Resources</strong> (verifiers, tools, sandboxes, and reward models) behind a uniform interface. This is the plug point for the agentic stages: the SWE repo sandboxes, the terminal harness, and the web-search tools all attach here, and to the training loop they look the same as a simple math verifier.</li>
</ul>
<p>That uniformity is what makes the staged curriculum above practical: a booster's rule-based checker and a full SWE sandbox present the same interface to GRPO.</p>
<p>This split is also what makes the <strong>asynchronous</strong> training loop described above physically possible: generation and policy updates live on separate GPU pools, so the expensive generation fleet — including the live agentic environments — stays busy instead of idling through optimizer steps.</p>

<h2 class="relative group flex items-baseline">
	<a id="quantization" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#quantization" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Quantization
	</span>
</h2>
<p>We also released four quantized variants of the Granite 4.2 models for inference with vLLM. The models are converted to FP8, NVFP4, and MXFP4 using LLM Compressor, and to the GGUF format using the llama.cpp framework for reduced-memory deployment.</p>
<h3 class="relative group flex items-baseline">
	<a id="fp8" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#fp8" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		FP8
	</span>
</h3>
<p>The FP8 version is quantized with dynamic per-channel weights and per-token activations.  No calibration is used.</p>
<h3 class="relative group flex items-baseline">
	<a id="fp4" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#fp4" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		FP4
	</span>
</h3>
<p>The NVFP4 and MXFP4 versions are quantized using GPTQ calibrated on 2K samples drawn from the SFT dataset.  Max context length is 2K during calibration.</p>
<h3 class="relative group flex items-baseline">
	<a id="gguf" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#gguf" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		GGUF
	</span>
</h3>
<p>Conversion of the Granite 4.2 models to GGUF is done with the canonical llama.cpp tool as described in <a href="https://github.com/IBM/gguf#gguf-conversion--quantization" rel="nofollow">https://github.com/IBM/gguf#gguf-conversion--quantization</a>.</p>
<p>Several GGUF formats are provided:</p>
<ul>
<li>Q8_0</li>
<li>Q6_K</li>
<li>Q5_K_S</li>
<li>Q5_K_M</li>
<li>Q5_1</li>
<li>Q5_0</li>
<li>Q4_K_S</li>
<li>Q4_K_M</li>
<li>Q4_1</li>
<li>Q4_0</li>
<li>Q3_K_S</li>
<li>Q3_K_M</li>
<li>Q3_K_L</li>
<li>Q2_K</li>
</ul>

<h2 class="relative group flex items-baseline">
	<a id="infrastructure" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#infrastructure" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Infrastructure
	</span>
</h2>
<h3 class="relative group flex items-baseline">
	<a id="hardware" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#hardware" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Hardware
	</span>
</h3>
<p>We trained the Granite 4.2 language models on an NVIDIA GB200 NVL72 cluster hosted by CoreWeave, featuring:</p>
<ul>
<li>A 72-GPU NVLink domain for high-speed intra-rack communication</li>
<li>A non-blocking Fat-Tree NDR 400 Gb/s InfiniBand fabric for full-bandwidth inter-rack connectivity</li>
<li>Thousands of GPUs operating at cluster scale</li>
</ul>
<p>This infrastructure delivers the high-bandwidth, low-latency communication required for efficient large-scale distributed training.</p>
<h3 class="relative group flex items-baseline">
	<a id="software-stack" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#software-stack" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Software Stack
	</span>
</h3>
<p>The training software stack is packaged into <code>.sqsh</code> container images, each giving a run a reproducible, portable environment with its SBSA-compatible CUDA targets, Linux aarch64 Python wheels, and GPU-specific binaries pinned. The large-scale SFT runs build on an NGC PyTorch base image (Ubuntu 22.04, CUDA 12.8, Python 3.12); the RL stack runs in its own NeMo-RL container.</p>

<h3 class="relative group flex items-baseline">
	<a id="basic-inference-thinking-mode" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#basic-inference-thinking-mode" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Basic Inference (Thinking Mode)
	</span>
</h3>
<pre><code class="language-python"><span class="hljs-keyword">import</span> torch
<span class="hljs-keyword">from</span> transformers <span class="hljs-keyword">import</span> AutoModelForCausalLM, AutoTokenizer

model_path = <span class="hljs-string">"ibm-granite/granite-4.2-30b"</span>
tokenizer = AutoTokenizer.from_pretrained(model_path)
model = AutoModelForCausalLM.from_pretrained(model_path, device_map=<span class="hljs-string">"cuda"</span>, torch_dtype=torch.bfloat16)
model.<span class="hljs-built_in">eval</span>()

messages = [
    {<span class="hljs-string">"role"</span>: <span class="hljs-string">"user"</span>, <span class="hljs-string">"content"</span>: <span class="hljs-string">"How many r's are in the word 'strawberry'?"</span>},
]

text = tokenizer.apply_chat_template(messages, tokenize=<span class="hljs-literal">False</span>, add_generation_prompt=<span class="hljs-literal">True</span>, enable_thinking=<span class="hljs-literal">True</span>)
inputs = tokenizer(text, return_tensors=<span class="hljs-string">"pt"</span>).to(model.device)

	</a>
	<span>
		OpenHands
	</span>
</h3>
<p><a href="https://www.openhands.dev" rel="nofollow">OpenHands</a> is an AI software engineer that can plan, write code, and execute commands.</p>
<ol>
<li><p><strong>Install and launch OpenHands</strong> following the <a href="https://docs.openhands.dev/openhands/usage/agent-canvas/setup" rel="nofollow">official installation guide</a>.</p>
</li>
<li><p><strong>Configure the LLM</strong> in the OpenHands settings with:</p>
<ul>
<li><strong>Model:</strong> <code>granite-4.2-30b</code></li>
<li><strong>Base URL:</strong> <code>http://localhost:8000/v1</code></li>
<li><strong>API Key:</strong> your vLLM <code>--api-key</code> value</li>
</ul>
</li>
</ol>
<blockquote>
<p><strong>Note:</strong> The <code>openai/</code> prefix is required when connecting to OpenAI-compatible endpoints like vLLM. Refer to the <a href="https://docs.openhands.dev/openhands/usage/llms/local-llms" rel="nofollow">OpenHands local LLM documentation</a> for detailed setup instructions, troubleshooting, and alternative installation methods.</p>
