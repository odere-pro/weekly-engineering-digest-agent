<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]--><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_6.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_6.png" alt="Benchmarking transformers revisions across different metrics"></a></p>
<p align="center">
  <em>Benchmarking transformers revisions across different metrics</em>
</p>
<br>

<blockquote>
<p>This is a human-made, agent-focused blogpost.</p>
</blockquote>
<p>Coding agents increasingly work with our software instead of us: describe a task, and the agent picks the library,
writes the calls, runs them, and debugs its own mistakes. When the library gets in the way, it will
happily bypass it and rewrite the logic from scratch. This introduces a new concept in library development:
the code should not only be correct and fast, but should be designed so that an agent can drive it effectively. A clunky API
or stale docs annoy us developers, but it now also sends the agent down a longer, more expensive path.</p>
<p>Most benchmarks just look at the final answer. We wanted the whole process instead: not just whether the agent got
it right, but how much work it took to get there, and how that shifts across models, library revisions, and
tasks. We measured exactly that, using <code>transformers</code> as our case study.</p>
<p>Here, we will introduce a tool specific benchmark focusing on how the answer was found, and provide a simple 
implementation of one such harness, running entirely on open models driven by the
<a href="https://www.npmjs.com/package/@mariozechner/pi-coding-agent" rel="nofollow">pi</a> coding agent, with the full sweep of
models × revisions × tasks fanned out across <a href="https://huggingface.co/docs/huggingface_hub/guides/jobs">Hugging Face Jobs</a>
so every run sees identical hardware.</p>
<br>
<p align="center">
    But, <b><i>how do you optimize software for agents?</i></b>
</p>
<br>

<p>We're strong believers in the following two software principles:</p>
<ul>
<li>If it isn't tested, then it doesn't work</li>
<li>If it isn't documented, then it doesn't exist</li>
</ul>
<p>This remains the same within the realm of agentic-optimized tooling, and, for once, the two are directly tied to
each other.</p>
<p>You want your tool to exist for an agent: it needs to be discoverable. The API needs to be clear and the docs
need to be extensive. They need to be structured in a way that the agent has rapid access to the useful files and
examples. If you want your tool to work for an agent, then you should test it for agentic-use. </p>
<h2 class="relative group flex items-baseline">
	<a id="testing-software-for-agentic-use" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#testing-software-for-agentic-use" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Testing software for agentic-use
	</span>
</h2>
<p>We'll use <code>transformers</code> as an example throughout this blogpost: agents <em>using</em> it to solve ML tasks (classifying
text, captioning images, transcribing audio), not contributing code to it; though the harness was designed to work
with any tool that can be operated from the command line.</p>
<p>Our intuition on <code>transformers</code> was that usage could be dramatically simplified
with a few changes: a CLI, a Skill, and self-contained, task-specific examples. This is the same recipe
recently applied to the <a href="https://huggingface.co/blog/hf-cli-for-agents"><code>hf</code> CLI, redesigned to be agent-optimized</a>,
where agents used 1.3–1.8× (and up to 6×) fewer tokens. We wanted to know whether that kind of win generalizes, and
whether it could be useful for transformers as well.</p>
<p>Intuition is a powerful tool, but we wanted more evidence before we opened PRs that add several thousand lines of code to such a widely used codebase as <code>transformers</code>. We set out to measure what success looks like.</p>
<h3 class="relative group flex items-baseline">
	<a id="not-all-successes-are-equal" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#not-all-successes-are-equal" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Not all successes are equal
	</span>
</h3>
<p>Two agents can both produce the correct label for a sentiment-classification task,
but one:</p>
<ul>
<li>writes a 40-line Python script, imports <code>transformers</code>, debugs a shape error,
re-runs twice, and finally prints the answer;</li>
</ul>
<p>while the other</p>
<ul>
<li>types <code>transformers classify --model ... --text "..."</code> and is done in one call.</li>
</ul>
<p>Both reach <code>POSITIVE (0.9999)</code>, and here are the two paths an agent actually took on this exact task:</p>
<pre><code class="language-diff"># Task: classify the sentiment of "I absolutely loved the movie, it was fantastic!"

<span class="hljs-deletion">- # one agent: pipe a script into python and parse the output</span>
<span class="hljs-deletion">- python - &lt;&lt;'PY'</span>
<span class="hljs-deletion">- from transformers import AutoTokenizer, AutoModelForSequenceClassification</span>
<span class="hljs-deletion">- import torch</span>
<span class="hljs-deletion">- import torch.nn.functional as F</span>
<span class="hljs-deletion">-</span>
<span class="hljs-deletion">- model = AutoModelForSequenceClassification.from_pretrained("distilbert/distilbert-base-uncased-finetuned-sst-2-english")</span>
<span class="hljs-deletion">- tokenizer = AutoTokenizer.from_pretrained("distilbert/distilbert-base-uncased-finetuned-sst-2-english")</span>
<span class="hljs-deletion">- inputs = tokenizer("I absolutely loved the movie, it was fantastic!", return_tensors="pt")</span>
<span class="hljs-deletion">- with torch.no_grad():</span>
<span class="hljs-deletion">-     logits = model(**inputs).logits</span>
<span class="hljs-deletion">- probs = F.softmax(logits, dim=1)</span>
<span class="hljs-deletion">- idx = torch.argmax(probs, dim=1).item()</span>
<span class="hljs-deletion">- print(model.config.id2label[idx], probs[0][idx].item())</span>
<span class="hljs-deletion">- PY</span>

<span class="hljs-addition">+ # the other agent: one command</span>
<span class="hljs-addition">+ transformers classify \</span>
<span class="hljs-addition">+   --model distilbert/distilbert-base-uncased-finetuned-sst-2-english \</span>
<span class="hljs-addition">+   --text "I absolutely loved the movie, it was fantastic!"</span>
</code></pre>
<p>Both methods reach the same result. But they have very different profiles in <strong>cost, latency, token usage, and failures</strong>.</p>
<p>If your evaluation only checks the final string, you're blind to these as well as
whether a change you shipped to the library (a CLI improvement, better error messages, a
Skill) actually helped agents.</p>
<p>Our goal with this harness is to evaluate how much work
an agent has to do to perform a given task, and whether changes to the library improve performance.</p>
<h3 class="relative group flex items-baseline">
	<a id="how-do-we-run-evaluations" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#how-do-we-run-evaluations" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		How do we run evaluations?
	</span>
</h3>
<p>A few words on how we'll evaluate agents here.</p>
<p>We run every task under three variants (or "tiers"); three different ways an agent can come at <code>transformers</code>:</p>
<pre><code class="language-text">bare     pip install transformers, and nothing else
clone    the full transformers source, checked out in the working directory
skill    a packaged Skill: the CLI's docs + task examples, loaded in context
</code></pre>
<p>These aren't nested: <code>skill</code> doesn't contain <code>clone</code> (it ships curated docs, not the source tree), and neither
strictly contains the other, each gives the agent a different kind of help. As we'll see, a model can sometimes 
do better on <code>clone</code> than on <code>skill</code>.</p>
<p>A few more choices:</p>
<ul>
<li>For now we only focus on deterministic tasks which can provide an exact match, as they provide a very nice ground for experimentation. Model-as-a-judge and other schemes are the obvious next steps for other tasks.</li>
<li>Every run is its own Hugging Face Job: one per (model × revision × task), so the whole sweep runs in parallel on identical hardware, which keeps the comparison fair at scale.</li>
<li>Results and traces land in a Hugging Face Bucket: fast, no versioning needed, and handles very high write concurrency.</li>
</ul>
<h3 class="relative group flex items-baseline">
	<a id="which-models-to-benchmark-against" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#which-models-to-benchmark-against" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Which models to benchmark against?
	</span>
</h3>
<p>Not all models driving agents are equal, and their difference changes what you should look at when running them.</p>
<p><em>Large open models</em></p>
<p>At one end, you have the largest, most capable open models. On reasonably common tasks,
these should get the right answer, eventually. For them, task completion saturates near
100% and stops telling you much about your tool; a more relevant benchmark is the effort
it took the agent to get there: how many turns, tokens and seconds it took, and whether they walked a clean
path or used deprecated APIs.</p>
<p><em>Local</em></p>
<p>Local models vary widely in size, and so do their abilities.
Metrics such as <strong>"match %"</strong> are more relevant than for their larger counterparts,
as you can see how model sizes/capabilities affect results on your specific
tool.</p>
<p>This harness not only provides guidance to library maintainers on how to improve a repository for agent interactions, it also helps assess how different agents and models perform on the tasks users care about.</p>
<p>The harness scores every run on several axes, so that you can ask what actually matters
for each class of model:</p>
<ul>
<li><strong>match %</strong>: did the final answer contain the expected result (per-task,
case-insensitive substring / regex / exact, all explicit in the report);</li>
<li><strong>median time</strong> and <strong>median tokens</strong> (new vs. cached vs. generated);</li>
<li><strong>runs with error %</strong>: including a guard that flags runs which produced <em>nothing</em>
(0 output tokens, no tool calls, no answer) so silent failures don't masquerade
as "0";</li>
<li><strong>marker adoption</strong>: tool-defined behavior markers; see below for an explanation
of what this is.</li>
</ul>
<p>All of it lands in a report you can directly examine:</p>
<p align="center">
<iframe src="https://transformers-community-is-transformers-agentic.static.hf.space" frameborder="0" width="100%" height="900" sandbox="allow-scripts" referrerpolicy="same-origin"></iframe>
<br>
  <em>The live report: Overview, Coverage, and Results, all client-side.</em>
</p>

<p>And because it captures the native agent trace of every run, numbers are just the beginning: you
can read exactly what the agent did, command by command. The traces are shareable
through the Hub's <a href="https://huggingface.co/docs/hub/agent-traces">agent-traces viewer</a>:</p>
<p align="center">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_11.png" alt="A run rendered in the Hub's agent-traces viewer: MiniMax-M2.7 on the answer-question task" width="85%"><br>
  <em>A run rendered in the Hub's agent-traces viewer: MiniMax-M2.7 on the answer-question task.</em><br>
  <a href="https://huggingface.co/buckets/lysandre/transformers-agentic-use/tree/traces/22404f7951/pi/MiniMaxAI--MiniMax-M2.7/bare__answer-question__run1.jsonl"><b>Open this trace on the Hub ↗</b></a>
</p>

<p>Before the results, a quick recap of the setup. Each run varies four things: the <strong>model</strong> driving the agent,
the <strong><code>transformers</code> revision</strong> it runs against, the <strong>task</strong>, and the <strong>tier</strong> (<code>bare</code> / <code>clone</code> / <code>skill</code>).
As discussed, we look at different metrics for the two different model categories.</p>
<h3 class="relative group flex items-baseline">
	<a id="large-open-models-hold-the-model-vary-the-revision" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#large-open-models-hold-the-model-vary-the-revision" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Large open models: hold the model, vary the revision
	</span>
</h3>
<p>Since a large open model will usually get to the correct result, what you're really
measuring is the effort it took to do so. Did it take ten turns or one? Did it follow
an API path you deprecated because it trusted obsolete documentation? Did it hit an
error you hadn't foreseen?</p>
<p>The natural experiment is to fix one strong model and vary the tool's
revisions: the successive git versions of <code>transformers</code> we test against, from released tags like
<code>v5.8.0</code> and <code>v5.9.0</code> to the specific commit that introduces the CLI and Skill. We want to watch whether the load
it puts on the agent goes up or down. We used the harness on <code>transformers</code> to check
whether adding a dedicated CLI and Skill actually lightened the agents' work.</p>
<p>For the three large models we used in our tests, the average time spent on all tasks indicates that the Skill commit
results in less time spent working on the tasks:</p>
<p align="center">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_13.png" alt="Median time per revision, by tier" width="85%"><br>
  <em>Median time per revision, by tier: the skill commit (green dot) is the fastest.</em>
</p>

<p>On the other hand, in the experiments in which we cloned the repository, we can see a significant increase
in token consumption due to the commit that introduced the CLI and examples, as we'll see in a moment.</p>
<p align="center">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_12.png" alt="Median new tokens per revision, by tier" width="85%"><br>
  <em>Median new tokens per revision, by tier: the clone variant jumps once the CLI lands in the repo.</em>
</p>

<p>Reading the clone-variant traces explains why. The commit adds a command, but it also ships the
CLI's implementation and a set of <code>cli/agentic/*.py</code> usage examples into the repository directly. </p>
<p>On the <code>clone</code> variant the agent has a full transformers checkout in front of it, and roughly a third of the runs go read the new
surface (the <code>/cli/</code> tree and the example scripts) to learn the interface before calling it. This raises the
median input from ~4k to ~6.4k tokens. </p>
<p>The two charts are then two sides of one tradeoff: the commit buys the large models less time 
(they reach for the CLI instead of debugging Python) at the cost of more
tokens (they read the code that taught them the CLI). A tradeoff worth knowing about before merging PRs.</p>
<p>One caveat works in the CLI's favor, though, which isn't benchmarked yet: the cost of reading it is amortized 
with successive runs. Our setup is built for one-off experiments. Each run is a fresh agent that rediscovers 
the CLI from scratch, so it pays the discovery cost every time. In real usage an agent learns the interface 
once and then solves task after task within the same session, amortizing that cost across many requests. The
token bump we measure here is closer to a worst case than to what a user would see day to day.</p>
<h3 class="relative group flex items-baseline">
	<a id="small-models-hold-the-revision-vary-the-model" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#small-models-hold-the-revision-vary-the-model" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Small models: hold the revision, vary the model
	</span>
</h3>
<p>Open models give us fine-grained control over the variables that matter most here: size, configuration, quantization,
provider, training, and anything that would differ from one model to the next. They're also where a good tool surface
matters most: a small model asked to "use <code>transformers</code> to do X" on a <code>bare</code> environment can
guess an API that changed some releases ago, may do unnecessary tool calls, and can
get the wrong answer.</p>
<p>So here the experiment is the opposite of the above: hold the revision and sweep the model. This helps
see which models actually take care of the task, not just by token count and time,
but down to which ones can't reliably handle the tool calls. Our intuition is
that the smaller the model, the harder both tool use and the task get; we ran the
harness across a range of model sizes to test exactly that:</p>
<p align="center">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_14.png" alt="Match % across models, by tier" width="85%"><br>
  <em>Match % across models, by tier: the skill tier lifts the larger models but drops the smaller ones.</em>
</p>

<p>which also seems to be correlated with the number of tokens ingested</p>
<p align="center">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_15.png" alt="Median new tokens across models, by tier" width="85%"><br>
  <em>Median new tokens across models, by tier.</em>
</p>

<blockquote>
<p>A note on fair comparison: naively averaging across tasks is misleading when
coverage is uneven (a model that only finished the quick tasks looks fast). The
report has a <strong>"shared tasks only"</strong> toggle (across models and/or revisions) so
you compare like-for-like, and a <strong>Coverage</strong> heatmap so you can see exactly which
task × revision × model cells actually ran.</p>
</blockquote>
<h2 class="relative group flex items-baseline">
	<a id="tweaking-the-tool-markers-and-results" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#tweaking-the-tool-markers-and-results" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Tweaking the tool: markers and results
	</span>
</h2>
<p>Two things come together here: how to look past whether the agent succeeded to what it did and how it
did it; as well as the first results we pulled out of the harness.</p>
<h3 class="relative group flex items-baseline">
	<a id="whats-a-marker" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#whats-a-marker" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		What's a marker?
	</span>
</h3>
<p>Match %, tokens, and time tell you the cost of a run but don't tell you much about what happened under the hood.</p>
<p>This is why we've introduced the concept of markers. A marker is a named pattern the profile (the
small per-tool plugin that teaches the harness how to build and drive a given library) matches against
a run. </p>
<p>It is a one-line label for a behavior you care about, checked against the shell
commands the agent ran, the code it wrote, the files it read, or its final
answer. A run can fire several markers or none; the report shows how often each one fired,
per model and per revision.</p>
<p>For <code>transformers</code> we declare a handful but we'll only look at the two most relevant ones:</p>
<ul>
<li><strong><code>cli</code></strong>: the agent invoked the <code>transformers</code> command-line tool (e.g.
<code>transformers classify …</code>) instead of writing Python.</li>
<li><strong><code>pipeline</code></strong>: it reached for the high-level <code>pipeline(...)</code> Python API.</li>
</ul>
<p>These are what we watch to see whether a change actually shifted the agent's behavior. Interestingly here,
the larger the model, the more it leverages the new context instead of using its memory; therefore leveraging
the newly introduced CLI.</p>
<p align="center">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_16.png" alt="CLI adoption by tier across models" width="85%"><br>
  <em>CLI adoption by tier across models: only the skill tier reaches for it, and more so as models grow.</em>
</p>

<p>CLI adoption is new: the CLI lands in a single commit, isn't in any model's training data, and is only
lightly documented. The effect is clear: it's the Skill variant, the one that ships the CLI's
documentation, that actually reaches for it, at 55.3%.</p>
<h3 class="relative group flex items-baseline">
	<a id="is-the-cli--skill-commit-helping" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#is-the-cli--skill-commit-helping" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Is the CLI + Skill commit helping?
	</span>
</h3>
<p>Comparing the commit across model sizes, the CLI + Skill helps the bigger models: on the <code>skill</code> tier, Kimi and the other large agents reach for the CLI and finish in fewer turns. (On <code>clone</code> they spend <em>more</em> input tokens first, reading the new CLI code, as we saw above, so the win shows up in time and turns, not raw tokens.)</p>
<p align="center">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_5.png" alt="Kimi-K2.6, GLM-5.1, and MiniMax-M2.7 across revisions" width="85%"><br>
  <em>Kimi-K2.6, GLM-5.1, and MiniMax-M2.7 across revisions</em>
</p>

<p>But in some smaller-model settings, it appears to hurt performance. One plausible explanation is that small
models lean on memorized API patterns, reproducing <code>pipeline(...)</code> snippets
they've seen in their training data. The new concepts are then a larger
surface for them to get wrong. You can watch this directly on the harness: lower
match %, more retries, the <code>cli</code> marker barely firing. It is particularly striking on the Qwen3-4B model:
the Skill barely changes its match rate yet its cost distribution is significantly affected. </p>
<p>Almost all of that comes from the <code>clone</code> tier. The checkout now contains
the CLI's implementation and <code>cli/agentic/*.py</code> examples, and the 4B agent reads them in bulk: its median new
tokens jump from ~2.4k to ~23k, with time and output skyrocketing as well, for no gain in
accuracy.</p>
<p align="center">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_7.png" alt="Qwen3-4B cost distributions across revisions: elapsed, new tokens, repeat tokens, out tokens" width="85%"><br>
  <em>Qwen3-4B across revisions. The CLI + Skill commit fans the cost distribution wide open, on the <code>clone</code> tier the agent reads the newly-shipped CLI source in bulk (~10× the new tokens), for no gain in match %. (<code>repeat tokens</code> stays flat: this setup uses no prompt caching.)</em>
</p>

<p>Sometimes, though, the Skill breaks correctness outright. Reading the traces shows how, for example for Qwen3-14B: 
adding the Skill drops its overall match rate from 67% (bare) to 43%, and on the simplest tasks the collapse is very
visible: <code>classify-sentiment</code> goes from 100% on the <code>clone</code> variant to <strong>0%</strong> with the Skill. </p>
<p align="center">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_17.png" alt="Qwen3-14B classify-sentiment match % by tier across revisions" width="85%"><br>
  <em>Qwen3-14B on <code>classify-sentiment</code>, by tier: <code>clone</code> (blue) holds at 100% across revisions, but the Skill variant (green) collapses to 0% at the CLI + Skill revision.</em>
</p>

<p>Looking at the traces, the model mistakes the CLI for a <em>tool it can call directly</em> (as in an agentic-harness
tool, like web-search). The Skill is <strong>not</strong> an executable tool: it's documentation loaded
into the agent's context, and the <code>transformers</code> CLI is only ever meant to be run from the shell (via <code>bash</code>); so this
will not work.</p>
<p>Qwen3-14B reads the Skill and, in 39 of its 56 Skill runs, either emits a <code>transformers(command="classify", ...)</code>
tool call (a tool that was never registered) or, finding nothing like it among its <code>read</code>/<code>bash</code>/<code>edit</code>/<code>write</code>
tools, concludes it <em>can't</em> run a model and gives up. Either way, rather than fall back to the one-line
<code>pipeline(...)</code> that scored 100% on the <code>clone</code> checkout, it declares the task impossible.</p>
<p align="center">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_10.png" alt="Qwen3-14B gives up on classify-sentiment under the Skill variant" width="85%"><br>
  <em>Qwen3-14B on classify-sentiment (Skill variant): it reasons that read/bash/edit/write can't run a model, and gives up.</em>
</p>

<p>This is exactly what we built the harness to catch: the same change that speeds the large models
ends up breaking the small ones, which seemed a bit counterintuitive to us at first and something we'd likely have
shipped as-is. The takeaway for maintainers: <strong>agent-facing APIs should be evaluated across model sizes, because a
new affordance can reduce work for strong models while adding ambiguity for smaller ones.</strong> It also hints at a fix:
rather than hand-write a Skill and check it after the fact, you could generate and validate one against the weaker
models up front. </p>
<p>This is exactly what <a href="https://huggingface.co/blog/upskill">Upskill</a> does: it turns a strong model's solution into 
a Skill only when it measurably helps the smaller ones.</p>
<h2 class="relative group flex items-baseline">
	<a id="trying-it-yourself" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#trying-it-yourself" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Trying it yourself
	</span>
</h2>
<p>The harness is one CLI, <code>agent-eval</code>. Install it, run a suite, fan it out across models × revisions on HF Jobs, and publish the
report as a Hugging Face Space. </p>
<blockquote class="warning">
<p><strong>Trusted local use only.</strong> The harness runs a coding agent with bypassed permissions and executes code from
whatever revision you point it at, and traces can contain prompts, output, and local paths. See
<a href="https://github.com/huggingface/is-it-agentic-enough/blob/main/SECURITY.md" rel="nofollow">SECURITY.md</a> before pointing it at code you didn't write or sharing results.</p>
</blockquote>
<p>The full, kept-current setup and usage instructions live in the <a href="https://github.com/huggingface/is-it-agentic-enough" rel="nofollow">README</a>.</p>
<h2 class="relative group flex items-baseline">
	<a id="closing" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#closing" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Closing
	</span>
</h2>
<p>Checking the final answer tells you whether an agent <em>can</em> use your library. It
doesn't tell you what it costs: the turns, tokens, errors, and the path it took to
get there. This harness measures that, across the revisions and models you pick.</p>
<p>On <code>transformers</code>, it caught something we'd have shipped on faith: the CLI + Skill
helps the largest open models and hurts the smallest ones. Worth knowing before merging!</p>
<p>It's profile-based, and designed to be adaptable: point it at your own library, define
a few tasks and their expected answers, get the same report. Code and tasks are in
the <a href="https://github.com/huggingface/is-it-agentic-enough" rel="nofollow">repo</a>, traces are on the Hub.
Let us know if you use it for your project!</p>

		<span class="header-link"> </span>
