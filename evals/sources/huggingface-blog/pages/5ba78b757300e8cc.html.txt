<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]-->In our <a href="https://huggingface.co/blog/ibm-research/altk-evolve-sldd/">previous post</a>, we compared <strong><a href="https://agenttoolkit.github.io/altk-evolve/" rel="nofollow">ALTK-Evolve</a></strong> with <a href="https://arxiv.org/abs/2510.04618" rel="nofollow">ACE</a> and showed that <em>how</em> you deliver an agent's self-distilled guidelines — a few retrieved per task vs. the whole set injected — drives both accuracy and cost. This post steps back to the question that comes before it: <em>how much</em> should you give it?</p>
<p>Equipping an agent with agentic memory sounds simple: distill lessons from its past work, put them back in context, and more experience should mean better performance. It doesn't always work that way. When we scaled the evaluation to <strong>eight models</strong> — from a 30B dense model to frontier proprietary systems — one finding stood out:</p>
<blockquote>
<p><strong>Agentic memory is not a feature you switch on. It's a dose you calibrate to the model.</strong></p>
</blockquote>
<p><strong>TL;DR</strong></p>
<ul>
<li><p><strong>ALTK-Evolve</strong> lets an agent learn from its own past trajectories: distilling reusable guidelines and injecting them back at inference time, with no weight updates and no human annotation.</p>
</li>
<li><p><strong>The right dose differs by model tier:</strong> strong models with headroom want the full guideline set, weaker models do best with a compact core plus per-task retrieval, and saturated models show no measurable gain.</p>
</li>
<li><p><strong>Curated retrieval can be both the most accurate and the cheapest option:</strong> gpt-oss-120b gained +16.1pp task completion at only +5% tokens — and prompt caching keeps even the full guideline set affordable in production.</p>
</li>
</ul>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="the-key-insight-dosage-depends-on-capability" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-key-insight-dosage-depends-on-capability" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The Key Insight: Dosage Depends on Capability
	</span>
</h2>
<p>Not every model benefits from the same amount of memory. Across eight models spanning the capability spectrum, we saw three recurring patterns:</p>
<ul>
<li><p><strong>Strong models with headroom</strong> want the full guideline set — every guideline, including rare edge-case lessons. They have the capacity to absorb and apply all of it. DeepSeek-V3.2 (671B MoE) climbed <strong>+9.5 percentage points</strong> in task completion when given its full self-mined guideline set.</p>
</li>
<li><p><strong>Smaller or weaker models get drowned by a large guideline set.</strong> For these, a tight, high-confidence core plus a handful of task-relevant guidelines retrieved per task works best. gpt-oss-120b (117B MoE) gained <strong>+16.1pp</strong> with this selective approach — while the full guideline set gained less <em>and</em> cost ~50% more tokens.</p>
</li>
<li><p><strong>Already-saturated models show no measurable gain.</strong> We call this the saturated pattern — the label describes what we observed, not a proven cause. The model may already have been near its ceiling on these tasks, the guidelines may not have addressed its remaining failures, or it may not have applied the guidance effectively. GLM-5 (745B MoE) sat here in our runs.</p>
</li>
</ul>
<p><em>What puts a model into one pattern rather than another isn't simply parameter count.</em> Benchmark headroom, context-window size, architecture, guideline quality, and task distribution all appear to shape where a model lands, and separating those factors is ongoing work. The practical takeaway holds either way: <strong>the right dose of memory depends on the model, and we can calibrate it.</strong></p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="learning-happens-around-the-model-not-inside-it" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#learning-happens-around-the-model-not-inside-it" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Learning happens around the model, not inside it
	</span>
</h2>
<p>"Memory" here doesn't mean replaying a past transcript. It means a <strong>guideline set</strong> — strategies that worked, mistakes to avoid, and edge cases — distilled from the agent's own prior trajectories. The loop is straightforward:</p>
<ol>
<li><p>The agent attempts tasks and produces trajectories.</p>
</li>
<li><p>ALTK-Evolve extracts behavioral guidelines from both its successful and unsuccessful runs.</p>
</li>
<li><p>It consolidates those guidelines into a reusable set.</p>
</li>
<li><p>At inference time, the agent receives either the full guideline set or a task-relevant selection of it.</p>
</li>
</ol>
<p>No model weights are updated. The learning loop changes the <em>guidance available to the agent</em>, not the underlying model — which is exactly why it's cheap to adopt and portable across the eight models we tested.</p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="results-across-the-spectrum" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#results-across-the-spectrum" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Results Across the Spectrum
	</span>
</h2>
<p>We evaluated on <strong>AppWorld</strong> — 585 multi-step tasks (168 <code>test_normal</code> + 417 <code>test_challenge</code>) across 9 simulated apps (calendars, messaging, payments, and so on). Tasks are scored two ways: whether the agent fully completes each task (<strong>TGC — Task Goal Completion</strong>) and whether <em>every</em> variant of a scenario passes (<strong>SGC — Scenario Goal Completion</strong>, a stricter, all-or-nothing bar). Full definitions are in the appendix.</p>
<h3 class="relative group flex items-baseline">
	<a id="the-three-configurations-we-compare" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-three-configurations-we-compare" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The three configurations we compare
	</span>
</h3>
<p>Because the confusing part of any memory study is <em>what's actually in the context window</em>, we define the configurations up front.</p>
<p>Both memory configurations draw from <strong>the same guideline set</strong>, mined once (via the loop above) from AppWorld's <strong>training split</strong> only. What changes between them is only <em>how that one set is delivered</em> — the <strong>full guideline set</strong> injects all of it every step, while <strong>curated retrieval</strong> delivers a selected subset — never how the guidelines were produced, and no test-split data ever goes into building it.</p>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th>Configuration</th>
<th>What's in the agent's context</th>
</tr>

		</thead><tbody><tr>
<td>Baseline</td>
<td>No memory — the agent as shipped.</td>
</tr>
<tr>
<td>Full guideline set</td>
<td>Every mined guideline, injected on every ReAct step.</td>
</tr>
<tr>

<td>A fixed, high-confidence core of those same guidelines plus a few task-relevant ones retrieved for each task (a fixed portion + a variable portion).</td>
</tr>
</tbody>
	</table>
</div>
<p>The number of guidelines a model mines depends on its own capability, so we report configurations by <strong>strategy</strong> — "full guideline set" vs. "curated retrieval" — rather than by raw counts, which aren't comparable across models.</p>

<h2 class="relative group flex items-baseline">
	<a id="the-cheapest-memory-strategy-can-also-be-the-best" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-cheapest-memory-strategy-can-also-be-the-best" rel="nofollow">
		<span class="header-link"> </span>

	<span>
		The Cheapest Memory Strategy Can Also Be the Best
	</span>
</h2>

<p>Two takeaways:</p>
<ol>
<li><p><strong>Curated retrieval keeps cost near baseline.</strong> For weaker models, where selection wins on accuracy, it also wins on cost — the best of both worlds (<strong>+16.1pp TGC at only +5% tokens</strong> for gpt-oss-120b). Better performance here does <strong>not</strong> require more inference cost.</p>
</li>
<li><p><strong>Memory doesn't blow up the reasoning loop.</strong> DeepSeek runs about the same number of ReAct steps with memory as without (≈18–19 on average), so the added cost is input-token inflation, not longer trajectories.</p>
</li>
</ol>
<p>The real efficiency lever in production is <strong>prompt caching</strong>: the static portion of the guideline set is identical across steps and can be cached, cutting effective cost substantially. Cache-aware prompt design — keeping the shared guideline-set prefix stable so it stays cacheable — is worth engineering for. We also hypothesize that <strong>context-window size</strong> plays a role: models with larger windows may absorb the full guideline set more effectively, while smaller-context models benefit more from retrieval that keeps injected content compact. We have not yet run controlled experiments isolating this factor.</p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="memory-should-be-calibrated-not-merely-accumulated" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#memory-should-be-calibrated-not-merely-accumulated" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Memory Should Be Calibrated, Not Merely Accumulated
	</span>
</h2>
<p>The lesson isn't to give an agent everything it has learned. It's to give it the amount of experience it can actually use.</p>
<ul>
<li><p>For <strong>weak models</strong>, that means a compact core plus a few task-specific lessons — which, conveniently, is also the cheapest option.</p>
</li>
<li><p>For <strong>strong models with headroom</strong>, it means preserving the full guideline set, kept affordable in production via prompt caching.</p>
</li>
<li><p>For <strong>saturated models</strong>, it means spending no extra context until their remaining failure modes are better understood.</p>
</li>
</ul>
<p>The gains are real across the board — automatic, leakage-free, and requiring no human annotation — but only when the dose fits the model.</p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="whats-next" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#whats-next" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		What's Next
	</span>
</h2>
<p>This is a starting point, not the finish line:</p>
<ul>
<li><p><strong>A learned selector.</strong> Our current retrieval ranks guidelines by cosine similarity, which we've shown doesn't perfectly predict which guidelines help a given task. A selector trained on outcome signal is the natural next step.</p>
</li>
<li><p><strong>Memory for very weak models.</strong> Below a minimum capability baseline, self-distillation lacks signal. Teacher-distilled memory for very weak models is a separate problem we're exploring.</p>
</li>
<li><p><strong>Beyond AppWorld.</strong> These results are validated on AppWorld — a rigorous multi-step benchmark, but a single one. Broader agent benchmarks and real-world deployments are in progress.</p>
</li>
<li><p><strong>Isolating context window.</strong> As above, we want controlled experiments that separate context-window size from raw capability.</p>
</li>
</ul>

</blockquote>

<h2 class="relative group flex items-baseline">
	<a id="appendix-understanding-the-metrics" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#appendix-understanding-the-metrics" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Appendix: Understanding the Metrics
	</span>
</h2>
<p>AppWorld tasks are graded by two metrics, both reported as percentages (higher is better):</p>
<ul>
<li><p><strong>TGC — Task Goal Completion.</strong> The share of individual tasks the agent completes fully and correctly. This is the headline <em>"did it get the job done"</em> number.</p>
</li>
<li><p><strong>SGC — Scenario Goal Completion.</strong> A stricter, all-or-nothing metric. Each <em>scenario</em> bundles several variants of the same task (the same request with different data, phrasing, or edge conditions). SGC counts a scenario as passing only if the agent succeeds on <strong>every</strong> variant. It measures <strong>reliability</strong> — an agent that solves a task most of the time but fails on one variant scores on TGC but not on SGC.</p>
</li>
</ul>
