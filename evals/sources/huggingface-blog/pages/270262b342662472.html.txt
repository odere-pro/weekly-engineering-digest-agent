<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]--><em>A walkthrough of the LeRobot integration in Strands Robots - one agent loop, from a Hub dataset to a physical robot, with sim-to-real datasets in the same on-disk format and policies you swap with a string.</em></p>
<p>You have a robot, a folder of demonstration data on the <a href="https://huggingface.co">Hugging Face Hub</a>, and a new task you want it to learn. Today that takes five separate tools: one to record new demonstrations, another to train, a third to test in simulation, custom code to deploy on hardware, and yet another to coordinate when you have more than one robot. The pieces work on their own. They don't talk to each other.</p>
<p><a href="https://github.com/strands-labs/robots" rel="nofollow">Strands Robots</a> is an open source SDK from AWS (<a href="https://www.apache.org/licenses/LICENSE-2.0" rel="nofollow">Apache 2.0</a>) that exposes robot abstractions, simulation, and the <a href="https://github.com/huggingface/lerobot" rel="nofollow">LeRobot</a> stack as AgentTools that you compose into a single Strands agent. The integration is deliberately thin: LeRobot's own scripts handle hardware recording and calibration, and the Strands AgentTools come in for the parts an agent actually orchestrates. The simulation tool records LeRobotDatasets in the same format LeRobot writes on hardware. <a href="https://strands-labs.github.io/robots/policies/lerobot-local/" rel="nofollow">LerobotLocal</a> serves policy inference behind one interface for <a href="https://github.com/NVIDIA/Isaac-GR00T" rel="nofollow">GR00T</a>, ACT, SmolVLA, and MolmoAct2 checkpoints. A peer mesh fans the agent out to remote robots. The dataset format stays exactly as LeRobot wrote it; the agent loop is the glue.</p>
<p>This post walks you through five steps inside a single agent: build the agent over the LeRobot AgentTools, record a demonstration as a LeRobotDataset in simulation, run a policy on the same robot, deploy the same agent code to a physical <a href="https://github.com/TheRobotStudio/SO-ARM100" rel="nofollow">SO-101</a>  with one keyword argument change, and broadcast commands across a fleet over the <a href="https://zenoh.io" rel="nofollow">Zenoh</a> mesh. At the end, you can clone the working sample application from GitHub and run it on your laptop in simulation. No hardware, no GPU, no Hugging Face credentials needed for the default path. The runnable companion to this post lives at <a href="https://github.com/strands-labs/robots/blob/main/examples/lerobot/hub_to_hardware.py" rel="nofollow"><code>examples/lerobot/hub_to_hardware.py</code></a> and <a href="https://github.com/strands-labs/robots/blob/main/examples/lerobot/hub_to_hardware.ipynb" rel="nofollow"><code>hub_to_hardware.ipynb</code></a>. The notebook is sim-only and Mock-policy by default.</p>
<h2 class="relative group flex items-baseline">
	<a id="what-youll-build" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#what-youll-build" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		What you'll build
	</span>
</h2>
<p>The Strands Robots SDK exposes the LeRobot stack as AgentTools that you compose into one Strands agent. The example agent in this post does four things: record new demonstrations in simulation, push the result to the Hub as a LeRobotDataset, run a policy in simulation against that same format, and deploy the same agent code to a physical robot with one keyword argument change. When you have more than one robot, the agent can coordinate the whole fleet through a built-in peer mesh. For hardware recording and calibration, LeRobot's own CLIs (<code>lerobot-record</code>, <code>lerobot-calibrate</code>) handle the bring-up; the agent picks up from there.</p>
<p><a href="https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/23tSv83E-Y06YWhpso9AS.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/23tSv83E-Y06YWhpso9AS.png" alt="arch_hugginface"></a></p>
<p><strong>Figure 1. <em>Robot("so100") defaults to a MuJoCo-backed simulation; mode="real" returns a hardware robot driven by LeRobot. Both modes share the same DatasetRecorder and the same policy providers, so a dataset captured in sim and a dataset captured on hardware use the same on-disk LeRobotDataset format.</em></strong></p>
<p>Two design choices make this work. First, <a href="https://strands-labs.github.io/robots/getting-started/robot-factory/" rel="nofollow">Robot("so100")</a> returns a simulation by default (no hardware, no risk), and mode="real" returns a hardware-backed robot driven by LeRobot. The agent code is identical across both modes. Second, the DatasetRecorder that writes a LeRobotDataset is shared between the <a href="https://strands-labs.github.io/robots/simulation/overview/" rel="nofollow">simulation path</a> and LeRobot's own hardware recording, so a dataset captured in <a href="https://mujoco.org" rel="nofollow">MuJoCo</a> and one captured from a physical <a href="https://github.com/TheRobotStudio/SO-ARM100" rel="nofollow">SO-101</a> are in the same format.</p>
<p>The whole workflow in five lines of Python:</p>
<pre><code class="language-python"><span class="hljs-keyword">from</span> strands_robots <span class="hljs-keyword">import</span> Robot
<span class="hljs-keyword">from</span> strands <span class="hljs-keyword">import</span> Agent

arm = Robot(<span class="hljs-string">"so100"</span>) <span class="hljs-comment"># mode="sim" (default - safe, no hardware)</span>
agent = Agent(tools=[arm])
agent(<span class="hljs-string">"Pick up the red cube"</span>)
</code></pre>
<p>What follows is what's actually happening inside that call, step by step.</p>
<h2 class="relative group flex items-baseline">
	<a id="prerequisites" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#prerequisites" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Prerequisites
	</span>
</h2>
<h4 class="relative group flex items-baseline">
	<a id="minimal-default-simulation-path" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#minimal-default-simulation-path" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Minimal (default simulation path)
	</span>
</h4>
<ul>
<li>Python 3.12+, on Linux or macOS (Apple Silicon supported for the MuJoCo backend).</li>
<li>A Strands-compatible model provider for the agent's reasoning. <a href="https://aws.amazon.com/bedrock/" rel="nofollow">Amazon Bedrock</a> with AWS credentials, the <a href="https://docs.anthropic.com" rel="nofollow">Anthropic API</a>, OpenAI, or <a href="https://ollama.com" rel="nofollow">Ollama</a> running locally.</li>
<li>Strands Robots installed with the <a href="https://strands-labs.github.io/robots/getting-started/installation/" rel="nofollow">install extras</a>: <code>uv pip install "strands-robots[sim-mujoco,lerobot,mesh]&gt;=0.5.3,&lt;1.0" </code></li>
</ul>
<p>That's it. The example in this post runs end-to-end on a laptop with these three.</p>
<h4 class="relative group flex items-baseline">
	<a id="advanced-hardware-deployment-real-policies-hub-push" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#advanced-hardware-deployment-real-policies-hub-push" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Advanced (hardware deployment, real policies, Hub push)
	</span>
</h4>
<ul>
<li>A Hugging Face account and token with write permission, for pushing datasets and pulling policy checkpoints from the Hub.</li>
<li>For the hardware path: an SO-101 follower and leader pair, or any other LeRobot-supported robot. Both devices need calibration files under <code>~/.cache/huggingface/lerobot/calibration/</code>.</li>
<li>For GR00T inference: an NVIDIA GPU and the GR00T extra, <code>uv pip install "strands-robots[groot]&gt;=0.5.3,&lt;1.0"</code>. GR00T N1.7 loads in-process through LeRobot, so no container or Docker is needed. Set <code>STRANDS_TRUST_REMOTE_CODE=1</code> to allow the checkpoint to load.</li>
</ul>

<h2 class="relative group flex items-baseline">
	<a id="step-2---record-demonstrations-and-push-to-the-hub" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#step-2---record-demonstrations-and-push-to-the-hub" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Step 2 - Record demonstrations and push to the Hub
	</span>
</h2>
<p>The simulation tool <a href="https://strands-labs.github.io/robots/recording/" rel="nofollow">records LeRobotDatasets</a> in the same format LeRobot writes on hardware. No hardware required. The <code>Simulation</code> tool's <code>start_recording</code> action writes through the same <code>DatasetRecorder</code> class: same parquet schema for joint states and actions, same per-camera MP4 layout. The agent prompt is almost identical:</p>
<pre><code class="language-python"><span class="hljs-keyword">from</span> strands <span class="hljs-keyword">import</span> Agent
<span class="hljs-keyword">from</span> strands_robots <span class="hljs-keyword">import</span> Robot

robot = Robot(<span class="hljs-string">"so100"</span>)  <span class="hljs-comment"># mode="sim" by default</span>
agent = Agent(tools=[robot])

agent(
    <span class="hljs-string">"Record a demonstration of 'pick the red cube and place it in the box' "</span>
    <span class="hljs-string">"using the Mock policy provider at FPS 30. Write the dataset to "</span>
    <span class="hljs-string">"my_user/cube_picking_sim and push to the Hub when done."</span>
)
</code></pre>
<p><a href="https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/DBe5futoSUQ9z9s4ECZ79.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/DBe5futoSUQ9z9s4ECZ79.png" alt="sim_scene"></a></p>
<p><strong>Figure 2. <em>The recording scene in MuJoCo simulation: the SO-100 arm reaching toward a red cube on the ground plane, captured to a LeRobotDataset. No hardware, no GPU, no Hugging Face credentials needed for this default path.</em></strong></p>
<p>The Mock policy is intentional: it generates placeholder joint actions so the workflow runs end-to-end without a trained checkpoint. The robot moves through random motions rather than completing the grasp, and the recording is structurally complete (valid joint states, valid camera frames, a well-formed LeRobotDataset episode), but the demonstration itself isn't useful as training data. Step 3 below swaps in a GR00T checkpoint through LerobotLocal for real grasping behavior. To see actual cube-picking in this step, run <code>--policy lerobot_local --checkpoint allenai/MolmoAct2-SO100_101</code> (a <a href="https://huggingface.co/allenai/MolmoAct2-SO100_101">MolmoAct2 checkpoint</a>, auto-detected from its config.json and routed through the LerobotLocal path); the prompt, dataset format, and agent code stay the same.</p>
<p>The proof is what happens next. LeRobot's own dataset loader reads the sim-recorded data with no Strands-specific code path:</p>
<pre><code class="language-python"><span class="hljs-keyword">from</span> lerobot.datasets.lerobot_dataset <span class="hljs-keyword">import</span> LeRobotDataset

dataset = LeRobotDataset(<span class="hljs-string">"my_user/cube_picking_sim"</span>)
<span class="hljs-built_in">print</span>(dataset.features)
<span class="hljs-comment"># {'observation.state': Sequence(...),</span>
<span class="hljs-comment">#  'observation.images.front': VideoFrame(...),</span>
<span class="hljs-comment">#  'action': Sequence(...),</span>
<span class="hljs-comment">#  'episode_index': Value(...), 'frame_index': Value(...), ...}</span>
</code></pre>
<p>This features dict is identical in shape to any LeRobot dataset on the Hub: same column names, same parquet+MP4 layout, same loader path. Training scripts that consume hardware-recorded data consume the sim-recorded data without modification. Datasets pushed from sim sit alongside hardware recordings in the same Hub repository if you want them to.</p>

<h4 class="relative group flex items-baseline">
	<a id="recording-on-hardware" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#recording-on-hardware" rel="nofollow">

	<span>
		<strong>Recording on hardware</strong>
	</span>
</h4>
<p>To record demonstrations on a physical SO-101 instead of simulation, use LeRobot's record CLI directly. The Strands integration doesn't wrap that command as an AgentTool because LeRobot already does the job cleanly:</p>
<pre><code class="language-bash">lerobot-calibrate --robot.type=so101_follower --robot.id=my_follower
lerobot-calibrate --robot.type=so101_leader   --robot.id=my_leader

lerobot-record \
  --robot.type=so101_follower --robot.id=my_follower \
  --teleop.type=so101_leader  --teleop.id=my_leader \
  --dataset.repo_id=my_user/cube_picking \
  --dataset.single_task=<span class="hljs-string">'Pick up the red cube and place it in the box'</span> \
  --dataset.num_episodes=25 \
  --dataset.push_to_hub=<span class="hljs-literal">true</span>
</code></pre>
<p>The dataset that lands on the Hub from this command is in the same format as the simulation recording. To fine-tune a policy on it, run LeRobot's training CLI (<code>lerobot-train</code>); training itself is out of scope for this post and follows the standard LeRobot workflow. From Step 3 onward, the agent picks up either the original or a fine-tuned checkpoint interchangeably. For full SO-101 hardware setup, calibration walkthroughs, and troubleshooting, see the <a href="https://github.com/strands-labs/robots/blob/main/examples/lerobot/README.md" rel="nofollow">README in the example folder</a>.</p>
<h2 class="relative group flex items-baseline">
	<a id="step-3---run-a-policy-in-simulation" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#step-3---run-a-policy-in-simulation" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Step 3 - Run a policy in simulation
	</span>
</h2>
<p>With the dataset on the Hub, the next step is to run a policy. The example uses the <code>Robot()</code> factory in its default sim mode and runs a GR00T checkpoint through the LerobotLocal provider, in the same process:</p>
<pre><code class="language-python"><span class="hljs-keyword">import</span> os

os.environ[<span class="hljs-string">"STRANDS_TRUST_REMOTE_CODE"</span>] = <span class="hljs-string">"1"</span>  <span class="hljs-comment"># GR00T loads through LeRobot</span>

<span class="hljs-keyword">from</span> strands <span class="hljs-keyword">import</span> Agent
<span class="hljs-keyword">from</span> strands_robots <span class="hljs-keyword">import</span> Robot

robot = Robot(<span class="hljs-string">"so100"</span>)  <span class="hljs-comment"># mode="sim" by default</span>
agent = Agent(tools=[robot])

agent(
    <span class="hljs-string">"Run the LerobotLocal policy 'my_user/cube-picker' on the robot with "</span>
    <span class="hljs-string">"the instruction 'pick up the red cube' for 200 steps."</span>
)
</code></pre>
<p>Under the hood, the agent runs a <code>run_policy</code> action on the simulated robot with <code>policy_provider="lerobot_local"</code>. The provider downloads the checkpoint from the Hub and loads it through <a href="https://strands-labs.github.io/robots/policies/lerobot-local/" rel="nofollow">LeRobot's GR00T policy</a> in the same process. The simulation steps with the policy's action chunks, and a render of the result is available via <code>Simulation.render</code>. To run inference on a separate GPU host instead, start <code>strands_robots.inference.server.PolicyServer</code> there and use <code>policy_provider="remote"</code>.</p>
<p><a href="https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/70ZHVAM2CTkP0_kjNy08U.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/70ZHVAM2CTkP0_kjNy08U.png" alt="sim_grasp"></a></p>
<p><strong>Figure 3. <em>With a trained policy (a GR00T or MolmoAct2 checkpoint), the agent drives the SO-100 to grasp the red cube in simulation, the behavior the Mock policy stands in for.</em></strong></p>
<p>The same provider loads any LeRobot checkpoint. A model ID under the <code>lerobot/</code> organization routes to it by name:</p>
<pre><code class="language-python"><span class="hljs-keyword">from</span> strands_robots.policies <span class="hljs-keyword">import</span> create_policy
policy = create_policy(<span class="hljs-string">"lerobot/act_aloha_sim_transfer_cube_human"</span>)
</code></pre>
<p><code>LerobotLocalPolicy</code> supports <a href="https://tonyzhaozh.github.io/aloha/" rel="nofollow">ACT</a>, <a href="https://diffusion-policy.cs.columbia.edu" rel="nofollow">Diffusion Policy</a>, <a href="https://huggingface.co/blog/smolvla">SmolVLA</a>, <a href="https://www.pi.website/blog/pi0" rel="nofollow">π0</a>, and <a href="https://www.pi.website/blog/pi05" rel="nofollow">π0.5</a>, anything LeRobot's own policy registry can resolve from a <code>config.json</code>. <a href="https://www.pi.website/research/real_time_chunking" rel="nofollow">Real-Time Chunking</a> turns on automatically for flow-matching policies that ship an <code>rtc_config</code> (π0, SmolVLA).</p>
<p>NVIDIA's recently released <a href="https://huggingface.co/nvidia/Cosmos3-Nano">Cosmos 3</a> is also available as a policy provider behind the same interface, so the agent code stays the same whichever provider you point it at.</p>
<p><em>Note: LerobotLocalPolicy loads Hugging Face models with trust_remote_code=True. Set</em> <code>STRANDS_TRUST_REMOTE_CODE=1</code> <em>to opt in, and only load checkpoints from organizations you trust.</em></p>

	</span>

<p>This is the same code as Step 3, with one keyword argument changed. The <code>Robot</code> factory returns a hardware-backed robot driven by LeRobot's <code>make_robot_from_config</code>:</p>
<pre><code class="language-python">robot = Robot(

    mode=<span class="hljs-string">"real"</span>,

        <span class="hljs-string">"front"</span>: {<span class="hljs-string">"type"</span>: <span class="hljs-string">"opencv"</span>, <span class="hljs-string">"index_or_path"</span>: <span class="hljs-string">"/dev/video0"</span>, <span class="hljs-string">"fps"</span>: <span class="hljs-number">30</span>},

<p>The same agent prompt now runs against a physical arm. The hardware path uses LeRobot's robot abstraction for joint commands and camera reads, and the same GR00T checkpoint, loaded in-process, generates the action chunks.</p>
<p>Before this runs against your SO-101, calibration for both follower and leader has to be in place. <h2 class="relative group flex items-baseline">
	<a id="step-5---coordinate-multiple-robots-with-the-mesh" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#step-5---coordinate-multiple-robots-with-the-mesh" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Step 5 - Coordinate multiple robots with the mesh
	</span>
</h2>
<p>Up to now we've driven one robot at a time. <a href="https://strands-labs.github.io/robots/mesh/" rel="nofollow">The mesh</a> is how Strands Robots handles more than one. Picture a leader arm on your desk teleoperating a follower arm in another room, or five SO-101s running the same warehouse task in parallel, or a humanoid coordinating with a mobile base. All of those are mesh patterns. The mesh is built on Zenoh, an open source peer-to-peer protocol, and you don't manage IP addresses, write discovery code, or pick a broker; new robots show up on the mesh the moment they come up, and the agent can talk to all of them at once.</p>
<p>A <code>Robot()</code> or <code>Simulation()</code> joins a Zenoh peer mesh when you pass <code>mesh=True</code>, or set <code>STRANDS_MESH=true</code>; the mesh is off by default. The <code>robot_mesh</code> tool gives the agent a vocabulary for fleet operations such as discovery, structured commands, broadcasts, and emergency stop:</p>
<pre><code class="language-python"><span class="hljs-keyword">from</span> strands <span class="hljs-keyword">import</span> Agent
<span class="hljs-keyword">from</span> strands_robots <span class="hljs-keyword">import</span> Robot, robot_mesh

robot = Robot(<span class="hljs-string">"so100"</span>, mesh=<span class="hljs-literal">True</span>)  <span class="hljs-comment"># joining the mesh is opt-in</span>
agent = Agent(tools=[robot_mesh])

agent(
    <span class="hljs-string">"List every robot and simulation on the mesh. "</span>
    <span class="hljs-string">"Then send 'go to home pose' to each one in parallel."</span>
)
</code></pre>
<p>The agent calls <code>robot_mesh(action="peers")</code> to enumerate locals and discovered peers, then <code>robot_mesh(action="broadcast", ...)</code> to send the structured command to every peer with a timeout. Add the <code>[mesh-iot]</code> extra to route this traffic over AWS IoT Core for cross-network fleets. The <code>robot_mesh</code> tool's action reference in the project documentation covers the full vocabulary: subscribe, watch, inbox, and structured peer-to-peer commands.</p>
<p>By default, every physically-actuating mesh action pauses for a human approval interrupt before it runs: the fleet-wide broadcast and emergency_stop, plus the single-peer tell, send, and stop. You can tune this set with the STRANDS_MESH_HITL_ACTIONS environment variable (set it to all, none, or a comma-separated subset). The first time you run this example, you'll see a robot_mesh-broadcast-approval prompt in your terminal; type y (or yes / approve) to authorize the broadcast. The approval is delivered out-of-band of the LLM's tool arguments, so a prompt-injection attempt that tries to slip an approval flag into the command body cannot bypass the gate.</p>
<p>The transport scales without touching agent code. The built-in Zenoh mesh is the automatic fallback: on the LAN, Zenoh peers find each other with no broker (gossip by default; set STRANDS_MESH_MULTICAST=true for multicast scouting), and adding the [mesh-iot] extra routes traffic through <a href="https://aws.amazon.com/iot-core/" rel="nofollow">AWS IoT Core</a> (MQTT5 with mTLS) for cloud fleets, with a BridgeTransport that fans LAN and cloud behind one API (select it with STRANDS_MESH_BACKEND=bridge).</p>
<p>For production fleets, Device Connect, a device-aware networking layer developed in collaboration with Arm, handles discovery, presence, structured RPC, event routing, and safety. The same robot_mesh tool dispatches through Device Connect when it is available and falls back to the built-in Zenoh mesh otherwise, so the agent code in this post is unchanged either way. See the <a href="https://strands-labs.github.io/robots/device-connect/" rel="nofollow">Device Connect documentation</a> for setup and current availability.</p>

<h2 class="relative group flex items-baseline">
	<a id="security-considerations" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#security-considerations" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Security Considerations
	</span>
</h2>
<p>The code snippets shown in this setup represent a “hello world” example of setting up Strands Robots with HuggingFace. For more serious, production-ready use cases there are some important considerations users should be aware of:</p>
<h4 class="relative group flex items-baseline">
	<a id="prompt-injection" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#prompt-injection" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Prompt Injection
	</span>
</h4>
<p>Supplying untrusted data into agents can lead to prompt injection, where untrustworthy context is treated as LLM instructions. Given the actuation of these robots in physical space, this is an important risk to track. To mitigate this behavior, developers should be careful to feed the robots only data that comes from a trusted source. If not all input data can be trusted, developers should restrict the tools available to the agent to prevent the robots from making safety-critical actions. </p>
<h4 class="relative group flex items-baseline">
	<a id="robot-mesh-auth-behavior" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#robot-mesh-auth-behavior" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Robot Mesh Auth Behavior
	</span>
</h4>
<p>The <code>STRANDS_MESH_LOCAL_DEV=1</code> setting shared in the code snippets in this blog initializes the robot mesh without authentication or access controls. This means that any device on the same network can provide commands to the robot fleet. This is acceptable for trusted development environments, but is not suitable for untrusted networks or production environments. For these use cases, <code>STRANDS_MESH_AUTH_MODE=mtls</code> is required.</p>
<h4 class="relative group flex items-baseline">
	<a id="operator-approval-for-fleet-wide-actions" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#operator-approval-for-fleet-wide-actions" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		<strong>Operator approval for fleet-wide actions</strong>
	</span>
</h4>
<p>The robot_mesh tool's physically-actuating actions affect peers on the network: broadcast and emergency_stop reach every peer, while tell, send, and stop reach a single targeted peer. To prevent an agent from issuing these commands autonomously (or under prompt injection), all five are gated behind a human-in-the-loop interrupt by default. When the agent invokes a gated action, the Strands runtime pauses the agent loop and asks the operator to approve out-of-band of the LLM's tool arguments. You can adjust the gated set with the STRANDS_MESH_HITL_ACTIONS environment variable (all, none, or a comma-separated subset). Per-action rate limits, command validation, and an audit trail run alongside the interrupt. Outside an agent loop (a bare script or unit test), the gated actions fail closed.</p>
<h2 class="relative group flex items-baseline">
	<a id="clean-up" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#clean-up" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Clean up
	</span>
</h2>
<p>The preceding workflow opens serial ports on hardware and writes a local dataset cache. To return your environment to a clean state:</p>
<ul>
<li><strong>Release the serial ports:</strong> if you ran the hardware path, disconnect the SO-101 follower and leader.</li>
<li><strong>Optionally remove the local dataset cache:</strong> the recorded dataset lives under <code>~/.cache/huggingface/lerobot/&lt;repo_id&gt;</code>. Datasets you pushed to the Hub are unaffected.</li>
</ul>
<h2 class="relative group flex items-baseline">
	<a id="how-this-fits-together" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#how-this-fits-together" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		How this fits together
	</span>
</h2>
<p>The integration's central design choice is that Strands Robots doesn't reimplement what LeRobot already provides. Hardware abstraction, calibration, and the dataset format stay upstream. Strands adds the AgentTool surface that makes them composable from natural language.</p>
<p>Two consequences follow. For users, every dataset on the Hub is an asset an agent can extend, fine-tune from, and deploy against with no conversion step. For developers, simulation data and hardware data share a single file format, so training scripts written for one consume the other unchanged. The line between sim and real becomes a deployment detail, not an architectural divide.</p>

		<span class="header-link"> </span>
	</a>
	<span>
		Where to go from here
	</span>
</h2>
<p><a href="https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/LC9TP6EKBDCBC4waZEXJo.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/LC9TP6EKBDCBC4waZEXJo.png" alt="fleet"></a></p>
<p><strong>Figure 4. <em>The Strands Robots catalog spans arms, humanoids, quadrupeds, and hands, all in the same MuJoCo simulation and behind the same <code>Robot()</code> factory. The SO-100 in this post is one of many supported embodiments.</em></strong></p>
<p>The full <a href="https://strands-labs.github.io/robots/" rel="nofollow">Strands Robots documentation</a> covers the robot catalog, simulation, policy providers, the mesh, and Device Connect in depth. For larger workloads, Strands Robots also ships heavier simulation backends, Isaac Sim and Newton. Both backends plug into the same Robot abstraction shown in this post, so the agent code stays the same as you scale up.</p>
<p>Contributions are welcome under Apache 2.0. If you build something with this workflow, open an issue with what worked and what didn't. The SDK improves fastest when developer feedback lands directly on the surface that needs it.</p>
