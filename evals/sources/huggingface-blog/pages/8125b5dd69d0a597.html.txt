<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]-->For most teams, models and datasets live in a bucket in one region of one cloud. The GPUs you can get, whether for development, training, or serving, increasingly sit on a different cloud than your data. The moment those two come apart, you pay a cross-cloud transfer tax just to read your own data onto your own GPUs.</p>
<p>Together with Hugging Face, we've joined the two halves: your models and datasets stay on the Hub, and SkyPilot runs the compute (dev, training, or serving) on whatever cluster has the GPUs. Mount a Hugging Face Bucket or any Hub repo into a SkyPilot job with one <code>hf://</code> URL and the <code>HF_TOKEN</code> you already have, then launch it wherever capacity is. Hugging Face charges no egress, so reading your data onto those GPUs costs nothing, on any cloud.</p>
<p>Here's what's new:</p>
<ul>
<li><strong>Your Hub data in any job.</strong> <code>store: hf</code> mounts a Hugging Face <strong>Bucket</strong> (read-write) or any <strong>model / dataset / Space repo</strong> (read-only) into a SkyPilot task with one <code>hf://</code> URL and your existing <code>HF_TOKEN</code>, via <code>MOUNT</code> or <code>COPY</code>.</li>
<li><strong>Run it on any GPU, on any cloud.</strong> <a href="https://docs.skypilot.co/" rel="nofollow">SkyPilot</a> finds that job compute across 20+ clouds, Kubernetes, Slurm, and on-prem, so the same run uses whichever of your reserved or on-demand GPUs is available, on any vendor.</li>
<li><strong>No egress to read your data.</strong> Hugging Face Storage charges <a href="https://huggingface.co/pricing">no egress or CDN fees</a>, so wherever SkyPilot lands the job, it reads your models and datasets straight from the same bucket, with no per-cloud copies and no egress bill to pull them in.</li>
<li><strong>Xet-backed dedup.</strong> Buckets are built on <a href="https://huggingface.co/docs/hub/xet/overview">Xet</a>, so incremental checkpoints and model variants only store and transfer the chunks that changed.</li>
<li><strong>Built together.</strong> <a href="https://huggingface.co/">Hugging Face</a> and <a href="https://docs.skypilot.co/" rel="nofollow">SkyPilot</a> shipped this jointly, and the Hugging Face team upstreamed the <code>hf-mount</code> FUSE fixes that make it work in unprivileged containers.</li>
</ul>
<h2 class="relative group flex items-baseline">
	<a id="hugging-face-storage-is-now-a-first-class-skypilot-backend" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#hugging-face-storage-is-now-a-first-class-skypilot-backend" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Hugging Face Storage is now a first-class SkyPilot backend
	</span>
</h2>
<p><a href="/blog/assets/skypilot-hf-storage/architecture.png" rel="nofollow"><img src="/blog/assets/skypilot-hf-storage/architecture.png" alt="SkyPilot mounts Hugging Face models, datasets, and checkpoints into jobs running on reserved GPU clusters across CoreWeave, Nebius, GCP, and 20+ more, with zero-egress reads."></a></p>
<p>SkyPilot tasks already read and write cloud object stores (S3, GCS, Azure, R2, and many more) by mounting them at a local path. Hugging Face Storage now joins that list as <code>store: hf</code>, reached through the <code>hf://</code> scheme:</p>
<pre><code class="language-yaml"><span class="hljs-attr">file_mounts:</span>
  <span class="hljs-comment"># A Hugging Face Bucket, read-write, for checkpoints, logs, processed data.</span>
  <span class="hljs-string">/checkpoints:</span>
    <span class="hljs-attr">source:</span> <span class="hljs-string">hf://buckets/my-org/qwen-sft</span>
    <span class="hljs-attr">store:</span> <span class="hljs-string">hf</span>
    <span class="hljs-attr">mode:</span> <span class="hljs-string">MOUNT</span> <span class="hljs-comment"># or COPY</span>
  <span class="hljs-comment"># A model repo, mounted read-only.</span>
  <span class="hljs-string">/base-model:</span>
    <span class="hljs-attr">source:</span> <span class="hljs-string">hf://Qwen/Qwen3.5-4B</span>
    <span class="hljs-attr">store:</span> <span class="hljs-string">hf</span>
    <span class="hljs-attr">mode:</span> <span class="hljs-string">MOUNT</span>
  <span class="hljs-comment"># A dataset repo, pinned to a revision, read-only.</span>
  <span class="hljs-string">/data:</span>
    <span class="hljs-attr">source:</span> <span class="hljs-string">hf://datasets/my-org/my-dataset@main</span>
    <span class="hljs-attr">store:</span> <span class="hljs-string">hf</span>
    <span class="hljs-attr">mode:</span> <span class="hljs-string">MOUNT</span>
</code></pre>
<p>That one <code>hf://</code> scheme covers the whole lifecycle: read the <strong>model</strong> and <strong>dataset</strong> from their repos, write <strong>checkpoints</strong> to a Bucket while you train, publish the finished model back to a repo, and pull it onto inference servers when you serve. Most teams already keep their models and datasets on the Hub, so there is no migration step and no new storage account to create.</p>
<p><code>MOUNT</code> uses Hugging Face's <a href="https://github.com/huggingface/hf-mount" rel="nofollow"><code>hf-mount</code></a> FUSE backend, so a bucket or repo shows up as a local path next to SkyPilot's other FUSE mounts (<code>gcsfuse</code>, <code>blobfuse2</code>, <code>rclone</code>, <code>goofys</code>). The fetching happens at the filesystem layer: when your code issues a <code>read()</code>, the driver pulls just those bytes from the Xet backend, so only the data you actually touch crosses the network, and <code>hf-mount</code> keeps an on-disk cache so repeat reads stay local. That on-disk cache is the behavior SkyPilot gives its other backends under <a href="https://docs.skypilot.co/en/latest/reference/storage.html" rel="nofollow"><code>MOUNT_CACHED</code></a>, where a plain <code>MOUNT</code> instead streams every read from the bucket with nothing kept locally. For the <code>hf</code> store, <code>MOUNT</code> and <code>MOUNT_CACHED</code> behave the same, so either mode keeps the cache.</p>
<p>Because reads are lazy, a process can start working through a large file before the whole file has downloaded, instead of blocking on a full copy first. That keeps the GPU busy almost immediately, training on data as it streams in rather than sitting idle (and billing) while a dataset or checkpoint copies down. It pays off most on the first epoch, when nothing is cached yet. <code>COPY</code> takes the other route and downloads through <code>huggingface_hub</code> up front, with no special requirements.</p>
<p>Authentication is the token you already have. Set <code>HF_TOKEN</code> in your environment and hand it to a run with <a href="https://docs.skypilot.co/en/latest/running-jobs/environment-variables.html" rel="nofollow"><code>--secret HF_TOKEN</code></a>; SkyPilot uses it for the mount on whatever cloud the job lands. One token works whether the job lands on AWS, GCP, Azure, Nebius, Lambda, or your own Kubernetes cluster, so there are no per-cloud bucket keys to juggle.</p>
<h2 class="relative group flex items-baseline">
	<a id="no-egress-storage-stops-deciding-where-you-run" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#no-egress-storage-stops-deciding-where-you-run" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		No egress: storage stops deciding where you run
	</span>
</h2>
<p>GPU capacity rarely comes from one place anymore. To get enough H100s and H200s, teams hold reserved and committed capacity across several vendors at once (a block on a hyperscaler, a cluster on a neocloud, maybe an on-prem rack) and run wherever they have allocation. SkyPilot is built for this: one job spec, scheduled across 20+ clouds, Kubernetes, and on-prem, landing on whichever reserved cluster is free.</p>
<p>Object storage has been the catch. Object stores are regional and per-cloud, so feeding a GPU or an inference server that sits in a different vendor's data center means either keeping a copy of your data in every vendor's bucket or paying to pull it across. Most clouds charge egress (around $0.09/GB out of AWS) the moment data leaves their network, and often between regions inside one cloud. Pulling a base model onto every inference node, or iterating a dataset for several epochs from a cluster on another cloud, adds a hefty bill on top of GPUs you have already reserved. Teams end up pinning each run to whichever vendor holds the data and leaving the rest of their capacity idle.</p>
<p>Hugging Face Storage takes that cost off the table where it bites: the read side. With <a href="https://huggingface.co/pricing">no egress or CDN fees</a> and storage at $12-18/TB/month (versus AWS S3 at roughly $23/TB plus egress), the same bucket is reachable from every one of those clusters, and reading from it is free no matter where the GPUs run. Writing back still costs your compute cloud's usual egress, the same as it would to any off-cloud store, but for most AI work the reads dominate: a dataset streamed over many epochs, or model weights pulled onto every new training or inference node. So you stop pinning each run to whichever vendor holds a copy of the data.</p>
<h2 class="relative group flex items-baseline">
	<a id="a-quick-benchmark" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#a-quick-benchmark" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		A quick benchmark
	</span>
</h2>
<p>To collect some benchmark numbers, we ran a small fine-tune: <a href="https://huggingface.co/Qwen/Qwen3.5-4B"><code>Qwen/Qwen3.5-4B</code></a> on the <a href="https://huggingface.co/datasets/HuggingFaceH4/Multilingual-Thinking"><code>HuggingFaceH4/Multilingual-Thinking</code></a> dataset with TRL's <a href="https://huggingface.co/docs/trl/sft_trainer"><code>SFTTrainer</code></a>, mounting the model read-only from its Hub repo and writing every checkpoint to a Hugging Face Bucket. The same SkyPilot YAML ran on AWS, GCP, and Lambda, changing only <code>--infra</code>. SkyPilot placed each job wherever GPUs were free, and all three read and wrote the same bucket.</p>

<h2 class="relative group flex items-baseline">
	<a id="xet-backed-storage-dedup-for-checkpoints-and-model-variants" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#xet-backed-storage-dedup-for-checkpoints-and-model-variants" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Xet-backed storage: dedup for checkpoints and model variants
	</span>
</h2>
<p>Hugging Face Buckets are built on <a href="https://huggingface.co/docs/hub/xet/overview">Xet</a>, which uses <a href="https://huggingface.co/docs/hub/xet/deduplication">content-defined chunking</a> to split files into ~64 KB chunks and store each unique chunk once. Because the boundaries follow the content, an edit changes only the chunks it touches and the rest are recognized as already stored. This pays off in a few places:</p>
<ul>
<li><strong>Incremental and adapter checkpoints.</strong> When you freeze layers, train adapters, or otherwise leave most weights untouched between saves, only the changed chunks upload instead of the whole checkpoint.</li>
<li><strong>Model variants that share a base.</strong> Fine-tunes and quantizations of one base model overlap heavily, so the shared chunks are stored once across all of them.</li>
<li><strong>Datasets you append to.</strong> Logs like conversation traces or inference outputs grow by appending rows to large Parquet files. The existing row groups stay byte-identical, so only the new rows transfer: in Hugging Face's <a href="https://huggingface.co/blog/parquet-cdc">test</a>, appending 10K rows to a 100K-row table moved about 10 MB instead of the full ~106 MB. (If you edit or delete rows in place, write with <code>use_content_defined_chunking=True</code> to keep changes local.)</li>
<li><strong>Re-uploads skip what's already stored.</strong> In our test, re-uploading an 8.43 GB blob already in the bucket took about 8 seconds, versus 24 seconds for the first upload, because only chunk hashes move. The same mechanism lets server-side <code>hf buckets cp</code> between repos and buckets copy by reference instead of re-uploading bytes.</li>
</ul>
<p>How much you save depends on how much your artifacts overlap, but the deduplication is automatic: you write a checkpoint as usual, and only the new chunks leave the machine.</p>

<h2 class="relative group flex items-baseline">
	<a id="built-together-hugging-face-and-skypilot" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#built-together-hugging-face-and-skypilot" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Built together: Hugging Face and SkyPilot
	</span>
</h2>
<p>The initial <code>store: hf</code> support <a href="https://github.com/skypilot-org/skypilot/pull/9418" rel="nofollow">started as a contribution</a> from Nikhil Jha. The Hugging Face team <a href="https://github.com/skypilot-org/skypilot/pull/9698" rel="nofollow">carried it forward</a> and upstreamed the <code>hf-mount</code> FUSE fixes that let it mount in unprivileged containers, the default on many Kubernetes clusters. The SkyPilot team wired it into the storage backend. The whole path is open source: SkyPilot, Hugging Face's <code>hf-mount</code>, and the <code>huggingface_hub</code> client.</p>
