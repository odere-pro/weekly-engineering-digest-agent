<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]--><em>*Free as in beer, excluding the cost of electricity, and assuming you already own the hardware</em></p>
<p>June 2026 will go down as the moment that people realized closed models can be taken away. With the removal of Anthropic's latest flagship model Claude Fable 5 fresh in memory, one can see why it is more important than ever to own your AI stack and be able to run models locally, especially if you are building your business on top of AI.</p>
<p>In that light, we wanted to share how we use local models like Gemma and Qwen in an agent harness, to run classification tasks<sup id="note-1-ref"><a href="#note-1" rel="nofollow">[1]</a></sup>. This approach is different from using a model like BERT for classification. A local model in an agent harness like Pi can be used in tandem with structured outputs, to assign labels. We chose this approach because we already had local models and the harness on hand, and have conviction that similar setups will increase in popularity as local models improve in capability.<sup id="note-2-ref"><a href="#note-2" rel="nofollow">[2]</a></sup></p>
<p>Our starting point was open source contributions in the OpenClaw repo. OpenClaw gets hundreds of issues and PRs every day, which need to be triaged, prioritized and routed to maintainers. I, Onur, am working to make local models work well with OpenClaw. Being a maintainer of this specific vertical, I need to react quickly to any P0 issues.</p>
<p>With SOTA closed models like GPT-5, Opus, or Sonnet, this is a pretty straightforward task. But I happen to sit on 128 GB of unified memory, namely an NVIDIA GB10. So I took on the task:</p>
<blockquote>
<p>Can I build a real-time notification system that filters and notifies me for only the issues that I am responsible for... with local open-weight models?</p>
</blockquote>
<figure class="image table text-center m-0 w-full" style="text-align: center;">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/local-models-pr-triage/dgx-spark.png" alt="NVIDIA DGX Spark" style="display: block; width: 50%; min-width: 280px; margin: 0 auto;">
  <figcaption>This tiny box, a.k.a. DGX Spark, can run gemma-4-26b-a4b with high concurrency and generate hundreds of tokens per second.</figcaption>
</figure>

<p>If I set up my OpenClaw main agent running on a $200/mo ChatGPT Pro plan to trigger a job on every new issue or PR, that would use up my quota. I might instead set it to run every 2 hours, or 6 hours. This would batch issues over longer periods, so we would be trading real-time notifications for delayed processing.</p>
<p>If I were to run this on a local model on the hardware I already have up and running, I would not only have near-instantaneous notifications, I would also be able to do it for free (or rather, for the cost of electricity).</p>
<h2 class="relative group flex items-baseline">
	<a id="categorizing-issues-and-prs" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#categorizing-issues-and-prs" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Categorizing issues and PRs
	</span>
</h2>
<p>We came up with a finite set of labels representing the categories of issues we need to triage, and then use a local model to classify each issue into one of those categories, like <code>local_models</code>, <code>self_hosted_inference</code>, <code>acp</code>, <code>agent_runtime</code>, <code>codex</code>, <code>ui_tui</code> and so on.<sup id="note-3-ref"><a href="#note-3" rel="nofollow">[3]</a></sup></p>
<p>But how do we classify pull requests? A simple single request to a Chat Completions endpoint with a tool JSON schema, with the topics as an enum?</p>
<p>Kind of. But this is 2026, not 2023, and we have AGENTS. We can do better!</p>
<p>For the local model choices, we tested <code>gemma-4-26b-a4b</code> and <code>qwen3.6-35b-a3b</code>. With performance optimizations, both can generate hundreds of tokens per second locally.</p>
<p>We use an agent harness to drive the classification run. For this, we bundle <a href="https://pi.dev" rel="nofollow">pi</a> as a harness that can call local model endpoints.</p>
<p>The agent by default receives the PR title, body and a truncated excerpt of the PR diff in the first prompt. Then, it can choose to use the <code>bash</code> tool to perform read-only operations on the OpenClaw repo (in case it needs to look at the codebase), or the <code>final_json</code> tool to submit the final classification result.</p>
<p>You wouldn't want to give full bash access to a local model running in this high-throughput setting, because a prompt-injected issue or PR could otherwise steer the model into doing something unrelated to classification.</p>
<p>For that reason, we use <a href="https://github.com/osolmaz/localpager/tree/main/reposhell" rel="nofollow"><code>reposhell</code></a> instead of <code>bash</code>: a restricted <code>bash</code>-like shell that only allows read-only operations (<code>ls</code>, <code>find</code>, <code>cat</code>, <code>grep</code>, etc.) on the OpenClaw repo. The model thinks it is using <code>bash</code>, but any operation that is not allowed is rejected:</p>
<pre><code>reposhell bound cwd=/repo/openclaw repos=openclaw
type help for allowed commands; exit or quit to leave

reposhell /repo/openclaw&gt; help
allowed: pwd, ls, find, rg, grep, sed -n, cat, head, tail, wc -l, git status --short, git show --name-only, git grep, git ls-files
search: rg -n -i "lm studio" or grep -R -n -i "lm studio" .
files: rg --files -g "*.ts" or git ls-files src
examples: rg -n reposhell README.md | sed is not allowed; use one simple command at a time

reposhell /repo/openclaw&gt; head README.md
# 🦞 OpenClaw — Personal AI Assistant

&lt;p align="center"&gt;
    &lt;picture&gt;
        &lt;source media="(prefers-color-scheme: light)" srcset="https://raw.githubusercontent.com/openclaw/openclaw/main/docs/assets/openclaw-logo-text-dark.svg"&gt;
        &lt;img src="https://raw.githubusercontent.com/openclaw/openclaw/main/docs/assets/openclaw-logo-text.svg" alt="OpenClaw" width="500"&gt;
    &lt;/picture&gt;
&lt;/p&gt;

&lt;p align="center"&gt;

reposhell /repo/openclaw&gt; curl localhost
reposhell policy denied command: unsupported command "curl"
exit_code=2

reposhell /repo/openclaw&gt;
</code></pre>
<p>Here is a concrete example where this mattered. In one <a href="https://huggingface.co/datasets/dutifuldev/openclaw-classification-dataset/blob/main/session-examples/README.md">saved session example</a>, <code>qwen3.6-35b-a3b</code> was classifying <a href="https://github.com/openclaw/openclaw/pull/84621" rel="nofollow"><code>openclaw/openclaw#84621</code></a>, titled <code>Fix Kimi tool-call rewriting stop reason handling</code>. The thinking block shows the model initially considering <code>coding_agent_integrations</code> because the changed path <code>extensions/kimi-coding</code> made it look plausible. The model used reposhell to inspect the local repo with simple read-only commands like <code>ls extensions</code>, <code>ls extensions/kimi-coding</code>, and <code>cat extensions/kimi-coding/package.json</code>. That package metadata showed the extension was actually <code>@openclaw/kimi-provider</code>, an OpenClaw Kimi provider plugin. So the model corrected the final labels to <code>inference_api</code> and <code>tool_calling</code>, and explicitly excluded <code>coding_agent_integrations</code>.</p>
<p>We have mentioned earlier that we bundle a specific <code>pi</code> configuration that can only perform read-only operations and return classification output. We call it <a href="https://github.com/osolmaz/localpager/tree/main/localpager-agent" rel="nofollow"><code>localpager-agent</code></a>, named after <code>localpager</code>, the main project here. Each PR and issue generates a prompt, which is then passed to the CLI like below, alongside other args:</p>
<pre><code class="language-bash">localpager-agent \
  --model <span class="hljs-string">"&lt;model-id&gt;"</span> \
  --base-url <span class="hljs-string">"&lt;openai-compatible-base-url&gt;"</span> \
  --session-dir <span class="hljs-string">"&lt;session-output-dir&gt;"</span> \
  --final-schema <span class="hljs-string">"&lt;runtime-schema.json&gt;"</span> \
  --tools bash,final_json \
  --reposhell-socket <span class="hljs-string">"&lt;reposhell.sock&gt;"</span> \
  --reposhell-default-repo <span class="hljs-string">"&lt;repo-id&gt;"</span> \
  --reposhell-visible-repos <span class="hljs-string">"&lt;repo-id&gt;[,&lt;repo-id&gt;...]"</span> \
  -p <span class="hljs-string">"<span class="hljs-subst">$(cat &lt;rendered-prompt.md&gt;)</span>"</span>
</code></pre>
<h2 class="relative group flex items-baseline">
	<a id="processing-incoming-prs-and-issues" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#processing-incoming-prs-and-issues" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Processing incoming PRs and issues
	</span>
</h2>
<p>So then what orchestrates everything in between the incoming PR/issue and the final notification on Discord?</p>
<figure class="image table text-center m-0 w-full" style="text-align: center;">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/local-models-pr-triage/discord-notification.jpg" alt="Localpager Discord notification" style="display: block; width: 100%; min-width: 300px; margin: 0 auto;">
  <figcaption>This is what the final filtered Discord notification looks like: a PR about the desired vertical gets routed to me.</figcaption>
</figure>

<p>The orchestration around this is very simple; only the classification step involves an LLM:</p>
<ol>
<li>We use <a href="http://github.com/openclaw/gitcrawl" rel="nofollow">openclaw/gitcrawl</a> to act as a local mirror for the repo. Whenever there is a new PR or issue, each item is normalized into the same shape and written into localpager's own SQLite database. If the item is new, localpager creates a classification job for it.</li>
<li>A worker then claims jobs from that queue. It builds a GitHub context object containing the issue or PR title, body, labels, author, state, and optionally comments, changed files, and selected diff excerpts. That means the local model does not need to browse GitHub or open the URL itself most of the time. It is handed all the relevant context.</li>
<li>The context object is rendered into a prompt and passed to <code>localpager-agent</code> as described in the previous section. The agent can think and use reposhell, but must eventually output a classification result in the defined schema.</li>
<li>The output is stored back in localpager SQLite database, and relayed to Discord based on the notification policy configured by the user (i.e. notify me for these topics, but not these other ones).</li>
</ol>
<p>Below is a figure showing the overall architecture of localpager:</p>
<figure class="image table text-center m-0 w-full" style="text-align: center;">
  <img src="/blog/assets/local-models-pr-triage/localpager-architecture.svg" alt="Localpager architecture" style="display: block; width: 70%; min-width: 300px; margin: 0 auto;">
</figure>

<p>The architecture is semi-agentic. Labeling is done agentically, while sending a notification is handled by deterministic rules. This is to make the notification pipeline faster by removing the need for inference for the most straightforward parts of the task. Local inference is free but each task has a resource contention cost: GPU bandwidth should be reserved for tasks where inference is absolutely needed. This also reduces chance of errors from notification.</p>
<h2 class="relative group flex items-baseline">
	<a id="can-local-models-triage-prs" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#can-local-models-triage-prs" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Can local models triage PRs?
	</span>
</h2>
<p>Let's be frank: the first local versions of this system were noisy. The first model tested - <code>gemma-4-e4b-it</code> was useful for getting the end-to-end local pipeline working, but it also had a tendency to put too many unrelated labels on a PR or issue. False positive labels make the Discord feed noisy and don't focus my attention on the right issues. That pushed us toward testing larger local models, including <code>gemma-4-26b-a4b</code> and <code>qwen3.6-35b-a3b</code>, on the 330-row evaluation set below.</p>
<p>For early prompt work, we also used <code>DeepSeek-V4-Flash</code> through the antirez DS4 implementation<sup id="note-4-ref"><a href="#note-4" rel="nofollow">[4]</a></sup> to create the earlier dataset labels. That setup used the DS4 server over CUDA. We eventually gave up on DS4 as the labeler because it was not labeling consistently across runs. We also did not consider it as the main <code>localpager-agent</code> model because it was too big to get enough throughput on our hardware: the DS4 server gave us around 14 tokens per second, with maximum concurrency of 1.</p>
<p>To test model performance, we selected and generated labels for 330 GitHub issues and PRs. Each item was labelled five times (3x GPT-5.5 and 2x Opus 4.8) with the models needing to be in agreement to be accepted. This process involved hand adjudicating, improving label definitions and highlighting internal product design choices for the models. This gave us a set of stable, reproducible labels to compare our smaller models against.</p>
<p>We did not need to do prompt optimization for <code>gemma-4-26b-a4b</code> or <code>qwen3.6-35b-a3b</code> before getting useful results on this evaluation set. Using the same routing prompt, Gemma had higher recall and lower wall-clock time per row, while Qwen had higher precision, higher exact match, and fewer false positives. We also ran <code>DeepSeek-V4-Flash</code> on the same set as a reference. It had the fewest false positives, but the model size and throughput make it impractical for executing these tasks in real time on the NVIDIA GB10. Since each row can have multiple labels, false positives and false negatives are total label counts across all rows. The Qwen results below are after retrying structured-output failures where the model ran out of output tokens before calling <code>final_json</code>. For Gemma and Qwen, repeated-run metrics report mean ± sample standard deviation across three runs. <code>DeepSeek-V4-Flash</code> was run once as a reference.</p>

<p>For the Gemma benchmark, we served <code>gemma-4-26b-a4b</code> with vLLM using the optimizations we found available for this setup. A big part of that is the NVFP4 quantization: on GB10-class Blackwell hardware, it is not just a smaller model file, but a hardware-friendly format that can use the NVIDIA/vLLM execution path more directly than a portable GGUF quantization like Q4_K_M. In practice, that means less memory traffic and more room for batching. We also enabled prefix caching, FP8 KV cache, the CUTLASS MoE backend, and language-model-only mode. The full 330-row run finished in about 7.5 minutes at concurrency 16.</p>
<h2 class="relative group flex items-baseline">
	<a id="tracking-and-validating-real-time-performance-using-openclaw" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#tracking-and-validating-real-time-performance-using-openclaw" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Tracking and validating real-time performance using OpenClaw
	</span>
</h2>
<p>We have mentioned earlier that instead of running a job with a local model for every new issue or PR, we can run a batch job with a SOTA cloud model, like GPT-5.5 running in OpenClaw, every n hours (e.g. every 2 hours) to achieve the same end.<sup id="note-5-ref"><a href="#note-5" rel="nofollow">[5]</a></sup></p>
<p>In that case, we would need a ChatGPT Pro plan. Since the model is SOTA, we can still expect it to perform reasonably well, despite batching 2 hours of issues/PRs together.</p>
<p>Because we want to see how well the local classifier performs against GPT-5.5, we run both simultaneously, and let GPT-5.5 be the judge of false positives and negatives, every 2 hours.</p>
<p>To be safe, we run the OpenClaw job in a sandbox, with only access to the <a href="https://github.com/osolmaz/onurclaw" rel="nofollow">public repo</a> we report results to. In our case, we let the OpenClaw job update a machine-readable file, then a simple script reads the Codex-assigned labels and computes the false positive/negative status. Example output:</p>
<blockquote>
<p>False negatives</p>
<ul>
<li>Issue #88499 openai-responses provider: 404 on previous_response_id when store=false (default)<ul>
<li>inventory area: OpenAI-compatible/proxy; notifier topics: agent_runtime, api_surface, sessions; notification: none</li>
</ul>
</li>
</ul>
<p>False positives</p>
<ul>
<li>PR #88275 fix(models-config): allow self-hosted providers without apiKey in models.json (#88267)<ul>
<li>notifier interest: i0; topics: self_hosted_inference, local_model_providers, config; notification: sent</li>
</ul>
</li>
<li>PR #88266 refactor: extract model catalog core package<ul>
<li>notifier interest: i1; topics: config, api_surface, local_model_providers; notification: sent</li>
</ul>
</li>
<li>PR #88247 feat: add hosted model providers<ul>
<li>notifier interest: i0; topics: local_model_providers, model_serving, docs, api_surface; notification: sent</li>
</ul>
</li>
</ul>
</blockquote>
<p>The instructions on how to classify, edit the machine-readable file, get the false positives and false negatives using a script are present in an <a href="https://github.com/osolmaz/onurclaw/blob/main/.agents/skills/openclaw-onur-inventory/SKILL.md" rel="nofollow">agent skill</a> which is referenced in an <a href="https://docs.openclaw.ai/automation/cron-jobs" rel="nofollow">OpenClaw cron job</a> that runs every 2 hours. The OpenClaw agent then ingests any new issues or PRs, adds them to the JSON file with appropriate labels, runs the scripts and reports back in the same Discord channel. This way, we can observe the local model's performance every few hours, and get notified of the misses.</p>
<h2 class="relative group flex items-baseline">
	<a id="conclusion" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#conclusion" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Conclusion
	</span>
</h2>
<p>We think that the issue/PR triage task is a specific case of a broader set of tasks which we call "high throughput triage". This post explored the idea of using a local model to filter out information in real time in only one domain, that is, open source contributions. The ability of medium-sized local models like <code>gemma-4-26b-a4b</code> and <code>qwen3.6-35b-a3b</code> to zero-shot classify with good accuracy without any need for fine-tuning makes them a good first choice for quick prototyping, before one moves on to more cost-efficient traditional classifier models.</p>
<p>However, the same approach can be applied to other domains as well:</p>
<ul>
<li>News categorization in journalism</li>
<li>Filtering for posts of interest in social media and forums like X or Reddit</li>
<li>Triaging customer support tickets</li>
<li>Triaging content moderation appeals</li>
<li>Filtering potential outreach while doing sales</li>
<li>Filtering for certain topics on arXiv while doing research</li>
</ul>
<p>The list can be extended, but we think that the idea should be clear.</p>
<p>Besides triaging, we have also explored how classification can be performed with agent harnesses running fast local models in a secure manner. A good naming for the approach would be <em>agentic classification</em>: the model is not fed the entire body of information upfront, but can search for more context before returning structured data. While we cannot exactly call this a novel approach, we hope for this blog post to be a good reference for the specific <a href="https://pi.dev" rel="nofollow">Pi</a>+a restricted shell+<code>final_json</code> recipe.</p>
