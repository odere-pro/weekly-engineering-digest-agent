<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]-->Great news from the OGs of open source LLMs! Muse Glimmer, released today, is Meta’s new multimodal model, especially designed for local agentic use cases. Distilled from Muse to <strong>30B</strong> parameters, and released under the <strong>Apache 2.0 license</strong>, it’s ideal deploying locally for privacy, reducing costs, or just hacking around. It’s intended for privacy-aware applications such as coding, document analysis, personal assistants, Claw- or Hermes-like setups.</p>
<p>To celebrate, we are shipping with Meta day-0 support in <code>transformers</code>, <code>llama.cpp</code>, <code>vLLM</code>, Inference Endpoints, and other libraries. We built a few cool things and explain our findings in this blog.</p>
<p><a href="#demos" rel="nofollow"><strong>Check out the demos below for inspiration.</strong></a></p>
<p>You can find <a href="https://huggingface.co/meta-models/Muse-Glimmer-30B">Muse Glimmer on the Hugging Face Hub</a>.</p>

<h2 class="relative group flex items-baseline">
	<a id="architecture" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#architecture" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Architecture
	</span>
</h2>
<p>Muse Glimmer is a dense 30B parameter model consisting of:</p>
<ul>
<li>2B ViT-style encoder for vision (Perception Encoder)  </li>
<li>28B parameter text decoder</li>
</ul>
<p>In addition to the main VLM, there’s also a speculative decoding drafter implemented on DFlash. Usage of this module is optional, and it can provide much faster generation in exchange for some memory cost. We found this drafter to be particularly well suited to structured content generation such as coding.</p>
<h3 class="relative group flex items-baseline">
	<a id="text-decoder" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#text-decoder" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Text Decoder
	</span>
</h3>
<p>The language model uses the following architecture components:</p>
<ul>
<li><strong>Hybrid attention:</strong> Alternating between three sliding window layers (of 2,048 tokens) using rotary position embedding, followed by a fourth layer that uses full attention and NoPE (no positional embedding). The pattern is therefore (SWA, SWA, SWA, Full), repeated 13 times to a total of 52 layers. This allows the model to retain relative order and distance information with RoPE and preserve information globally with NoPE.  </li>
<li><strong>Gated Grouped-Query Attention:</strong> Each key-value head is shared by 16 query heads, which reduces KV-cache memory by 16x and makes generation faster and cheaper.  </li>
<li><strong>Q-K normalization with extra query scaling:</strong> Before computing attention, Muse Glimmer applies RMS normalization to every query and key head to keep attention logits stable. After this, queries are multiplied by a scale factor to set the target logit scale after normalization. The extra query scaling behaves like an inverse temperature at the softmax level.</li>
</ul>
<h3 class="relative group flex items-baseline">
	<a id="perception-encoder" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#perception-encoder" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Perception Encoder
	</span>
</h3>
<p>Muse Glimmer uses one image encoder to handle both images and videos. Unlike the relatively small vision encoders used in other VLMs, this is a sizable 2B ViT-like model designed after the Perception Encoder architecture. Perception Encoder was previously introduced by Meta <a href="https://huggingface.co/papers/2504.13181">as a backbone for various downstream spatial and multimodal tasks</a>.<br>The encoder patchifies images to a shape of 2 frames x 3 channels x 14 x 14, and passes them through a linear layer for projection. An interpolated absolute position embedding from a learned position table is then added to these embeddings. These are then sent to the vision tower which consist of 50 layers and GELU MLPs. Similar to the language model, the attention pattern consists of three window attention layers followed by one full attention layer. Inside the attention layers, 2D RoPE is applied to the queries and keys.</p>
<p>After transformer, pixel shuffle concatenates 2x2 groups of neighboring spatial tokens which reduces the number of image tokens 4x without discarding their channels. The merged features are then projected to the shared embedding space of the text decoder.</p>
<p>Videos go through the same encoder frame by frame, where each frame is converted into patches (of shape [batch, temporal groups, grid height, grid width, 2 frames, 3 channels, 14, 14]). The processor targets 2 frames per second and caps the clip at 96 frames sampled evenly across video. The processor creates timestamped video placeholders, interleaving text with frame e.g. “Time: 0.0s &lt;|video|&gt; x N” in which the final video embeddings are replaced before the final projection layer.</p>

            {<span class="hljs-string">"type"</span>: <span class="hljs-string">"text"</span>, <span class="hljs-string">"text"</span>: <span class="hljs-string">"What is shown in this image?"</span>}
        ]

]

inputs = processor.apply_chat_template(
    messages,
    tokenize=<span class="hljs-literal">True</span>,
    return_dict=<span class="hljs-literal">True</span>,
    return_tensors=<span class="hljs-string">"pt"</span>,
    add_generation_prompt=<span class="hljs-literal">True</span>,

    **inputs,

    speculation_type=<span class="hljs-string">"dflash"</span>,

</code></pre>
<h3 class="relative group flex items-baseline">
	<a id="speculative-decoding-with-llamacpp" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#speculative-decoding-with-llamacpp" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Speculative Decoding with llama.cpp
	</span>
</h3>
<p>You can start llama server using following command. <code>--spec-draft-n-max</code> argument controls how many future tokens DFlash proposes during each speculative-decoding step. Muse Glimmer’s DFlash model was trained with a block size of 16, one anchor token plus 15 proposed tokens, so any value above 15 will be clamped to 15.</p>
<pre><code class="language-bash">llama serve -hf meta-models/Muse-Glimmer-30B-GGUF --spec-type draft-dflash --spec-draft-n-max 15
</code></pre>
<p>You can also use llama cli with speculative decoding drafter as follows.</p>
<pre><code class="language-bash">llama cli -hf meta-models/Muse-Glimmer-30B-GGUF --spec-type draft-dflash
</code></pre>

<h2 class="relative group flex items-baseline">
	<a id="connect-openclaw-to-muse-glimmer" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#connect-openclaw-to-muse-glimmer" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Connect OpenClaw to Muse Glimmer
	</span>
</h2>
<p>Assume the Inference Endpoint exposes an OpenAI-compatible <code>/v1</code> API.</p>
<p>Set <code>HF_TOKEN</code> in the OpenClaw gateway environment, then add this to <code>~/.openclaw/openclaw.json</code>:</p>
<details>
<summary>OpenClaw configuration</summary>

<pre><code class="language-json5">{
  models: {
    mode: "merge",
    providers: {
      muse: {
        baseUrl: "https://YOUR-ENDPOINT.endpoints.huggingface.cloud/v1",
        apiKey: {
          source: "env",
          provider: "default",
          id: "HF_TOKEN"
        },
        api: "openai-completions",
        authHeader: true,
        models: [{
          id: "meta-models/Muse-Glimmer-30B",
          name: "Muse Glimmer",
          reasoning: false,
          input: ["text", "image"],
          contextWindow: 32768,
          maxTokens: 8192
        }]
      }
    }
  },
  agents: {
    defaults: {
      model: { primary: "muse/meta-models/Muse-Glimmer-30B" }
    }
  }
}
</code></pre>
<p>Restart OpenClaw:</p>
<pre><code class="language-bash">openclaw gateway restart
</code></pre>
<p>Validate from a fresh session:</p>
<pre><code class="language-bash">openclaw agent --message <span class="hljs-string">"Reply with: muse-ready"</span>
</code></pre>
</details>

<p>Use the exact model ID returned by the endpoint’s <code>/v1/models</code> response if it differs.</p>
<h3 class="relative group flex items-baseline">
	<a id="hey-muse-glimmer-quantize-yourself" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#hey-muse-glimmer-quantize-yourself" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Hey Muse Glimmer, quantize yourself
	</span>
</h3>
<p>If we hook up Muse Glimmer to the <a href="https://huggingface.co/mcp">Hugging Face MCP</a> and update its <a href="http://AGENTS.md" rel="nofollow"><code>AGENTS.md</code></a> we give it the capability to find a quantized version of itself on the hub and run locally. This is handy if you want to work on something private, or just cut costs.</p>
<p>If you do this a second time, Muse Glimmer will find the cached weights and switch to them, so feel free to add a convenient command like <code>/spawn</code>. </p>
<p>Muse Glimmer inspects the machine and Hub, selects or creates a Q4_K_M GGUF, launches llama-server, and validates model discovery and chat completion. The result is a smaller local build behind an OpenAI-compatible API. Here’s the prompt we added to <code>AGENTS.md</code>.</p>
<p><a href="https://huggingface.co/buckets/huggingface/muse-glimmer-assets/resolve/Muse%20Glimmer%20Quantisation%20Demo%20-%20explained.mp4?download=true">https://huggingface.co/buckets/huggingface/muse-glimmer-assets/resolve/Muse%20Glimmer%20Quantisation%20Demo%20-%20explained.mp4?download=true</a></p>
<p>By adding this to <a href="http://AGENTS.md" rel="nofollow"><code>AGENTS.md</code></a> openclaw or hermes will be able to solve the rest.</p>
<details>
<summary>Local quantization prompt</summary>

<pre><code class="language-text">## Local model deployment

When asked to deploy locally, perform the work; do not give instructions.

1. Inspect hardware and the Hugging Face cache.
2. Search the Hub for compatible GGUF weights using `apps=llama.cpp`; confirm exact filenames through the model-tree API.
3. Prefer an existing suitable GGUF, normally `Q4_K_M`. Treat `mmproj-*.gguf` as projector weights.
4. If no GGUF exists, download the source weights, convert with `convert_hf_to_gguf.py`, then quantize with `llama-quantize`.
5. Preserve source weights and record the repository, revision, filenames, and quantization.
6. Start `llama-server` with an `onyx` alias and an OpenAI-compatible endpoint.
7. Validate `/v1/models` and `/v1/chat/completions`, requiring non-empty, correct content.
8. Report concise progress and logs. Claim completion only after validation passes.
</code></pre>
</details>

<h3 class="relative group flex items-baseline">
	<a id="hey-muse-glimmer-deploy-yourself" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#hey-muse-glimmer-deploy-yourself" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Hey Muse Glimmer, deploy yourself
	</span>
</h3>
<p>Muse Glimmer can also take care of the opposite. Let’s get Glimmer to deploy itself on Hugging Face Inference Endpoints. Which is useful if you want to speed up on some cutting edge hardware.</p>
<p>N.B. You can also just deploy <a href="https://endpoints.huggingface.co/huggingface/new/meta-models/Muse-Glimmer-30B" rel="nofollow">Muse Glimmer to Inference Endpoints</a> directly and connect your agent.</p>
<p>Muse Glimmer pins the model revision, deploys it to a protected Hugging Face Inference Endpoint, and verifies health, model discovery, and chat completion. It then connects the Claw agent with secrets and rollback preserved. Here’s the prompt we added to <a href="http://AGENTS.md" rel="nofollow"><code>AGENTS.md</code></a>. Muse glimmer will also need the <a href="https://huggingface.co/mcp">Hugging Face MCP</a> and/or the <a href="https://huggingface.co/docs/hub/en/agents-skills">Hugging Face CLI and Skills</a>.</p>
<details>
<summary>Inference Endpoint deployment prompt</summary>

<pre><code class="language-text">## Hugging Face Inference Endpoint deployment

When asked to deploy on Hugging Face Inference Endpoints, perform the work; do
not give instructions.

1. Inspect Hugging Face authentication, the current model repository, and any
   existing endpoints.
2. Confirm the exact model repository and immutable revision through the Hub
   API; inspect its architecture, configuration, and chat template.
3. Confirm that the model is supported by vLLM, then deploy or update a
   protected Inference Endpoint using the managed native vLLM engine.
4. Choose an available region and the smallest suitable accelerator. Use one
   replica and enable scale-to-zero when supported.
5. Preserve the previous endpoint configuration for rollback. Do not expose
   tokens, publish private weights, or replace an unrelated endpoint.
6. Wait for the endpoint to become ready. If startup fails, inspect the logs
   and report the actual blocker rather than repeatedly changing settings.
7. Validate `/health`, `/v1/models`, and `/v1/chat/completions`, requiring the
   expected model and non-empty, correct content. When agent use is required,
   also validate a real structured tool call.
8. Configure the Claw agent to use the endpoint's OpenAI-compatible `/v1` URL,
   storing credentials as secrets and retaining the previous provider as
   rollback. Test the connection in a fresh session.
9. Report concise progress and finish with the repository, revision, engine,
   hardware, endpoint URL, scaling state, and validation results. Claim
   completion only after every required check passes.
</code></pre>
</details>

<h3 class="relative group flex items-baseline">
	<a id="hey-muse-glimmer-optimize-yourself" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#hey-muse-glimmer-optimize-yourself" rel="nofollow">

	</a>
	<span>
		Hey Muse Glimmer, optimize yourself
	</span>
</h3>
<p>Finally, let’s get Muse Glimmer to do some light RSI. We can instruct our agent to optimize its own inference engine for specific hardware, in this case a Nvidia H100. To do this, the agent will need to use another inference engine, like Inference Endpoints above.</p>
<p>Muse Glimmer benchmarks its own single-H100 serving stack, testing one reversible change at a time while holding the workload fixed. It keeps only correctness-passing gains and finishes with the fastest reproducible configuration. Here’s the prompt we added to <a href="http://AGENTS.md" rel="nofollow"><code>AGENTS.md</code></a>. Muse glimmer need the <a href="https://huggingface.co/mcp">Hugging Face MCP</a> and the <a href="https://huggingface.co/docs/hub/en/agents-skills">Hugging Face CLI and Skills</a>.</p>
<details>
<summary>Self-optimization prompt</summary>

<pre><code class="language-text">You are Muse Glimmer acting as an autonomous inference-optimization engineer for your own serving stack.

Goal: maximize valid single-H100 aggregate completion throughput in tokens/second.

Protocol:
1. Establish a correctness-passing baseline.
2. Test one reversible optimization at a time.
3. Keep the prompt, concurrency, sampling, request count, warm-up, and decode length fixed.
4. Reject results that fail correctness or prefix checks.
5. Record every experiment chronologically with its configuration, raw throughput, correctness, and delta.
6. Keep improvements and revert regressions.
7. Stop after six consecutive regressions or when the experiment budget is exhausted.
8. Report the best valid configuration and exact reproduction command.

Create a minimal scientific animation of the results:
- white background;
- raw tokens/second—never normalize;
- one point revealed per experiment;
- connect every point chronologically;
- begin with the lowest valid result;
- stop at the best result;
- export as a GIF.

Never fabricate, interpolate, or count correctness-failing measurements.
</code></pre>
</details>

<p>Muse Glimmer uses one image encoder to handle both images and videos. Unlike the relatively small vision encoders used in other VLMs, this is a sizable 2B ViT-like model designed after the Perception Encoder architecture. Perception Encoder was previously introduced by Meta as <a href="https://movieboxfree.app/" rel="nofollow">moviebox</a> a backbone for various downstream spatial and multimodal tasks.<br>The encoder patchifies images to a shape of 2 frames x 3 channels x 14 x 14, and passes them through a linear layer for projection. An interpolated absolute position embedding from a learned position table is then added to these embeddings. These are then sent to the vision tower which consist of 50 layers and GELU MLPs. Similar to the language model, the attention pattern consists of three window attention layers followed by one full attention layer. Inside the attention layers, 2D RoPE is applied to the queries and keys.</p>
</blockquote>
<p>After transformer, pixel shuffle concatenates 2x2 groups of neighboring spatial tokens which reduces the number of image tokens 4x without discarding their channels. The merged features are then projected to the shared embedding space of the text decoder.</p>
<p>Muse Glimmer looks like a really exciting step for practical open-source AI, especially with its focus on local, agentic, and multimodal workloads. A 30B-parameter model combining a 2B vision encoder with a 28B text decoder gives developers a strong foundation for coding, document analysis, personal assistants, and other privacy-sensitive applications. 🔥🤖</p>
<p>The Apache 2.0 license is another major highlight because it makes the model much more approachable for developers who want to experiment, customize, and deploy without relying entirely on hosted inference. Local deployment can also bring meaningful benefits around privacy, latency, and infrastructure costs, which makes this especially interesting for personal and enterprise workflows. 🚀</p>
<p>I also like the architectural choices here, particularly the hybrid attention pattern, grouped-query attention, and Q-K normalization. Alternating sliding-window and full-attention layers seems like a thoughtful way to balance long-context capability with efficiency, while sharing KV heads across query heads can significantly reduce memory requirements during generation.</p>
<p>The day-zero ecosystem support makes the release even more compelling. Having integrations across Transformers, llama.cpp, vLLM, and other tools means developers can start testing real-world workflows immediately instead of waiting for the surrounding ecosystem to catch up. Open multimodal models that are genuinely practical to run locally could be a huge part of where AI development goes next. 💡👏</p>
