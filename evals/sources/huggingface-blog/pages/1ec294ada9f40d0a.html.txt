<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]-->At Microsoft Build 2026, we announced <strong>Foundry Managed Compute</strong> and <strong>Hugging Face models on Foundry</strong> — a curated catalog of open-weight models from the Hugging Face ecosystem, refreshed weekly, deployable in one click onto Foundry Managed Compute. Weights are pre-staged in Azure, runtimes are built and scanned by Microsoft, and every model in the Collection ships with the same enterprise security, governance, observability, and billing that applies to every other model on Foundry.</p>
<h2 class="relative group flex items-baseline">
	<a id="the-platform-microsoft-foundry-and-managed-compute" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-platform-microsoft-foundry-and-managed-compute" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The Platform: Microsoft Foundry and Managed Compute
	</span>
</h2>
<p>Microsoft Foundry is a platform for building and operating agentic AI applications. Foundry starts with the widest model selection on any cloud — models from Microsoft, OpenAI, Anthropic, Meta, Mistral, DeepSeek, Hugging Face, and others, spanning frontier, open-source, and custom weights — all accessible through a single endpoint and a single set of SDKs in Python, C#, JavaScript, and Java.</p>
<p>On top of those models sits the <strong>Foundry Agent Service</strong>: multi-agent orchestration with built-in memory, knowledge grounding through Foundry IQ, and a catalog of connectable tools via agentic protocols, so agents can work with enterprise data. Once agents are running, Foundry provides end-to-end tracing, real-time monitoring, continuous evaluations, and a prompt optimizer that improves agent behavior based on eval results — observability and quality loops that are part of the platform.</p>
<p>Alongside that, developers get access to:</p>
<ul>
<li>Content safety filters</li>
<li>Task-adherence guardrails</li>
<li>An AI Red Teaming Agent for adversarial testing</li>
<li>Unified RBAC</li>
<li>Private networking</li>
<li>Azure Policy integration directly within the platform</li>
</ul>
<p>Alongside pay-per-token (lowest-friction path to get started) and provisioned throughput (predictable, high-performance production workloads on frontier models), <strong>Foundry Managed Compute</strong> is the third deployment option in Foundry: a managed GPU platform-as-a-service for open-source and custom models.</p>
<p>You deploy a model instance described by the things that matter to your workload — parameter count, context length, and whether you want to optimize for latency or throughput — and Foundry handles the GPU topology underneath, whether the instance lands on one accelerator or several, so you think and plan in model terms.</p>
<p>Microsoft takes care of the machine: container updates, runtime upgrades, and security patches happen automatically on the supported runtimes — <strong>vLLM, SGLang, TensorRT-LLM, NIM, TEI, llama.cpp</strong> — without redeploying your model, while model configuration, deployment behavior, and routing stay with you.</p>
<p>That consistency carries through the developer surface — pay-per-token, provisioned throughput, and Managed Compute share:</p>
<ul>
<li>A single endpoint</li>
<li>The same SDKs</li>
<li>The same authentication</li>
<li>The same observability</li>
<li>A single bill</li>
</ul>
<p>Open-source models integrate with Foundry Agents the same way frontier models do, so you can mix model types in a single agent without a separate integration path.</p>
<p>Managed Compute offers:</p>
<ul>
<li><strong>Global deployments</strong> — broadest capacity and best pricing</li>
<li><strong>Data Zone deployments</strong> — residency and sovereignty</li>
</ul>
<p>Same code, same workflow. Quota is aligned to accelerator families, so a plan built on the H100 family today carries forward as new hardware generations come online.</p>
<h2 class="relative group flex items-baseline">
	<a id="why-hugging-face" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#why-hugging-face" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Why Hugging Face
	</span>
</h2>
<p>Hugging Face is the public square of open AI: <strong>15 million builders, 400,000 organizations, and over 3 million open models published</strong>, with new frontier capabilities — agentic coding, video segmentation, speech, embeddings — landing weekly. It's the GitHub of open models, where the community publishes weights, writes model cards, compares evaluations, and pulls models for experimentation.</p>
<p>Open models have closed the gap with proprietary models on benchmark after benchmark, and they unlock things proprietary endpoints can't:</p>
<ul>
<li><strong>State-of-the-art is now open.</strong> Leading open-weight models are competitive with the top closed frontier models on the most widely used benchmarks.</li>
<li><strong>Deep customization.</strong> Full weights make it possible to fine-tune, distill, quantize, and adapt with LoRA — tailoring models to your domain, your data, and your latency and cost targets.</li>
<li><strong>Your model, your hosting.</strong> Weights run in your tenant on infrastructure you control, behind your inference endpoint, with your identity and network boundaries.</li>
<li><strong>Cost shaping.</strong> Pay for accelerators by the hour, scale to zero when idle, and right-size GPUs to the specific model — useful for steady, high-volume, or latency-sensitive workloads where per-token pricing is harder to predict.</li>
<li><strong>Version control.</strong> Pin a specific model version, evaluate it, deploy it, and move forward or roll back on your own release cadence.</li>
</ul>
<p>The catch has always been the operational layer: discovery, license review, security screening, runtime selection, GPU sizing, image building, CVE patching, and standing the model up behind an enterprise-grade endpoint. Hugging Face, by itself, is not an enterprise serving platform. <strong>Hugging Face models on Foundry is that operational layer, run by Microsoft.</strong></p>
<h2 class="relative group flex items-baseline">
	<a id="hugging-face-models-on-foundry" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#hugging-face-models-on-foundry" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Hugging Face Models on Foundry
	</span>
</h2>
<p>The Hugging Face Collection brings a curated subset of models directly into the Foundry Model Catalog:</p>
<ul>
<li><strong>Refreshed weekly</strong> — trending models from the Hugging Face ecosystem are added continuously as the community publishes them.</li>
<li><strong>Every modality</strong> — text, vision, audio, and multimodal: LLMs and VLMs for chat and agents, ASR and speech translation, embeddings, segmentation, image generation.</li>
<li><strong>Safetensors only, no untrusted code</strong> — every model in the Collection is security-screened and ships in the SafeTensors weight format, with no <code>trust_remote_code</code> execution paths unless rigorously reviewed.</li>
<li><strong>The right runtime for the model</strong> — vLLM and SGLang for LLMs, TensorRT-LLM and NIM where applicable, TEI for embeddings, llama.cpp for CPU — Foundry picks the engine that matches the model.</li>
</ul>
<p>From your side, an open-weight model in the Hugging Face Collection looks and behaves like any other model in the Foundry Model Catalog, and every model in the Collection has been put through a multi-stage publishing pipeline before it ever shows up there.</p>
<h3 class="relative group flex items-baseline">
	<a id="the-curation-pipeline" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-curation-pipeline" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The Curation Pipeline
	</span>
</h3>
<p>Hugging Face and Microsoft work together to bring the most popular open-weight models from the Hugging Face ecosystem to Microsoft Foundry — production-ready for enterprise environments — through a systematic curation process:</p>
<ol>
<li><strong>Identify trending models</strong> in the Hugging Face ecosystem — based on community signals, partner requests, and customer demand — and select candidates for enterprise readiness.</li>
<li><strong>Screen for compliance and security</strong> — model licenses are reviewed against Microsoft's enterprise distribution policy (with license metadata captured and preserved on the catalog model card), and repositories are inspected for <code>trust_remote_code</code> patterns and custom executable code; any model that would require executing third-party Python at load time is either remediated or excluded.</li>
<li><strong>Build, scan, and publish runtimes</strong> — Microsoft builds inference container images on supported runtimes (vLLM, SGLang, TensorRT-LLM, NIM, TEI, llama.cpp), scans them for CVEs, and signs and publishes them to a Microsoft-managed container registry.</li>
<li><strong>Upload weights to secure Azure storage</strong> — model weights are pulled from Hugging Face once, validated against the published model card, and stored in Microsoft-managed Azure storage in the regions where the model is served.</li>
<li><strong>Validate and publish to the catalog</strong> — every model + runtime + accelerator combination is tested for API conformance (chat completions, embeddings, rerank, etc.) and performance (latency, throughput, time-to-first-token, inter-token decode time), then the validated model — with its templates, runtime images, and weights — is published to the Foundry Model Catalog with a one-click deploy path onto Managed Compute.</li>
</ol>
<p>Because weights are pre-staged in Azure storage and runtime images live in a Microsoft-managed registry, your deployments won't need outbound network access to Hugging Face Hub — you can deploy to production inside a private network.</p>
<h2 class="relative group flex items-baseline">
	<a id="model-runtimes" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#model-runtimes" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Model Runtimes
	</span>
</h2>
<p>Hugging Face models on Foundry are powered by a versatile collection of community-built, open-source inference runtimes — each selected and tuned for Foundry Managed Compute, and matched to the model architectures it serves best. Across all runtimes, the systematic curation process means new versions and patches land on Foundry quickly, and existing model deployments are upgraded automatically — without requiring you to redeploy.</p>
<ul>
<li><p><strong>vLLM</strong> — the default high-throughput serving engine for open large language models, tuned for production GPU workloads. Because Hugging Face is a direct contributor to vLLM, any model in the Transformers library can run on vLLM out of the box — so when a new model lands on Hugging Face, it can be served on Foundry the same day, with no waiting on a custom integration.</p>
</li>
<li><p><strong>SGLang</strong> — a serving engine for language and multi-modal models, with strong support for structured outputs (JSON, regex, grammar-constrained generation) that agentic and tool-using workloads depend on. Hugging Face and the SGLang team have built a Transformers backend integration for SGLang, so any model in the Transformers library runs on SGLang out of the box — and reaches Foundry the same day it lands on Hugging Face.</p>
</li>
<li><p><strong>Text Embeddings Inference (TEI)</strong> — the runtime for embedding, reranker, and sequence-classification models. Accelerator-specific images ship with kernels compiled for each GPU and CPU family Foundry supports, keeping the embedding hot path lean for RAG and semantic-search workloads.</p>
</li>
<li><p><strong>llama.cpp</strong> — the CPU and small-GPU path for GGUF-quantized models. Useful for cost-optimized deployments, smaller models, and CPU-only regions, with the same OpenAI-compatible API as vLLM and SGLang.</p>
</li>
<li><p><strong>TensorRT-LLM and NIM</strong> — used on NVIDIA hardware where NVIDIA's optimized kernels and Triton-based serving deliver meaningfully better latency or throughput for specific model families.</p>
</li>
<li><p><strong>hf-serve</strong> — Hugging Face's own multi-model inference server, used for model architectures outside the LLM and embedding fast paths (vision, audio, segmentation, and other Transformers-native pipelines) so the Collection can cover every modality with a consistent serving layer.</p>
</li>
</ul>
<h2 class="relative group flex items-baseline">
	<a id="deploying-and-scoring-an-open-weight-model" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#deploying-and-scoring-an-open-weight-model" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Deploying and Scoring an Open-Weight Model
	</span>
</h2>
<p>The Hugging Face Collection in the Foundry Model Catalog is where you start, and deployment is five steps:</p>
<ol>
<li><strong>Browse the catalog and pick a model</strong> — the deploy wizard also surfaces the model id, deployment template id, and <code>acceleratorType</code> you'll need if you're scripting the deploy via SDK or REST.</li>
<li><strong>Choose a deployment template</strong> — latency- vs throughput-optimized, accelerator family, context length, quantization.</li>
<li><strong>Configure instance count</strong> — scale throughput by adding model instances.</li>
<li><strong>Deploy</strong> — from the portal, CLI, SDK, or REST.</li>
<li><strong>Score</strong> via the unified Foundry endpoint with the SDK you already use.</li>
</ol>
<h3 class="relative group flex items-baseline">
	<a id="deployment-templates" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#deployment-templates" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Deployment Templates
	</span>
</h3>

<h3 class="relative group flex items-baseline">
	<a id="deploy--python-sdk" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#deploy--python-sdk" rel="nofollow">

	</a>
	<span>
		Deploy — Python SDK
	</span>
</h3>
<pre><code class="language-python"><span class="hljs-keyword">from</span> azure.identity <span class="hljs-keyword">import</span> DefaultAzureCredential

	</a>
	<span>
		Score — OpenAI SDK
	</span>
</h3>
<p>The deployment is reachable through the unified Foundry endpoint with the OpenAI SDK — the `model` field takes the deployment name you just created:</p>
<pre><code class="language-python"><span class="hljs-keyword">from</span> openai <span class="hljs-keyword">import</span> OpenAI

completion = openai_client.chat.completions.create(
    model=deployment.name,
    messages=[{<span class="hljs-string">"role"</span>: <span class="hljs-string">"user"</span>, <span class="hljs-string">"content"</span>: <span class="hljs-string">"What is the capital of France?"</span>}],

	<a id="use-it-in-an-agent" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#use-it-in-an-agent" rel="nofollow">

	<span>
		Use It in an Agent
	</span>
</h3>
<p>A chat-completions model from the Collection slots into Foundry Agents as an admin-connected model and is callable through the Foundry Responses API with the same OpenAI SDK — same auth, same endpoint, same observability.</p>
