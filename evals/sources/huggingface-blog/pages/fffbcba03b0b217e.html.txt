<h2 class="relative group flex items-baseline">
	<a id="tldr" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#tldr" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		TL;DR
	</span>
</h2>
<p>We introduce <em><strong>NeoMME</strong></em>, a family of 260M and 800M multilingual multimodal encoders. Unlike many generative visual language models, <em>NeoMME</em> does not use a separate pretrained vision tower or a causal language model. A single bidirectional Transformer processes both text tokens and raw image patches, and we train the entire model from scratch with a masked discrete-diffusion objective.</p>
<p>We fine-tuned <em>NeoMME</em> for visual document retrieval using ColPali's page-image approach. <em>NeoMME</em>-Retriever returns dense and late-interaction embeddings in one forward pass. Both model sizes lie on the ViDoRe v3 Pareto frontier for nDCG@10 and model size. At a matched 2048×2048 image input size on an NVIDIA L40S GPU, the 260M model encodes about 51 pages per second, or about twice ColModernVBERT's throughput. Hierarchical token pooling and asymmetric quantization reduce late-interaction index storage from roughly 1.5 MB to 6 kB per page (255× smaller) while retaining more than 95% of baseline nDCG@10.</p>
<p><em>NeoMME</em> is available in Hugging Face Transformers. We release all model checkpoints under the Apache 2.0 license.</p>

<h2 class="relative group flex items-baseline">
	<a id="why-another-multimodal-encoder" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#why-another-multimodal-encoder" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Why another multimodal encoder?
	</span>
</h2>
<p>Many recent visual document retrievers are adapted from pretrained generative visual language models. A separately pretrained vision encoder produces visual features, which a projector maps into the language model's input space. A causal decoder then processes the combined image and text representations. Retrieval, classification, and token labeling do not generate text autoregressively, so they do not require a causal decoder or the parameter and compute overhead of this architecture.</p>
<p><a href="https://huggingface.co/blog/modernbert">ModernBERT</a> brought efficient architecture and training improvements to bidirectional encoders. For visual document retrieval, <a href="https://huggingface.co/blog/paultltc/modernvbert">ModernVBERT</a> applied a bidirectional ModernBERT-style text encoder while retaining a separate pretrained SigLIP2 vision tower. We wanted to push this even further by designing and training a multimodal encoder without having to carry over the parameter and compute overhead of a VLM.</p>
<p><em><strong>NeoMME</strong></em> (pronounced "nee-oh-me", IPA /ˈniː.oʊ.mi/) is a multilingual, multimodal foundation encoder that generates vector representations for input text and/or images using a single Transformer encoder. It is not based on an existing pretrained vision tower, text encoder, or text decoder.</p>
<figure>
  <img src="https://github.com/tonywu71/colpali-cookbooks/blob/481c6ec8866f6f5d39d2d9dd06b5547c2d9a67fa/assets/neomme/architecture.webp?raw=true" alt="Comparison of dual-tower, VLM, ModernVBERT, and NeoMME input paths">
  <figcaption>Unlike dual-tower and VLM encoders, <em>NeoMME</em> processes image patches and text tokens in one bidirectional Transformer, without a pretrained vision tower or a pretrained text encoder or decoder.</figcaption>
</figure>

<p>Images and text use the same computational path, so <em>NeoMME</em> can more easily support pretraining, fine-tuning, parallelization, and serving across both modalities.</p>

<h3 class="relative group flex items-baseline">
	<a id="one-transformer-for-images-and-text" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#one-transformer-for-images-and-text" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		One Transformer for images and text
	</span>
</h3>
<p><em>NeoMME</em> comes in two sizes, <a href="https://huggingface.co/Hcompany/NeoMME-260M">260M</a> and <a href="https://huggingface.co/Hcompany/NeoMME-800M">800M</a>. Both variants share the same architecture:</p>
<ul>
<li><strong>Native multimodal inputs:</strong> text inputs use factorized token embeddings, while images are divided into a grid of non-overlapping 32×32 patches and projected with a small MLP. Both enter the same Transformer encoder.</li>
<li><strong>Dynamic image resolution:</strong> images keep their aspect ratio and size. This allows the model to use more tokens on a high-resolution, information-dense document page than on a smaller image with less content.</li>
<li><strong>Long bidirectional context:</strong> both models have a context length of 16,384 tokens (enough for up to two standard 3840×2160 4K UHD images). Most layers use symmetric sliding-window attention, while every sixth layer and the final layer use global attention.</li>
<li><strong>A modern encoder stack:</strong> <em>NeoMME</em> uses recent encoder improvements such as grouped-query attention, query-key normalization, gated attention, 2D rotary position embeddings, and squared-ReLU MLPs, among others.</li>
<li><strong>Multilingual text:</strong> we trained a BPE tokenizer with a 131k-token vocabulary from scratch on multilingual text, code, mathematics, and machine-produced image transcripts.</li>
</ul>
<figure>
  <img src="https://github.com/tonywu71/colpali-cookbooks/blob/481c6ec8866f6f5d39d2d9dd06b5547c2d9a67fa/assets/neomme/encoder-stack.webp?raw=true" alt="Alternating sliding-window and global-attention layers in NeoMME">
  <figcaption>Alternating sliding-window and global-attention layers in the <em>NeoMME</em> encoder stack.</figcaption>
</figure>

<h3 class="relative group flex items-baseline">
	<a id="learning-from-images-through-masked-text" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#learning-from-images-through-masked-text" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Learning from images through masked text
	</span>
</h3>
<p>We pretrain <em>NeoMME</em> from scratch as a discrete masked-diffusion text denoiser. For each text-only example, we sample a corruption rate uniformly between 0 and 1. Each eligible text token is then independently masked at that rate.</p>
<p>Multimodal examples use corruption rates between 0.3 and 1. The image patches remain visible while <em>NeoMME</em> reconstructs masked text. With light masking, the model can often recover a missing word from the surrounding text alone. For example, "cat" is a plausible completion of "The [MASK] sat on the mat," even without an image. But high masking forces the model to learn image-grounded descriptions with little to no signal from the non-masked input text tokens.</p>
<figure>
  <img src="https://github.com/tonywu71/colpali-cookbooks/blob/481c6ec8866f6f5d39d2d9dd06b5547c2d9a67fa/assets/neomme/masked-diffusion.webp?raw=true" alt="Effect of text corruption on the textual and visual evidence available to NeoMME">
  <figcaption>Higher text corruption removes language-only shortcuts and encourages <em>NeoMME</em> to use visible image evidence.</figcaption>
</figure>

<p>Pretraining mixes multilingual text, code, mathematics, natural images, and document images. Each model processes about 524 billion packed input tokens, including 290 billion tokens from text-only examples. This text budget is relatively small compared with ModernBERT's 2 trillion training token budget. Hence, we chose the NorMuon optimizer to improve data efficiency during training.</p>
<h2 class="relative group flex items-baseline">
	<a id="neomme-retriever" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#neomme-retriever" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		<em>NeoMME</em>-Retriever
	</span>
</h2>
<p>To get a meaningful downstream evaluation of the backbone, we fine-tune <em>NeoMME</em> for visual document retrieval using the page-image methodology introduced by <a href="https://huggingface.co/blog/manu/colpali">ColPali</a>. While traditional text-based retrieval consists of retrieving text chunks, <em>NeoMME</em>-Retriever ranks document page screenshots and bypasses all the preprocessing OCR steps necessary to extract text from PDFs. Treating the pages as images preserves layout, charts, tables, font type and size, and other visual clues that cannot be captured even by a perfect OCR model.</p>
<h3 class="relative group flex items-baseline">
	<a id="a-dual-head-design-for-dense-and-late-interaction-retrieval" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#a-dual-head-design-for-dense-and-late-interaction-retrieval" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		A dual-head design for dense and late-interaction retrieval
	</span>
</h3>
<p><em>NeoMME</em>-Retriever reuses the <em>NeoMME</em> backbone but adds two jointly trained heads on top of it for retrieval:</p>
<ul>
<li>The dense head averages the backbone's hidden state vectors into a normalized vector (mean pooling). Dense embeddings are most common today: they are compact and work naturally with approximate nearest-neighbor (ANN) techniques for fast retrieval.</li>
<li>The late-interaction head projects each text token or image patch from the backbone's output hidden states to a 128-dimensional normalized vector. Compared to dense embeddings, the finer granularity preserves local matches between individual query tokens and image regions.</li>
</ul>
<figure>
  <img src="https://github.com/tonywu71/colpali-cookbooks/blob/481c6ec8866f6f5d39d2d9dd06b5547c2d9a67fa/assets/neomme/retrieval-heads.webp?raw=true" alt="Late-interaction and dense retrieval heads for NeoMME">
  <figcaption>Late-interaction and dense retrieval heads for both <em>NeoMME</em> model sizes.</figcaption>
</figure>

<blockquote class="note">
<p>Omar Khattab, who introduced late-interaction in ColBERT, <a href="https://x.com/lateinteraction/status/1894696983077785980" rel="nofollow">explains why</a> the term is more precise than "multi-vector." It describes the granularity and learnability of the scoring function, not simply the number of stored vectors.</p>
<p>To learn more about late-interaction, we recommend reading <a href="https://meet.ameliechatelain.com/lectures/multi-vector-search/" rel="nofollow">this crash course</a> by Amélie Chatelain.</p>
</blockquote>
<p>One <em>NeoMME</em>-Retriever forward pass returns both representations, which gives you flexibility no matter your use case and infrastructure. We recommend using late-interaction embeddings in general since they are more powerful and can be used easily with open-source libraries like <a href="https://github.com/lightonai/next-plaid" rel="nofollow">NextPlaid</a>. However, if you have a very large corpora, you can run a single forward pass with <em>NeoMME</em>-Retriever to get the dense embedding, retrieve a small number of documents through an ANN index, and then use late-interaction to rerank the retrieved candidates.</p>
<h3 class="relative group flex items-baseline">

<h3 class="relative group flex items-baseline">
	<a id="making-high-resolution-retrieval-practical-for-late-interaction" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#making-high-resolution-retrieval-practical-for-late-interaction" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Making high-resolution retrieval practical for late-interaction
	</span>
</h3>
<p>Late-interaction storage scales linearly with the number of vectors in the output embedding. Higher-resolution images contain more patches, so they produce larger embeddings. For example, a 2048×2048 square page produces embeddings containing 4,200 vectors with <em>NeoMME</em>-Retriever, or about 2.1 MB in float32. Across the ViDoRe v3 benchmark, the measured average is about 1.5 MB per document.</p>
<p>To reduce the storage footprint of the late-interaction index, we combine two complementary compression methods:</p>
<ol>
<li><a href="https://www.answer.ai/posts/colbert-pooling.html" rel="nofollow">Hierarchical token pooling</a> clusters similar document vectors in a given multi-vector embedding and replaces each cluster with its mean, hence reducing the number of vectors stored for each page.</li>
<li><a href="https://www.mixedbread.com/blog/asymmetric-quant" rel="nofollow">Asymmetric quantization</a> quantizes document embeddings to int8 or binary. Because query embeddings are not stored and only generated on-the-fly, they can be kept at a higher precision.</li>
</ol>
<p>We tested this setup on ViDoRe v3. With a pooling factor 10 and int8 queries and documents, storage decreased from about 1.5 MB to 39 kB per page, a 39× reduction, while keeping more than 99% of the baseline nDCG@10. A more aggressive configuration uses pooling factor 8, int8 queries, and binary documents. That version uses 6 kB per page (255× smaller) and keeps more than 95% of the original retrieval quality.</p>
<figure>
  <img src="https://github.com/tonywu71/colpali-cookbooks/blob/481c6ec8866f6f5d39d2d9dd06b5547c2d9a67fa/assets/neomme/compression-frontier-260m.webp?raw=true" alt="Quality and storage frontier for the NeoMME-260M late-interaction index">
  <figcaption>Quality and storage frontier for the <em>NeoMME</em>-260M late-interaction index on ViDoRe v3. Labels show pool factor, retained quality, compression, and storage.</figcaption>
</figure>

<p>Users can pick a compression setting from that frontier based on storage budget and required retrieval quality.</p>
<h4 class="relative group flex items-baseline">
	<a id="fast-inference-for-cheaper-multimodal-corpus-indexing" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#fast-inference-for-cheaper-multimodal-corpus-indexing" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Fast inference for cheaper multimodal corpus indexing
	</span>
</h4>
<p>Before you can search a corpus, a retriever model must turn your documents into embeddings, which will be stored in a vector store like Qdrant, Weaviate, or Milvus. Faster encoding makes building and adding new documents to the index faster, thus reducing the GPU uptime and compute cost required.</p>
<p>So we measured image encoding speeds for <em>NeoMME</em>-Retriever against other multimodal document retrievers. We used preprocessed image tensors and calibrated the batch size separately for each model and image size. At a matched 2048×2048 input size on one NVIDIA L40S, <em>NeoMME</em>-Retriever-260M encodes about 51 pages per second, nearly twice ColModernVBERT's 26 pages per second. Both 260M and 800M <em>NeoMME</em>-Retriever models are also faster than the other models we compared on smaller input images.</p>

  <img src="https://github.com/tonywu71/colpali-cookbooks/blob/c5e737e7e474363822b6f2d95290c0120e0fa993/assets/neomme/indexing-throughput-l40s.webp?raw=true" alt="Document-encoding throughput across image resolutions on an NVIDIA L40S">
  <figcaption>Document-encoding throughput by retriever and input resolution on one NVIDIA L40S.</figcaption>

<h3 class="relative group flex items-baseline">
	<a id="fine-tuning-with-sentence-transformers" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#fine-tuning-with-sentence-transformers" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Fine-tuning with Sentence Transformers
	</span>
</h3>
<p>We provide separate <a href="https://huggingface.co/Hcompany/NeoMME-260M-Retriever-ST-dense">dense</a> and <a href="https://huggingface.co/Hcompany/NeoMME-260M-Retriever-ST-late">late-interaction</a> checkpoints for fine-tuning with <a href="https://huggingface.co/blog/multi-vector-encoder">Sentence Transformers v6</a>. Following the same pattern as text encoders such as ModernBERT, Sentence Transformers loads the backbone through <a href="https://huggingface.co/docs/transformers/main/en/model_doc/neomme#transformers.NeoMMEModel"><code>NeoMMEModel</code></a> rather than the dual-head <a href="https://huggingface.co/docs/transformers/main/en/model_doc/neomme#transformers.NeoMMEForRetrieval"><code>NeoMMEForRetrieval</code></a> class. Sentence Transformers currently supports one retrieval head per model, so each checkpoint lets you fine-tune the dense or late-interaction head independently. To train both heads together, use <code>NeoMMEForRetrieval</code> with a custom <code>Trainer</code>.</p>
<h3 class="relative group flex items-baseline">
	<a id="from-retrieval-to-visual-rag" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#from-retrieval-to-visual-rag" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		From retrieval to visual RAG
	</span>
</h3>
<p>Visual document retrieval can be used as the first stage of a visual retrieval-augmented generation (RAG) system. Unlike text RAG, which retrieves extracted text chunks, visual RAG retrieves the original page images and sends them to a visual language model. The model can then use tables, plots, diagrams, and page layout that text extraction may flatten or omit. Here is how visual RAG works:</p>
<ol>
<li>Indexing: Convert each PDF page to an image, generate an embedding with a retrieval model, and store the embeddings in a vector store.</li>
<li>Retrieval: Generate an embedding for the user's query with the same model and retrieve the top-k most relevant pages.</li>
<li>Generation: Append the images after the query in the chat message (<em>e.g.</em>, <code>{query}{img_1}{img_2}...{img_k}</code>) and send it to a VLM to generate the answer.</li>
</ol>
<p>You can test visual RAG directly with <em>NeoMME</em>-Retriever in our HF Space: 🤗 <a href="https://huggingface.co/spaces/tonywu71/neomme-retriever-demo">tonywu71/neomme-retriever-demo</a>.</p>

<h2 class="relative group flex items-baseline">
	<a id="conclusion" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#conclusion" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Conclusion
	</span>
</h2>
<p><em>NeoMME</em> replaces separate pretrained image and text encoders with one long-context bidirectional Transformer. We train it from scratch to process both multilingual text tokens and raw 32×32 image patches.</p>
<p><em>NeoMME</em>-Retriever is a fine-tuned version of <em>NeoMME</em> for visual document retrieval. One forward pass produces both dense and late-interaction representations. The 260M model outperforms all evaluated models strictly below 800M parameters and, at a matched 2048×2048 input size, encodes pages at about 2× ColModernVBERT's throughput. To reduce the large storage footprint of late-interaction embeddings for high-resolution documents, we experimented with hierarchical token pooling and asymmetric quantization and managed to reduce the late-interaction embeddings from roughly 1.5 MB to 6 kB per page, a 255× compression, while retaining more than 95% of the baseline nDCG@10.</p>
<p>We release all <em>NeoMME</em> model checkpoints and a day-zero Hugging Face Transformers implementation to allow practitioners to build efficient multimodal and multilingual representation models on top of our work.</p>
