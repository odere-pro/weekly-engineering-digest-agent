<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]-->Beam by Reflection is out on Hugging Face! It is the first model from the new US lab, Reflection, and it’s open! It's a mixture-of-experts (MoEs) model with 501B parameters (23B active per token), supports text as input, has a <strong>context window of 1M tokens</strong>, and is released under the Apache 2.0 license.</p>
<p>Beam is focused on <em>coding</em> and <em>agentic</em> use cases. It is for teams that want a frontier-scale model on their own hardware, infrastructure, or cloud, and want to customize it to their own use cases. Beam ships with its own dedicated open source Rust based harness that delivers the best performance from the model.</p>
<p>Beam has a native transformers implementation, as well as downstream libraries like vLLM and SGLang. We’ve worked with the Reflection team to bring you inference, SFT (supervised fine tuning), and RL (reinforcement learning) recipes for you to build with this model for your needs. On top of day-0 support in transformers, SGLang and vLLM, this post shows you how to run it, how to post-train it, and what we built with it.</p>
<p><strong>TL;DR</strong></p>
<blockquote>
<ul>
<li>501B-parameter MoEs LLM with 23B active per token. 52 layers, 256 experts per MoE layer, 8 routed per token.</li>
<li>Text in, text out with <strong>context window of 1M tokens.</strong></li>
<li>Checkpoint formats: <a href="https://huggingface.co/reflection/Beam-1.0-501B-A23B"><strong>BF16</strong></a><strong>, <a href="https://huggingface.co/reflection/Beam-1.0-501B-A23B-FP8">FP8</a>,</strong> and <a href="https://huggingface.co/reflection/Beam-1.0-501B-A23B-NVFP4"><strong>NVFP4</strong></a></li>
<li>Reasoning that can stay in context across turns (<code>preserve_thinking</code>), tool calling with a dedicated grammar. The model supports five reasoning values: "low", "medium" (default), "high", "xhigh", and "max".</li>
<li>Response template in the tokenizer.</li>
<li>Speculative decoding drafter model with DFlash2</li>
<li>Day-0 libraries: transformers, SGLang, vLLM. Full-parameter RL with Miles.</li>
<li>Ships with a <a href="https://developers.reflection.ai/mirror-overview" rel="nofollow">Rust-based custom harness.</a></li>
<li>Apache 2.0.</li>
</ul>
</blockquote>

<h2 class="relative group flex items-baseline">
	<a id="what-is-beam" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#what-is-beam" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		What is Beam?
	</span>
</h2>
<p>Beam is a text-only model built for long-context (1M context length) reasoning and agentic work. It is a sparse MoE model, where each token is computed by a small fraction of the network, so it runs at the speed of a much smaller model while keeping the capacity of a large one.</p>
<img src="https://huggingface.co/buckets/huggingface/Beam-blog-assets/resolve/images/beam-architecture.png" alt="Beam architecture: three dense layers followed by 49 mixture-of-experts layers, with hybrid attention and weighted residual connections." width="624" style="max-width: 100%; height: auto; background-color: white;">

<h3 class="relative group flex items-baseline">
	<a id="attention" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#attention" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Attention
	</span>
</h3>
<p>The decoder has 52 layers with a hidden size of 5,120. Most layers use sliding-window attention over the previous 512 tokens; every sixth layer, and the last one, attend to the full context. That gives 43 sliding-window layers and 9 global ones.</p>
<img src="https://huggingface.co/buckets/huggingface/Beam-blog-assets/resolve/images/beam-attention.png" alt="Attention block with grouped-query attention, RoPE or scalable-softmax query scaling, and a learned sigmoid gate." width="624" style="max-width: 100%; height: auto; background-color: white;">

<p><em>Inside the attention block (both layer types)</em></p>
<p>The two kinds of layers handle position differently. Sliding-window layers use RoPE, since relative position matters most within a short window. <strong>Global layers use no positional encoding</strong>. Instead, each query is multiplied by a scaler that grows slowly with the number of visible tokens, <code>(1 + (pos + 1) / 2048) ** 0.1</code>. It acts as a temperature: the softmax keeps its precision as the context lengthens instead of flattening out. The implementation calls this scalable-softmax query scaling.</p>
<p>Attention uses grouped-query attention with 48 query heads and 8 key-value heads, with RMSNorm on queries and keys. A learned sigmoid gate, computed from the layer input, scales every channel of every head before the output projection.</p>
<h3 class="relative group flex items-baseline">
	<a id="mixture-of-experts" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#mixture-of-experts" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Mixture of Experts
	</span>
</h3>
<p>The first 3 layers use a dense SwiGLU MLP. The other 49 replace it with a Mixture-of-Experts block of 256 experts, each a SwiGLU MLP with an intermediate size of 2,560, or about 39M parameters. The experts hold 98.4% of the model's parameters.</p>
<p>The router follows DeepSeek-V3's group-limited scheme. It scores all 256 experts with a sigmoid, splits them into 8 groups of 32, keeps the 4 best groups (ranked by the sum of each group's top two scores), then picks the top 8 experts inside them. Beam uses the same group sizes as DeepSeek-V3 but no shared expert. Expert outputs are combined with normalized router weights and scaled by 2.5.</p>
<img src="https://huggingface.co/buckets/huggingface/Beam-blog-assets/resolve/images/beam-expert-routing.png" alt="Beam router scores 256 experts and selects groups before routing each token to eight experts." width="624" style="max-width: 100%; height: auto; background-color: white;">

<p>Only 8 experts run per token, so the model computes each token with about 23B parameters. All 256 experts stay in memory, so deployment needs the memory of a 501B model but runs at the speed of a 23B one. The BF16 checkpoint is about 1 TB in safetensors format. The NVFP4 checkpoint stores most parameters in 4-bit precision for NVIDIA Blackwell GPUs, some parameters are kept in BF16 for accuracy. There are also FP8 checkpoints on the hub which are ideal for Hopper and Ampere series chips.</p>
<p>If you want to deploy Beam yourself, check out the vLLM or SGLang recipes below.</p>
<h3 class="relative group flex items-baseline">
	<a id="residual-stream" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#residual-stream" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Residual Stream
	</span>
</h3>
<p>The residual connections are the most distinctive part. A standard transformer adds each sublayer output to the stream with weight 1, so the stream grows with depth.</p>
<img src="https://huggingface.co/buckets/huggingface/Beam-blog-assets/resolve/images/standard-residual-stream.png" alt="Standard transformer residual stream adds each sublayer output with weight one." width="624" style="max-width: 100%; height: auto; background-color: white;">

<p>Beam counts the input embedding as step 1. At step <code>k</code> it adds the sublayer output with weight <code>1/sqrt(k)</code> and keeps the existing stream with weight <code>sqrt((k-1)/k)</code>. The squares of the two weights sum to one, so the stream stays at a constant scale from the first layer to the last. After all 104 additions, every sublayer output and the input embedding carry the same weight in the final hidden state.</p>
<img src="https://huggingface.co/buckets/huggingface/Beam-blog-assets/resolve/images/beam-residual-stream.png" alt="Beam residual stream uses depth-dependent weights to keep the accumulated hidden state at a constant scale." width="624" style="max-width: 100%; height: auto; background-color: white;">

<p>Every sublayer is also normalized before and after, and the final logits pass through a tanh softcap at ±30, computed in FP32. The implementation fixes where it computes in FP32: the router, the SwiGLU product, the norms, RoPE, the query scaling and the softcap.</p>
<h3 class="relative group flex items-baseline">
	<a id="long-context" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#long-context" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Long Context
	</span>
</h3>
<p>Hybrid attention works well for long contexts. Each layer caches 2 x 8 KV heads x 128 dims = 2,048 values per token. If all 52 layers kept every token, the cache would grow by 208 KiB per token. Only the 9 global layers keep the whole sequence. The 43 sliding-window layers hold a fixed 512-token window each and stop growing. So the cache grows by 36 KiB per token, roughly a sixth of the naive rate.</p>

<h2 class="relative group flex items-baseline">
	<a id="hardware-requirements" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#hardware-requirements" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Hardware Requirements
	</span>
</h2>
<p>The most practical way to serve the model is serving the NVFP4 checkpoint, which retains most of the quality of the bf16 checkpoint.  NVFP4 stores some weights in 4 bits, and this way, it shrinks the 501B parameters in BF16 from 1 TB to ~280 GB. Blackwell GPUs run NVFP4 natively but GPUs older than Blackwell like the H200 can't. The FP8 checkpoints are suitable for GPUs older than Blackwell.</p>
<p>A B200 has 180 GB of HBM3e, so two of them (360 GB) can hold the Beam weights, with little room left for activations and the KV cache. Plan for four B200s (720 GB), which leaves plenty of room for long contexts and concurrent requests. You can also serve it on a full 8xB200 node, or on two B300s at 288 GB each, or even 8xRTX Pro 6000. If you don't have Blackwell hardware, use Inference Providers (serverless) to test Reflection.</p>

	<a id="inference-support" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#inference-support" rel="nofollow">

	</a>
	<span>
		Inference Support
	</span>
</h2>
<p>Beam comes with day-0 support in transformers, SGLang and vLLM.</p>
<h3 class="relative group flex items-baseline">
	<a id="transformers" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#transformers" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Transformers
	</span>
</h3>
<p>Install the latest version of transformers.</p>
<pre><code class="language-sh">pip install -U <span class="hljs-string">"transformers&gt;=5.20.1"</span>
</code></pre>
<p>The easiest way to run Beam is the text-generation pipeline:</p>
<pre><code class="language-py"><span class="hljs-keyword">from</span> transformers <span class="hljs-keyword">import</span> pipeline

pipe = pipeline(
    <span class="hljs-string">"text-generation"</span>, model=<span class="hljs-string">"reflection/Beam-1.0-501B-A23B"</span>, device_map=<span class="hljs-string">"auto"</span>
)

messages = [
    {<span class="hljs-string">"role"</span>: <span class="hljs-string">"user"</span>, <span class="hljs-string">"content"</span>: <span class="hljs-string">"Write a limerick about Python exceptions."</span>}
]
output = pipe(messages, max_new_tokens=<span class="hljs-number">2000</span>)
output[<span class="hljs-number">0</span>][<span class="hljs-string">"generated_text"</span>][-<span class="hljs-number">1</span>]
</code></pre>
<p>The pipeline returns the whole chat. The last message is Beam's reply, already parsed by the response template.</p>
<p>Going one level lower, use <code>AutoModelForCausalLM</code> and <code>AutoTokenizer</code>.</p>
<pre><code class="language-py"><span class="hljs-keyword">from</span> transformers <span class="hljs-keyword">import</span> AutoModelForCausalLM, AutoTokenizer

model_id = <span class="hljs-string">"reflection/Beam-1.0-501B-A23B"</span>
tokenizer = AutoTokenizer.from_pretrained(model_id)

model = AutoModelForCausalLM.from_pretrained(
    model_id, dtype=<span class="hljs-string">"auto"</span>, device_map=<span class="hljs-string">"auto"</span>
)
</code></pre>
<h4 class="relative group flex items-baseline">
	<a id="chat" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#chat" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Chat
	</span>
</h4>
<pre><code class="language-py">messages = [
    {<span class="hljs-string">"role"</span>: <span class="hljs-string">"system"</span>, <span class="hljs-string">"content"</span>: <span class="hljs-string">"You should only answer with a number."</span>},
    {<span class="hljs-string">"role"</span>: <span class="hljs-string">"user"</span>, <span class="hljs-string">"content"</span>: <span class="hljs-string">"What is 17 * 23?"</span>},
]

inputs = tokenizer.apply_chat_template(
    messages,
    add_generation_prompt=<span class="hljs-literal">True</span>,
    tokenize=<span class="hljs-literal">True</span>,
    return_dict=<span class="hljs-literal">True</span>,
    return_tensors=<span class="hljs-string">"pt"</span>,
    reasoning_effort=<span class="hljs-string">"medium"</span> <span class="hljs-comment"># by default</span>
).to(model.device)

input_len = inputs[<span class="hljs-string">"input_ids"</span>].shape[-<span class="hljs-number">1</span>]

outputs = model.generate(**inputs, max_new_tokens=<span class="hljs-number">2000</span>)

tokenizer.parse_response(
    outputs[<span class="hljs-number">0</span>][input_len:], prefix=inputs[<span class="hljs-string">"input_ids"</span>][<span class="hljs-number">0</span>]
)
</code></pre>
<p>Beam's tokenizer carries a response template. <code>parse_response</code> reads it and turns the raw output into a message dict, with the reasoning, the answer, and any tool calls in separate fields. This avoids the usual regex for splitting reasoning from answers from tool calls. And the rules ship with the tokenizer, so the parsed structure matches what Beam was trained to produce. The chat template can pre-write part of the assistant turn, which the parser needs to see.</p>
<h4 class="relative group flex items-baseline">
	<a id="tool-calling" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#tool-calling" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Tool calling
	</span>
</h4>
<details>
<summary>Complete tool-calling example</summary>

<pre><code class="language-py"><span class="hljs-keyword">def</span> <span class="hljs-title function_">get_weather</span>(<span class="hljs-params">city: <span class="hljs-built_in">str</span>, unit: <span class="hljs-built_in">str</span> = <span class="hljs-string">"celsius"</span></span>):
    <span class="hljs-string">"""</span>
<span class="hljs-string">    Get the current weather for a city.</span>
<span class="hljs-string"></span>
<span class="hljs-string">    Args:</span>
<span class="hljs-string">        city: The city to look up.</span>
<span class="hljs-string">        unit: Temperature unit, "celsius" or "fahrenheit".</span>
<span class="hljs-string">    """</span>
    ...

tools = [get_weather]
messages = [
    {<span class="hljs-string">"role"</span>: <span class="hljs-string">"user"</span>, <span class="hljs-string">"content"</span>: <span class="hljs-string">"I land in Paris tonight. Do I need a coat?"</span>}
]

inputs = tokenizer.apply_chat_template(
    messages,
    tools=tools,
    add_generation_prompt=<span class="hljs-literal">True</span>,
    tokenize=<span class="hljs-literal">True</span>,
    return_dict=<span class="hljs-literal">True</span>,
    return_tensors=<span class="hljs-string">"pt"</span>,
).to(model.device)

input_len = inputs[<span class="hljs-string">"input_ids"</span>].shape[-<span class="hljs-number">1</span>]
outputs = model.generate(**inputs, max_new_tokens=<span class="hljs-number">1000</span>)

message = tokenizer.parse_response(
    outputs[<span class="hljs-number">0</span>][input_len:], prefix=inputs[<span class="hljs-string">"input_ids"</span>][<span class="hljs-number">0</span>], tools=tools
)
message.get(<span class="hljs-string">"tool_calls"</span>)
</code></pre>
</details>

<p>Pass <code>tools</code> to <code>parse_response</code> as well. Beam writes tool-call arguments inline, in its own XML-style grammar, so a bare <code>7</code> could be a number or a string. With the tool schemas, the parser casts each argument to its declared type.</p>
<h4 class="relative group flex items-baseline">
	<a id="multi-gpu-and-multi-node" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#multi-gpu-and-multi-node" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Multi-GPU and multi-node
	</span>
</h4>
<p>Beam's config defines an expert-parallel plan. Expert parallelism puts each expert on one device. Attention, the dense layers, the embeddings and the LM head are replicated on every device. That is 8B parameters, or 16 GB in BF16. Load the model with a <code>DistributedConfig</code>:</p>
<pre><code class="language-py"><span class="hljs-keyword">import</span> os

<span class="hljs-keyword">from</span> transformers <span class="hljs-keyword">import</span> AutoModelForCausalLM
<span class="hljs-keyword">from</span> transformers.distributed <span class="hljs-keyword">import</span> DistributedConfig

model = AutoModelForCausalLM.from_pretrained(
    <span class="hljs-string">"reflection/Beam-1.0-501B-A23B"</span>,
    distributed_config=DistributedConfig(
        tp_size=<span class="hljs-built_in">int</span>(os.environ[<span class="hljs-string">"WORLD_SIZE"</span>]), ep_size=<span class="hljs-built_in">int</span>(os.environ[<span class="hljs-string">"WORLD_SIZE"</span>]), tp_plan={}
    ),
)
</code></pre>
<p>Launch the script with <code>torchrun</code> across 16 H200 GPUs. Each one then holds 78 GB of weights. With 8 GPUs each would hold 139 GB, which leaves no room on a 141 GB H200. The number of devices must divide the number of experts, 256.</p>
<h3 class="relative group flex items-baseline">
	<a id="vllm" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#vllm" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		vLLM
	</span>
</h3>
<p>Beam has day-0 support in vLLM. The command below serves the BF16 checkpoint with tensor parallelism across 16 GPUs (two 8x H200 nodes) and exposes an OpenAI-compatible API:</p>
<pre><code class="language-sh">vllm serve reflection/Beam-1.0-501B-A23B --tensor-parallel-size 16 --served-model-name beam
</code></pre>
<p>For faster generation, add DFlash2 speculative decoding. A small drafter model proposes up to 15 tokens ahead, and Beam checks them all in one forward pass, so each step can accept several tokens. The cost is a little extra memory for the drafter:</p>
<pre><code>vllm serve reflection/Beam-1.0-501B-A23B \
  --tensor-parallel-size 16 \
  --speculative-config '{ "method": "dflash", "model": "reflection/dflash2-drafter-preview", "num_speculative_tokens": 15 }'
</code></pre>
<p>Both commands start an OpenAI-compatible server, so you can point any OpenAI client at <code>http://localhost:8000/v1</code>. For additional serving configurations, see the <a href="https://github.com/vllm-project/recipes/pull/1132" rel="nofollow">proposed Beam recipe for vLLM</a>.</p>
<h3 class="relative group flex items-baseline">
	<a id="sglang" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#sglang" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		SGLang
	</span>
</h3>
<p>Beam also has day-0 support in SGLang. We recommend serving it with DFlash2 speculative decoding, which both commands below turn on. On Blackwell, the NVFP4 checkpoint fits on 4 B300s:</p>
<pre><code class="language-sh">python -m sglang.launch_server \
--model-path reflection/Beam-1.0-501B-A23B-NVFP4 \
--served-model-name beam \
--tp 4 \
--attention-backend trtllm_mha \
--page-size 64 \
--context-length 1048576 \
--mem-fraction-static 0.85 \
--enable-unified-memory \
--speculative-algorithm DFLASH \
--speculative-draft-model-path reflection/Beam-1.0-501B-A23B-DFlash2 \
--speculative-dflash-block-size 8 \
--tool-call-parser beam --reasoning-parser beam \
--host 0.0.0.0 --port 30000
</code></pre>
<p>On Hopper GPUs, use the FP8 checkpoint on 8 H200s instead. Only three flags change: the checkpoint, the tensor-parallel size (8 instead of 4), and the attention backend (fa3 instead of trtllm_mha, which needs Blackwell):</p>
<pre><code>python -m sglang.launch_server \
--model-path reflection/Beam-1.0-501B-A23B-FP8 \
--served-model-name beam \
--tp 8 \
--attention-backend fa3 \
--page-size 64 \
--context-length 1048576 \
--mem-fraction-static 0.85 \
--enable-unified-memory \
--speculative-algorithm DFLASH \
--speculative-draft-model-path reflection/Beam-1.0-501B-A23B-DFlash2 \
--speculative-dflash-block-size 8 \
--tool-call-parser beam --reasoning-parser beam \
--host 0.0.0.0 --port 30000
</code></pre>

<h2 class="relative group flex items-baseline">
	<a id="post-training-beam" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#post-training-beam" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Post-training Beam
	</span>
</h2>
<p>You can fine tune Beam for your own use cases. Here, we share some examples in TRL and Miles to get you started on supervised fine-tuning and reinforcement learning.</p>
<h3 class="relative group flex items-baseline">
	<a id="sft-with-trl" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#sft-with-trl" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		SFT with TRL
	</span>
</h3>
<p>The quickest way to adapt Beam to your own data is supervised fine-tuning with TRL's SFTTrainer. To keep memory manageable, we train LoRA adapters with PEFT rather than updating all 501B parameters:
We used TRL’s <code>SFTTrainer</code> to adapt Beam to a simple goal: keep its reasoning in the language requested by the user. We fine-tuned on <a href="https://huggingface.co/datasets/HuggingFaceH4/Multilingual-Thinking">Multilingual-Thinking</a> with LoRA, which trains a small set of adapter weights while keeping the base model frozen.</p>
<p>The setup combines model sharding at load time, expert parallelism, FlashAttention 4 and sequence packing. LoRA SFT fits on a single node with 8 B300 GPUs, reaching around 19,000 tokens per second. The corresponding H100 setup uses four nodes.</p>
<p>After one epoch of Multilingual-Thinking, Beam reasoned in the requested language on 16 out of 16 held-out prompts, compared with 3 out of 16 for the base model. This small evaluation measures language adherence, rather than the correctness of the reasoning itself.</p>
<img src="https://huggingface.co/buckets/huggingface/Beam-blog-assets/resolve/images/trl-sft-training.png" alt="Training loss and mean token accuracy over a 500-step LoRA supervised fine-tuning run on one eight-GPU B300 node." width="624" style="max-width: 100%; height: auto; background-color: white;">

<p><em>Training loss (left) and mean token accuracy (right) during a separate 500-step run on a reasoning subset of open-r1/Mixture-of-Thought, using one 8-GPU B300 node. These training metrics are from the official <a href="https://github.com/huggingface/trl/pull/7629" rel="nofollow">TRL example PR</a>.</em></p>
<h3 class="relative group flex items-baseline">
	<a id="grpo-with-miles" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#grpo-with-miles" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		GRPO with Miles
	</span>
</h3>
<p>Reflection and RadixArk built a recipe that trains the model with GRPO in Miles, in BF16. You can update the full model or use LoRA to train adapters while keeping the base weights frozen. Megatron trains, SGLang generates the rollouts, and Miles publishes the new weights to the rollout engines after each update. We reviewed the recipe.</p>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="left">Workload</th>
<th align="left">Reference configuration</th>
</tr>

		</thead><tbody><tr>
<td align="left">Inference / eval, BF16</td>
<td align="left">16x H200 per engine</td>
</tr>
<tr>
<td align="left">Full-parameter GRPO, BF16 (Miles)</td>
<td align="left">96x H200: 64 train, 32 rollout. Or 64x H200 colocated.</td>
</tr>
<tr>
<td align="left">LoRA GRPO, BF16 (Miles)</td>
<td align="left">32x H200: 16 train, 16 rollout.</td>
</tr>
<tr>
<td align="left">Full-parameter GRPO, BF16, 128-token context (Miles)</td>
<td align="left">48x H200: 32 train, 16 rollout. The setup Reflection and RadixArk first validated on the real checkpoint.</td>
</tr>
</tbody>
	</table>
</div>
<p>The recipe runs GRPO on DAPO-Math-17K and evaluates on AIME25. Build the image, download the data, and submit the job to a Ray cluster of twelve 8x H200 nodes:</p>
<pre><code class="language-sh">docker build -f docker/Dockerfile.beam -t miles-beam .

python scripts/run_beam.py prepare \
  --model-id reflection/Beam-1.0-501B-A23B \
  --model-dir /root/models/Beam \
  --data-dir /data/datasets

<span class="hljs-built_in">export</span> MASTER_ADDR=10.0.0.1
<span class="hljs-built_in">export</span> RAY_ADDRESS=http://<span class="hljs-variable">${MASTER_ADDR}</span>:8265

python scripts/run_beam.py execute \
  --model-dir /root/models/Beam \
  --data-dir /data/datasets \
  --output-dir /root/shared_data/beam-run \
  --num-rollout 100
</code></pre>
<p>What happens in a rollout:</p>
<p><strong>Sample:</strong> 32 prompts are passed to the model with 8 responses each. Two SGLang engines serve the rollouts on 16 GPUs each.</p>
<p><strong>Score:</strong> the boxed answer is checked against the label, with a soft penalty for responses near the length limit.</p>
<p><strong>Update:</strong> one optimizer step on all 256 samples. Group-relative advantages with truncated importance sampling, no KL or entropy penalty.</p>
<p><strong>Train in parallel:</strong> tensor parallelism 8, expert parallelism 8, data parallelism 8, with sequence parallelism and full recompute.</p>
<p><strong>Optimizer:</strong> Adam at a constant 1e-6. Gradients in BF16, master weights in FP32, moments in BF16. The optimizer state streams through node-local NVMe, so each trainer node needs 2 TB of scratch.</p>
<p><strong>Evaluate:</strong> AIME25 every five rollouts, eight samples per problem. A checkpoint is saved every twenty.</p>
<img src="https://huggingface.co/buckets/huggingface/Beam-blog-assets/resolve/images/miles-grpo-aime2025.png" alt="Full-parameter GRPO evaluation on AIME 2025: accuracy increases from 46.25% to 55.8% with a 4,000-token output limit." width="624" style="max-width: 100%; height: auto; background-color: white;">

<p>The next rollout is generated while the current one trains, so responses are one update behind. Add <code>--resume</code> to continue from the last checkpoint. <code>execute-colocate</code> runs the same recipe on eight nodes, with every GPU training and serving in turn.</p>
<h3 class="relative group flex items-baseline">
	<a id="train-with-lora" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#train-with-lora" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Train with LoRA
	</span>
</h3>
<p>You can also run GRPO with LoRA on four 8× H200 nodes: 16 GPUs for training and 16 for rollouts. The recipe trains rank-16 adapters on Beam’s attention, dense MLP, and expert layers while keeping the base weights frozen. Only adapter weights are synchronized with SGLang, and the optimizer state stays in GPU memory, removing the need for NVMe optimizer offloading.</p>
<pre><code class="language-sh">python scripts/run_beam_lora.py execute \
  --model-dir /root/models/Beam \
  --data-dir /data/datasets \
  --output-dir /root/shared_data/beam-run \
  --num-rollout 100
</code></pre>
<img src="https://huggingface.co/buckets/huggingface/Beam-blog-assets/resolve/images/miles-lora-grpo-aime2025.png" alt="LoRA GRPO evaluation on AIME 2025: accuracy rises from 42.9% to 64.2% while mean output length falls from 3,188 to 2,197 tokens." width="624" style="max-width: 100%; height: auto; background-color: white;">

<h3 class="relative group flex items-baseline">
	<a id="hey-beam-build-a-native-local-macos-application" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#hey-beam-build-a-native-local-macos-application" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Hey Beam, build a native local MacOS application!
	</span>
</h3>
<p>At Hugging Face we love open and local models that run native to their hardware, but building native apps on Mac can be hard! Let’s see if Beam can help us out.</p>
<p>We asked Beam to build a native MacOS application that turns speech to text, and conveniently drops it at your cursor. We want to use MLX to get the most out of our Mac Metal and the Parakeet Model for great speech-to-text.</p>
<pre><code>Build BeamSpeak, a native macOS menu bar dictation app with a compact recording pill and no main window or account.

Use ⌘⇧Space to start and stop microphone recording, showing elapsed time, microphone level, and transcription status. Run speech recognition entirely locally using a Hugging Face model, preferably Parakeet v3 through MLX, and keep the model loaded between recordings. Paste the transcript into the original app if it remains focused and Accessibility permission is granted; otherwise copy it to the clipboard, preserving newer clipboard changes and never pressing Enter. Handle permissions, cancellation, silence, errors, a two-minute recording limit, and temporary audio cleanup. Deliver source code, a runnable BeamSpeak.app, setup instructions, and verification of offline transcription, the physical shortcut, microphone capture, and text delivery.
</code></pre>
<p>We used Beam with the Pi coding harness to build the initial native macOS menu bar app, running Parakeet with MLX. The saved run includes follow-up prompts; the final source also includes later Codex repairs. The prompt above is a condensed version of the build requirements.</p>

<h3 class="relative group flex items-baseline">
	<a id="hey-beam-how-do-you-scale-on-multiple-agents" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#hey-beam-how-do-you-scale-on-multiple-agents" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Hey Beam, how do you scale on multiple agents?
	</span>
</h3>
<p>We wanted to see whether Beam could make faster progress by splitting a programming task across agents. We paired Beam with the open-source Pi coding agent and compared three setups: 1. one agent working alone, 2. five persistent peers collaborating through a shared Git repository, and 3. a lead agent delegating work to asynchronous subagents. The harness ran on Hugging Face jobs with inference through Reflection’s platform API.</p>
<p>For the tasks, we used ProgramBench: agents must recreate a program from its compiled executable and documentation, without seeing its source code or the evaluator’s tests. Each setup had the same 8M API-token ceiling and two-hour solver limit per task, shared across its agents. We saved implementation snapshots and evaluated them against fixed hidden-test suites from the <a href="https://huggingface.co/datasets/programbench/ProgramBench-Tests">ProgramBench-Tests dataset</a>.</p>
<p>Our <a href="https://burtenshaw-beam-pi-programbench.hf.space/study" rel="nofollow">score-versus-latency plot</a> shows the average fraction of tests passed. The time axis uses fixed reference rates for model tokens plus measured tool time, rather than elapsed wall time. We initially ran five tasks. The current figure shows a post-hoc subset of jq, xsv, FIGlet, and hexyl; ripgrep was excluded across all three setups because grading its saved artifacts was too slow. The published results retain all 15 original episodes.</p>

<h3 class="relative group flex items-baseline">
	<a id="hey-beam-finetune-a-decision-model-for-my-code-base" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#hey-beam-finetune-a-decision-model-for-my-code-base" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Hey Beam, finetune a decision model for my code base!
	</span>
</h3>
<p>Decision models are all the rage at the moment because they’re super fast and practical for many use cases. We started with Beam in Pi after Beam’s quota ran out to train and evaluate a custom decision model for developer incident triage.</p>
<p>We wanted to see whether a coding agent could turn an incident-triage policy into a small, fast decision model. The task was to read a developer incident and choose the responsible team, its severity, and whether someone should be pinged immediately. Using Unsloth, we fine-tuned Qwen3.5-0.8B to score these choices directly.</p>
<p>First, the workflow built a synthetic dataset containing 2.3k incidents split by incident cluster for training, calibration, and testing. We trained a LoRA adapter and decision head for three epochs, with a 4-bit backbone, on one H100 80GB on the Science Slurm cluster.</p>
<p>For a baseline, we prompted the unadapted model with the full triage policy and ticket, without examples, and asked it to generate the three decisions as JSON. On the same 320 synthetic test tickets, the fine-tuned decision model got all three answers correct on 76.25%, versus 4.69% for prompted zero-shot. Mean ticket latency fell from 1,218.06 ms to 102.58 ms, an 11.9× speedup.</p>
<img src="https://huggingface.co/buckets/huggingface/Beam-blog-assets/resolve/images/decision-model-results.png" alt="Incident triage decision model: accuracy rises from 4.69% to 76.25% and mean latency falls from 1,218.06 ms to 102.58 ms." width="624" style="max-width: 100%; height: auto; background-color: white;">

<p>If you want to try out this experiment for yourself, check out the <a href="https://huggingface.co/buckets/burtenshaw/qwen35-incident-triage-reproduction">artifact bucket</a> which contains the data, code, checkpoints and results.</p>
