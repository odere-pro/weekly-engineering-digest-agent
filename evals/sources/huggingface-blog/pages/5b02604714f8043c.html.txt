<blockquote>
<p><em>What you cannot profile, you cannot optimize.</em></p>
</blockquote>
<p>Whether you are trying to squeeze more tokens per second out of a Large Language Model (LLM), shave milliseconds off inference, or just understand why your training loop runs slower than the spec sheet promises, the path eventually runs through profiling.</p>
<p>The catch is that profiling has a <strong>steep</strong> on-ramp. The traces are dense walls of colored rectangles. The events carry intimidating names. Most tutorials assume you can already read them. So even when we <em>know</em> we should be profiling, opening a trace can feel like a chore best left for later (or for someone else). This post, and the series it kicks off, is our attempt to lower that on-ramp.</p>
<div style="border: 1px solid #1f5c48; border-radius: 6px; padding: 1.5rem 2rem; background: #17211f; color: #ddd; font-size: 1.1rem; line-height: 1.7;">

  <p>
    This is the opening post of Profiling in PyTorch, a series where we slowly build the skill of reading profiler traces and use it to drive optimization:
  </p>

  <ol>
    <li>
      <a href="https://huggingface.co/blog/torch-profiler" style="color: #10b981;">
        Profiling in PyTorch (Part 1): A Beginner's Guide to torch.profiler
      </a>
      <em style="color: #aaa;">(current)</em>
    </li>
    <li>
      <a href="https://huggingface.co/blog/torch-mlp-fusion" style="color: #10b981;">
        Profiling in PyTorch (Part 2): From nn.Linear to a Fused MLP
      </a>
    </li>
    <li>
      <a href="https://huggingface.co/blog/torch-attention-profile" style="color: #10b981;">
        Profiling in PyTorch (Part 3): Attention is all you profile
      </a>
    </li>
  </ol>

</div>

<p>We document the journey from a beginner's point of view. No prerequisites apart from basic PyTorch. Treat this as a leisurely read with some "Aha!" moments. The structure of the post is intentionally question-led: we open a trace, ask "wait, why is <em>that</em> happening?", and chase the answer until something clicks. By the end you should know:</p>
<ul>
<li>how to set up <code>torch.profiler</code> and what it actually hands back,</li>
<li>how to read the profiler table and the trace (CPU lane, GPU lane, and the suspicious gaps in between),</li>
<li>the chain of events from a Python call all the way down to a CUDA kernel,</li>
<li>what changes (and, more interestingly, what does <strong>not</strong> change) when you slap <code>torch.compile</code> on top.</li>
</ul>
<p>Before we begin, two definitions that will make everything below read better:</p>
<ol>
<li>A GPU <strong>kernel</strong> is a program that runs in parallel on many threads of the GPU.</li>
<li>The CPU <strong>schedules and launches</strong> these kernels.</li>
</ol>
<p>You don't usually have to write GPU kernels yourself; when you use a PyTorch operation, it is automatically translated to one or more kernels that do the job on GPU.</p>
<p>With those two ideas in your back pocket, let's start asking questions.</p>
<blockquote class="note">
<p>Here is the entire script that we use for the post: <a href="https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py"><code>01_matmul_add.py</code></a>. We recommend opening this script in a separate tab and walk through the code step by step. We use the <code>NVIDIA A100-SXM4-80GB</code> GPU to run the scripts. It is really easy to setup a GPU on the Hugging Face infrastructure and experiment with the scripts using the <a href="https://huggingface.co/docs/hub/spaces-dev-mode">Dev Mode with Spaces</a>. One could also run the scripts with the <a href="https://huggingface.co/docs/huggingface_hub/en/guides/jobs">Hugging Face Jobs pipeline</a>.<br>(Note: The traces in this blog were generated using PyTorch 2.13. If you are using a different version, some trace details like CompiledFxGraph might differ or be absent.)</p>
</blockquote>
<h2 class="relative group flex items-baseline">
	<a id="the-matrix-multiplication-and-addition-operation" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-matrix-multiplication-and-addition-operation" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The matrix multiplication and addition operation
	</span>
</h2>
<p>As correctly <a href="https://youtu.be/7knwihgj0fU?si=uvzGH-J9bsCHP4Nn&amp;t=2199" rel="nofollow">quipped by Dr. Sara Hooker</a>, just as we are primarily made up of water, Deep Neural Networks are primarily made up of matrix multiplies. As fundamental as they are, it would be a shame to start our profiling journey with anything else.</p>
<pre><code class="language-py"><span class="hljs-keyword">def</span> <span class="hljs-title function_">fn</span>(<span class="hljs-params">x, w, b</span>):
  <span class="hljs-keyword">return</span> torch.add(torch.matmul(x, w), b)
</code></pre>
<blockquote>
<p>The matrix addition along with the matrix multiplication mimics how weights and biases interact in a neuron. This addition (pun intended) will help us understand how it paves the way for compilation <a href="#lets-see-some-torch-compile-at-work" rel="nofollow">later in the post</a>.</p>
</blockquote>
<p>To profile, we will be using the <code>torch.profiler</code> module. The steps involved are:</p>
<ol>
<li>Have the <a href="https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L26-L27">code to profile ready</a> (here <code>def fn</code>, which wraps the matrix multiplication and matrix addition)</li>
<li><a href="https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L32">Annotate</a> the algorithm. While this is completely optional, we recommend doing this. The <code>record_function</code> annotates our function as <code>matmul_add</code>, which will be easy to navigate in the traces (as we note later)</li>
</ol>
<pre><code class="language-py"><span class="hljs-keyword">def</span> <span class="hljs-title function_">step</span>():
  <span class="hljs-keyword">with</span> torch.profiler.record_function(<span class="hljs-string">"matmul_add"</span>):
    <span class="hljs-keyword">return</span> fn(x, w, b)
</code></pre>
<ol start="3">
<li>Wrap the code with the <code>torch.profiler.profile</code> <a href="https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L53-L62">context manager</a></li>
</ol>
<pre><code class="language-py">  <span class="hljs-keyword">with</span> torch.profiler.profile(
    activities=[
        torch.profiler.ProfilerActivity.CPU,  <span class="hljs-comment"># the cpu activities</span>
        torch.profiler.ProfilerActivity.CUDA, <span class="hljs-comment"># the gpu activities</span>
    ],
  ) <span class="hljs-keyword">as</span> prof:
    <span class="hljs-comment"># it is recommended to run events multiple times to warm up the GPUs</span>
    <span class="hljs-keyword">for</span> _ <span class="hljs-keyword">in</span> <span class="hljs-built_in">range</span>(<span class="hljs-number">5</span>):
      step()
      prof.step()
</code></pre>
<ol start="4">
<li>Export the <a href="https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L70">profile</a></li>
</ol>
<pre><code class="language-py"><span class="hljs-comment"># the profiler table</span>
prof.key_averages().table(sort_by=<span class="hljs-string">"cuda_time_total"</span>, row_limit=<span class="hljs-number">15</span>)

<span class="hljs-comment"># the profiler trace</span>
prof.export_chrome_trace(trace_path)
</code></pre>
<p>The profiler exports two distinct artifacts:</p>
<ol>
<li>The profiler table: Provides the statistical summary of the algorithm. It answers "What is taking the most time". This becomes really helpful to figure out hotspots. A hotspot would be events that take the most amount of time, can be a bottleneck of the pipeline, or an event that is triggered a lot of times.</li>
<li>The profiler trace: Provides the temporal execution view. Answers "When and Why an operation happened", depicting the activities taking place on the CPU and the GPU. This is helpful when we want to investigate the kernel(s) that were launched, any delays in launching them, any overlap between CPU and GPU activities, etc.</li>
</ol>
<p>Let's see the two in action with our first execution. (<a href="https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py">Here is the entire <code>01_matmul_add.py</code> script</a>)</p>
<blockquote class="note">
<p>It is recommended to run this script on a machine with a GPU.</p>
</blockquote>
<pre><code class="language-bash">uv run 01_matmul_add.py --size 64
</code></pre>

<p>The <code>.txt</code> file holds the profiler table. Upon opening the file, as shown in Figure 1, one would be greeted with a big table with the first column consisting of the events that were triggered inside the scope of profile.</p>
<p>The other columns are related to the time the event takes on the CPU or GPU or any other device(s) specified in <code>activities</code> within <code>torch.profiler.profile</code>. Look at which events take the most amount of time, and try to intuitively understand if that event should in fact take that time. It is also important to look at the column "# of Calls" which dictates how many times the event was triggered.</p>
<p>While we are at it, let's also talk about "Self CPU/CUDA" vs "CPU/CUDA total". The "Self" columns measure time spent only inside the event itself, excluding its children. The "total" columns include the event and all of its children together. So if you look at the "CPU total" of <code>matmul_add</code>, it consists of the time it took on self plus the children events it triggered. This is an important nuance to note.</p>
<p>If you look at the last two lines out of the table you would notice that the profiler tells us that</p>
<pre><code class="language-bash">Self CPU time total: 2.314ms
Self CUDA time total: 23.104us
</code></pre>
<p>The CPU time is in <code>ms</code> while the GPU time is in <code>us</code>. To put things in perspective, the time spent on GPUs (the kernel <code>ampere_bf16_s16816gemm...</code>) is less than 1% of the time spent on the CPU (the <code>matmul_add</code> operation).  The GPU stays idle most of the time, which is an immediate red flag. The reason this happens is that the GPU can compute a small matmul very quickly, so our code spends most of the time preparing the kernels, launching them on the GPU, sending the data to multiply and gathering the results. This concept is known as an <em>overhead-bound</em> algorithm.</p>
<p>The easiest way to move out of this regime is to use bigger matrix multiplications.</p>
<pre><code class="language-bash">uv run 01_matmul_add.py --size 4096 
</code></pre>

<p>In Figure 12, we see the nested CPU calls. This is an important visualization, where one gets to understand what a chain of dispatch really looks like.</p>
<p>We begin with <code>ProfileStep#&lt;id&gt;</code> which encapsulates the profiling step. Due to us annotating the step, we see the <code>matmul_add</code> row. The <code>matmul_add</code> consists of two <code>aten</code> calls, one for matrix multiplication and one for matrix addition.</p>
<p>The <code>aten::matmul</code> is the <a href="https://github.com/pytorch/pytorch/tree/main/aten/src/ATen" rel="nofollow">ATen-level</a> dispatch that those user-facing PyTorch matmul calls land on. <code>aten::mm</code> is the 2D matrix-matrix multiply backend.</p>
<p>It is very interesting to note how PyTorch calls <code>aten::bmm</code> (batched matrix multiplication) if we add the batch axis to our matrices. Let's take a detour and see the <code>aten::bmm</code> in action.</p>
<pre><code class="language-diff"><span class="hljs-deletion">- x = torch.randn(args.size, args.size, device=device, dtype=dtype)</span>
<span class="hljs-deletion">- w = torch.randn( args.size, args.size, device=device, dtype=dtype)</span>

<h3 class="relative group flex items-baseline">
	<a id="why-does-matmul-have-an-extra-cuda-runtime-call" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#why-does-matmul-have-an-extra-cuda-runtime-call" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Why does matmul have an extra CUDA runtime call?
	</span>
</h3>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="center"><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/cudaoccupancy.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/cudaoccupancy.png" alt="CPU lane showing cudaOccupancyMaxActiveBlocksPerMultiprocessor preceding the matmul cudaLaunchKernel"></a></th>
</tr>

		</thead><tbody><tr>
<td align="center">Figure 14: A CUDA occupancy query fires before the matmul kernel launch</td>
</tr>
</tbody>
	</table>

<p>We notice that for <code>aten::mm</code> there are two CUDA Runtime calls, namely <code>cudaOccupancyMaxActiveBlocksPerMultiprocessor</code> (boxed in Figure 14) and <code>cudaLaunchKernel</code>, while for <code>aten::add</code> there is only the <code>cudaLaunchKernel</code>.</p>
<p><code>cudaOccupancyMaxActiveBlocksPerMultiprocessor</code> is a planning call and is purely CPU side. It asks: "given a kernel function, a chosen block size, and a chosen dynamic shared memory size, how many blocks of this kernel can simultaneously reside on one SM (Streaming Multiprocessor)?"</p>
<p>This begs the question, why do we need planning for matmul and not for add?</p>
<p>To understand this, we have to look at the kernel's resource footprint. If you click on the GPU kernels, you will be able to inspect the resource footprint for the respective kernel.</p>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="center"><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/matmul-footprint.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/matmul-footprint.png" alt="cuBLAS matmul kernel resource footprint: registers, shared memory and block size in Perfetto"></a></th>
<th align="center"><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/add-footprint.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/add-footprint.png" alt="elementwise add CUDA kernel resource footprint with 32 registers and zero shared memory"></a></th>
</tr>

		</thead><tbody><tr>
<td align="center">Figure 15: Matmul footprint</td>
<td align="center">Figure 16: Add footprint</td>
</tr>
</tbody>
	</table>
</div>
<p>In Figure 15, we note that for matrix multiplication the <code>registers per thread</code> and <code>shared memory</code> are dynamic (based on the size of the matrix). cuBLAS ships hundreds of kernel variants, and each has a heuristic-driven launch path that needs runtime information about hardware capacity. The occupancy query is part of that heuristic. Conceptually, we can think of GPU-accelerated matmuls as <a href="https://alvinwan.com/how-to-tile-matrix-multiplication/" rel="nofollow">working on independent tiles</a>: how many tiles we use and how big each tile needs to be depends on the matrices and the hardware. Modern algorithms are way more complicated than that, but this is still a good reference framework.</p>
<p>From Figure 16 we see that the footprint of addition says 32 registers and zero shared memory. That fits trivially. There's nothing to query, because no hardware resource is going to limit occupancy. The kernel is, by design, resource-light.</p>
<blockquote class="note">
<p>You can use this as a quick diagnostic when reading any trace. Scan the CPU lane for <code>cudaOccupancyMaxActiveBlocksPerMultiprocessor</code>. Each occurrence flags a "heavyweight, adaptively launched" kernel, usually a GEMM (GEneral Matrix Multiplication), conv, or similar. The kernels without a preceding occupancy query are the elementwise/reduction crowd that PyTorch launches mechanically.</p>
</blockquote>
<h3 class="relative group flex items-baseline">
	<a id="why-is-cudadevicesynchronize-so-big-178-ms" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#why-is-cudadevicesynchronize-so-big-178-ms" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Why is cudaDeviceSynchronize so big (~1.78 ms)?
	</span>
</h3>
<p><code>cudaDeviceSynchronize</code> blocks the CPU until all GPU work on this device finishes. The profiler emits this sync at the end of the active window to flush events. Without it, kernel timings would be missing.</p>
<p>A 1.78 ms sync covering 26 µs of real GPU work tells you this run was 98% idle. That's the textbook overhead-bound symptom.</p>

<h2 class="relative group flex items-baseline">
	<a id="lets-see-some-torchcompile-at-work" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#lets-see-some-torchcompile-at-work" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Let's see some torch.compile at work
	</span>
</h2>
<p>Working with <code>torch.compile</code> has always amazed us. One writes normal eager PyTorch code, but PyTorch tries to capture tensor-heavy regions, turn them into graphs, optimize them, and run generated code. The default backend is usually <code>TorchInductor</code>, and the broad pipeline is:</p>
<ol>
<li><code>TorchDynamo</code> captures Python execution into an FX graph</li>
<li><code>AOTAutograd</code> prepares forward/backward graphs when gradients are involved</li>
<li><code>Inductor</code> lowers the graph into optimized CPU or GPU code.</li>
</ol>
<p>In this section, we talk about compilation and look at the profiler traces.</p>
<pre><code class="language-bash">uv run 01_matmul_add.py --size 4096 --warmup --compile
</code></pre>
<p>The <code>args.compile</code> flag triggers the following code:</p>
<pre><code class="language-py"><span class="hljs-keyword">def</span> <span class="hljs-title function_">fn</span>(<span class="hljs-params">x, w, b</span>):
  <span class="hljs-keyword">return</span> torch.add(torch.matmul(x, w), b)

fn = torch.<span class="hljs-built_in">compile</span>(fn) <span class="hljs-keyword">if</span> args.<span class="hljs-built_in">compile</span> <span class="hljs-keyword">else</span> fn
</code></pre>

	<span>
		Did we fuse the matmul and add kernels into one?
	</span>
</h3>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="center"><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/fused-ops.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/fused-ops.png" alt="Compiled trace showing aten::addmm replacing the eager aten::add and aten::mm pair"></a></th>

<p>Looking at Figure 20 we ask the question, did we actually fuse the multiplication and addition operations together into one?</p>
<p>This is operator fusion at the graph level. Inductor took our <code>torch.add(torch.matmul(x, w), b)</code> and rewrote it into a single <code>aten::addmm(b, x, w)</code> call. The important thing to note here is that it did <strong>not</strong> produce a <strong>new</strong> fused CUDA kernel. The actual GPU work is still <code>ampere_bf16_s16816gemm_bf16_128x256_ldg8_f2f_stages_64x3_nn</code>, the same cuBLAS kernel eager mode used. So the "fusion" here is at the dispatcher level, not at the kernel level.</p>
<blockquote class="note">
<p>PyTorch provides the <a href="https://docs.pytorch.org/docs/2.12/generated/torch.addmm.html" rel="nofollow"><code>torch.addmm</code></a> function that does what we did in two steps, that is multiply and add. We encourage the reader to look at the traces of this function and comment your observations in the comments below!</p>
</blockquote>
<h3 class="relative group flex items-baseline">
	<a id="torchcompiles-runtime-architecture" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#torchcompiles-runtime-architecture" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		torch.compile's runtime architecture
	</span>
</h3>
<p>While we know in theory what happens when we compile our functions it is equally important to see it in action. Let's look at the CPU-side hierarchy which reflects <code>torch.compile</code>'s runtime architecture.</p>
<p><strong>TorchDynamo Cache Lookup</strong> is where Dynamo checks that the current call still matches what was compiled with the same input shapes, dtypes, devices, and tensor metadata. If anything mismatched, Dynamo would recompile. This cost is paid every call, even after compilation.</p>
<p><strong>Torch-Compiled Region</strong> is the wrapper that "enters" the compiled version. <strong>AOTDispatcher Runtime Wrapper Prologue</strong> is AOT Autograd's runtime wrapper. Even though we don't need gradients here, AOTDispatcher is always in the stack handling tensor metadata, view tracking, and would set up the backward pass if <code>requires_grad</code> were true.</p>
<p><strong>## Call CompiledFxGraph </strong> is where the actual generated code runs. The string after "CompiledFxGraph" is the content hash of the FX graph. It's the same across all three active steps, confirming cache hits.</p>
<blockquote class="tip">
<p>You can find the generated code on disk under <code>/tmp/torchinductor_&lt;user&gt;/fxgraph</code> keyed by this hash, useful when you want to read the Triton/C++ that Inductor actually produced.</p>
</blockquote>
<h3 class="relative group flex items-baseline">
	<a id="do-the-cuda-launches-go-down-by-half" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#do-the-cuda-launches-go-down-by-half" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Do the CUDA launches go down by half?
	</span>
</h3>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="center"><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/memcpy.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/memcpy.png" alt="compiled matmul trace showing Memcpy DtoD and GEMM kernels launched per step"></a></th>
</tr>

		</thead><tbody><tr>
<td align="center">Figure 21: Each compiled step still launches two GPU kernels, a Device-to-Device memcpy and the GEMM</td>
</tr>
</tbody>
	</table>
</div>
<p>Looking at the traces in Figure 21, we were really happy to notice only one <code>cudaLaunchKernel</code> per step. This observation was directly contradicting what we were seeing in the GPU trace. There were still two kernels being launched per step, namely the <code>Memcpy DtoD (Device -&gt; Device)</code> and the GEMM. Going back to the CPU trace, we noticed that we had completely missed the <code>cudaMemcpyAsync</code> dispatch.</p>
<p><code>addmm</code> computes <code>out = α·A·B + β·C</code>, and cuBLAS's GEMM-with-bias-add epilogue writes into a destination buffer that needs to already contain the bias. An epilogues can be thought of all the operations that happen <em>after</em> a GEMM. In the world of deep-learning we constantly come up with GEMM-Epilogues like activations, bias addition, normalization and many more. This is why there are cuBLAS GEMM-with- kernel variants.</p>
<blockquote>
<p>If you use different <code>mode</code>s for <code>torch.compile</code> you would notice different kernel variants being launched. You can try it for yourself and add a comment below about your observations!</p>
</blockquote>
<p>So Inductor-generated code does:</p>
<ul>
<li><code>out = copy(C)</code> ← that's the DtoD memcpy (32 MB, takes ~33 µs)</li>
<li><code>out = α·(A·B) + β·out</code> ← GEMM with <code>α=β=1</code>, fusing the bias add into the writeback</li>
</ul>
<p>The result is mathematically still the same. The bias add isn't free, as we pay a memcpy upfront plus a slightly more expensive GEMM epilogue.</p>
<p>The fusion one might have hoped for, where <code>x·w + b</code> (here <code>out = α·A·B + β·C</code>) collapses into a single kernel with no extra memory traffic, isn't what happened. Inductor preserved the two memory-touching operations, it just relabeled the bias copy as a memcpy and the addition as a GEMM epilogue.</p>
<p>A truly fused implementation would skip the memcpy. That's what FlashAttention-style hand-written kernels do, and what Inductor can do via Triton codegen, but for a <code>4096×4096 bf16 matmul</code>, Inductor evidently decided "use cuBLAS, do the bias via epilogue setup" was the best path.</p>

	<span>
		Trace reading cheatsheet
	</span>
</h2>
<p>A quick reference for the patterns we walked through. The idea is: if you see this in a trace, this is what it usually means.</p>
<h3 class="relative group flex items-baseline">
	<a id="profiler-table" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#profiler-table" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Profiler table
	</span>
</h3>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="left">What you see</th>
<th align="left">What it usually means</th>
</tr>

		</thead><tbody><tr>
<td align="left"><code>Self CPU time total</code> ≫ <code>Self CUDA time total</code> (CPU in ms, GPU in µs)</td>
<td align="left">Overhead-bound. The CPU spends more time dispatching than the GPU spends computing. Make the work bigger (larger matrices, batched ops) or fuse calls.</td>
</tr>
<tr>
<td align="left"><code>Self CPU time total</code> ≈ <code>Self CUDA time total</code>, both in ms</td>
<td align="left">Compute-bound. The GPU is the bottleneck, which is usually what you want.</td>
</tr>
<tr>
<td align="left">One event dominates <code>CUDA total</code></td>
<td align="left">That's your hotspot. Start the optimization there.</td>
</tr>
<tr>
<td align="left">One event has a huge <code># of Calls</code></td>
<td align="left">A potential bottleneck even if each call is cheap. Check whether it can be fused or batched.</td>
</tr>
<tr>
<td align="left"><code>CPU total</code> ≫ <code>Self CPU</code> for a row</td>
<td align="left">Most of the cost lives in children. Drill into the nested events, not the parent.</td>
</tr>
</tbody>
	</table>

<h3 class="relative group flex items-baseline">
	<a id="cpu-lane" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#cpu-lane" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		CPU lane
	</span>
</h3>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="left">What you see</th>
<th align="left">What it usually means</th>
</tr>

		</thead><tbody><tr>
<td align="left">First <code>ProfileStep</code> much wider than the rest</td>
<td align="left">Cold-start overhead: workspace allocation, cuBLAS heuristics, lazy module loading. Add warmup iterations and/or the schedule's <code>warmup</code> argument.</td>
</tr>
<tr>
<td align="left">Big gap between <code>record_function("...")</code> start and the first <code>aten::*</code> inside it</td>
<td align="left">Same cold-start tax, just zoomed in. The annotation entered, but the dispatch hadn't happened yet.</td>
</tr>
<tr>
<td align="left"><code>cudaOccupancyMaxActiveBlocksPerMultiprocessor</code> before a <code>cudaLaunchKernel</code></td>
<td align="left">A heavyweight, adaptively-launched kernel (GEMM, conv, etc.). cuBLAS is asking the driver how many blocks fit on an SM so it can pick a kernel variant.</td>
</tr>
<tr>
<td align="left"><code>cudaLaunchKernel</code> with no preceding occupancy query</td>
<td align="left">An elementwise or reduction kernel with a fixed, resource-light footprint. Nothing to plan.</td>
</tr>
<tr>
<td align="left">A long <code>cudaDeviceSynchronize</code> at the end of the active window</td>
<td align="left">The profiler flushing events. Its duration is mostly the GPU finishing pending work, not a real CPU cost. A sync covering tiny GPU work is a classic overhead-bound symptom.</td>
</tr>
<tr>
<td align="left">A <code>cudaMemcpyAsync</code> you didn't write</td>
<td align="left">Often a hidden Device-to-Device copy. Common when <code>addmm</code> seeds its destination buffer with the bias before the GEMM epilogue.</td>
</tr>
</tbody>
	</table>
</div>
<h3 class="relative group flex items-baseline">
	<a id="gpu-lane" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#gpu-lane" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		GPU lane
	</span>
</h3>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="left">What you see</th>
<th align="left">What it usually means</th>
</tr>

		</thead><tbody><tr>
<td align="left"><code>Activity Buffer Request</code> on the GPU lane</td>
<td align="left">The profiler is allocating/refilling its own event buffer. The first one usually accounts for the initial CPU↔GPU lane offset.</td>
</tr>
<tr>
<td align="left">A gap between two kernels in a single step</td>
<td align="left">Likely another buffer request mid-execution. Confirm by running more iterations: if it appears only once, it's the profiler, not your code.</td>
</tr>
<tr>
<td align="left">The same kernel timing differently across steps</td>
<td align="left">GPU clocks, thermals, power management, driver housekeeping. Read the trace, not just the mean.</td>
</tr>
<tr>
<td align="left">A kernel named like <code>ampere_bf16_s16816gemm_...</code></td>
<td align="left">The actual cuBLAS GPU work for a matmul. The kernel name is typically the same in eager and compiled mode for the same shapes/dtypes.</td>
</tr>
<tr>
<td align="left"><code>Memcpy DtoD</code> immediately before a GEMM</td>
<td align="left">The bias copy for an <code>addmm</code> epilogue. The "fusion" is at the dispatcher level, not in the kernel.</td>
</tr>
</tbody>
	</table>
</div>
<h3 class="relative group flex items-baseline">
	<a id="dispatch-chain" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#dispatch-chain" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Dispatch chain
	</span>
</h3>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="left">What you see</th>
<th align="left">What it usually means</th>
</tr>

		</thead><tbody><tr>
<td align="left"><code>ProfileStep#N</code> → <code>&lt;record_function name&gt;</code> → <code>aten::*</code> → <code>aten::mm</code> / <code>aten::bmm</code> / <code>aten::add</code></td>
<td align="left">The canonical nested call hierarchy. Self time excludes children; Total time includes them.</td>
</tr>
<tr>
<td align="left"><code>aten::matmul</code> resolving to <code>aten::mm</code></td>
<td align="left">2D × 2D matrix multiply.</td>
</tr>
<tr>
<td align="left"><code>aten::matmul</code> resolving to <code>aten::bmm</code> (with extra CUDA runtime calls)</td>
<td align="left">Batched matmul on 3D+ tensors. cuBLAS does more heuristic work to pick the variant.</td>
</tr>
<tr>
<td align="left"><code>aten::addmm(b, x, w)</code> instead of a separate <code>aten::add</code> + <code>aten::mm</code> pair</td>
<td align="left">Operator fusion at the dispatcher level. The GPU kernel is still the same GEMM, with the bias add folded into the epilogue.</td>
</tr>
</tbody>
	</table>
</div>
<h3 class="relative group flex items-baseline">
	<a id="torchcompile" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#torchcompile" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		torch.compile
	</span>
</h3>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="left">What you see</th>
<th align="left">What it usually means</th>
</tr>

		</thead><tbody><tr>
<td align="left">A <code>Torch-Compiled Region: K/M</code> row in the CPU lane</td>
<td align="left">You're inside a compiled function.</td>
</tr>
<tr>
<td align="left"><code>TorchDynamo Cache Lookup</code> on every step</td>
<td align="left">Dynamo is verifying shapes/dtypes/devices match the cached compile. Paid on every call, even after compilation.</td>
</tr>
<tr>
<td align="left"><code>AOTDispatcher Runtime Wrapper Prologue</code> even with no grads</td>
<td align="left">AOTAutograd's runtime wrapper is always in the stack, handling tensor metadata and view tracking.</td>
</tr>
<tr>
<td align="left"><code>## Call CompiledFxGraph &lt;hash&gt;</code> with the same hash across steps</td>
<td align="left">Cache hits on the generated code. The generated source lives under <code>/tmp/torchinductor_&lt;user&gt;/fxgraph/&lt;hash&gt;</code>.</td>
</tr>
<tr>
<td align="left">Per-step CPU time higher under <code>torch.compile</code> than eager for a tiny op</td>
<td align="left">Expected. The Dynamo → AOTAutograd → Inductor stack is a tax that only amortizes over many ops.</td>
</tr>
</tbody>
	</table>
</div>
<h2 class="relative group flex items-baseline">
	<a id="conclusion" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#conclusion" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Conclusion
	</span>
</h2>
<p>We started with a tiny <code>matmul + add</code> and used it as an excuse to learn how to read a PyTorch profiler. Along the way we picked up a few mental models that travel well to bigger workloads. This was the first stop in the <strong>Profiling PyTorch</strong> series. <a href="https://huggingface.co/blog/torch-mlp-fusion">In the posts</a> that follow, we will gradually leave this two-op toy behind and walk up the ladder of complexity, looking at larger building blocks and, eventually, real models.</p>
