<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]--><strong>TL;DR</strong></p>
<ul>
<li><code>AsyncGRPOTrainer</code> can now train a LoRA adapter and sync only that adapter to vLLM (TRL v1.14).</li>
<li>A rank-1 adapter is a few megabytes, so it can travel through a Storage Bucket mounted in every Job instead of over NCCL. The trainer and the vLLM replicas run as separate Hugging Face Jobs on separate machines.</li>
<li>A small proxy in front of the replicas adds the auth header, routes each rollout to the replica that already holds its KV prefix, and broadcasts adapter loads to every replica.</li>
<li>The AsyncGRPO metrics show where the bottleneck sits. Five runs take the same recipe from 3 h 27 min to 53 min for 500 steps.</li>
</ul>
</blockquote>
<p>LoRA support recently landed in TRL's <a href="https://huggingface.co/docs/trl/en/async_grpo_trainer"><code>AsyncGRPOTrainer</code></a> with <a href="https://github.com/huggingface/trl/pull/7017" rel="nofollow">PR #7017</a>, and ships with TRL v1.14. The asynchronous trainer can now train an adapter instead of the full model, and it syncs only the LoRA adapter to vLLM. This post covers a real-world project built on top of it, where training and inference no longer share a machine.</p>
<p>LoRA training is particularly suited for RL, as shown in Thinking Machines's blog <a href="https://thinkingmachines.ai/blog/lora/" rel="nofollow">LoRA Without Regret</a>. They show that LoRA can match full fine-tuning for policy-gradient RL, even with rank 1. This stems from the fact that the advantage function only gives <code>~O(1)</code> bits of information per episode, so there is not that much to learn from each step, from a total-bits-of-information point of view. A rank-1 adapter has enough capacity to absorb it.</p>
<p>There is also a systems consequence of LoRA training. A rank-1 adapter for a 1.5B model is a few megabytes, while the full model is around 3 GB. Instead of sending the full policy to the inference workers after every update, we can just send the adapter. vLLM can also keep several adapters loaded at once. Old rollouts finish with the policy they started with, while new rollouts use the latest one.</p>
<p>TRL's <code>AsyncGRPOTrainer</code> already separates training and generation. The trainer and vLLM can run on different machines and at their own speed. This is easy in a single-node or cluster setting where both processes share a filesystem or can form an NCCL group.</p>
<p>What we want is to run the same setup with <a href="https://huggingface.co/docs/huggingface_hub/guides/jobs">Hugging Face Jobs</a>. Essentially, an HF Job is one container running on one VM. This means that one Job cannot spawn multiple nodes (at least for now) to hold a trainer and a fleet of vLLM servers (we are limited to 8xH200 at most per node). The <code>AsyncGRPOTrainer</code> is built for exactly that kind of scale, so the question became: how far can we get if we drop the requirement that the trainer and the inference servers share a node?</p>
<p>Well, with a full-weight sync, the answer would be "not far". Every update would have to move gigabytes between machines, which is what NCCL is for in a dense cluster, but Jobs can't communicate <em>across</em> nodes. There is no shared local disk and obviously no shared <code>localhost</code>. With LoRA, a sync is only a few megabytes. For the filesystem part, HF Jobs provide volumes backed by <a href="https://huggingface.co/docs/hub/storage-buckets">Storage Buckets</a>! These buckets can then be mounted as a FUSE filesystem in every Job and are enough to work as a shared FS between nodes. No network path between the Jobs is needed at all.</p>
<p>The setup ended up being quite small:</p>
<ul>
<li>a <strong>trainer Job</strong> running <code>AsyncGRPOTrainer</code> with LoRA (and FSDP, more on that later),</li>
<li><strong>two vLLM Jobs</strong>, each serving the base model plus whatever adapter the trainer last published,</li>
<li>a <strong>Storage Bucket</strong> mounted in all three at the same path, which is how the adapter gets from the trainer to the servers,</li>
<li>a <strong>proxy server</strong>. We'll dive deeper into why we need one, but at a high level we need a proxy that routes each rollout to the replica most likely to hold its KV cache, and broadcasts every adapter update to all vLLM replicas.</li>
</ul>
<h2 class="relative group flex items-baseline">
	<a id="the-architecture-leveraging-hugging-face-jobs-and-storage-buckets-🪣" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-architecture-leveraging-hugging-face-jobs-and-storage-buckets-🪣" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The architecture: leveraging Hugging Face Jobs and Storage Buckets 🪣
	</span>
</h2>
<p>The new adapter-only sync path in <code>AsyncGRPOTrainer</code> works like this. The trainer does not send tensors to vLLM. Every few optimizer steps, it saves the adapter under <code>&lt;output_dir&gt;/.vllm_lora/trl-policy-v{N}</code>, publishes the directory with an atomic rename, then sends its path to vLLM's <code>/v1/load_lora_adapter</code> endpoint. vLLM loads the files from disk, so the rollout worker can then request <code>model="trl-policy-v{N}"</code>.</p>
<p>This is how runtime adapter loading already works in vLLM. The endpoint takes a path, not tensors, so the trainer and the server are expected to share a filesystem. On a Slurm cluster, that is the network filesystem. On Jobs, we get the same thing by mounting a <a href="https://huggingface.co/docs/hub/storage-buckets">Storage Bucket</a> as a volume at the same path in every Job, as we mentioned earlier. Under the hood, it uses <a href="https://github.com/huggingface/hf-mount" rel="nofollow"><code>hf-mount</code></a>, which exposes the bucket as a POSIX filesystem inside the container:</p>
<pre><code class="language-sh"><span class="hljs-comment"># every Job gets the same bucket at the same absolute path</span>
hf <span class="hljs-built_in">jobs</span> run ... -v hf://buckets/aminediroHF/asyncgrpo-lora-buckets:/lora ...
</code></pre>
<p>Nothing in TRL or vLLM had to change for this. The trainer writes to <code>/lora/&lt;run&gt;/.vllm_lora/</code> and the servers read from the same path. The path sent in the POST request is already valid inside every container.</p>
<figure class="image text-center">
  <img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/architecture.png" alt="Async GRPO with LoRA across Hugging Face Jobs. The trainer Job runs AsyncGRPOTrainer and the proxy, two vLLM Jobs serve the base model plus the latest adapter, and a Storage Bucket is mounted at /lora in all three.">
  <figcaption>The three Jobs and the bucket. TRL talks to the proxy over localhost, the proxy talks to the replicas over HTTPS, and the adapter directory travels through the bucket mount.</figcaption>
</figure>

<p>Note that we also store the checkpoints and the final adapter in the bucket. The HF Jobs are ephemeral, but a preempted trainer can resume training, as the final adapter is always persisted to the bucket and is never lost when the Job stops.</p>
<h2 class="relative group flex items-baseline">
	<a id="the-three-jobs" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-three-jobs" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The three Jobs
	</span>
</h2>
<h3 class="relative group flex items-baseline">
	<a id="the-vllm-replicas" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-vllm-replicas" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The vLLM replicas
	</span>
</h3>
<p>Each replica uses one GPU and the stock <code>vllm/vllm-openai</code> image. We only need to enable <a href="https://docs.vllm.ai/en/latest/features/lora/?h=lora#serving-lora-adapters" rel="nofollow">runtime LoRA</a> loading and reserve enough adapter slots.</p>
<p>The number of adapter slots follows from <code>max_staleness</code>. In <code>AsyncGRPOTrainer</code>, every weight sync bumps the policy version by one, and <code>max_staleness</code> is how many versions a rollout sample may lag behind the current policy before the trainer discards it. With <code>max_staleness=4</code>, a sample generated under <code>trl-policy-v3</code> is still used for training while the trainer is at <code>v7</code>. A rollout that started under <code>v3</code> must also be able to finish under <code>v3</code>. So at any moment, vLLM has to serve the current policy plus the four before it. That is why the trainer keeps <code>max_staleness + 1</code> adapter versions registered and unloads anything older. Each sync loads the new version before it unloads the oldest one, which needs one more slot during the swap. That gives <code>--max-loras 6</code>. With only five, vLLM would silently evict a policy that still has rollouts in flight at every sync.</p>
<pre><code class="language-sh"><span class="hljs-comment"># --expose 8000                       reachable at https://&lt;job_id&gt;--8000.hf.jobs</span>
<span class="hljs-comment"># -v ...:/lora:ro                     read-only: the server only reads adapters</span>
<span class="hljs-comment"># VLLM_ALLOW_RUNTIME_LORA_UPDATING=1  enables /v1/load_lora_adapter</span>

    --expose 8000 \
    -v <span class="hljs-string">"hf://buckets/<span class="hljs-variable">${BUCKET}</span>:/lora:ro"</span> \

    -e VLLM_SERVER_DEV_MODE=1 \

<p>We pin vLLM to <code>v0.27.1</code>. vLLM moves fast, and the flags above and the runtime LoRA endpoints are the ones that version exposes, so treat the version as part of the recipe.</p>
<p>There is another possible design where the trainer keeps only the latest adapter and always publishes it under the same name. We did not go that way, because vLLM keys its prefix cache by adapter name. With a single name, KV blocks computed under the previous weights would still match after the swap, so the prefill would not be redone and a rollout could get its prefix from one policy version and its decode from the next. The trainer would have no way to tell, and it would show up as <code>ratio</code> drifting away from 1. Versioned names make this impossible: a name always means one set of weights, and a cached prefix can never match a newer version.</p>
<h3 class="relative group flex items-baseline">
	<a id="the-dataset-choice-the-sanity-set" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-dataset-choice-the-sanity-set" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The dataset choice: the Sanity set
	</span>
</h3>
<p>We chose <a href="https://huggingface.co/datasets/sail/Sanity-Test-R1D-1.5B"><code>sail/Sanity-Test-R1D-1.5B</code></a>, the dataset from <a href="https://huggingface.co/papers/2510.26788">Defeating the Training-Inference Mismatch via FP16</a> (Qi et al., 2025). The reproduction code is in <a href="https://github.com/sail-sg/Precision-RL" rel="nofollow"><code>sail-sg/Precision-RL</code></a>.</p>
<p>The authors generated 40 answers for each MATH problem with <a href="https://huggingface.co/deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B">DeepSeek-R1-Distill-Qwen-1.5B</a>. They kept problems with a success rate between 20% and 80%, yielding 1,460 questions. This dataset is really good for RL validation because the questions are neither already solved nor completely hopeless for that model, meaning the model can get a good early signal to train on and improve.</p>
<p>This is awesome as a robust end-to-end test: if one vLLM replica silently serves the base model under an adapter name, we want to see that in the curve within a few dozen steps. Also, this dataset is small enough to cycle through in less than two hours.</p>
<p>We also take the hyperparameters from the paper's LoRA scripts in <a href="https://github.com/sail-sg/Precision-RL/tree/main/oat/scripts/lora" rel="nofollow"><code>oat/scripts/lora</code></a>: <code>Qwen/Qwen2.5-Math-1.5B</code>, LoRA rank 1 with alpha 2, a learning rate of 4e-5, 8 samples per prompt, 128 completions per step, a maximum of 3,000 generated tokens and a 4,096-token context.</p>
<h3 class="relative group flex items-baseline">
	<a id="the-trainer" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-trainer" rel="nofollow">

The training script is a normal <code>AsyncGRPOTrainer</code> script. The only Job-specific values are the output directory and the server URL.</p>

<h2 class="relative group flex items-baseline">
	<a id="the-proxy" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-proxy" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The proxy
	</span>
</h2>
<p>Now onto the fun stuff. We need a proxy between the trainer and the vLLM Jobs for two reasons:</p>
<ol>
<li><p>Exposed Job ports require an <code>Authorization: Bearer &lt;HF token&gt;</code> header on every request. The proxy is where that header gets added, so TRL does not need to know about it.</p>
</li>
<li><p>We want more than one GPU generating. On a single vLLM server, the usual way to get that is <code>--data-parallel-size &gt; 1</code>, but TRL refuses adapter-only sync in that mode, for a good reason: a call to <code>/v1/load_lora_adapter</code> only reaches the DP rank that answers it, so the other ranks would keep serving the base model under the new policy name. On Jobs the question does not even arise, since each replica is its own machine. So the data parallelism has to live one level up, in something that fans the adapter load out to every replica.</p>
</li>
</ol>
<p>We therefore run a small proxy at <code>127.0.0.1:8000</code> on the trainer Job and point TRL to it as if it were a single vLLM server. Besides adding the header, the proxy does two things functionally:</p>
<ul>
<li>It sends each completion request to one replica, chosen so that the eight rollouts of a prompt land where their prefix is already cached (details on this below).</li>
<li>It broadcasts every <em>state-changing</em> request, such as <strong>adapter loads, pause and resume</strong>, to all replicas, so that a policy name means the same thing everywhere.</li>
</ul>
<h3 class="relative group flex items-baseline">
	<a id="routing-rollouts-by-kv-prefix" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#routing-rollouts-by-kv-prefix" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Routing rollouts by KV prefix
	</span>
</h3>
<p>A quick reminder of why this matters. Generating a completion has two phases with very different workload profiles:</p>
<ul>
<li>The prefill processes the <strong>whole prompt at once</strong> and computes the attention keys and values for every prompt token.</li>
<li>The decode phase then produces one token at a time, and each new token attends to the keys and values of all the tokens before it.</li>
</ul>
<p>Those keys and values are the KV cache. Because attention is causal, the KV of a token depends only on the tokens before it, not on what comes after. Two requests that share a prefix therefore share the KV of that prefix, and a replica that already has it in cache can <strong>skip that part of the prefill entirely</strong>. The whole game now is to find that replica, so a request can benefit from landing on the replica that has already seen its prefix.</p>
<p>vLLM stores its <a href="https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/kv_cache_utils.py" rel="nofollow">prefix KV cache</a> in blocks of 16 tokens. Because of GRPO, the rollout worker sends <code>G</code> requests with the same prompt (in our case <code>G=8</code>). If they all reach the same replica, the first request computes the prefill and the next seven reuse it. With round-robin routing, half would go to a replica that doesn't have the prefix cached, and those four requests would redo the prefill work and waste valuable GPU compute.</p>
<p>The job of <a href="https://github.com/AmineDiro/hfjobs-lora-buckets/blob/main/src/lora_proxy.py" rel="nofollow">our router</a> is to track which replica has seen which <strong>block hash</strong>. One important detail is that the hashes are chained, so the hash of block 3 represents blocks 1, 2 and 3, not just block 3. This mirrors causal attention: the KV of block 3 is only valid if blocks 1 and 2 are the same too. We also seed the chain with the adapter name because the KV cache also depends on the adapter that generated it: a prefix cached for policy v3 is useless for policy v4!</p>
<figure class="image text-center">
  <video controls="" autoplay="" loop="" muted="" playsinline="" style="max-width: 100%; margin: auto;">
    <source src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/kv-prefix-router.mp4" type="video/mp4">
    Your browser does not support the video tag.
  </video>
  <figcaption>The routing decision for two prompts and four requests on two replicas: 16-token blocks, chained hashes, the common prefix, one affinity hit and one spill.</figcaption>
</figure>

<p>The video walks through the entire decision process for choosing a replica. The steps below go through a real 135-token completion request example (from the Sanity dataset problems):</p>
<p><strong>1. Split the prompt into blocks.</strong> The router receives token ids and cuts them into 16-token blocks, just like vLLM. It only hashes complete blocks, so the last 7 tokens are ignored here.</p>
<p><strong>2. Hash the prefix.</strong> Each block is hashed with the previous hash, starting from the adapter seed. <code>h3</code> therefore identifies blocks 1, 2 and 3 in order. Two prompts with the same first <code>k</code> blocks get the same hashes up to <code>hk</code>. Once one block changes, every hash after it changes too. This is why we seed the hashes with the adapter name: the same prompt under <code>trl-policy-v4</code> starts from another seed and cannot match entries from <code>v3</code>. This is what we want because the old KV blocks were computed with different weights.</p>
<p><strong>3. Compare two prompts.</strong> Problem 1 has 103 tokens. Both prompts start with the same 23-token chat template. Their first block is identical, but block 2 already contains the problem text. The hashes differ from there.</p>
<p><strong>4. Store the owners.</strong> For every hash, the router remembers which replicas served it and which hashes came after it (we cap the successor set at two because we only need to know whether a block has one continuation or several). After a few prompts, the template block <code>h1</code> is owned by both replicas and already has several successors, <code>h2</code> to <code>h8</code> are owned by A only and each has a single successor, and <code>h2'</code> to <code>h6'</code> are owned by B only.</p>
<p>In practice, every prompt in a run starts with the same tokens. Here, it is the chat template and the system prompt, which amount to the first 23 tokens of all 1,460 problems. In an agent setting, it would be the tool descriptions, and in a multi-turn environment it would be the shared conversation history. These blocks are in every replica's cache within seconds, so matching on them tells us nothing about where a particular prompt lives.</p>
<p>A block is <em>common</em> if every replica has served it, or if it has more than one successor. Common blocks are ignored during routing because they do not identify a particular prompt. More on this below!</p>
<p><strong>5. Pick a replica.</strong> The router counts how many leading blocks match on each replica and removes the common prefix. What is left is the number of blocks specific to this prompt. Then:</p>
<ul>
<li>If one replica has specific blocks and it is not swamped, meaning it is at most 8 requests ahead of the least-loaded replica, the request goes there. We call this an <strong>affinity</strong> hit.</li>
<li>If a replica has specific blocks but it is more than 8 requests ahead, we give up on the cache and send the request to the least-loaded replica. We call this a <strong>spill</strong>.</li>
<li>If no replica has specific blocks, this is a new prompt. It goes to the least-loaded replica, round-robin on ties. We call this <strong>unmatched</strong>.</li>
</ul>
<p>Here is the rule applied to four requests. Start from a state where replicas A and B both have 3 requests in flight, and only the template block <code>h1</code> is known on both replicas.</p>
<ul>
<li><strong>Request 1, problem 0, rollout 1.</strong> Both replicas match one block, the template, and that block is common. So nothing specific matches anywhere. The request is unmatched, both replicas are equally loaded, and round-robin sends it to A. The router records <code>h2</code> to <code>h8</code> as owned by A. A now has 4 requests in flight.</li>
<li><strong>Request 2, problem 0, rollout 2.</strong> Same prompt. A matches all 8 blocks, B matches only the template. After removing the one common block, A has 7 specific blocks and B has none. A is only 1 request ahead of B, well within the limit of 8, so the request goes to A. This is an affinity hit: A already has the whole prompt in its KV cache.</li>
<li><strong>Request 3, problem 1, rollout 1.</strong> A new prompt. Both replicas match only the template block, so nothing specific matches. The request is unmatched and goes to the least-loaded replica, B, which has 3 in flight against A's 5. The router records <code>h2'</code> to <code>h6'</code> as owned by B.</li>
<li><strong>Request 4, problem 0, rollout 9.</strong> Suppose that by now A has 12 requests in flight while B is back to 3. A still has the 7 specific blocks, but it is now 9 requests ahead of B, more than the limit. The request spills to B. B prefills problem 0 once, and the router records <code>h2</code> to <code>h8</code> as owned by B as well. Every replica has now served those blocks, so problem 0 becomes common too, and its later rollouts are placed by load alone.</li>
</ul>
<p><strong>6. Reuse the prefill.</strong> Request 2 is the reason for doing all this. It reuses the prefill computed by Request 1: blocks 1 to 8 are already in A's KV cache, so A skips straight to decoding the completion. Had it gone to B, B would have prefilled all 135 tokens again while A's cache sat unused. Request 3 shows why the <code>common</code> rule is needed. Without it, the shared chat template would make every new prompt look like a cache hit. Request 4 keeps the load bounded. Saving one prefill is not worth letting a replica fall far behind.</p>
<pre><code class="language-python"><span class="hljs-keyword">def</span> <span class="hljs-title function_">choose</span>(<span class="hljs-params">self, upstreams, model, prompt</span>):

    common = self.common_prefix_len(hashes)           <span class="hljs-comment"># leading blocks that identify no prompt (see below)</span>
    specific = [<span class="hljs-built_in">max</span>(<span class="hljs-number">0</span>, m - common) <span class="hljs-keyword">for</span> m <span class="hljs-keyword">in</span> matched]  <span class="hljs-comment"># what actually distinguishes replicas</span>

    best = <span class="hljs-built_in">max</span>(<span class="hljs-built_in">range</span>(self.n), key=<span class="hljs-keyword">lambda</span> i: (specific[i], -upstreams[i].inflight))

        self.rr += <span class="hljs-number">1</span>
    ...record `pick` <span class="hljs-keyword">as</span> an owner of every block, <span class="hljs-keyword">and</span> each block<span class="hljs-string">'s successor...</span>

<p>The <code>common</code> prefix is the annoying part. Every request starts with the same system prompt and chat template. A simple longest-prefix match would give the first replica a match for almost every new prompt. We detect the shared prefix through fan-out instead: a block with several different successors is common, while a block that always leads to the same successor belongs to a particular prompt. Only the blocks after that common prefix count as affinity.</p>
<h3 class="relative group flex items-baseline">
	<a id="broadcasting-the-adapter" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#broadcasting-the-adapter" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Broadcasting the adapter
	</span>
</h3>
<p>The proxy also needs to broadcast the adapter loads to every replica. We treat the operation as <strong>all-or-nothing</strong>. Each replica has its own bucket mount, so they do not necessarily see a new adapter at exactly the same time. A <code>No adapter found for &lt;path&gt;</code> error usually means that one bucket mount has not caught up yet, and we retry only that replica. For any other error, we unload the adapter from the replicas that accepted it so that a policy name never exists on only part of the replicas.</p>
<pre><code class="language-python"><span class="hljs-keyword">async</span> <span class="hljs-keyword">def</span> <span class="hljs-title function_">load_one</span>(<span class="hljs-params">u</span>):

<p>We also broadcast <code>/pause</code>, <code>/resume</code> and <code>/v1/unload_lora_adapter</code> in the same way. <code>/health</code> returns 200 only if every replica is healthy. <code>/server_info</code> and <code>/v1/models</code> only need one answer. From TRL's point of view, the proxy is a single <code>data_parallel_size=1</code> server, so it selects adapter-only sync.</p>
<p>We initially wondered whether a Python asyncio proxy would become a bottleneck. It does not (at least at this scale). There are at most 128 non-streaming JSON requests in flight, and routing only computes a few hashes. One thread handles this easily. A more refined router that needs to handle more traffic would probably need to be written in a faster language (We see you 🦀).</p>
<h2 class="relative group flex items-baseline">
	<a id="full-run-results" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#full-run-results" rel="nofollow">

	<span>

<h2 class="relative group flex items-baseline">
	<a id="chasing-the-bottleneck-ping-pong" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#chasing-the-bottleneck-ping-pong" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Chasing the bottleneck ping-pong
	</span>
</h2>
<p>Async RL is a pipeline between training and generation. Making one side faster does nothing if the other side cannot keep up. Fortunately, in <code>AsyncGRPOTrainer</code> we've added enough timings and metrics to see this directly.</p>
<p>All the useful metrics are documented in the <a href="https://huggingface.co/docs/trl/en/async_grpo_trainer#logged-metrics">Logged metrics</a> section. <code>perf/rollout_wait_s</code> tells us how long the trainer waits for samples. <code>rollout/backpressure_s</code> tells us how long generation waits for space in the rollout queue. They are diametrically opposed to each other and should not both be high. Together with the queue size, they tell us which side is slow.</p>
<p>We ran five experiments. Each one starts from a problem visible in the previous run's dashboard. Unless mentioned otherwise, the model, recipe and three-Job layout stay the same. The names below are the trackio run names.</p>
<h3 class="relative group flex items-baseline">
	<a id="reading-the-dashboard" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#reading-the-dashboard" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Reading the dashboard
	</span>
</h3>
<p>We keep these four groups of metrics visible:</p>
<ul>
<li><strong><code>perf/step_s</code></strong> and <strong><code>perf/fwd_bwd_s</code></strong>: how long an optimizer step takes, and how much of it is forward+backward. If a step takes nearly as long as the forward+backward, then the trainer is clearly compute-bound.</li>
<li><strong><code>perf/rollout_wait_s</code></strong>: how long the trainer sat waiting for samples before it could start a step. Near zero means generation is ahead of training. Samples are available immediately to be trained on.</li>
<li><strong><code>sample/rollout_queue_size</code></strong> against <code>queue_maxsize</code>: the buffer between the two sides. Full means generation is being throttled; empty means the trainer is starving.</li>
<li><strong><code>rollout/backpressure_s</code></strong> and <strong><code>rollout/score_block_s</code></strong>: how long the rollout worker sat blocked because that buffer was full. The worker is a two-stage pipeline: generation hands finished groups to a scoring stage, and scoring pushes scored samples into the rollout buffer. When the buffer is full, scoring cannot enqueue and blocks, which is <code>rollout/backpressure_s</code>. Scoring then stops draining its own input queue, so generation cannot hand over the next group either, which is <code>rollout/score_block_s</code>. Both are the same stall, seen first at the scoring stage and then propagated back to generation.</li>
</ul>
<p>The diagnosis is simple: a full queue with zero rollout wait and high backpressure means the trainer is too slow. An empty queue with rising rollout wait and no backpressure means generation is too slow. Comparing <code>perf/mfu_wall_clock</code> with <code>perf/mfu_fwd_bwd</code> also shows how much time the trainer GPUs spend waiting instead of training.</p>
<h3 class="relative group flex items-baseline">
	<a id="run-1-r1-dp2-a-trainer-that-cannot-keep-up" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#run-1-r1-dp2-a-trainer-that-cannot-keep-up" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Run 1, <code>r1-dp2</code>: a trainer that cannot keep up
	</span>
</h3>
<p><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig1-r1-dp2-trainer-bound.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig1-r1-dp2-trainer-bound.png" alt="Figure 2"></a></p>
<p><em>Figure 2. trackio run <code>r1-dp2</code>. Panels: <code>perf/step_s</code>, <code>perf/fwd_bwd_s</code>, <code>sample/rollout_queue_size</code>, <code>rollout/backpressure_s</code>. Step time and forward+backward overlap almost completely; the queue sits pinned near 476 of 512 and backpressure never drops below 11 s per rollout group: trainer-bound.</em></p>
<p><code>perf/step_s</code> is 22.9 s and <code>perf/fwd_bwd_s</code> is 21.9 s. Forward and backward take 96 % of the step time. The queue stays full and the trainer waits only 0.02 s for rollouts, and the rollout worker spends 15 seconds per group blocked by backpressure. The two vLLM replicas generate faster than the trainer consumes. The reported 4.6k tokens/s is not their actual limit; they simply have nowhere to put more output.</p>
<p>The batch metrics explain the terrible 3.9 % MFU. <code>batch/microbatches_per_step</code> is 64 and <code>batch/samples_per_row</code> is 1.0. Each rank processes one sequence of around 1.2k tokens, 64 times per step. This comes from the reference recipe's <code>per_device_train_batch_size=1</code>. For a 1.5B model on an H200, this is completely latency-bound.</p>
<h3 class="relative group flex items-baseline">
	<a id="run-2-r1-dp2-tb16k-pack-the-microbatch" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#run-2-r1-dp2-tb16k-pack-the-microbatch" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Run 2, <code>r1-dp2-tb16k</code>: pack the microbatch
	</span>
</h3>
<p>The fix is not to change the batch size. We keep 128 completions per optimizer step and only change how they are laid out on the GPU: instead of one sequence per microbatch, we pack many sequences densely into each row. The trainer supports this through <strong>token-budget batching</strong>. With <code>token_budget &gt; 0</code>, it packs several samples into one padding-free row per rank. An optimizer step processes <code>gradient_accumulation_steps</code> rows. We set <code>token_budget=16384</code> and <code>gradient_accumulation_steps=6</code>.</p>
<p><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig2-r1-dp2-vs-tb16k-packing.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig2-r1-dp2-vs-tb16k-packing.png" alt="Figure 3"></a></p>
<p><em>Figure 3. trackio runs <code>r1-dp2</code> and <code>r1-dp2-tb16k</code> overlaid over their first 154 steps. Panels: <code>batch/samples_per_row</code>, <code>batch/microbatches_per_step</code>, <code>perf/step_s</code>, <code>perf/fwd_bwd_s</code>, <code>perf/mfu_fwd_bwd</code>, <code>rollout/generated_tok_s</code>. Packing takes samples per row from 1 to 13, microbatches from 64 to 6, step time from 23 s to 5.9 s, and generation from 4.2k to 27.5k tok/s with no change on the vLLM side.</em></p>
<p><code>batch/samples_per_row</code> goes from 1.0 to ~12.7 and the number of microbatches drops from 64 to 6. The rows are 95 % full! Forward and backward fall from 21.9 s to 5.6 s, while MFU rises from 3.9 % to 19 %. We now train on around 150 samples per step because the rows pack better than the mean-length estimate predicted.</p>
<p>Generation also jumps from 4.6k to 25k tokens/s, even though we changed nothing on the vLLM side. The queue is no longer constantly full, so the replicas can finally run. This is why we do not like optimizing pipeline stages in isolation. We need to be careful to evaluate the whole system, as a slow stage can hide the real performance of everything before it.</p>
<h3 class="relative group flex items-baseline">
	<a id="run-3-r1-dp2-tb16k-nockpt-stop-recomputing-the-forward" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#run-3-r1-dp2-tb16k-nockpt-stop-recomputing-the-forward" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Run 3, <code>r1-dp2-tb16k-nockpt</code>: stop recomputing the forward
	</span>
</h3>
<p><code>perf/fwd_s</code> is 1.34 s while <code>perf/fwd_bwd_s</code> is 5.6 s. A normal backward costs roughly twice the forward, and with frozen base weights it should be closer to once. A ratio of 3.2 is suspicious.</p>
<p>The reason is that <code>AsyncGRPOConfig</code> defaults to <code>gradient_checkpointing=True</code>. Every microbatch recomputes its forward during the backward. This also explains why a 16k-token row only uses 25 GB on a 141 GB H200! It's a memory optimization for this trainer, but we don't need it in this specific case: the model is small enough to fit into VRAM with the activations kept for the backward.</p>
<p><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig3-tb16k-vs-nockpt-crossover.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig3-tb16k-vs-nockpt-crossover.png" alt="Figure 4"></a></p>
<p><em>Figure 4. trackio runs <code>r1-dp2-tb16k</code> and <code>r1-dp2-tb16k-nockpt</code> overlaid over their first 134 steps. Panels: <code>perf/fwd_s</code>, <code>perf/fwd_bwd_s</code>, <code>perf/weight_sync_s</code>, <code>sample/rollout_queue_size</code>, <code>perf/rollout_wait_s</code>, <code>perf/mfu_fwd_bwd</code>. Forward+backward drops by one forward; the queue falls from ~420 to ~60, and rollout wait rises from 0.02 s to 0.5 s: the bottleneck shifts to generation.</em></p>
<p>With <code>gradient_checkpointing=False</code>, forward and backward drop to 4.6 s, almost exactly one forward less, and MFU reaches 23 %. The queue now falls to 71 and rollout wait rises from 0.04 s to 0.6 s. The trainer consumes samples faster than two replicas generate them. We <em>successfully</em> moved the bottleneck to generation.</p>
<p>This exposes two more costs. A 7.6-second weight sync every four steps now takes 25 % of wall-clock time. It was only 8 % when each step took 23 seconds. Also, backward is still 2.5 times slower than forward. With frozen base weights, there are around 2 seconds per step that do not look like normal model math.</p>
<h3 class="relative group flex items-baseline">
	<a id="run-4-r1-dp3-tb16k-nockpt-three-replicas-and-a-surprise" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#run-4-r1-dp3-tb16k-nockpt-three-replicas-and-a-surprise" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Run 4, <code>r1-dp3-tb16k-nockpt</code>: three replicas, and a surprise
	</span>
</h3>
<p>Since generation was now too slow, we added a third replica. We also reduced the adapter retry interval from 2 s to 0.5 s in the proxy and disabled <code>fsdp_reshard_after_forward</code> to check whether FSDP2 re-gathers caused the extra 2 seconds in backward.</p>
<p><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig4-dp2-vs-dp3-inflight-cap.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig4-dp2-vs-dp3-inflight-cap.png" alt="Figure 5"></a></p>
<p><em>Figure 5. trackio runs <code>r1-dp2-tb16k-nockpt</code> and <code>r1-dp3-tb16k-nockpt</code> overlaid over their first 134 steps. Panels: <code>perf/weight_sync_s</code>, <code>rollout/generated_tok_s</code>, <code>rollout/inflight</code>, <code>perf/fwd_bwd_s</code>. Sync falls from 7.6 s to 5.8 s; generation and forward+backward do not move; <code>rollout/inflight</code> reads 128 in both runs, which is the cap the third replica ran into.</em></p>
<p>Weight sync falls from 7.6 s to 5.8 s, so the shorter retry helps. Forward and backward stay at 4.6 s, which rules out resharding. Generation moves from 25k to only 26k tokens/s. The third replica does basically nothing.</p>
<p>The reason was sitting in <code>rollout/inflight</code>: 128 in every run. The proxy shows those requests split as 44 + 43 + 41 across the three replicas. <code>max_inflight_tasks</code> limits concurrency for the whole rollout worker, not per replica. A 1.5B model on an H200 processes 43 and 130 concurrent sequences at almost the same cost per token. Splitting 128 requests over three GPUs gives nearly the same throughput as splitting them over two.</p>
<p>So vLLM was not the limit. Our own client-side constant was. We had set it conservatively because we did not know how hundreds of long HTTPS requests would behave through the public Jobs proxy. At this point, 130,000 rollout completions had crossed it without a single transport error.</p>
<h3 class="relative group flex items-baseline">
	<a id="run-5-r1-dp3-inflight384-lift-the-cap-on-in-flight-requests" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#run-5-r1-dp3-inflight384-lift-the-cap-on-in-flight-requests" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Run 5, <code>r1-dp3-inflight384</code>: lift the cap on in-flight requests
	</span>
</h3>
<p><code>max_inflight_tasks=384</code> and <code>queue_maxsize=768</code>, nothing else.</p>
<p><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig5-all-runs-scoreboard.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig5-all-runs-scoreboard.png" alt="Figure 6"></a></p>
<p><em>Figure 6. All five trackio runs (<code>r1-dp2</code>, <code>r1-dp2-tb16k</code>, <code>r1-dp2-tb16k-nockpt</code>, <code>r1-dp3-tb16k-nockpt</code>, <code>r1-dp3-inflight384</code>) overlaid, x-axis in steps. Panels: <code>perf/step_s</code>, <code>reward</code>, <code>sample/rollout_queue_size</code>, <code>sample/staleness_mean</code>. Step time falls from 22.9 s to 4.8 s across the series while the reward curves stay on top of each other; the last run's queue refills to ~690 of 768 and its staleness settles at 2. Runs 2 to 4 were stopped early once the dashboard had answered the question.</em></p>
<p>With 384 requests in flight, each replica gets 128. The queue quickly fills to around 690 out of 768 and stays there. Backpressure returns to 5 seconds and rollout wait falls to 0.03 seconds. Training is the bottleneck again! Forward and backward take 4.6 seconds, weight sync adds an amortized 1.5 seconds, and median step time is 4.8 seconds.</p>
<p>Mean staleness rises from 1.5 to 2.0 versions because samples wait longer in the larger queue. This is still below <code>max_staleness=4</code>, and <code>ratio</code> remains very close to 1.000.</p>

<p>LoRA training is particularly suited for RL, as shown in Thinking Machines's blog LoRA Without Regret. They show that LoRA can match full fine-tuning for policy-gradient RL, even with <a href="https://www.sportzfy4u.app/" rel="nofollow">sportzfy</a> rank 1. This stems from the fact that the advantage function only gives ~O(1) bits of information per episode, so there is not that much to learn from each step, from a total-bits-of-information point of view. A rank-1 adapter has enough capacity to absorb it.</p>
</blockquote>
<p>Really interesting take on how LoRA changes the systems side of RL training, not just the training itself. The idea of separating training and inference across different machines while only moving a small adapter instead of the full model makes a lot of practical sense, especially when working with HF Jobs. The “bucket, proxy, and no NCCL” approach feels like a good example of simplifying distributed infrastructure by moving the communication boundary to something much smaller and easier to manage.</p>
<p>I also like the connection to the LoRA Without Regret work, particularly the point that policy-gradient updates may not require huge adapter capacity to capture the useful signal. Sending only a few MB instead of several GB after updates can make a massive difference in both bandwidth and iteration speed. Would be really interested to see more details on how the bucket/proxy setup behaves at scale and whether there are any noticeable trade-offs once the number of inference workers or concurrent rollouts increases.</p>
