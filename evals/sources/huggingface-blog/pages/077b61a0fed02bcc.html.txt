<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]--><em>ALTK-Evolve and ACE both let an agent learn from its own trajectories. The difference is what they do with what they learn — and that decides the token bill.</em></p>
<p>Give an LLM agent a realistic multi-step task — split a bill, find a song, reconcile an order across nine simulated apps — and when it fails, it usually isn't for lack of knowledge. It mis-paginates an API, resolves the wrong person, or returns a value when none was asked for. The model knows the APIs; what it hasn't internalized is <em>how to use them reliably</em>. That's learnable from the agent's own history.</p>
<p>Two recent systems do exactly this, on the same kind of agent: <a href="https://arxiv.org/abs/2510.04618" rel="nofollow"><strong>ACE</strong></a> (Agentic Context Engineering) and our <strong>ALTK-Evolve</strong> (<a href="https://huggingface.co/blog/ibm-research/altk-evolve">introduced here</a>). Both are a form of <strong>agentic memory</strong> — turning an agent's past trajectories into reusable <strong>lessons</strong> and feeding them back at inference time, no weight updates, no human labels. They even agree on the hard part. Where they part ways is <em>delivery</em>.</p>
<p>A note on words, because the two systems name things differently: we'll call the raw thing an agent learns a <strong>lesson</strong>. ACE organizes its lessons into one comprehensive, evolving <strong>playbook</strong>; we consolidate ours into individually retrievable <strong>guidelines</strong>. Same lessons, two containers.</p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="what-we-agree-on" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#what-we-agree-on" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		What we agree on
	</span>
</h2>
<p>Both systems refuse to compress.</p>
<p>ACE names the failure modes precisely: <strong>brevity bias</strong> — optimization collapsing toward short, generic instructions — and <strong>context collapse</strong> — a model asked to rewrite its whole context each step summarizing the detail away. Its answer is to keep a rich, itemized playbook, with a helpful/harmful counter on every bullet, and let the model distill relevance at read time.</p>
<p>We reach the same conclusion from the other direction. Every distinct guideline keeps a <strong>support count</strong> — how many independent episodes produced it — and we never summarize the store down to a handful of rules. A lesson five different tasks discovered is a different object from one that appeared once, and both are worth keeping.</p>
<p>So on the core question — <em>should you compress an agent's hard-won lessons into a tidy summary?</em> — ACE and ALTK-Evolve give the same answer: <strong>no. Count them, don't collapse them.</strong> ACE's per-bullet counters and our support counts are two spellings of the same idea.</p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="where-we-differ" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#where-we-differ" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Where we differ
	</span>
</h2>
<p>Two places: how the memory is <strong>built</strong>, and how it's <strong>delivered</strong> — and it's the delivery difference that shows up in the token bill.</p>
<p><strong>Consolidation (how the store is built).</strong> ACE grows one playbook through a <strong>Generator → Reflector → Curator</strong> loop, applying incremental delta updates and de-duplicating by embedding. We cluster near-duplicate lessons and merge <em>within</em> a cluster, <strong>support-conserving</strong> — when several lessons merge, the survivor inherits their combined count, so the store shrinks without losing the record of how much experience backs each guideline. We also extract <em>typed</em> guidelines — strategy, recovery, and optimization — with causal attribution and provenance back to the source trajectory, and at subtask granularity, so a lesson learned on one app can transfer to another.</p>
<p><strong>Delivery (what reaches the model at inference).</strong> This is the one that drives the numbers. ACE injects the <strong>comprehensive playbook</strong> on every step, the same way regardless of model or task. We treat delivery as a dial, not a constant: a small fixed core of high-support guidelines, extended per task with a handful selected for the task at hand (cosine or LLM-guided, priority-weighted) — or, when a model has the headroom to use it, the full consolidated set. The same lessons are <em>available</em> to both agents; the difference is that ACE always sends all of them, and we send however many a given model can actually use.</p>

<p>On the strong model we're better on both metrics at <strong>~40% of ACE's inference cost</strong>. On the weak model we edge ACE 56.0 to 54.8 — close enough that we call it a <strong>tie on accuracy</strong> (a repeat run of ours landed at 54.8, matching ACE almost exactly, which is within this benchmark's run-to-run noise) — at <strong>about one-seventh</strong> the cost.</p>
<p>A fair word on cost: ACE's own efficiency story is about <em>building</em> its context cheaply. Ours is on a different axis — <em>serving</em> it. Retrieving a few guidelines per task instead of injecting the whole playbook on every step is where the tokens go, and it's the direct consequence of the delivery difference above.</p>
<p>Where does the accuracy come from? The by-difficulty breakdown tells two different stories:</p>
<p><a href="https://cdn-uploads.huggingface.co/production/uploads/6435a1131860001f144239ea/RlNmW6Vps10XLGW4DuJQh.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/6435a1131860001f144239ea/RlNmW6Vps10XLGW4DuJQh.png" alt="image"></a></p>
<p><em>Figure 1. Post-memory Task Goal Completion by difficulty, ours vs. ACE. On DeepSeek-V3.2 (right) we win Easy, Hard, and Overall; ACE only edges Medium. On gpt-oss-120b (left) ACE leads easy and medium, but per-task selection wins the hard tasks — and the aggregate. Each system improves from its own no-memory baseline (see the by-difficulty reference tables under Method notes below).</em></p>
<p>The two models tell different stories. On gpt-oss-120b, ACE's full playbook has the edge on Easy and Medium — there's enough of the task solved by generic instruction-following that a comprehensive prompt helps more than it distracts. But on Hard tasks, where the model has to pick the <em>right</em> lesson rather than wade through all of them, curated retrieval pulls ahead — and that's the tier that decides the aggregate. On DeepSeek-V3.2 the story flips: the stronger model absorbs ACE's full playbook well enough to edge us on Medium, but we lead Easy, Hard, and Overall — with more capacity to spare, more lessons (delivered our way) keep helping instead of crowding each other out.</p>
<p>We give each model its <strong>best configuration</strong> — the full consolidated set for the strong model, selective retrieval for the weaker one, because a large context overwhelms a weaker model rather than helping it. (Exactly <em>how much</em> to inject, and how it scales across the capability spectrum, is the focus of our <a href="https://huggingface.co/blog/ibm-research/altk-evolve-hmm/"><strong>follow-up post</strong></a>.)</p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="same-lessons-different-delivery" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#same-lessons-different-delivery" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Same lessons, different delivery
	</span>
</h2>
<p>Both systems refuse to compress an agent's hard-won experience into a tidy summary — that part, we agree on. The difference is whether delivery is fixed or calibrated: ACE sends the whole playbook every step no matter what; we send however much of the guideline set a given model can actually use. That calibration is what bought the numbers above — same-or-better accuracy at a fraction of ACE's inference cost — and on the weaker model, it was the difference between guidance that helped and guidance that got in the way.</p>

<h2 class="relative group flex items-baseline">
	<a id="method-notes" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#method-notes" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Method notes
	</span>
</h2>
<p>AppWorld <code>test_normal</code>, 168 tasks. A ReAct code agent (each step writes Python; the environment returns the output). <strong>TGC</strong> = Task Goal Completion; <strong>SGC</strong> = Scenario Goal Completion, which requires <em>every</em> variant of a scenario to pass. Memory is mined from <strong>train/dev only</strong>; results are single runs (pass@1), as is standard on this benchmark.</p>
<p>The ACE numbers are our own runs of the ACE agent, evaluated in-house on the same AppWorld splits and the same base models as ALTK-Evolve (DeepSeek-V3.2 and gpt-oss-120b). The ACE paper reports on a different base model (DeepSeek-V3.1), so running it ourselves keeps the comparison controlled for model and harness. Both systems are the <em>same</em> ReAct agent and differ only in the prompt template — which is why the two no-memory baselines differ (72.0 vs 79.8 TGC); we don't rest the comparison on that baseline gap, only on the claims a prompt tweak can't touch: same-or-better accuracy at a fraction of the tokens.</p>
