These add a speculative decoding path that trades a minimal memory increase for a large decoding speedup without changing output quality:</p>
<ul>
<li><strong>Faster inference</strong>: up to 3.18 throughput improvement on a GPU and up to 2.87x on-device.  </li>
<li><strong>Toward on-device agentic inference</strong>: cuts function-calling latency by 57% on average for LFM2.5-2.6B  </li>
<li><strong>Day-one support for llama.cpp and SGLang</strong>: LFM-compatible DSpark integration is open-sourced upstream</li>
</ul>
<h2 class="relative group flex items-baseline">
	<a id="how-does-dspark-work" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#how-does-dspark-work" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		How does DSpark work
	</span>
</h2>
<p>The decode phase in LLM inference is traditionally memory-bound. Most latency comes from streaming weights from DRAM into SRAM, not from intense computation. Speculative decoding addresses this by using a lightweight draft model to produce candidate tokens, then having the target model verify them all in a single forward pass, sharing the cost of loading the weights across all tokens we verify.</p>
<p>Over the years, multiple approaches of speculation have been proposed, with the most prominent being <a href="https://huggingface.co/papers/2503.01840">EAGLE-3</a>, <a href="https://huggingface.co/papers/2602.06036">DFlash</a>, and, most recently, <a href="https://huggingface.co/papers/2607.05147">DSpark</a>, which combines three components:</p>
<ul>
<li><strong>DFlash-style parallel backbone</strong> conditioned on the target model’s context features, producing hidden states for all draft tokens in a single forward pass.   </li>
<li><strong>A lightweight sequential head</strong>, modeled as a Markov chain between neighboring tokens, that adds inter-token dependency, raising the acceptance rate at later positions.  </li>
<li><strong>A confidence-scheduled verifier</strong> that predicts each token’s survival probability and prunes low-confidence suffixes when verification would cost more than it saves.</li>
</ul>
<p><a href="https://cdn-uploads.huggingface.co/production/uploads/644249b08443bce4c9890a0f/QSig7XupRwDH70cDopwv2.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/644249b08443bce4c9890a0f/QSig7XupRwDH70cDopwv2.png" alt="DSpark"></a></p>
<h2 class="relative group flex items-baseline">
	<a id="training-and-architecture" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#training-and-architecture" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Training and Architecture
	</span>
</h2>
<p>We follow the DSpark recipe with a larger and more diverse data mix covering SFT, chat, code, and function-calling data. Based on our ablations, the first versions of the draft models are simplified attention-only draft models, with 5 layers and a block of 9. For each draft model, we ran 15 epochs on the entire dataset and selected the epoch with the highest acceptance rate rather than the lowest loss. </p>
<p>The resulting draft models are relatively small, with each around ~300M parameters.</p>

<h2 class="relative group flex items-baseline">
	<a id="quality-parity" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#quality-parity" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Quality parity
	</span>
</h2>
<p>Under greedy decoding, a draft token is only accepted if it matches the target model’s distribution. On rejection, the target model's own token takes its place. The emitted sequence is therefore <strong>identical to baseline greedy</strong> by construction, so benchmark accuracy (pass@1 or exact match) is unchanged.</p>
<h2 class="relative group flex items-baseline">
	<a id="inference-speed-up-on-cpu-and-gpu" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#inference-speed-up-on-cpu-and-gpu" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Inference Speed Up on CPU and GPU
	</span>
</h2>
<p>Our DSpark draft models for LFM2.5 ship with day-one support for <strong>llama.cpp</strong> (implementation <a href="https://github.com/ggml-org/llama.cpp/pull/27383" rel="nofollow">builds on top of the official codebase</a>, which we run with <a href="https://github.com/ggml-org/llama.cpp/pull/27441" rel="nofollow">experimental metal kernels</a>) and **SGLang (**implementation <a href="https://github.com/sgl-project/sglang/pull/31041" rel="nofollow">builds on the official SGLang implementation of DSpark</a>). </p>
<p>We measure on-device throughput with llama.cpp and Metal on an M4 Max MacBook Pro using FP16 GGUF weights and up to 256 output tokens. We measure GPU throughput with SGLang on a single H100 80 GB in BF16. Both configurations use a DSpark block size of 9, a batch size of 1, and a temperature of 0. We evaluate them on five benchmark datasets.</p>
<p>All three drafter models deliver noticeable throughput improvements on both the large-scale accelerator (H100) and the edge deployment (M4 Max MacBook). </p>
<p>For <strong>LFM2.5-2.6B,</strong> speedup on the MacBook is especially noticeable, as it pushes the interactivity level a user can enjoy far beyond the throughput offered by most proprietary cloud models (around ~140 tok/s, depending on the dataset). </p>

<h2 class="relative group flex items-baseline">
	<a id="how-to-use-lfm25-dspark" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#how-to-use-lfm25-dspark" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		How to use LFM2.5-DSpark
	</span>
</h2>
<p>Running the DSpark draft models with <strong>SGLang</strong> requires an SGLang build with DSpark support for LFM2 targets (<a href="https://github.com/sgl-project/sglang/pull/31041" rel="nofollow">PR #31041</a>). Launch the target with the draft attached:</p>
<pre><code class="language-shell">python -m sglang.launch_server \
  --model-path LiquidAI/LFM2.5-2.6B \
  --speculative-algorithm DSPARK \
  --speculative-draft-model-path LiquidAI/LFM2.5-2.6B-DSpark \
  --speculative-draft-attention-backend flashinfer \
  --disable-radix-cache --mem-fraction-static 0.75 --port 30000
</code></pre>
<p>Then query the OpenAI-compatible endpoint at <code>http://localhost:30000/v1</code>. The block size is read from the draft's <code>config.json</code>; the baseline is the same command without the three <code>--speculative-*</code> flags.</p>
<p>Running them with <strong>llama.cpp</strong> requires the respective llama.cpp build (<a href="https://github.com/ggml-org/llama.cpp/pull/27383" rel="nofollow">PR#27383</a>).</p>
<pre><code class="language-shell">llama-server -m LFM2.5-2.6B-F16.gguf \
  -md LFM2.5-2.6B-DSpark-F16.gguf \
  --spec-type draft-dspark --spec-draft-n-max 10 --spec-draft-n-min 0 \
  -fa on -ngl 99
</code></pre>
<p>The block size is read from the sidecar metadata (n-max is clamped to it). Speculative decoding is <strong>exact</strong>: the target verifies every proposed token, so greedy output equals the target alone; per-response <code>timings</code> report <code>draft_n</code> / <code>draft_n_accepted</code>.</p>
