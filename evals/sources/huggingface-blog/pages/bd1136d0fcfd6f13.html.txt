	<span>
		This is a joint blog by Microsoft and Hugging Face, special thanks to Tommy Guy (founder at Enderis AI, previously Microsoft), Sergio Paniego from Hugging Face and our former interns Zhuochun Li (University of Pittsburgh), Ali Keramati (UC Irvine), Youngmin Ko (Northwestern) for co-authoring/reviewing efforts.

</h4>
<p>A customer writes in. Her $745 kitchen appliance has been stuck in a courier "exception" at a Nashville distribution center, fifteen days past its estimated delivery date.</p>
<p>The AI agent does careful work. Nine tool calls: it pulls the order, checks tracking, looks up her customer profile, searches the refund policy twice, confirms no ticket exists, opens one, documents the timeline, and reads the policy correctly; her account segment genuinely does not qualify for late-delivery compensation.</p>
<p>Then it closes the ticket as <strong>resolved</strong> and replies “ <em>Since your query is resolved, is there anything I may assist you with?</em> ”</p>
<p>Two things are wrong. The carrier exception is still open, so the required end state was <strong>on hold</strong>, pending resolution. And the customer never got a real answer to what she actually asked.</p>
<p>An AI grader checking tool calls would see nine well-formed ones. The grader checking whether the agent wrote to the database would see that too. The database is what <strong>disagrees</strong>.</p>
<p>That gap is what ThinkingBox measures. Across 507 stateful business workflows, each run 20 times against various LLM models, it grades agents on terminal backend state and side effects. This post covers what we found, what consistency costs, and how to run the benchmark yourself through <a href="https://github.com/huggingface/OpenEnv/tree/main/envs/thinkingbox_env" rel="nofollow">OpenEnv</a>.</p>
<p><strong>You can run this one yourself:</strong> the example above is adapted from a benchmark task <a href="https://github.com/microsoft/thinkingbox-data/blob/thinkingbox-bench-v1.0/dataset/test_case/sandbox_external_retail/sandbox_external_retail_group1.py#L984-L1223" rel="nofollow">sandbox_external_retail_group1.py:test_case_ST003_006</a>, and the executable check that fails is a single field: the ticket's status is solved where the required end state is hold. The full trace is in <a href="https://arxiv.org/pdf/2608.19741" rel="nofollow"> Appendix D.4, Case 3 of our paper</a>.</p>

<h2 class="relative group flex items-baseline">
	<a id="a-tool-call-is-not-an-outcome" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#a-tool-call-is-not-an-outcome" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		A tool call is not an outcome
	</span>
</h2>
<p>Final responses and valid tool calls are only proxies. An agent can sound correct while leaving the wrong value, changing the wrong record, or creating an extra side effect. Only the records it leaves behind settle the question.</p>
<p>The gap is substantial. In a common-set ablation covering 121,680 valid trials across 12 LLM models, 79,853 attempts failed the executable checks. Of those failures, 67.24% still terminated cleanly, invoked a state-changing tool, and reported no final tool error. Executable checks nevertheless found wrong field values in 77.61% of them, unintended extra effects in 43.30%, and missing required effects in 25.36%. Those state-check findings overlap.</p>
<blockquote>
<p>A trajectory is a claim. Database state is the evidence. Repetition is the trust test.</p>
</blockquote>
<h2 class="relative group flex items-baseline">
	<a id="one-success-is-not-reliability" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#one-success-is-not-reliability" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		One success is not reliability
	</span>
</h2>
<p>An agent that processes a refund correctly once and mishandles it the next four times is not a working refund agent. So every task runs <strong>20 independent times</strong>, each from an identical clean backend, and we report three different things:</p>
<p><em>Table 1: The three numbers we report, and the question each one answers.</em></p>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th>Metric</th>
<th>What it measures</th>
<th>What it answers</th>
</tr>

		</thead><tbody><tr>
<td>pass@1</td>
<td>Share of all attempts that succeeded</td>
<td>How does it usually do?</td>
</tr>
<tr>
<td>pass@20</td>
<td>Share of tasks solved <strong>at least once</strong> in 20 tries</td>
<td>Can it <em>ever</em> do this? Breadth.</td>
</tr>
<tr>
<td>Observed 20/20</td>
<td>Tasks that actually passed <strong>all</strong> 20 recorded attempts</td>
<td>Can it <em>always</em> be correct?</td>
</tr>
</tbody>
	</table>
</div>
<p>We use <strong>observed 20/20</strong> in this blog post as the literal count of how many of the 507 tasks passed 20 out of 20. No estimator, no smoothing. </p>

<h2 class="relative group flex items-baseline">
	<a id="can-you-depend-on-the-model-behind-your-agent" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#can-you-depend-on-the-model-behind-your-agent" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Can you depend on the model behind your agent?
	</span>
</h2>
<p><a href="https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/NONd2WGm4vtGpsVgs-CIq.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/NONd2WGm4vtGpsVgs-CIq.png" alt="Figure-3"></a></p>
<p><em>Figure 3: Breadth and consistency pull apart. Twelve of the eighteen models are shown; six below 33% pass@1 are omitted for legibility.</em></p>
<p><strong>Kimi-K3 has the broadest coverage of any model we tested.</strong> It solves <strong>93.89%</strong> of the benchmark at least once: 476 of 507 tasks. Only 31 tasks defeat it entirely, the lowest count in the field. On retail workflows it leads outright at 82.24% pass@1, ahead of every proprietary model.</p>
<p><strong>Kimi-K3 is also among the least consistent.</strong> Just 68 of 507 tasks, 13.41%, succeed in all 20 attempts.</p>
<p>Claude Opus 5 inverts this. It solves fewer tasks at least once (79.09%; 106 defeat it entirely) but completes <strong>47.53%</strong> of the benchmark on every single attempt.</p>
<p><strong>A newer model does not fix this.</strong> Claude Opus 5.5 scores higher than Claude Opus 5 on every-attempt average, 67.16% against 66.50%, and solves more tasks at least once. It passes exactly the same number of tasks on all 20 attempts: 241. Half a point of headline accuracy bought no additional dependability at all.</p>
<ul>
<li>Kimi-K3 solves <strong>75 more tasks at least once</strong> than Opus 5.</li>
<li>Opus 5 solves <strong>173 more tasks consistently</strong> than Kimi-K3.</li>
</ul>
<p>If you are choosing a model for work that touches real records, pass@20 is the wrong column to look at.</p>
<h2 class="relative group flex items-baseline">
	<a id="what-consistency-costs" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#what-consistency-costs" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		What consistency costs
	</span>
</h2>
<p>Capability comparisons usually stop at the score. For anyone deploying, the relevant question is what a successful unit of work costs. We measure that as cost per successful task attempt. We say task attempt because every benchmark task is run repeatedly and cost is incurred per attempt, so pass@1 is the matching quality denominator.</p>
<p>We took each model's recorded token usage from its full 507 × 20 campaign and priced it at undiscounted list rates available on <a href="https://openrouter.ai/" rel="nofollow">OpenRouter</a><sup>+</sup>, reversing promotional discounts and excluding endpoints that declare quantization. Input, output and cache rates all come from one provider endpoint per model.</p>
<p>Then we divided one run's cost by the number of attempts that <strong>succeeded</strong>:</p>
<blockquote>
<p><strong>Cost per successful task attempt = estimated cost for 507 attempts, one per task ÷ (507 × pass@1)</strong></p>
</blockquote>
<p>This is a comparative efficiency index, not an invoice, and not the price of serving one production request. It also prices single successes, not consistency. We price consistency next.</p>
<p><strong>Example:</strong> GPT-5.4 costs $43.49 for 507 attempts (one attempt per task) and has 65.36% pass@1, so $43.49 ÷ (507 × 0.6536) = $0.131 per successful task attempt.</p>
<h3 class="relative group flex items-baseline">
	<a id="pareto-cost-frontier" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#pareto-cost-frontier" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Pareto cost frontier
	</span>
</h3>
<p>A model is on the frontier if no other model is both <em>no more expensive</em> <strong>and</strong> <em>at least as accurate</em>. Three models qualify; every other model is dominated on at least one axis.</p>
<p><a href="https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/oGmXYrxoNPJfsQndxlcMD.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/oGmXYrxoNPJfsQndxlcMD.png" alt="Figure-4"></a></p>
<p><em>Figure 4: Cost per successful task attempt against pass@1. Ringed dots are pareto cost frontier models.</em></p>
<p><strong>The frontier has three steps.</strong> GPT-5.6 Sol has the <strong>lowest cost per success</strong> at $0.127; GPT-5.4 raises pass@1 by 3.45 percentage points for $0.004 more per success; Claude Opus 5.5 adds another 1.80 points at $0.276 per success. Each of the three remains on the cost frontier line because no cheaper model matches its pass@1.</p>
<p>Claude Opus 5 is the clearest case: at $0.475 per successful attempt and 66.50% pass@1, it is both more expensive and less accurate than Claude Opus 5.5 at $0.276 and 67.16%.</p>
<h3 class="relative group flex items-baseline">
	<a id="now-price-consistency" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#now-price-consistency" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Now price consistency
	</span>
</h3>
<p>Cost per success rewards a model that is cheap and often right. It does not reward a model that is right every time. So we also compute cost per dependable task: the cost of the full 20-run campaign divided by the number of tasks the model passed on all 20 attempts.</p>
<blockquote>
<p><strong>Cost per dependable task = estimated cost of 20 runs of 507 attempts ÷ tasks passing 20/20</strong></p>
</blockquote>
<p><strong>Example:</strong> GPT-6-Astra costs 20 × $86.03 = $1,720.60 for the campaign and passes 231 tasks on every attempt, so $1,720.60 ÷ 231 = $7.45 per dependable task.</p>

<h2 class="relative group flex items-baseline">
	<a id="failure-signatures" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#failure-signatures" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Failure signatures
	</span>
</h2>
<p>We assign each failed trace one deterministic diagnostic signature, and the headline is actionable: roughly four in five failures are tool handling, not reasoning. Across an ablation study in <a href="https://arxiv.org/pdf/2608.19741" rel="nofollow">Table 5 of our paper</a>:</p>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th>Failure signature</th>
<th>Share of failures</th>
</tr>

		</thead><tbody><tr>
<td>Tool usage</td>
<td>79.9%</td>
</tr>
<tr>
<td>Wrong state updates</td>
<td>10.3%</td>
</tr>
<tr>
<td>Incomplete user resolutions</td>
<td>7.0%</td>

<td>2.9%</td>
</tr>
</tbody>

<p>These are unweighted averages of per-model shares and observable labels, not unique causal explanations.</p>
<p>The practical pattern is simple: agents usually get far enough to attempt the workflow, then fail to recover from tool errors, failed preconditions, or empty lookups. That is a retry and error-recovery problem before it is a model problem.</p>
<p>Difficulty also changes by domain: across the models listed in Table 2 above, retail averages 59.52% pass@1 while auto insurance averages 33.83%.</p>
<p><strong>What to do about it.</strong> Treat the 20/20 rate as a design input, not a verdict. The same signal the benchmark grades on is available in production: check the terminal state before you commit, not the model's summary of it.</p>
<p>Classify tool and system errors so retries target the recoverable ones. Cut the tool surface to what the workflow needs. And require human approval on the changes you cannot cheaply reverse. We have not measured the lift from any of these on this benchmark, which is exactly the kind of thing the environment now makes testable.</p>
<h2 class="relative group flex items-baseline">
	<a id="how-it-works" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#how-it-works" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		How it works
	</span>
</h2>
<p>ThinkingBox is the agent sandbox, while ThinkingBox-Bench is a dataset benchmark to evaluate agents. The diagram at the top of this post shows the loop; here is what each part does.</p>
<p><a href="https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/elbRGqTXW6PIqci7xcEJN.png" rel="nofollow"><img src="https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/elbRGqTXW6PIqci7xcEJN.png" alt="Figure-1a"></a></p>
<p><em>Figure 5: The sandbox loop from panel A in Figure 1 above: isolated tool session, terminal database state, side effects, executable judges.</em></p>
<p>Each task defines a starting backend state, a user goal, the available MCP tools, the domain policy, and executable checks over the terminal state. A simulated user holds private context (a booking reference, a preference, or a date of birth) and releases it only when asked.</p>
<p>Every attempt gets an isolated MCP session with freshly initialized state. Two attempts of the same task never share a database row or cached tool state, which is what makes 20-trial comparison meaningful.</p>
<p>At the end, a side-effect extractor derives what actually changed, and deterministic judges compare it against the required end state, accepting <em>any</em> trajectory that produces the right outcome while rejecting wrong, missing or extra effects. For requirements with no clean database value ("did the agent disclose this is not guaranteed?"), a narrow binary rubric question handles the semantics. 477 of the 507 tasks are graded on state alone; 30 add response rubrics.</p>
<p>The trust boundary: the model sees tasks, dialogue and tool schemas. Golden state, assertions, grading internals and credentials stay on the evaluator side.</p>
<h2 class="relative group flex items-baseline">
	<a id="run-it-yourself" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#run-it-yourself" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Run it yourself
	</span>
</h2>
<p>ThinkingBox is now on Hugging Face, both <a href="https://huggingface.co/docs/openenv/environments/thinkingbox">the harness</a> and <a href="https://huggingface.co/datasets/microsoft/ThinkingBox-Bench">the dataset</a>. ThinkingBox-Bench now sits behind the OpenEnv interface, and each finished episode returns a binary pass/fail reward. The released adapter is designed for evaluation; separate, non-benchmark scenarios can use the same interface in training workflows.</p>
<h3 class="relative group flex items-baseline">
	<a id="before-you-start" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#before-you-start" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Before you start
	</span>
</h3>
<p>Tested on Linux and WSL, with Python 3.11+, <a href="https://docs.astral.sh/uv/" rel="nofollow">uv</a> and Docker. You also need a <a href="https://github.com/microsoft/thinkingbox-data" rel="nofollow">thinkingbox-data</a> checkout at the pinned release and model endpoints for the agent, simulated user and judge. One endpoint can serve all three roles, which is the simplest way to start. The OpenEnv image starts <em>only the OpenEnv API</em>; everything else you run yourself.</p>
<h3 class="relative group flex items-baseline">
	<a id="install" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#install" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Install
	</span>
</h3>
<pre><code class="language-bash"><span class="hljs-comment"># 1. OpenEnv + the ThinkingBox environment</span>
git <span class="hljs-built_in">clone</span> https://github.com/huggingface/OpenEnv
<span class="hljs-built_in">cd</span> OpenEnv
uv <span class="hljs-built_in">sync</span> --project envs/thinkingbox_env --frozen
<span class="hljs-comment"># 2. The executable benchmark, at the pinned release</span>
git <span class="hljs-built_in">clone</span> https://github.com/microsoft/thinkingbox-data
git -C thinkingbox-data checkout thinkingbox-bench-v1.0
<span class="hljs-comment"># 3. The ThinkingBox CLI, which provides `tb`</span>
uv tool install <span class="hljs-string">"thinkingbox @ git+https://github.com/microsoft/thinkingbox"</span>
</code></pre>
<h3 class="relative group flex items-baseline">
	<a id="start-typesense" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#start-typesense" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Start Typesense
	</span>
</h3>
<p>In a <strong>second terminal</strong>, start Typesense 30.1 and wait for its health check:</p>
<pre><code class="language-bash"><span class="hljs-built_in">mkdir</span> -p .typesense-data
docker run --<span class="hljs-built_in">rm</span> -d --name thinkingbox-typesense \
  -p 8108:8108 \
  -v <span class="hljs-string">"<span class="hljs-variable">$PWD</span>/.typesense-data:/data"</span> \
  typesense/typesense:30.1 \
  --data-dir /data --api-key=Fake --enable-cors
<span class="hljs-keyword">until</span> curl -fsS http://127.0.0.1:8108/health; <span class="hljs-keyword">do</span> <span class="hljs-built_in">sleep</span> 1; <span class="hljs-keyword">done</span>
</code></pre>
<h3 class="relative group flex items-baseline">
	<a id="start-the-mcp-servers" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#start-the-mcp-servers" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Start the MCP servers
	</span>
</h3>
<p>In a <strong>third terminal</strong>, start the Session Proxy and MCP servers.</p>
<pre><code class="language-bash"><span class="hljs-built_in">cd</span> OpenEnv
tb mcp-start --host 127.0.0.1 --port 7111 \
  --servers <span class="hljs-string">"<span class="hljs-variable">$PWD</span>/thinkingbox-data/servers/servers.yaml"</span>
curl -fsS http://127.0.0.1:7111/health
</code></pre>
<h3 class="relative group flex items-baseline">
	<a id="start-the-openenv-server" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#start-the-openenv-server" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Start the OpenEnv server
	</span>
</h3>
<p>Back in the first terminal, start the OpenEnv server against a ThinkingBox YAML config naming your three models (<a href="https://github.com/microsoft/thinkingbox/blob/main/docs/llm_endpoint_config.md" rel="nofollow">config guide</a>):</p>
<pre><code class="language-bash">OPENENV_TB_CONFIG=<span class="hljs-string">"<span class="hljs-variable">$PWD</span>/thinkingbox.yaml"</span> \
uv run --project envs/thinkingbox_env --frozen server
</code></pre>
<h3 class="relative group flex items-baseline">
	<a id="check-readiness" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#check-readiness" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Check readiness
	</span>
</h3>
<p>Gate on readiness before running anything. It returns 503 until its observable data, configuration and Session Proxy checks pass. It cannot observe Typesense or live-probe every model endpoint, so confirm those separately:</p>
<pre><code class="language-bash">curl -sS http://127.0.0.1:8000/ready
</code></pre>
<h3 class="relative group flex items-baseline">
	<a id="score-an-episode" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#score-an-episode" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Score an episode
	</span>
</h3>
<p>Now score a real episode. <a href="https://github.com/huggingface/OpenEnv/blob/main/examples/thinkingbox/example_usage.py" rel="nofollow">example_usage.py</a> only resets and lists tools; for agent actions, effects and assertions use the packaged evaluator:</p>
<pre><code class="language-bash"><span class="hljs-built_in">echo</span> <span class="hljs-string">"- sandbox_external_retail_group1.py:test_case_ST002_001"</span> &gt; one_task.yaml
uv run --project envs/thinkingbox_env thinkingbox-eval \
  one_task.yaml \
  --config <span class="hljs-string">"<span class="hljs-variable">$PWD</span>/thinkingbox.yaml"</span> \
  --output results.jsonl \
  --errors-output errors.jsonl \
  --repeat 1 --message-timeout 1800
</code></pre>
<p>The OpenEnv adapter writes operational failures to an errors sidecar so they can be rerun rather than silently mixed with model outcomes. A canonical result must resolve or explicitly account for those attempts; we counted system errors as unsuccessful trials.</p>
<p>Runs are gated on a pinned framework commit, a pinned data release and a bundle hash, so a canonical result is verifiable rather than asserted.</p>
<h2 class="relative group flex items-baseline">
	<a id="where-this-goes-next" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#where-this-goes-next" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Where this goes next
	</span>
</h2>
<p>The useful part of this work is not our pass@1 leaderboard. It is the environment.</p>
<p>If you are evaluating an agent that touches real records:</p>
<ol>
<li><strong>Inspect a failure.</strong> Find a run that terminated cleanly and still failed, and look at what actually changed in the database. It reframes what your own evals measure.</li>
<li><strong>Reproduce one task</strong> through OpenEnv with your own model.</li>
<li><strong>Report a repeat metric, and define it.</strong> Whatever k your use case justifies; say whether you are reporting best-of-k or every-of-k, and how you computed it.</li>
</ol>
