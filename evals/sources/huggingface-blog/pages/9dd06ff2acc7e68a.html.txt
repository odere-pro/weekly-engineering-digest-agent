<p>The series "Profiling in PyTorch" is meant to make you comfortable reading profiler traces and tables. In <a href="https://huggingface.co/blog/torch-profiler">Part 1</a> we profiled basic math operations like addition and multiplication. We saw how the profiler table uncovers hotspots, and how the profiler trace shows the order in which an algorithm runs over time.</p>
<p>In <a href="https://huggingface.co/blog/torch-mlp-fusion">Part 2</a> we wrapped that addition and multiplication into a torch linear layer. We then stacked several linear layers on top of each other (a multilayer perceptron) and profiled that. Along the way we also profiled fused and hand-tuned kernels.</p>
<p>From the perspective of the Transformer architecture, the next logical step for us to profile is yet another fundamental algorithm, attention. While being infamous for its quadratic-time complexity, many clever tricks exist to mitigate that issue and make it fast. Our goal here is not to cover every trick in detail. Instead, we want to see how each one looks different under the profiler.</p>

<h2 class="relative group flex items-baseline">
	<a id="naive-attention" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#naive-attention" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Naive attention
	</span>
</h2>
<p>Attention works with Queries (<code>q</code>), Keys (<code>k</code>), and Values (<code>v</code>). The interaction between them can be written as a short sequence of steps:</p>
<ol>
<li>Build the attention scores <code>scores</code>: <code>matmul(q, k.T)</code></li>
<li>Scale the scores: <code>scores * scale</code></li>
<li>Apply a causal mask to the scores: <code>scores.masked_fill(mask, "-inf")</code></li>
<li>Normalize the scores with softmax to get the attention weights <code>attn</code>: <code>softmax(scores)</code></li>
<li>Reweight the values with those weights: <code>matmul(attn, v)</code></li>
</ol>
<p>So attention is really a collection of primitive operations. Some of them we already know (the matmuls), and the rest are easy to spot. Let's write a naive attention module in PyTorch and profile it.</p>
<pre><code class="language-py"><span class="hljs-keyword">class</span> <span class="hljs-title class_">NaiveCausalAttention</span>(nn.Module):
    <span class="hljs-keyword">def</span> <span class="hljs-title function_">__init__</span>(<span class="hljs-params">self, head_dim</span>):
        <span class="hljs-built_in">super</span>().__init__()
        self.scale = <span class="hljs-number">1.0</span> / math.sqrt(head_dim)

    <span class="hljs-keyword">def</span> <span class="hljs-title function_">forward</span>(<span class="hljs-params">self, q, k, v, mask</span>):
        scores = torch.matmul(q, k.transpose(-<span class="hljs-number">2</span>, -<span class="hljs-number">1</span>))
        scores = scores * self.scale
        scores = scores.masked_fill(mask, <span class="hljs-built_in">float</span>(<span class="hljs-string">"-inf"</span>))
        attn = torch.softmax(scores, dim=-<span class="hljs-number">1</span>)
        out = torch.matmul(attn, v)
        <span class="hljs-keyword">return</span> out
</code></pre>
<p>Before opening the trace, let's do our usual exercise and guess what we should see. Tracing the <code>forward</code> of this module, we expect:</p>
<ul>
<li>a matmul kernel (<code>q . k.T</code>)</li>
<li>a mul kernel (the scaling)</li>
<li>an operation for the masking</li>
<li>a softmax kernel</li>
<li>a matmul kernel (<code>atten . v</code>)</li>
</ul>
<pre><code class="language-bash">uv run 04_a_naive_attention.py
uvx trace-util -f traces/ -b &lt;hf_uname&gt;/traces
</code></pre>

<p>Five of these are expected. The memory copy is the odd one out, so where does this come from? The clue is that PyTorch has in-place operations. When you operate on a tensor the ordinary (out-of-place) way, PyTorch often makes a copy, applies the requested operation to it, and returns the copy. Following the sequence of operations, the culprit here is our <a href="https://docs.pytorch.org/docs/2.13/generated/torch.Tensor.masked_fill.html" rel="nofollow"><code>masked_fill</code></a>.</p>
<p>What if we replaced this with an in-place operation?</p>
<h2 class="relative group flex items-baseline">
	<a id="naive-attention-with-inplace-causal-masking" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#naive-attention-with-inplace-causal-masking" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Naive attention with inplace causal masking
	</span>
</h2>
<p>All we change is <code>masked_fill</code> to <code>masked_fill_</code> (note the trailing underscore, PyTorch's convention for in-place operations), and we run the same script.</p>
<pre><code class="language-diff">def forward(self, q, k, v, mask):
    # q, k, v: [batch, heads, seq, head_dim]
    scores = torch.matmul(q, k.transpose(-2, -1))  # [batch, heads, seq, seq]
    scores = torch.mul(scores, self.scale)
<span class="hljs-deletion">-    scores = scores.masked_fill(mask, float("-inf"))</span>
<span class="hljs-addition">+    scores.masked_fill_(mask, float("-inf"))</span>
    attn = torch.softmax(scores, dim=-1)
    out = torch.matmul(attn, v)  # [batch, heads, seq, head_dim]
    return out
</code></pre>

<p>On the GPU lane the <code>Memcpy</code> kernel is gone for good (Figures 6 and 7). With a one line change we shaved a whole kernel off each forward pass. This may not look like much on its own, but remember this is a single attention operation. In the context of a transformer based large model (LLMs, Diffusion models, etc.), it repeats once per layer, and there are many layers, so the saving adds up quickly (and if it earns you a raise, sharing at least 10% with us feels only fair).</p>
<blockquote class="note">
<p>Out-of-place is PyTorch's default for a reason. To compute gradients, autograd has to remember the tensor values it saw on the forward pass, because many backward formulas reuse them. An in-place operation overwrites those values in memory, so the backward pass would read the wrong numbers. Due to the fact that we run <code>forward</code> under <code>torch.no_grad</code>, in-place is safe for us, with no backward pass and nothing to corrupt. It is also noteworthy that in-place operations do not only save time (like we see in our case) but also memory (due to no extra copy) which is great for large tensors like logits!</p>
</blockquote>
<h2 class="relative group flex items-baseline">
	<a id="scaled-dot-product-attention" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#scaled-dot-product-attention" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Scaled Dot Product Attention
	</span>
</h2>
<p>We just built attention from primitives, and even shaved off a <code>Memcpy</code>. The good news is that the PyTorch team has done all of this for us, and packaged the whole pipeline into a single function:</p>
<pre><code class="language-py"><span class="hljs-keyword">from</span> torch.nn <span class="hljs-keyword">import</span> functional <span class="hljs-keyword">as</span> F

F.scaled_dot_product_attention(q, k, v, is_causal=<span class="hljs-literal">True</span>)
</code></pre>
<p>This one line replaces our hand written module, and <code>is_causal=True</code> even saves us from building the mask by hand. It is worth pausing to appreciate how much this one call hides. And it hides more than just code lines. Scaled Dot Product Attention (SDPA) does not have a single implementation. Under the hood it <em>dispatches</em> to one of the several backends and picks the fastest one that supports our inputs (dtype, head dimension, mask, hardware, etc.).</p>
<p>The <a href="https://docs.pytorch.org/tutorials/intermediate/scaled_dot_product_attention_tutorial.html" rel="nofollow">official SDPA tutorial</a> walks us through this selection, and the backends themselves are listed in the <code>torch.nn.attention.SDPBackend</code> enum:</p>
<pre><code class="language-python"><span class="hljs-keyword">from</span> torch.nn.attention <span class="hljs-keyword">import</span> SDPBackend

BACKENDS = {
    <span class="hljs-string">"math"</span>: SDPBackend.MATH,
    <span class="hljs-string">"flash"</span>: SDPBackend.FLASH_ATTENTION,
    <span class="hljs-string">"efficient"</span>: SDPBackend.EFFICIENT_ATTENTION,
    <span class="hljs-string">"cudnn"</span>: SDPBackend.CUDNN_ATTENTION,
}
</code></pre>
<p>Normally SDPA chooses for us, but we can pin a specific backend with the <code>torch.nn.attention.sdpa_kernel</code> context manager. This is what we do in our scripts. This lets us profile each backend on its own and read how differently they show up in the trace. Let's go one at a time.</p>

<h4 class="relative group flex items-baseline">
	<a id="tensor-cores-left-vacant" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#tensor-cores-left-vacant" rel="nofollow">

	<span>
		Tensor cores left vacant

<p>In <a href="https://huggingface.co/blog/torch-mlp-fusion#where-did-the-transpose-go-kernel-layouts-and-pre-ops">Part 2</a> we learned to read a kernel name like a fingerprint. Let's use that habit here:</p>

<p>The A100s we used to capture these traces ship with <a href="https://www.nvidia.com/en-us/data-center/tensor-cores/" rel="nofollow">Tensor Cores</a>, specialised hardware for accelerated matmuls that is known to be far faster than the ordinary CUDA cores. To see why that matters here, it helps to know what lives inside a GPU. A Streaming Multiprocessor (SM) is the compute unit of a GPU, and each SM has two kinds of arithmetic units, the CUDA cores and the Tensor Cores. CUDA cores are general purpose and process a handful of elements at a time, while Tensor Cores multiply and accumulate a whole small matrix tile in a single instruction. So the question is simple, "Is each backend actually using the fast path?"</p>
<p>The kernel names answer it. The <code>s16816</code> in the naive kernel (Figure 10) is the signature of a <code>bfloat16</code> Tensor Core matmul (the <code>16x8x16</code> Tensor Core instruction), so the naive version is on the fast path. <code>sgemm</code> (Figure 11) is the classic single precision (<code>FP32</code>) matmul that runs on the ordinary CUDA cores. In other words, the math backend never touches the Tensor Cores at all: to trade speed for numerical accuracy it upcasts tensors to <code>FP32</code> (doubling the data moved, even when the inputs are in <code>bf16</code>) and falls back to the slower CUDA cores.</p>

	<a id="causal-masks-built" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#causal-masks-built" rel="nofollow">

<h4 class="relative group flex items-baseline">
	<a id="so-what-is-the-math-backend-for" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#so-what-is-the-math-backend-for" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		So what is the math backend for?
	</span>
</h4>
<p>Put together, the math backend is the reference implementation. It is a straightforward, dtype-safe, NaN-safe decomposition of attention into primitive ATen ops. It is essentially the naive attention we wrote by hand, but more careful. That carefulness is exactly what makes it extremely slow.</p>
<p>Its job is not to be fast, but to <em>always</em> work. This makes it the perfect baseline. Every backend we profile next (flash, efficient, cudnn) is trying to collapse the <code>20</code> GPU kernels into essentially one fused kernel that stays in bf16 and never materializes the intermediate matrices at all.</p>
<h3 class="relative group flex items-baseline">
	<a id="efficient-backend" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#efficient-backend" rel="nofollow">

	</a>
	<span>
		Efficient backend
	</span>
</h3>
<pre><code class="language-bash">uv run 04_c_sdpa_attention.py --backend efficient
uvx trace-util -f traces -b &lt;hf_uname&gt;/traces
</code></pre>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="center"><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/efficient-backend.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/efficient-backend.png" alt="Profiler trace of the SDPA efficient backend showing a single fused fmha_cutlassF attention kernel per forward"></a></th>

<p>Where the math backend launched 20 kernels across one profiler step, the efficient backend launches only one <code>fmha_cutlassF_bf16_aligned_64x64_rf_sm80</code> (as seen in Figure 14).</p>
<p>Let's decode the name of the kernel:</p>
<ul>
<li><code>fmha</code> (fused multi-head attention): All the primitive ops in attention is "fused" in one op now.</li>
<li><code>cutlassF</code>: built on CUTLASS (NVIDIA's open-source templates for tensor-core GEMMs), <code>F</code> for forward.</li>
<li><code>bf16_aligned</code>: runs in bfloat16 (no FP32 upcast, unlike math).</li>
<li><code>64x64</code>: the tile size.</li>
<li><code>rf</code> (register file): the working set is kept in registers, the fastest memory on the chip.</li>
<li><code>sm80</code>: compiled for Ampere (the A100's compute capability 8.0).</li>
</ul>
<p>This is the memory efficient attention kernel that grew out of Meta's <a href="https://github.com/facebookresearch/xformers" rel="nofollow">xformers</a> library and was upstreamed into PyTorch. When people say "the xformers backend," this <code>fmha_cutlassF</code> kernel is what they mean.</p>
<h3 class="relative group flex items-baseline">
	<a id="flash-backend" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#flash-backend" rel="nofollow">

		Flash backend

<p>The <code>void pytorch_flash</code> kernel (Figure 15) is <a href="https://arxiv.org/abs/2307.08691" rel="nofollow">FlashAttention-2</a> (Tri Dao's implementation), vendored into PyTorch.</p>
<p>Before we read the trace any further, it is worth answering the question you should be asking by now: <em>why is there a whole backend named "flash", and why does it matter so much?</em></p>
<h4 class="relative group flex items-baseline">
	<a id="why-flash-attention-exists" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#why-flash-attention-exists" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Why flash attention exists?
	</span>
</h4>
<p>Let's go back to the math backend for a moment. Its real problem was not the count of 20 kernels, it was what those kernels handed to each other.</p>
<p>Step 1 builds the full score matrix <code>attn = q . k.T</code>, which is <code>[seq, seq]</code> <strong>per head</strong>. For a sequence length of 4096 that is <code>4096 x 4096 ≈ 16 million</code> numbers for a single head. That matrix is written out to the HBM (the GPU's main memory), if there is even enough space to do so. Then, it is read back to be scaled, written again for the mask, read again for the softmax, and so on. Attention's cost is dominated by this <strong>back and forth traffic to HBM</strong>, not by the matmuls themselves.</p>
<p>FlashAttention attacks exactly this. Instead of computing the whole <code>s</code> matrix and only then reducing it, it walks over <code>k</code> and <code>v</code> in <strong>tiles</strong>, keeps a running softmax as it goes (the "online softmax" trick), and accumulates the output one tile at a time. The full <code>[seq, seq]</code> score matrix is <strong>never written to HBM</strong>, it only ever lives on-chip. This is the single idea that lets the entire attention pipeline collapse into one fused kernel that stays in bf16 on the Tensor cores.</p>
<h4 class="relative group flex items-baseline">
	<a id="why-flash-looks-wrong-under-the-profiler" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#why-flash-looks-wrong-under-the-profiler" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Why flash looks "wrong" under the profiler
	</span>
</h4>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="center"><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/flash-occupancy.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/flash-occupancy.png" alt="Perfetto footprint of the flash kernel reporting an estimated achieved occupancy of 13%"></a></th>
</tr>

		</thead><tbody><tr>
<td align="center">Figure 16: Estimated occupancy of flash kernel is seen to be 13%</td>
</tr>
</tbody>
	</table>
</div>
<p>Here is where flash surprises people who read profiler footprints. It is the fastest backend, yet the profiler reports it with very <strong>low occupancy</strong> (shown in Figure 16). To see why that is fine, we need three quick definitions.</p>
<p>A GPU kernel is essentially a series of instructions executed by many small execution units. These individual execution units (threads) take care of loading variables, adding them together, storing them back, etc. For each kernel, we launch many, many threads, and to keep track of them, we group them by blocks.</p>
<p>Blocks are scheduled onto Streaming Multiprocessors (SMs), the main compute units of a GPU. A block lives entirely on one SM, and an SM can host multiple blocks at once <em>if it has enough resources</em>. Those resources include registers, shared memory, maximum resident threads, and maximum resident warps. So when we say a kernel has low <strong>occupancy</strong>, we mean each SM has fewer resident warps than it could theoretically support.</p>
<blockquote class="tip">
<p>If you want to know more about threads, blocks, grids, etc. here is a <a href="https://huggingface.co/blog/mi300kernels#a-quick-introduction-to-the-mi300x">great resource</a>.</p>
</blockquote>
<p>If you click the flash kernel in the trace, its footprint tells the story (Figure 17).</p>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="center"><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/flash-reg-count.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/flash-reg-count.png" alt="Resource footprint of the pytorch_flash kernel in Perfetto, showing a high per-thread register count and large shared memory usage per block"></a></th>
</tr>

		</thead><tbody><tr>
<td align="center">Figure 17: The flash kernel footprint, heavy on registers and shared memory per block.</td>
</tr>
</tbody>
	</table>
</div>
<p>Flash uses a lot of per-thread registers and a large amount of shared memory per block. For example, if a block has 128 threads and each thread uses 255 registers, that block needs <code>128 × 255 = 32,640</code> registers. On an Ampere SM with 65,536 registers, only two such blocks fit at once. Each 128-thread block has <code>128 / 32 = 4</code> warps, so two blocks give only 8 resident warps. Against a maximum of 64 resident warps, that is roughly 13% occupancy. Flash has low occupancy not because it is poorly optimized, but because each block is deliberately very "heavy" in on-chip resource usage.</p>
<p>And that is the whole point. High occupancy helps <em>hide latency</em> by keeping many warps ready to run, but it does not make the work itself efficient. Flash spends those registers and that shared memory on purpose, to keep attention tiles on-chip, reuse data aggressively, and avoid ever materializing the full attention matrix in global memory.</p>
<h3 class="relative group flex items-baseline">
	<a id="cudnn-backend" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#cudnn-backend" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		cuDNN backend
	</span>
</h3>
<pre><code class="language-bash">uv run 04_c_sdpa_attention.py --backend cudnn
uvx trace-util -f traces -b &lt;hf_uname&gt;/traces
</code></pre>
<div class="max-w-full overflow-auto">
	<table>
		<thead><tr>
<th align="center"><a href="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/cudnn-backend.png" rel="nofollow"><img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-attention-profile/cudnn-backend.png" alt="Profiler trace of the SDPA cuDNN backend showing a single cudnn_generated attention kernel per forward"></a></th>

<p>By now the pattern is familiar. Like flash and efficient, cuDNN gives us one fused, flash-style kernel per forward (Figure 18). So the natural question is: <strong>if flash already fuses attention, why does PyTorch ship yet another flash backend?</strong> The answer is <em>who writes the kernel and how it is built</em>, and that difference is what makes the trace look different.</p>
<h4 class="relative group flex items-baseline">
	<a id="how-is-cudnn-kernel-different" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#how-is-cudnn-kernel-different" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		How is cuDNN kernel different
	</span>
</h4>
<p>Flash and efficient are <strong>fixed, pre-compiled kernels</strong> vendored into PyTorch. You get the same binary every time. cuDNN is NVIDIA's own deep learning library, and its attention kernel is <strong>generated and tuned for the specific problem</strong> at hand. It is closer in spirit to <code>torch.compile</code>'s codegen than to a fixed cuBLAS binary. You can read that straight off the (very long) kernel name:</p>
<pre><code class="language-bash">cudnn_generated_fort_native_sdpa_sm80_flash_fprop_wmma_f16_knob_6_128x64x64_4x1x1_cga1x1x1_kernel0_0
</code></pre>
<ul>
<li><code>cudnn_generated</code>: not a pre-shipped binary, it was generated by cuDNN.</li>
<li><code>flash_fprop</code>: a flash attention style forward pass. So the algorithm is the same family as the flash backend.</li>
<li><code>wmma_f16</code>: it uses the warp-level matrix multiply-accumulate (WMMA) API, the Tensor-core path on the 16-bit float pipeline.</li>
<li><code>knob_6</code>: cuDNN picks from a set of pre-tuned configurations ("knobs"). Different shapes select different knobs, much like cuBLAS picking a tile variant.</li>
<li><code>128x64x64</code>: the tile dimensions it chose.</li>
</ul>
<p>That one fact, <em>generated per problem</em>, explains everything else that looks unusual in the trace.</p>
<ol>
<li><p>No transposes: The CPU lane goes from <code>_cudnn_attention_forward</code> straight to a couple of <code>aten::empty</code> allocations and then the kernel, with zero <code>aten::transpose</code> (Figures 19, 20 and 21). Flash and efficient each insert four (metadata) transposes to reshape the tensors while cuDNN consumes the native <code>[B, H, S, D]</code> layout directly because its generator emits a kernel for that layout.</p>

	<span>
		The cost moved to the CPU
	</span>
</h4>
<p>The "no transposes" story tempts us to expect cuDNN to be the <em>leanest</em> backend on the CPU. It is the opposite.</p>

<p>Even with zero transpose ops, cuDNN spends about <strong>214 µs per forward on the CPU</strong>, more than flash (138) or efficient (117). Almost all of it sits in <code>aten::scaled_dot_product_attention</code> self time (26% of the whole run) and <code>_cudnn_attention_forward</code>. That is cuDNN's runtime engine selecting and preparing the plan (the "knob" search) on every call.</p>
<p>Fewer visible ATen ops did not mean less CPU work, it <strong>moved the work into the library</strong>, where the profiler can only show it as one fat, opaque bar. When a trace suddenly gets <em>cleaner</em>, the work has not always disappeared, sometimes it has just moved somewhere the profiler cannot break down.</p>
<p>On the GPU, cuDNN (186.3 µs) lands between efficient and flash. On this very flash-friendly shape, hand-written FlashAttention-2 edges it out. cuDNN often wins on <em>other</em> shapes (larger head dimensions, different sequence lengths) precisely because its generator retunes per problem, but that retuning is also what you just paid for on the CPU.</p>

<h2 class="relative group flex items-baseline">
	<a id="concluding-the-series" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#concluding-the-series" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Concluding the series
	</span>
</h2>
<p>If you take away only one thing from the whole series, let it be the habit we repeated before every single trace which is to <strong>guess first, then look.</strong></p>
<p>State out loud what you expect the trace to contain, open it, and treat any mismatch as the most interesting thing on the screen. Every real insight in these three posts, the hidden <code>Memcpy</code>, the <code>addmm</code> epilogue, the 20 kernel math backend, flash's "wrong-looking" occupancy, cuDNN's fat CPU bar, came from a guess that did not match the trace.</p>
<p>Profiling is not a separate, intimidating skill reserved for GPU experts. It is just the discipline of looking closely and asking "wait, why is <em>that</em> happening?" until the answer clicks. You now have the vocabulary and the reflexes to do that on your own models. Open a trace, form a guess, and go find the mismatch.</p>
