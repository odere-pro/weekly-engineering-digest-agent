<p><!--[--><!--[0--><div class="absolute -left-12 bottom-0 top-0 z-30 not-prose hidden lg:block"><div class="sticky top-4 flex"><div class="h-7 pt-[0.175rem]"><span class="peer" tabindex="0"><button class="select-none text-gray-400 hover:cursor-pointer hover:text-gray-800 dark:text-gray-500 dark:hover:text-gray-400"> <!----></button></span> <div class="invisible w-0 -translate-x-8 -translate-y-6 overflow-hidden rounded-xl border bg-white transition-transform hover:visible hover:w-52 hover:translate-x-0 peer-focus-within:visible peer-focus-within:w-52 peer-focus-within:translate-x-0"> </div></div></div></div><!--]--><!--]-->Your agent works in rehearsal, but during the live demo, it takes a different path and fails the same task.</p>
<p>That is embarrassing onstage. In production, it is a reliability problem: a workflow that succeeded once may fail the next time a user makes the same request. For mission-critical work, such as reconciling a financial transaction or checking a contract for an obligation, that can be a showstopper.</p>
<p>Most benchmarks hide this variability behind an average. On AppWorld, a ReAct agent using GPT-4.1 succeeded on <strong>77.4% of runs</strong> across five repetitions. But it succeeded in all five runs for only <strong>53.0% of tasks</strong> — a <strong>24.4-point consistency gap</strong>.</p>
<p>Most benchmarks report the first number. We built a way to measure the second — and improve it.</p>
<p>In an earlier post, we introduced <a href="https://huggingface.co/blog/ibm-research/altk-evolve">ALTK-Evolve</a> — a system that turns an agent's own past trajectories into reusable guidelines, distilled automatically and injected back at inference time. It measurably improves task success, but those results only asked the average-case question too.  This post introduces <strong>consistency guidelines</strong>, a new guideline type in <a href="https://github.com/AgentToolkit/altk-evolve" rel="nofollow"><code>altk-evolve</code></a> built on top of a diagnostic tool we call the <strong>Consistency Analyzer</strong>, that targets this gap directly. </p>
<p><strong>TL;DR</strong></p>
<ul>
<li><strong>Accuracy hides an unreliability problem.</strong> A ReAct agent (GPT-4.1 on AppWorld <code>test_normal</code>) that succeeds 77.4% of the time on average succeeds on <em>all 5</em> repeated runs for only 53.0% of tasks — a <strong>24.4-point consistency gap</strong>. On hard tasks it reaches 30 points.</li>
<li><strong>We built a diagnostic for exactly this.</strong> The Consistency Analyzer resamples an agent's own recorded trajectory to find <em>flip-prone</em> decision points — steps where the model was one token-sample away from doing something different. It needs one trace and no ground truth — it resamples each decision point in that trace with a single call requesting k completions (k=5 by default), rather than re-running the task end-to-end.</li>
<li><strong>Turning that diagnosis into guidelines halves the gap</strong> — from <strong>24.4pp to 12.0pp</strong> (same-task Pass⁵ +16.0pp, similar-task +13.0pp), without costing anything in average accuracy.</li>
<li><strong>Full methodology and evaluations</strong> are in the <a href="https://arxiv.org/abs/2609.08832" rel="nofollow">technical report on arXiv</a>.</li>
</ul>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="the-metric-almost-nobody-reports" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-metric-almost-nobody-reports" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The Metric Almost Nobody Reports
	</span>
</h2>
<p>Standard agent evaluation reports <strong>Mean@k</strong>: run a benchmark <em>k</em> times, average the pass rate. Often <em>k</em>=3, sometimes just 1. It's the number on every leaderboard, and it's what "77% accurate" means in practice.</p>
<p>Mean@k answers "how good is this agent, on average?" It does not answer the question a real user cares about: <strong>will it still be good if I ask this exact question again?</strong> For that you need <strong>Pass^k</strong>: the fraction of tasks where the agent succeeds on <em>all</em> k runs.</p>
<blockquote>
<p>⚠️ <strong>Pass^k is not Pass@k.</strong> The familiar <strong>Pass@k</strong> is <em>optimistic</em> — it asks whether <strong>at least one</strong> of k attempts succeeded, the right question when you can verify and retry. <strong>Pass^k</strong> is its pessimistic mirror image: <strong>every</strong> attempt must succeed. Same letters, opposite question. Pass^k ≤ Mean@k ≤ Pass@k, always.</p>
</blockquote>
<div align="center">
<img alt="Mean@5 vs. Pass^5 by task difficulty, GPT-4.1 on AppWorld test_normal, with the consistency gap called out in red" src="https://cdn-uploads.huggingface.co/production/uploads/6435a1131860001f144239ea/BdzmSgkon1dAtbOCWqmKF.png" width="500">
</div>


<p>A ReAct agent backed by GPT-4.1 posts a Mean@5 of <strong>77.4%</strong> — genuinely strong. But Pass^5 is only <strong>53.0%</strong>. Nearly a quarter of the benchmark consists of tasks the agent can <em>sometimes</em> solve and sometimes can't, with nothing about the task changing between runs. We call this gap — Mean@k minus Pass^k — the <strong>consistency gap</strong>.</p>
<p>This isn't a capability problem you fix with a bigger model. It's an orthogonal axis: <strong>an agent can be capable and inconsistent at the same time.</strong></p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="why-agents-flip-sharp-decisions-vs-flat-ones" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#why-agents-flip-sharp-decisions-vs-flat-ones" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Why Agents Flip: Sharp Decisions vs. Flat Ones
	</span>
</h2>
<p>Every time an LLM agent decides something — which API to call, what argument to pass, whether to retry — that decision comes out of a probability distribution over next tokens. What matters is the <strong>shape</strong> of that distribution. A <strong>sharp</strong> one puts most of its mass on a single token: the runners-up are far behind, and the same choice comes out run after run. A <strong>flat</strong> one spreads comparable mass across several near-tied tokens, and which one wins is close to a coin flip.</p>
<p>The shape decides how much noise it takes to change the outcome. Sharp distributions are resilient — GPU floating-point non-associativity, request batching, and other platform-side effects nudge the numbers slightly, but nowhere near enough to reorder a clear winner. Flat distributions are vulnerable to exactly that nudge: near-ties may reorder under small perturbations. And because a trajectory chains dozens of decisions, a small per-step chance of flipping compounds into a large chance that <em>some</em> run goes differently. That's where a 24-point gap comes from.</p>
<p>This is also why the problem survives your decoding settings. Greedy decoding and a fixed seed both govern <em>how a distribution gets turned into a token</em> — they say nothing about the distribution itself. On a hosted endpoint the probabilities shift slightly from run to run, so the same prompt to the same model at temperature zero can still resolve a near-tie one way today and the other way tomorrow. </p>
<blockquote>
<p><strong>Our setup:</strong> the ReAct agent runs at <strong>temperature 0.0</strong>, so none of the variance above is ordinary sampling.</p>
</blockquote>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="diagnose-then-fix" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#diagnose-then-fix" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Diagnose, Then Fix
	</span>
</h2>
<p>Which turns the problem into a search: which steps in a given trajectory were the flat ones — and what do you do about them once you know?</p>
<p>Consistency guidelines come out of a two-stage pipeline that plugs into ALTK-Evolve's existing machinery — with a new source signal driving what gets written.</p>
<div align="center">
<img alt="consistency-guideline-pipeline" src="https://cdn-uploads.huggingface.co/production/uploads/6435a1131860001f144239ea/gdUd7l6Q8DzXCgzmchxi3.png" width="680">
</div>

<p><strong>1. Detect — the Consistency Analyzer.</strong> 
Given one recorded trajectory, the analyzer replays each decision step through controlled resampling, measuring how much the model's output actually varies at that point. Concretely, that's one additional model call per decision step, done once offline — issued with the sampling parameter set to draw k completions at once (k=5 by default) — replayed against the already-recorded context, not new tool calls, not new environment interactions, and not a second end-to-end rollout of the task. This yields a consistency score per decision step that is written into a scorecard to pinpoint exactly which decisions are at risk of flipping on the next run. Detection is fully black-box — no logits, no model internals, no instrumentation beyond the trace you already have.</p>
<p><strong>2. Generate — targeted guidelines.</strong>  Every flagged step becomes a candidate consistency guideline in the standard ALTK-Evolve format, so it slots into the existing storage and retrieval pipeline. Here's a real example, generated by GPT-4.1 from a trajectory of the AppWorld task "How many activities are done in my bucket list as per my SimpleNote note?":</p>
<blockquote>
<p>[Guideline 1] When counting checkbox-style markers in note content, use a line-anchored regex match rather than a plain substring count — note titles often repeat the marker symbol in a legend line.</p>
<p>[Guideline 2] Always verify search results for note queries by checking for multiple matches and confirming the correct note before proceeding.</p>
</blockquote>
<p>Nothing here is task-specific trivia. String-counting bugs and unverified search results are decision points that show up with high uncertainty across many AppWorld tasks. That's the point: the analyzer targets instability, not failure — so it catches steps the agent happened to get right this time but could easily get wrong next time.</p>
<p><a href="https://www.youtube.com/watch?v=qlp7EzXe8Pg" rel="nofollow">Watch the 2-minute demo</a> — five parallel runs of the agent split 3-2 on this task because of agent uncertainty about the counting strategy, then run again after these guidelines in context: all five agree.</p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="results-reducing-the-gap-without-losing-accuracy" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#results-reducing-the-gap-without-losing-accuracy" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Results: Reducing the Gap Without Losing Accuracy
	</span>
</h2>
<p>We evaluated on AppWorld <code>test_normal</code> (168 tasks) with a ReAct agent on GPT-4.1, generating consistency guidelines from a single baseline trajectory per task and testing them on 5 fresh runs.</p>
<div align="center">
<img alt="Pass⁵ lift from baseline to consistency guidelines, by task difficulty, GPT-4.1 on AppWorld test_normal" src="https://cdn-uploads.huggingface.co/production/uploads/6435a1131860001f144239ea/E_7HyAt5BSzZy9Pj0k3Wc.png" width="680">
</div>

<div align="center">
<img alt="Mean@5 aggregate, baseline vs. consistency guidelines, same scale as the Pass⁵ chart above" src="https://cdn-uploads.huggingface.co/production/uploads/6435a1131860001f144239ea/jzxSU5MJ8Ajf21aEjANyB.png" width="680">
</div>

<p align="center"><sub>Mean@5 (%), aggregate — same scale as Pass^5 above.</sub></p>

<p><strong>The consistency gap is cut roughly in half.</strong> Aggregate Pass^5 rises 53.0% → 69.0% while Mean@5 rises 77.4% → 81.0%, narrowing the gap between "looks capable" and "can be counted on" from <strong>24.4pp to 12.0pp</strong>. Nearly a third of previously-inconsistent tasks become tasks the agent passes on <em>every single run</em>.</p>
<p><strong>The middle and hard tiers gain most.</strong> Medium +22.9pp (+44% relative), Hard +14.3pp (+45% relative) — effectively tied in relative terms, with Medium ahead absolutely. Easy gains +12.2pp, having had the least room. This is consistency guidelines doing what they're designed to do: finding and stabilizing the specific decision points where an agent's own uncertainty was leaking into the outcome.</p>
<p><strong>Mean@5 never drops.</strong> Preserving average accuracy was a hard requirement, not a nice-to-have: a system that boosts Pass^5 by trading away Mean@5 would just be shifting unreliability around, not fixing it. Mean accuracy holds or improves at every difficulty level.</p>
<h3 class="relative group flex items-baseline">
	<a id="the-guidelines-generalize--they-arent-patching-one-trajectory" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#the-guidelines-generalize--they-arent-patching-one-trajectory" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		The guidelines generalize — they aren't patching one trajectory
	</span>
</h3>
<p>Applied to a <strong>different but related task in the same AppWorld scenario</strong> — another variant of the scenario the guidelines were mined from — consistency guidelines still lift Pass^5 by <strong>+13.0pp</strong>, only 3 points below the same-task number. A guideline derived from one run isn't just patching that run; it's capturing something that transfers.</p>
<p>The sharper evidence comes from a weaker model, <strong>gpt-oss-120b</strong>. Same-task Pass^5 rose +6.0pp from a much lower baseline (10.1% → 16.1%) — and, interestingly, the similar-task generalization number (+8.7 pp) actually <em>exceeded</em> the same-task gain, suggesting the guidelines were capturing genuinely reusable failure patterns rather than memorizing one trajectory's specifics.</p>
<hr>
<h2 class="relative group flex items-baseline">
	<a id="if-youre-shipping-an-agent" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#if-youre-shipping-an-agent" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		If You're Shipping an Agent
	</span>
</h2>
<ul>
<li><strong>Report Pass^k next to Mean@k.</strong> Averages can't distinguish a reliable agent from a lucky one; even k=3 will surface a gap you didn't know you had.</li>
<li><strong>Expect the gap to widen with difficulty.</strong> Your hardest tier is where a single averaged number is most misleading.</li>
<li><strong>Don't reach for a bigger model first.</strong> Consistency is orthogonal to capability. A stronger model raises Mean@k; it doesn't necessarily reduce the consistency gap.</li>
<li><strong>Diagnosis needs no grader and no live replay</strong>. One extra LLM call per decision step (sampling k=5 completions by default) is enough — no ground truth, no re-running the task against the environment. That's what makes it usable on production traffic, where you often can't replay a task end-to-end even once.</li>
</ul>

<h2 class="relative group flex items-baseline">
	<a id="appendix-understanding-the-metrics" class="block pr-1.5 text-lg md:absolute md:p-1.5 md:opacity-0 md:group-hover:opacity-100 md:right-full" href="#appendix-understanding-the-metrics" rel="nofollow">
		<span class="header-link"> </span>
	</a>
	<span>
		Appendix: Understanding the Metrics
	</span>
</h2>
<ul>
<li><strong>Mean@k.</strong> Run a task <em>k</em> times, report the average pass rate — what most benchmarks call "accuracy."</li>
<li><strong>Pass^k.</strong> The fraction of tasks where the agent succeeds on <strong>all</strong> <em>k</em> independent runs. Always ≤ Mean@k. What a user experiences if they run the same query twice.</li>
<li><strong>Pass@k</strong> At least <strong>one</strong> of <em>k</em> runs succeeds — the optimistic counterpart, common in code-generation papers.</li>
<li><strong>Consistency gap.</strong> Mean@k − Pass^k, in percentage points.</li>
</ul>

<!----><p>The useful split is the one most dashboards still refuse to print: Mean@k answers “how good is this agent on average?” Pass^k answers “will the same request still succeed if I ask again?”</p>
<p>Once you’ve watched a trajectory chain dozens of near-tied tool choices, a strong average with a wide consistency gap is exactly the demo that fails live. Capability and consistency are orthogonal — buying a bigger model can lift Mean without closing the gap.</p>
<p>What I want teams to take from the Consistency Analyzer framing is operational, not the guideline machinery itself: treat flip-prone decision steps as first-class eval targets. One offline resample pass over a recorded trace is a cheaper reliability signal than another end-to-end leaderboard screenshot.</p>
<p>Practical ask for anyone shipping agents from this: do you report Pass^k (even k=3) next to Mean@k in the release gate, and do you refuse the “stable” label when the consistency gap is still large on your hard tier?</p>
<p>Reproducible reliability will not remove disagreement about which guidelines to inject. It will make the disagreement about the right metric.</p>

own right. Beyond that, knowing where they are also turns the eval into a diagnostic: a consistency gap tells you that an agent is unreliable, while the flip-prone steps tell you where and why.</p>
<p>On your release-gate question: we'd strongly encourage it, and k=3 is a sensible default. A few things we'd suggest to anyone adopting Pass^k as a gate:</p>
<ul>
<li><strong>Fix k, and there's no need to push it much past 3</strong>. Pass^k gets stricter as k grows, so "Pass^3 ≥ X" and "Pass^5 ≥ X" are different bars; pick one and keep it across releases. We used k=5 for the study, but for a release gate, the returns diminish quickly beyond k=3. In our experience, most inconsistent tasks show at least one failure within the first three runs, so going further adds cost linearly while adding comparatively little new insight into which tasks are unreliable.</li>
<li><strong>Mind the sample size</strong>. Pass^k gives each task a single all-or-nothing outcome, so its precision depends mainly on the number of tasks, not on k, and both Pass^k and Mean@k stay noisy on small task sets. Compare releases task by task rather than by aggregate scores, and report task counts or intervals before calling an agent stable or unstable.</li>
</ul>
<p>I'd like to understand your closing point better. In our experiments, we didn't choose among individual guidelines: for each new task, we injected the guidelines derived from the most similar task. I'm curious where you see the disagreement about which guidelines to inject arising.</p>
